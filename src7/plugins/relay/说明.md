# relay v1.4.5

以下投递未获回执时，按统一规则判断结果是否确定，并保留原投递键供核对。

- 飞书文件
- 决策图回信
- 外部任务投递

外部助手（别的 AI）的交办、收件、回信都在这里。

1. **转话**（`index.ts` 的 Relay）。配置写了 `helpers` 才挂。
   - 按助手前缀或机器人和群配置，把话转给外部助手。
   - 支持文件、HTTP 和 webhook 收发。
   - 可以直接回信，也可以由模型转述。
2. **外部 AI 任务通道**（`AgentTasks.ts`、`TaskRoutes.ts`、`TaskProtocol.ts`）。HTTP 就绪后挂载。
   - 支持执行端登记、任务领取和附件下载。
   - 用 `agent_task` 指定已登记的执行端。
   - 需回信的任务单写明模型、思考档、子代理和交回物，结果经 `bot/request` 入队。
   - 单向留言用 `reply: false`，领取即送达。

## 依赖

- 静态共享模块：`src7/utils/Failure.ts` 的 `Failure(status: number, message: string)`；保留 `status` 和 `Error.message`，HTTP边界仍按各自逻辑返回状态与错误正文。转话的接口和任务通道的接口都用它（任务通道原来的 TaskError 合并掉了）。来源：`src7/utils/Failure.ts:8`。

#### GET /api/relay/inbox

- 定义：`src7/plugins/relay/Routes.ts:24`
- 返回：{items:InboxItem[],last:number}，id>since且筛选命中，id升序；last为全库最大id；参数错400 {error}
- 作用：助手轮询收件，状态以DB为准
- 调用说明：src7/web/src生产代码未见此路由的请求调用，外部助手在项目外轮询；测试源码未运行。

#### POST /api/relay/reply

- 定义：`src7/plugins/relay/Routes.ts:41`
- 返回：{ok:true,item:InboxItem}，400字段/助手/归属不对，404未知id/聊天
- 写入与交回
  1. 写 `relay_replies`。`done` 时将 `relay_items` 置为 `replied`。
  2. 异步交回原会话或决策图节点。`file` 另行发送。
- 决策图收件回信由决策图插件写入节点。启动时补送未结清的回信，写图回执成功后更新 `delivered`。
- 调用说明：外部助手 HTTP 入口。

## 设计要点

- 对话转接和外部任务管理分开，direct 通过 request.answer 短路模型，model 模式由模型转述。
- 文件回信可离线留存位置，HTTP 可即时回错误，二者共用业务接收逻辑；按收件 origin 还原回话来源。
- 单向留言也入任务表，待执行端领取。`reply: false` 的任务单只有正文和附件等基本信息，领取同一次更新完成送达。任务不进结果队列，也不进入转话的超时提醒。
- 外部任务协议 v1
  - 沿用 `agent_tasks` 的 `new` → `taken` → `done`/`failed`。原任务表加 `protocol`，旧记录为 `NULL` 时走旧格式 `{ ok, text, uploads }`。
  - 交换目录为 `<数据根>/integrations/agents/<助手>/tasks/<任务号>/`。
    - `task.json` 供机器读。
    - `task.md` 供人读。
    - 附件放 `input/`。
- 领取时带 `claimKey`。
  - 同键重领原样返回。
  - 别人已领时回 409。
  - 执行者先核对自己能否开任务要求的子代理和模型档。缺能力交 `capability_missing`，不能由主代理做完却声称开了子代理。
- 交回按顺序处理
  1. 提交 `result.json`。HTTP 用 `protocolResult`，文件模式由定时扫描读取 `result/result.json`。两条路都走 finish。
  2. 记录要求的和实际的模型、思考档及子代理。证据不足写 `unknown`。
  3. 经 `bot/request` 排进派活会话，收到成功回执后才改任务状态。

当前边界：普通会话回信的 delivered 表示已交给会话流程；决策图回信要收到写图回执后才标 delivered。两者都不等于某个外部渠道已实际发送，仍须看对应渠道或节点的最终回执。

## 给外部助手的用法

2026-11-14（EST）写，2026-11-16（EST）改成多助手。jmbots 可以同时接几个外部助手，名单写在 `config.yaml` 的 relay `helpers`。每项填

- 名字（之后用 `<你的名字>` 指 `helpers` 里的 `name`）
- 前缀
- 可选的 webhook

第一个是默认助手。插件代码在 `src7/plugins/relay/`，设计见本文「设计要点」。

### 收件箱在哪

- 规则：`<运行时目录>/integrations/relay/<机器人名>/inbox.jsonl`。运行时目录就是 `bun src7/Main.ts --data <目录>` 的那个目录。
- 例：测试目录 `/home/leonppp/project/faidata/source/jmbots/cache/test-src7-relay/integrations/relay/jm开发/inbox.jsonl`。
- 正式数据在 Windows `F:\aidata\AIJMBots\jmbotsData` 时，虚拟机 130 上是 `/home/leonppp/project/faidata/AIJMBots/jmbotsData/integrations/relay/jm开发/inbox.jsonl`（`faidata` 就是共享的 `F:\aidata`）。
- 收件箱按**机器人**分，不按助手分：几个助手的收件都在同一个 `inbox.jsonl` 里，看每行的 `helper` 只挑自己的（或者用下面的接口按 `helper=` 筛）。
- 配了 `webhook_url` 的助手，转出时 jmbots 会推一次给它，不用一直轮询；推失败话还在收件箱里。
- 同一个文件夹还有
  - `replies.jsonl`：你写回信
  - `replies.pos`：jmbots 读到第几个字节，别动
  - `replies.err.jsonl`：没收下的回信和原因

### 收件每行的字段

```json
{"id":12,"bot":"jm开发","helper":"jm开发","session":"a1b2c3d4","channel":"http","text":"帮我看下 http 插件","files":[],"at":"2026-11-14 06:30:05","atMs":1794655805000,"state":"pending"}
```

- `id`：收件号，回信靠它对号
- `bot`：机器人
- `helper`：转给了哪个助手（11-16 新加，旧收件都算默认助手的）
- `session`：会话号
- `channel`：用户从哪来，`http` 是网页或接口，`feishu` 是飞书
- `text`：用户的话，同一步排着的几句用空行连起来
- `files`：这条带的图片和文件（11-16 新加，见下）
- `at`：本地时间
- `atMs`：毫秒
- `state`：状态
文件里的 `state` 永远是写入时的 `pending`；最新状态看接口。

`files` 是字符串数组，每项是附件相对运行时目录的路径，用 `/` 分隔，如 `bots/jm开发/workspace/inbox/2026-11-16/093005123_a.png`；没有附件是 `[]`。
要取文件就拼上运行时目录读它。`text` 里同一个附件还写着 `@绝对路径`（那是给机器人看的），以 `files` 为准。
`GET /api/relay/inbox` 的每条收件、推给 webhook 的 body 里也有同样的 `files`。HTTP 轮询的每个 `items` 条目用 `owner: true` 表示本人，`false` 表示未标为本人，旧数据缺标志也回 `false`。原始发话人 `open_id` 和回话地址留在内部。

### 怎么写回信

文件和 HTTP 两个入口共用回信校验和投递流程：普通收件交回原会话，决策图收件写入原节点对话，不去创建伪会话；是否实际送达仍看对应回执。

1. **写文件（默认用这个，不用令牌，jmbots 没在跑也不丢）**：往 `replies.jsonl` 末尾追加一行，**一定以换行结尾**（没换行的半行不处理，补上换行才处理），约 2 秒内送出：

   ```bash
   echo '{"id":12,"text":"看完了，没问题"}' >> <运行时目录>/integrations/relay/jm开发/replies.jsonl
   ```

   - `done` 省略时为 `true`，表示这条回完了。
   - `"done":false` 表示中途话，例如“收到，在看”。文字照样送出，这条仍算没回完。
   - 号不存在、格式不是 JSON、`text` 为空或号不属于这个机器人的行，记入 `replies.err.jsonl`，后续行照常处理。

2. **调接口（同机测试、要当场知道对错时用）**：

   ```bash
   curl -s -XPOST http://127.0.0.1:<端口>/api/relay/reply -H 'content-type: application/json' -d '{"id":12,"text":"看完了，没问题"}'
   ```

   - 成功回 `{"ok":true,"item":{…}}`。
   - 没有这个号回 404。
   - `id` 不是正整数或 `text` 空，回 400。

   **主动发**（没有收件号）

   - 给 `chat`（飞书 chat_id 或微信 chat）和 `helper`（你的名字，省略时用默认助手）。例如 `{"chat":"oc_…","helper":"<你的名字>","text":"…","done":false}`。
   - 优先挂到你在这个聊天最近一条收件上。该助手尚无收件时，只能借同聊天其他助手已有收件的渠道和地址新登记。
   - 该聊天从无可匹配收件时回 404，不会凭任意 chat 创建发送目标。`helper` 写了名单外的名字回 400。
   - 回给用户的话前面署“<你的名字>：”。
   - 本机调用无需令牌，其他机器加 `?token=…` 或 `Authorization: Bearer …`（令牌不要写进记忆）。

### 怎么只看没回的

- 接口筛选示例
  - 只看转给你的、没回完的：`curl -s -G http://127.0.0.1:<端口>/api/relay/inbox --data-urlencode "helper=<你的名字>" --data-urlencode state=pending`
  - 按机器人筛时中文名要编码：`curl -s -G http://127.0.0.1:<端口>/api/relay/inbox --data-urlencode "bot=jm开发" --data-urlencode state=pending`
- 查询参数
  - `since=号`：只给号更大的
  - `bot=机器人`
  - `helper=助手名`
  - `limit=`：默认 50，最多 200
- 返回 `{ items: [...], last: 最大收件号 }`，`items` 里的 `state` 是最新的。
  - `pending`：没回完
  - `replied`：回完了
  - `expired`：太久没回，先放下了，回了照样送到
- 只有文件时
  1. 记住上次看到的最大号 N。
  2. 从 `inbox.jsonl` 取 `id > N` 且 `helper` 是你的行。
  3. 减去 `replies.jsonl` 里已经 `done` 的号。
- 没回会怎样（提醒里说的是这条收件的助手名）：过 15 分钟提醒用户一次，过 120 分钟说“先放下”（`plugins` 里 `relay` 的 `remind_minutes`、`expire_minutes` 可改）。
