# bots v1.6.9

1.6.9 `Bots` 构造函数瘦身为纯登记，匿名监听体拆为 `onReady`、`onChange`、`onSay`、`onRequestError` 四个私有方法（`ctx.on` 与 `onRequestEvent` 留在构造函数内）；`index.ts` 与 `DispatchClaim.ts` 共 6 处认领记录及 `sourceClaims` 截断收拢为 `DispatchClaim.ts` 的 `rememberClaim`、`pushClaim`；`DispatchResults.ts` 散落的多处活动项释放、队列裁剪与落盘推进合成 `settle(session, drainNext)`。对外行为不变。

1.6.8 群攒批判定要接话时，地址带 `judgeHelper`（飞书群登记了 `judge_helper`）的这一批不排进前台自答：先记进前台当背景（`keep`），再由 `DispatchClaim.relayBatch(front, last, text, helper)` 照最后一句拼一条收件，地址副本去掉 `listenOnly`、写上 `relayHelper`，发一次 `bot/receive`；relay 认领（填了 `session`）就 `bot.deliver` 交给那场外部助手会话，没人认领就只留背景。没登记 `judge_helper` 的群照旧 `enqueueBatch` 自答。

1.6.7 requestEvent 改新写法（云端 19 第 1、2 条）：拿 `{ reply }` 或 `{ why }`，不再编假回执。查前台归档（memory 读本机索引）、取模型介绍（model-catalog 本机拼）不掐表；群攒批问决策模型不掐表、60 秒报警，decision 每个模型自己限时，没挂、出错按不接。删只用一次的 `FrontDesk.askMemory`，并进 `readFront`。

1.6.6 ready 时看 memory 有没有开工改读挂载结果的 `state === 'ok'`（骨架把 mounted、started、missing、error 合成了 `state` 加 `error`），行为不变。

1.6.5 自动回话在代码中用 `AUTO_REPLY_MODE`，会话 `frontTask.deliveryMode` 和 `resultQueue[].deliveryMode` 仍存 `legacy_auto`。按地址发的回执由 `normalizeAutoReplyReceipt` 转成标准回执。轮键保留 `'legacy'`，飞书重启后仍能认出流水中的幂等键。

1.6.4 是不是本人改问 channels 的 `isOwnerTurn`（挑模型和思考档、派活时认人、带不带模型介绍三处，原来的 `isNonOwnerSpeaker` 删了）；`SessionRow.customer` 只在 bots 声明一次。真实渠道的地址都写了身份，判断不变；只有非本机渠道、地址一个身份字段都没写的，从本人变成外人（宁严勿松）。

前台自己答一般技术解释、资料查询和简单问题，答不够交办自己的后台会话，不转外部助手；
同一群同一问题已交办后台在查的，前台只说“在查，做完发你”，后台结论为准，改口明说“更正：……”。

## 受管后台最终结果

`channel_tool` 受管后台同一轮只接收一次 `channel_reply(kind: final)`：
最终通知以 `work:<后台号>:<round>:final` 排进原前台，
与后台 `frontTask.finalRound` 在同一事务保存。
回执 `queued` 只表示已交回原前台，不代表渠道发送成功。
同轮再次调用 final 不另排一项；中途说明须用 progress，每次调用仍独立排队。

后台普通结束为 done 且本轮 final 已交回时，只推进 round，不再把普通最终文本交回一次。
没有显式 final 的轮次照旧自动交回；失败或停止仍交回真实原因，不能由成功通知掩盖。
入队或轮号保存失败恢复内存状态，原结果可重试；重启时用持久标记完成未收尾轮次。
前台原项的 rejected、partial、uncertain 等回执不改写，不用另一份最终结果冒充补发成功。

这不是按文本相似去重，也不追认升级前已排队、没有 finalRound 的旧 notice。
离线回归覆盖 final 后普通结束、自动完成、多次 progress、重复 final、
保存失败重试、元数据重载与 ready 恢复、渠道拒收保留及后续真实失败。


工作决策的已选结果通过 `bot/request` 进入提问会话的结果队列，按节点号去重。

共享工具 utils/Bots.ts 从资源快照读取机器人名单、语言和目录。收发与分派仍由 bots 服务执行。

内嵌提示词、普通收件目录和已校验工作区统一使用 `utils/Files.ts` 的 `ensureDir`。

1.5.4 保留派活校验工作区和查模型失败时的原异常链。

1.5.12 `Bots.send` 按地址发 `channel/reply`，`target.address` 带会话记的地址。渠道只登记名字，前台听 `channel/replied` 记往来，回执带请求正文。

1.6.0 进来的话听三个事件：`channel/direct`（私聊）、`channel/mention`（群里叫了机器人）、`channel/listen`（只听）；语音半句提前开工也走 `channel/direct`（`routing.partial`）；`bot/request` 的 `hand` 加可选 `replyTo`，群日报改走它。

## 挂载先后

本插件写在 `plugins` 段前面，排在 `tutorial`、`workspaces` 之后。五个对象依次挂监听。

1. `Bots`
2. `FrontDesk`
3. `Dispatch`
4. `ChannelTools`
5. `Prompt`

- `session/before-model` 按以下先后处理。
  1. 前台拼上下文，整个换掉 `request.messages` 并注入零次回复系统提醒。
  2. `Dispatch`、`ChannelTools`、`Prompt` 依次挂入。
  3. relay、memory、file-tools、approval、progress、context-fit、skills 这些插件再挂。
- `Prompt` 现在排在 relay、memory 前面，涉及以下请求字段。
  - relay 的 direct 会话只写 `request.answer`。
  - memory 只 `push` work 会话“开场先搜”的结果，这段现在落在人设、记忆文件后面。
  - 底座和功能声明用 `unshift`，永远在最前。
- 进来的 `channel/direct`、`channel/mention`、`channel/listen` 的审批与分派顺序见 [README · 一条消息怎么走](../../README.md#一条消息怎么走)。

语音经渠道认领和回话出口处理。

1. 半句（话还没说完先交机器人开工）发 `channel/direct`，`routing.partial` 为 true，和整句走同一个认领入口；记录类插件（memory）不记半句，approval 不当批复认，等同一消息号的整句。
2. 语音入档的整句（没叫机器人的话）发 `channel/listen`，`targetBots` 置空，bots 谁都不进，只有 memory、网页记；`voice/record` 事件的第三个参数 `waiting` 表示这句等不等回话（半句已开工的等，只入档的不等）。
3. 语音插件用 `bots.channel('voice')` 只登记渠道名；后台结果由 `Bots.send` 发 `channel/reply`，语音渠道接单后转为标准文字回复。

      thinking: medium     # 后台会话的思考档，不写 medium
      front:               # 前台；不写全用默认

        vision_model: 供应商名/模型ID   # 有图要转后台时用的看图模型；不写挑 providers 里第一个写了 vision: true 的
      prompt: true         # 系统提示词（原插件 prompt）；不写 true，写 false 不加
      reply_tool: false    # 工具 reply（原插件 reply-tool）；不写 false，要用写 true

apply 校验以下配置。

- 名单要是清单。
- `front` 要是一节。
- `recent` 为正整数。
- `vision_model` 的供应商要在 `providers` 里。
- `prompt`、`reply_tool` 写了要是 true 或 false。

## 群攒批（GroupBatch.ts）

飞书登记了 `listen: judge` 的群里，没叫机器人的话不再一句一判：每个（机器人，群）攒一批，满足两个触发之一才问一次决策模型要不要接话。
- 触发一：最后一句之后安静满 `quiet_seconds` 秒；触发二：攒满 `max_lines` 句。到点时前台正在转，等这一轮停下（session/change）再看。
- 每群每天最多看 `daily_limit` 次（0 不限），同群几个机器人共用，本地日期换天清零；看满了不问模型，这一批记成背景，`bot/judged` 写“judge:不看(今天看满 N 次)”。
- 判断发请求事件 `decision/judge`（不掐表，60 秒报警，decision 自己限时）；没挂决策插件或出错按不接。接话就照最后一句排进前台单队列（DispatchClaim.enqueueBatch），这一批几行“说话人：话”当这一轮的话；不接就记成背景（FrontDesk.listen）。一批发一次 `bot/judged`。
- 有人叫了机器人（私聊、@、引用）：DispatchClaim 用 take 拿走这一批，拼成“群里在这之前没叫你的话：… / 叫你的这句：…”；正在判断的那一批判完不再排队。
- 渠道撤回：本人或原发信人撤回的话从缓冲里拿掉。
- 配置 bots 的 `group_batch: { quiet_seconds, max_lines, daily_limit }`（样例 60、30、0），入口 `readGroupBatch` 校验一次；没写或缺键就不开攒批，judge 的群只记不判断，启动日志写明缺哪个；写错抛错。代码不写默认值。
- 缓冲只在内存，重启丢掉。直接收话时，`FrontDesk.onReceive` 把只听的话记成背景。
