# bots v1.5.9

共享工具 utils/Bots.ts 从资源快照读取机器人名单、语言和目录。收发与分派仍由 bots 服务执行。

内嵌提示词、普通收件目录和已校验工作区统一使用 `utils/Files.ts` 的 `ensureDir`。

1.5.4 保留派活校验工作区和查模型失败时的原异常链。

挂载 memory 后，模型使用以下工具。

- `memory_search` 查询本场往来和渠道提及。
- `memory_get` 取带编号的原文或按签名游标翻渠道历史。

这两个工具直接由记忆插件提供。bots 管理以下内容。

- 机器人名单
- 前后台会话
- 系统提示词
- 渠道工具
- 按原消息的撤回事件移除待办，通知活动会话由模型重判

渠道消息怎么认领、回复和收尾，见 [README · 一条消息怎么走](../../README.md#一条消息怎么走)。

## 挂载先后

本插件写在 `plugins` 段前面，排在 `tutorial`、`workspaces` 之后。五个对象依次挂监听。

1. `Bots`
2. `FrontDesk`
3. `Dispatch`
4. `ChannelTools`
5. `Prompt`

- `session/before-model` 按以下先后处理。
  1. 前台拼上下文，整个换掉 `request.messages` 并注入零次回复系统提醒。
  2. `Dispatch`、`ChannelTools`、`Prompt` 依次挂入。
  3. relay、memory、file-tools、approval、progress、context-fit、skills 这些插件再挂。
- `Prompt` 现在排在 relay、memory 前面，涉及以下请求字段。
  - relay 的 direct 会话只写 `request.answer`。
  - memory 只 `push` work 会话“开场先搜”的结果，这段现在落在人设、记忆文件后面。
  - 底座和功能声明用 `unshift`，永远在最前。
- `channel/message` 的审批与分派顺序见 [README · 一条消息怎么走](../../README.md#一条消息怎么走)。

语音经渠道认领和回话出口处理。

1. 用 `voice/dispatch` 让半句走同一个认领入口。
2. 最终 `channel/message` 上的 `routing.recordOnly` 表示只记录，bots 跳过认领。
3. 语音插件用 `bots.channel('voice', ...)` 注册发送出口，后台结果经该出口转为标准文字回复。

### 模型工具

- 三个派活工具仅给 `front`。

### 会话上加的字段（SessionRow，存在 sessions 的 meta）

| 字段 | 谁写 | 说明 |
|---|---|---|
| bot | Bots | 属于哪个机器人 |
| channel、address | Bots.route | 回话往哪个渠道、渠道认得的地址 |
| customer | Bots.route | 抄 `address.customer`；前台按它一个客户一场 |
| quiet | Dispatch | 这一轮结束的回话不自动发（受管后台、前台整理结果那一轮、或 `channel_tool` 轮） |
| sourceScope | FrontDesk / Dispatch | `{ channel, accountId, chatId }`：标准渠道前景归属域，防不同 `appId` 或来源串会 |
| sourceClaims | Bots / Dispatch | 已认领 `claimKey` 最近 200 条列表，实现同一条 `channel/message` 重推严格去重 |
| activeSourceSnapshot | Dispatch | 当前 `channel_tool` 活动轮的不可变 `SourceSnapshot`（存在时 `Bots.onChange` 不自动发 `row.reply`） |
| recalledStop | 旧版会话记录 | `Bots.onChange` 与 `DispatchResults.finishFront` 用于兼容历史撤回停跑记录，收尾时清掉。 |
| frontTask | Dispatch | 受管后台：`front`、`round`、`workspace`（只作显示：旧写法的文字，按 ID 选的是工作区名字）、`origin`、`deliveryMode`、`sourceSnapshot`、`paused`、`handedTo` |
| workspaceId | Dispatch / progress | 后台绑定的工作区 ID：new 时定下，append、`route` 都不改；progress 转新会话照抄；老的没绑定的后台 append 时补上 |
| resultQueue | Dispatch | 统一单队列：每项含 `key`、`kind`（result/user）、`hash`、`source`、`origin`、`payload`（含 `sourceSnapshot`）、`deliveryMode`、`replyControl`、`deliveryReceipt`、`startMessageIndex`、`stage`、`note`、`at`；处理完留最近 20 项并保留归档 `sourceSnapshot` |

- sent：渠道收下了

## 配置

```yaml
bots:                      # 顶层名单，不写是一个叫“助手”的机器人
  - name: 助手
    workspaces: { 源码: <登记的目录> }   # 可选：建机器人时登记成 private 工作区；hand_session 的 workspace 写登记名时用它（只给本人）
plugins:
  - name: bots
    config:
      thinking: medium     # 后台会话的思考档，不写 medium
      front:               # 前台；不写全用默认
        recent: 50         # 前台每一步带最近几条往来，正整数，不写 50
        vision_model: 供应商名/模型ID   # 有图要转后台时用的看图模型；不写挑 providers 里第一个写了 vision: true 的
      prompt: true         # 系统提示词（原插件 prompt）；不写 true，写 false 不加
      reply_tool: false    # 工具 reply（原插件 reply-tool）；不写 false，要用写 true
```

apply 校验以下配置。

- 名单要是清单。
- `front` 要是一节。
- `recent` 为正整数。
- `vision_model` 的供应商要在 `providers` 里。
- `prompt`、`reply_tool` 写了要是 true 或 false。

机器人名单项的 `workspaces` 由 `Bots.add` 校验（“名字: 非空目录”）。

原来单独挂的 `- name: prompt`、`- name: reply-tool` 从 `plugins` 段删掉；还留着的话启动时报“找不到这个插件”，只打一行，不挡别的插件。
