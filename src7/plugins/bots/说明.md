# bots v1.4.6

机器人名单、渠道收发、标准化 `channel/message` 独立认领与 `channel/recall` 撤回停跑，加上前台、前台派后台、系统提示词和 `reply` 工具（1.2.0 起原插件 bot-front-desk 并在这里；1.2.1 起接入渠道与机器人解耦第 1 步协议与零次回复兜底；1.3.0 起工作区交给 workspaces 插件，后台绑定工作区 ID；1.4.0 起原插件 prompt、reply-tool 并在这里，去掉渠道里的过渡监听；1.4.1 起网页、命令行、微信也走 channel_tool，消息上的 `deliveryMode` 删掉，`routing.sessionId` 指定会话，`routing.autoFinal` 零次回复直接发最后的话，一轮收尾发 `channel/settled`，`front.history_limit` 默认 80；1.4.3 起听 `channel/recall` 在用户撤回消息时清排队与停跑前台/后台且不发“已停止”；1.4.4 起 `channel_reply` 支持非群聊本人指定 `channel`、`chat` 跨渠道或跨聊天发纯文字；1.4.5 起跨渠道回复只在 `channel/reply` 带 `target: { channel, chat }`，聊天由目标渠道自己认，bots 不碰别家数据）。

`channel/message`（飞书、网页、命令行、微信都走它）：渠道先原始落盘再发 `channel/message` → `approval` 消息级审批只消费一次 → `Bots` 按 `targetBots` 逐个机器人独立物化附件并走兼容关口 `bot/receive` → 未被接管的由 `Dispatch.claimChannelMessage` 按 `claimKey` 去重后压入该机器人前台会话（按 `sourceScope` 找，同客户的旧前台补写范围沿用），带不可变 `sourceSnapshot` 与 `replyControl` → 模型一轮里调几次 `channel_reply` 就经 `channel/reply` ↔ `channel/replied` 发几条纯文字（关闭自动发送 `row.reply`）。本轮 0 次调用回复工具时：消息写了 `routing.autoFinal`（网页、命令行、微信）就把 `row.reply` 当 final 直接发出去（`Dispatch.sendLastWords`）；没写（飞书）触发唯一 1 次修复轮（`request.system` 注入 `'你还没调用回复工具'`）。收尾时发 `channel/settled`（来源快照、stage、note）。

- **指定会话**（`routing.sessionId`，网页“发给哪个会话”、引用别的渠道的消息，入口校验过）：只投给那场会话的机器人，别的机器人跳过；`bot/receive` 之前先填好 `event.session`。是前台就照上面排进**这场**前台（不改它的 `sourceScope`）；是后台等别的会话照旧 deliver，一轮结束自动回一条。`routing.replyOrigin` 只作记录（被引那条的原渠道、原机器人、原会话）。
- 别的插件在 `bot/receive` 里认领了会话的（relay）：按 `claimKey` 防重后 deliver；认领的会话 `sourceClaims` 里已有这条，记一条 `duplicate`，不再投。

旧入口 `ctx.bots.receive`（`Bot.receive`：问 `bot/receive` → `Dispatch.receive` → deliver）照旧能用。

想换一种分派办法：写一个插件听 `channel/message`（或旧入口 `bot/receive`），把 `event.session` 填上或设置 `handled`，前台就不接这条了。

## 挂载先后

本插件写在 `plugins` 段前面（`tutorial`、`workspaces` 之后），五个对象照这个先后挂监听：`Bots` → `FrontDesk` → `Dispatch` → `ChannelTools` → `Prompt`。所以：

- `session/request`：前台拼上下文（整个换掉 `request.messages`，并注入零次回复系统提醒）最先，接着 `Dispatch`、`ChannelTools`、`Prompt`，都排在 relay、memory、file-tools、approval、progress、context-fit、skills 这些后挂的插件前面；
- `Prompt` 并进来之前排在 relay、memory 后面，现在排到它们前面。核过没有逻辑上的先后要求：relay 的 direct 会话只写 `request.answer`；memory 只 `push` work 会话“开场先搜”的结果，这段现在落在人设、记忆文件后面；底座和功能声明用 `unshift`，永远在最前；
- `channel/message`：`approval` 以 `{ prepend: true }` 排在前面先消费消息级“同意 N”指令，之后 `Bots` 按 `targetBots` 逐个机器人问一圈 `bot/receive`，没人认领的交 `Dispatch.claimChannelMessage` 认领（带 `routing.sessionId` 的只给那场会话的机器人）。

### 数据库表

`bot_log` 存每个机器人和客户的往来（用户说的、机器人回的，跨渠道），给 `history*` 工具翻；一行是一句话。

## 配置

```yaml
bots:                      # 顶层名单，不写是一个叫“助手”的机器人
  - name: 助手
    workspaces: { 源码: <登记的目录> }   # 可选：建机器人时登记成 private 工作区；hand_session 的 workspace 写登记名时用它（只给本人）
plugins:
  - name: bots
    config:
      thinking: medium     # 后台会话的思考档，不写 medium
      front:               # 前台；不写全用默认
        recent: 50         # 前台每一步带最近几条往来，正整数，不写 50
        history_limit: 80  # 渠道历史工具默认每次返回条数（1..200，不写 80）
        vision_model: 供应商名/模型ID   # 有图要转后台时用的看图模型；不写挑 providers 里第一个写了 vision: true 的
      prompt: true         # 系统提示词（原插件 prompt）；不写 true，写 false 不加
      reply_tool: false    # 工具 reply（原插件 reply-tool）；不写 false，要用写 true
```

校验在 apply：名单要是清单；`front` 要是一节；`recent` 正整数；`history_limit` 为 1 到 200 整数；`vision_model` 的供应商要在 `providers` 里；`prompt`、`reply_tool` 写了要是 true 或 false。机器人名单项的 `workspaces` 由 `Bots.add` 校验（“名字: 非空目录”）。

原来单独挂的 `- name: prompt`、`- name: reply-tool` 从 `plugins` 段删掉；还留着的话启动时报“找不到这个插件”，只打一行，不挡别的插件。
