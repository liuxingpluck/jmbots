跨渠道认人：渠道把经平台核验的绑定元组（渠道、命名空间、账号、发话人）交来，people 答“这是谁”。
登记过的人照 `config.yaml` 给角色和记忆范围；没登记的自动建一张 guest 名片，固定只读自己的记忆。
权限只认配置，库里只存自动名片和绑定，自动建卡不提权、不按同名合并、不信请求里自报的身份。

## 一个人怎么被认出来

1. 渠道适配器拿到平台核验过的发话人，拼成绑定元组 `{ channel, authority, account, subject }`，四项一项都不能空。
2. 调 `resolvePerson(ctx, binding, hint)`，它发 `people/request`、等 `people/result`，最多等 1 秒。
3. people 先查**配置名单**（启动时建好的内存只读表，键是 `getBindingKey` 拼的 JSON 数组）；有就照配置给角色、记忆范围。
4. 配置里没有，查库里的**自动名片**；还没有就在一个事务里新建一张：`p_` 加随机 UUID，名字用平台显示名（截 64 字），没给叫“未命名访客”。
5. 回执三种：`ok` 带这个人；`unknown` 是绑定元组不完整、不建卡；`unavailable` 是 people 没挂、超时、中止或出错。后两种都不给任何角色，调用方按“认不出”处理，**不能回退成本人**。

几条硬规矩（都有单测）：

- 自动名片永远是 `guest`、记忆 `own`，库里不存角色；库被改了也提不了权。
- 只按绑定元组认人，不按显示名：和本人同名的陌生人，照样是另一张 guest 名片。
- 同一个 open_id 换一个飞书应用（`account` 不同），算另一个绑定。
- 从配置里删掉一个人，重启后他的绑定立刻按 guest 认，不沿用旧权限。

## 听的事件

| 事件 | 模式 | 谁发 | people 做什么 |
|---|---|---|---|
| `people/request` | 请求-回执 | 渠道适配器经 `resolvePerson` 发（现在还没有调用方） | `apply` 里用 `onRequestEvent` 接单，`action: 'resolve'` 交给 `People.resolve`，补上同一个 `requestId` 回 `people/result`（`people/index.ts:356`） |

请求字段：`requestId`（公共信封）、`action: 'resolve'`、`binding`（绑定元组）、`hint`（可选，平台显示名，只在新建自动名片时当名字）。

## 发的事件

| 事件 | 模式 | 谁接 | 内容 |
|---|---|---|---|
| `people/result` | 回执 | `resolvePerson` 按 `requestId` 配对收下 | `{ requestId, status: 'ok', person }` 或 `{ requestId, status: 'unknown' \| 'unavailable', reason }`；`reason` 一句人话，不带平台标识 |
| `trace` | 通知 | tutorial 等记轨迹的插件 | `People.resolve` 认出谁：显示名、渠道、人员号、来源（config/auto）、角色、记忆范围；不带 `subject` 等平台标识 |

## 对外函数

**`resolvePerson(ctx, binding, hint?, signal?)`**（`people/index.ts:312`）

- 给渠道适配器用：在发 `channel/direct`、`channel/mention`、`channel/listen` 和构造本轮来源快照之前调。
- 参数：`ctx` 调用方插件的 ctx；`binding` 经平台核验的绑定元组（不能拿消息正文里的名字、ID 拼）；`hint` 平台显示名；`signal` 可选中止信号。
- 返回：`people/result` 的回执。走事件，不直接调 `People` 的方法；限时 1 秒，没挂、超时、中止、出错一律 `unavailable`。

**`getBindingKey(binding)`**（`people/Checks.ts:49`）

- 把四项按位置放进 JSON 数组当键，任何字符都不会让两个元组拼成同一个键。
- 配置查重和配置投影都用它；以后迁移脚本对照绑定也用它。

**`checkPeopleConfig(raw)`**（`people/Checks.ts:61`）

- 插件入口校验一次配置名单，交回确定类型；报错只写第几项、哪个字段，不带平台标识。

导出的类型：`Person`、`PeopleRequest`、`PeopleResult`（`index.ts`），`Binding`、`ConfiguredPerson`、`Role`、`MemoryScope`、`ROLES`、`MEMORY_SCOPES`（`Checks.ts`）。

## 数据

两张表都在运行时 `data/jmbots7.db`，构造时 `CREATE TABLE IF NOT EXISTS`（`people/index.ts:135`）。只存自动名片；配置里登记的人不进库。

- `people_profiles`：一张自动 guest 名片一行。
- `people_bindings`：一个绑定元组一行，四项联合主键，所以一个绑定只能归一张卡。

建表还没走 db 插件的版本迁移账本；以后加列（撤销、证据、迁移映射）时要改成账本里的迁移。

## 数据字段表

| 表 | 列 | 类型 | 说明 |
|---|---|---|---|
| `people_profiles` | `id` | TEXT 主键 | 人员号，`p_` 加随机 UUID |
| `people_profiles` | `name` | TEXT | 显示名，建卡时取平台显示名，以后不改 |
| `people_profiles` | `created_at` | INTEGER | 建卡毫秒时间戳 |
| `people_bindings` | `channel` | TEXT | 渠道名，如 `feishu`、`wechat` |
| `people_bindings` | `authority` | TEXT | 租户或应用命名空间，渠道适配器按平台定 |
| `people_bindings` | `account` | TEXT | 本渠道接入的账号（哪个应用、哪个号） |
| `people_bindings` | `subject` | TEXT | 平台核验过的发话人原始标识（如飞书 open_id），原样比对 |
| `people_bindings` | `person_id` | TEXT | 指向 `people_profiles.id` |
| `people_bindings` | `created_at` | INTEGER | 绑定毫秒时间戳 |

角色和记忆范围**不在库里**：自动名片固定 `guest`、`own`，登记的人只看配置。

## 配置

写在 `config.yaml` 的 `plugins` 段，people 自己的 `config.people` 是名单（不写名单就只靠自动 guest 名片）：

```yaml
plugins:
  - name: people
    config:
      people:
        - id: p_me            # 稳定人员号，改名不变；不能和库里自动名片同号
          name: 我             # 显示名，可重名，不参与认人
          role: owner          # owner | builder | guest，不写是 guest
          # memory 不写：本人是 all，别人是 own；本人只能 all，非本人暂不开放 all
          bindings:
            - { channel: feishu, authority: 租户或应用, account: 飞书应用号, subject: open_id }
            - { channel: wechat, authority: 微信命名空间, account: 微信号, subject: 对方 ID }
```

- 同一个绑定登记给两个人、人员号重复、字段缺或写错，启动时报错，插件不挂（别的插件照常）。
- 一个人在飞书不同应用下 open_id 不同，几个应用就写几条绑定。
- 现在 people 还没登记进 `plugins/Index.ts`，写了这一段也挂不上；接线那一步一起加回。
- 飞书 `feishu` 插件配置里的 `people` 名单是旧位置，搬家规则见设计细节第 8 节：一次入口兼容、不双权威。
