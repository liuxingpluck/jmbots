# programs v1.7.8

1.7.8 按用户 #442/#444 停用 CPU 限制：资源守卫只守内存 60GiB 和逐卡显存 15.5GiB（默认值由 15.9/15 改为 15.5/14.5）。CPU 再高、读不到都不拒开工、不发告警、不改档位；`programs/pressure` 去掉 `cpuBusy` 和 `busy` 档。老配置里的 `cpu_percent`、`cpu_resume_percent` 照收不报错、不生效。CPU 读数仍保留给页面看，并修正 Windows 上 irq 被重复计入（libuv 的 sys 已含中断时间）。11-21 在宿主机对照 Windows 计数器核过：用户看到的约 50% 是真负载（3 台虚拟机等），不是统计错误。

1.7.7 主程序请程序退出（`/jmbots/v1/exit`）、暂停和恢复（`/jmbots/v1/pause`、`/jmbots/v1/resume`）时，请求头也带这次启动的密钥 `x-jmbots-key`，和渠道调用一样；不核密钥的老程序照常收。退出时密钥在作废前先留一份交给 `releaseChild`。

资源提醒的发件与去重目录由 `utils/Files.ts` 的 `ensureDir` 创建。

- 外置客服页和主站主动发件共用 Outbound 请求入口。
- 草稿及批准发送的 HTTP 时限取自 Outbound，外层留足返回和记账时间。

“外部程序”插件按 `config.yaml` 托管独立程序。

1. 读取程序在 stdout 报告的端口。
2. 核对身份。
3. 检查健康。
4. 崩溃后退避重启。
5. 关停时先请程序自行退出。

程序报了界面就在 `/programs/<名字>/` 转发，网页顶栏自动出现入口。资源守卫负责

- 重活准入
- 资源高线通知
- 有限的托管恢复

**一个外部程序都不配时守卫照样每 5 秒采样、越线照样发事件和飞书通知**。本文描述源码契约，不代表正在运行的服务已经换版。

## 依赖

- `resources` 提供数据目录和 SQLite。程序输出写进 `data/logs/<name>.log`。
- `http` 挂载时提供状态、启停和转发接口。`/programs/` 前缀的令牌检查在 http 插件里（http 1.1.3 起），本插件不另查令牌。

## 配置

在 `plugins` 中添加 `name: programs`，并在该项的 `config.programs` 列出程序。

| 字段 | 含义和默认值 |
|---|---|
| `name` | 唯一的程序名，由小写字母、数字和横线组成。程序在就绪行和接口中使用同一个名字。 |
| `title` | 显示名，默认 `name`。 |
| `file` | 可执行文件，相对数据目录或绝对路径。Windows 会补 `.exe`。 |
| `args`、`env` | 字符串参数列表与子进程环境变量，默认空。 |
| `cwd` | 工作目录，默认 `{runtime}`，也就是 jmbots 的数据目录。 |
| `autostart` | 主程序就绪后自动启动，默认为 `true`。 |
| `host`、`port` | 默认 `127.0.0.1`、`0`。端口为 `0` 时程序选空闲端口。指定端口时就绪行须与之相同。 |
| `mount` | 转发前缀，默认 `/api/ext/<name>`，每个前缀须唯一；不能写在 `/programs` 下（那里留给界面入口，按名字自动挂）。 |
| `heavy` | 是否为重活，默认false；CPU 限制停用后只留作标记。自动启动、手动启动和崩溃重试都过准入（内存、显存）。 |
| `closable` | 默认false；只有显式true、持有自有子进程、有效新鲜RSS且非原本手动暂停的项，才可能被内存守卫正常停止。 |
| `startup_ms`、`exit_wait_ms` | 等就绪行默认 120000 毫秒，退出请求后等待默认 5000 毫秒。 |
| `channels` | 可选，默认空。写成 `[{ name: example-channel, bot: 助手 }]`。渠道名由小写字母、数字和横线组成，在所有外部程序间唯一，并避开当前启用的内置渠道；机器人名须在顶层 `bots` 中。 |

下面四处都可使用 `{runtime}`、`{data}`、`{host}`、`{port}`。

- 文件路径
- 参数
- 工作目录
- 环境变量值

其中 `{data}` 是数据目录下的 `data/` 子目录。程序由启动器直接执行。

### 渠道接管

在 `plugins` 的 `programs` 项的 `config` 下可写 `channel_aliases: [[wechat, wechat-external]]`。

- 每组至少两个合法渠道名，每个名字只出现一处。
- 同组按一个渠道核对占用。
- 入站、回复和历史仍用 `channels` 登记的原名。

内置插件的渠道名

- `wechat` 和 `wechat-kefu` 都使用 `wechat`。
- `web-api` 使用 `http`。
- `feishu`、`cli`、`voice` 用各自名称。

1. 插件挂载时用已启用的内置插件清单核对外部登记。
2. 发生冲突的程序状态为 `blocked`。
   - 不登记渠道或自动拉起。
   - 手动 `start` 和 `restart` 返回 409 与原因。
3. 主服务就绪时，每个冲突程序记一次日志并尝试向飞书发件箱入队。反复点击启停不会再次入队，发件箱沿用十分钟去重。

内置渠道继续运行。

正式切换微信

1. 给 `plugins` 中已启用的 `wechat` 和 `wechat-kefu` 项加 `disabled: true`，确认旧实例已停。
2. 把外部微信程序的 `channels` 改为 `[{ name: wechat, bot: 助手 }]`。`args` 中的 `--channel` 同时改成 `wechat`。

切回内置微信

1. 停掉外部微信程序，移除该配置项。
2. 恢复原内置项，去掉 `disabled: true`。

别名配置可保留。

## 统一接口规范

程序绑定 `{host}` 后，立即在 stdout 输出并刷新一行 JSON。

- `name` 取配置名。
- `port` 填实际端口。
- `pid` 可省略。托管方使用自己从启动句柄获得的进程号。

```json
{"jmbots":1,"event":"ready","name":"example","version":"1.0.0","port":43121,"pid":7788}
```

宿主识别第一条具有数字 `jmbots` 字段的 JSON 行。协议版本目前为 `1`。日志照常写在 stdout 或 stderr，每行保持在几 KB 内。

程序自己的端口默认只听回环地址，下面的管理接口供本机 jmbots 调用，经主站转发一律 404。

有界面的程序在 info 里报 `ui`（如 `/`）。界面通过 `/programs/<名字>` 加该路径打开。

- 界面里使用相对资源和接口路径。
- 本机和 `server.trusted_ips` 里的地址无需令牌。
- 其他机器打开时地址带 `?token=…`。主站转发前会去掉它，界面需从 `location.search` 取出令牌，带到自己的接口请求中（参考 `memsvc/src/ui.html` 的 `request`）。
- 界面和主站同源，只配置自己信得过的程序。

| 方法与路径 | 成功回执与用途 |
|---|---|
| `GET /jmbots/v1/health` | `{ok:true,name,version,protocol}`，可提供 `rssMb`、`vramMb`。1 秒内答复，避免等待业务锁或查询数据库。 |
| `GET /jmbots/v1/info` | `{ok:true,name,version,protocol,ui,capabilities}`。`ui` 是相对入口或 `null`，`capabilities` 可包含 `pause`。 |
| `GET /jmbots/v1/license` | `{ok:true,state,until?}`。`state` 为 `licensed`、`expired`、`none` 或 `free`。 |
| `POST /jmbots/v1/exit` | 接收 `{graceMs}`，请求头带这次启动的密钥 `x-jmbots-key`；先答 `{ok:true}`，再停止接受新活并在约定时间内退出。 |
| `POST /jmbots/v1/pause`、`POST /jmbots/v1/resume` | 声明 `pause` 能力时可调，接收 `{reason}`，请求头带 `x-jmbots-key`，答 `{ok:true,paused}`。暂停重型后台任务，继续回答正常查询。 |

管理接口错误返回 4xx 或 5xx 和 `{ok:false,error:{code,message}}`。

- `code` 使用英文小写加下划线，约定值有 `not_ready`、`license_expired`、`paused`、`bad_request`、`internal`。
- `message` 用中文说明原因。

程序也应能响应 `SIGTERM` 和 Ctrl+C 并正常收尾。

## 渠道回调

两端都用 JSON POST，请求头 `x-jmbots-key` 带本次启动密钥。

- 宿主每次启动都生成新密钥，放在子进程环境 `JMBOTS_PROGRAM_KEY` 中。进程退出后密钥作废。
- 登记了渠道的子进程还从 `JMBOTS_CALLBACK_URL` 取主服务回调前缀。子进程仅处理自己的登记渠道。
- 密钥留在受托进程、宿主及两者之间的请求中，不写日志，也不交给浏览器。

- 入站走 `POST <JMBOTS_CALLBACK_URL>/channel/message`。这是给程序的接口路径，没跟着主程序内部的事件名走。
  - 必填 `channel, account, chat, chatType, nativeId, sender:{id,name?}, text`。
  - 可附 `chatName, createdAt, mentioned, attachments:[{name,mime?,size?}]`。
  - 聊天类型为 `p2p` 或 `group`。时间为 Unix 毫秒。
  - 重发使用相同渠道、账号和来源消息号。
  - 200 回 `{ok:true,status:'accepted'|'duplicate',messageId,reason?}`。
  - 拒绝回 `{ok:false,status:'rejected',reason}`。
    - 400 参数错
    - 401 密钥错或进程已退出
    - 403 渠道未登记
    - 500 分派异常
  - 主程序按配置定机器人，来源按外人处理。
  - 收到后算叫了没有：`called = chatType !== 'group' || mentioned`，经 channels 的 `emitInbound` 发：私聊发 `channel/direct`；群里 `mentioned` 为 true 发 `channel/mention`；群里没 @ 的发 `channel/listen`（登记的机器人只记背景、不回）。
- 回复走子进程的 `POST /jmbots/v1/channel/reply`。
  - 正文带 `requestId, channel, account, chat, chatName, text, bot, kind`。请求号不变时，程序重放已保存的结果。
  - 程序回 `{status:'sent'|'draft'|'failed'|'uncertain',reason?}`。
  - 程序离线回标准 `rejected` 并说明原因。明确的 `failed` 也映射为 `rejected`。
  - 请求发出后连接中断或回执读不到时回 `uncertain`。
  - 正文带 `channel, account, chat, limit, before?, senderId?`。外人只可查当前会话。
  - 成功回 `{ok:true,account,chat,items,next}`。`next` 是程序的下一页游标或 `null`。
  - 失败回 `{ok:false,error:{code,message}}`。
  - 每项含 `nativeId, direction, createdAt, sender, text, attachments`。消息号与入站对应，按时间正序返回。
  - 主程序核对账号、会话、发送者范围，再将子进程游标包成绑定当前查询范围的签名游标。

入站分派正常结束后，`program_channel_receipts.message_id` 保存渠道、账号和来源号组成的标准 ID，供重启后去重。并发重发等待同一次分派。回执表只保存标准 ID。

外置微信通过 `--channel` 启用回调，名称须与此程序的 `channels` 登记一致。

- 隔离验证可以用 `wechat-external`，并使用独立的 `--data` 和 `--engine` 目录。
- 经界面代理发送 `PUT /programs/wechat/api/wechat-kefu/watch`，正文 `{account,chat,name,watch:true,auto:false}`。
  1. 首轮只归档。
  2. 之后只提交新收到的私聊消息和群内提及本账号的消息。
- 草稿从同一前缀的 `api/wechat-kefu/outbox` 读取。
- 历史覆盖该账号和会话已同步到本地的记录，群内发信人标识沿用引擎给出的名称。

## 外置客服发件确认

主站把同源界面确认入口挂在 `/programs/<程序名>/_approval/`，请求为 JSON POST。使用主站本机或有效令牌鉴权。各接口成功时返回 `{intent}`，错误返回非 2xx 和 `{error}`。

- `prepare` 接收 `{draftId}`。显示返回意图的 `account`、`chat` 和原样 `text`，随后才可确认。
- `confirm` 接收 `{intentId, observedIntentDigest, interactionId, decision:"approve"}`。摘要取准备回执的 `digest`，同一次点击可以重用交互号。
- `status` 接收 `{intentId}` 或 `{draftId}`，只读查询主站原意图，适合发送在途或刷新页面后核对。
- `reconcile` 接收 `{intentId, outcome:"sent"|"not-sent"}`。给 uncertain 记录填写本人核对值，原始回执仍保留。

`intent` 的字段

- 标识：`intentId`、`requestId`、`draftId`
- 目标：`channel`、`account`、`chat`
- 正文与摘要：`text`、`digest`
- 期限和状态：`expiresAt`、`status`
- 核对及后续操作：可选 `receipt`、`checked`、`canPrepareAgain`

- 状态包括 waiting、sending、sent、failed、uncertain。
- 准备或确认时程序不可用返回 503。
- 草稿目标、正文、期限或程序代次改变需要重新准备。
- 明确在出站前拒绝的批准可由本人重新准备。`uncertain` 只允许核对。

运输只选已登记 `wechat` 或 `wechat-external` 的现行实例。

1. 用现有草稿接口按编号读取。
2. 按 approval 的固定参数和当前启动密钥调用 `POST /jmbots/v1/channel/send`。

每次实际启动生成独立代次，后台自动重启也会换代。

外置客服页的批准发送

1. 经同源代理调用 `/api/wechat-kefu/outbox/send`，正文在上述参数外增加 `action`。代理仅转交明确操作，旧单步 `{id}` 请求返回 409。
2. 外置程序以当前启动密钥调用宿主的 `/api/programs/<程序名>/channel/approval` 回调，主站使用同一个批准账。

管理发送路径和旧微信 `/api/wechat-kefu/send` 均不经代理。普通 `channel/reply` 仍落草稿。

## 外部接口

- `ctx.programs.status()` 返回所有配置项的状态。
  - 基本状态包含名称、显示名、阶段、说明、PID、端口、版本、重启次数、`generation` 和 `gaveUp`。
  - 暂停状态包含 `paused` 和 `canPause`。
  - RSS 状态包含 `rssMb` 和 `rssAt`，未知时保持缺席。
  - 授权状态包含 `license` 和 `licenseLabel`（`已授权/过期/不需要/未授权/未知`），未知授权保持缺席。程序自报 `free` 标“不需要”，`none` 标“未授权”。网页顶栏只在“已授权”“过期”时显示标签。
  - `ui` 在就绪且报了界面时是 `/programs/<名字><界面路径>`，否则为 `null`。
- `ctx.programs.url(name)` 返回已确认就绪的内部 HTTP 地址。
- `ctx.programs.resources()` 返回最新系统快照副本，所有容量为字节；尚未采样的指标为null。
- `GET /api/programs` 返回 `{ programs }`。每项的 `channels` 为已登记渠道名的字符串数组。
- `POST /api/programs/<name>/start`、`stop`、`restart` 返回 `{ program }`。
  - 重启等旧进程退出后再拉起。
  - 启动或重启遇到内置渠道冲突返回 409 和中文原因。
  - 资源拒绝返回 503，Host 自动重试同样过守卫。
- `<mount>` 和 `<mount>/*` 转发到相应程序，就绪前返回 503。默认前缀 `/api/ext/` 走主 HTTP 服务的令牌检查。
- `/programs/<名字>` 和 `/programs/<名字>/*` 是界面入口。
  - 将程序整个地址空间挂在前缀下，例如 `/programs/fake/echo` 转至程序的 `/echo`。
  - 只转发本插件拉起、状态为 ready 且 info 报了 ui 的程序，其余返回 404。
  - 缺尾斜线时回 302 补上，原样带过去查询参数。

两种转发共用 `forward`，界面入口在公共规则之外加上当前进程密钥。
- 转发要求原始地址以字面的程序前缀开头，编码前缀会返回 404。HTTP 插件按路由模式和解码后的路径检查令牌。
- 解码、转小写、合并重复斜线后落在 `/jmbots/v1` 下的（管理接口）404。
- 去掉两类客户端输入
  - 查询里的 `token`
  - 请求头 `authorization`、`cookie`、`referer`、`x-jmbots-key` 及连接专用头
- `/programs/<名字>/` 只对主站标记为本机或已核验令牌的请求，在上游注入当前已就绪程序的 `x-jmbots-key`。未配置令牌的远程请求、仅靠地址白名单放行的远程请求沿用原来的浏览权限。进程重启后下一次已核验请求使用新密钥。具体发件仍须自己的批准记录。
- 转发响应
  - 过滤程序回的 `x-jmbots-key` 及带密钥的其他响应头。
  - 流式遮盖响应正文里的密钥。
  - 转发失败返回通用错误，省去上游请求细节。
- 程序回的 `set-cookie` 不回给浏览器（整站同源，一个程序的 Cookie 会落到所有页面上）。`Location` 指向程序自己地址或以单个 `/` 开头的，换成前缀下的路径；相对路径和别的站点原样。

## 听和发的事件

| 方向 | 事件 | 数据与行为 |
|---|---|---|
| 听 | `ready` | 启动采样并监督autostart项；未ready不主动采样，不拉起进程。 |
| 听 | `programs/resource-request` | `{action:'can-start',requestId?,who?,heavy?,vram_mb?,owned_vram_mb?,gpu?}`；同步设handled=true，然后异步取数并返回。 |
| 发 | `programs/resource-result` | `{requestId,ok,reason}`；只在请求带requestId时回执；非法参数和内部异常也明确拒绝。 |
| 发 | `programs/pressure` | `{level:'ok'或'high',reason,memoryHigh,vramHigh,sample}`；内存或显存达到高线为 high，其余（含读数未就绪）为 ok，CPU 不参与；档位、逐卡档位或指标可用性变化才广播，非每个数值变化。没有任何程序时也发。 |
| 发 | `programs/state` | `{name,title,state,license,licenseLabel,ui}`。state 是 `starting/ready/unhealthy/paused/stopped/failed`（协议不兼容报 failed，ready 且守卫暂停了后台报 paused）；license 读不到是 `unknown`；ui 同 status()。只在这几项变化时发，健康读数、RSS 变化不发；从没启动过的程序停止不发。其他插件靠它知道谁在线，不直接调 programs 的函数。 |
| 发 | `channel/direct`、`channel/mention`、`channel/listen`（一条只发一个，`ChannelBridge.ts` 经 channels 的 `emitInbound` 发） | 将外部程序入站转成标准渠道消息，分派给渠道登记的机器人：私聊 direct，群里 @ 了 mention，群里没 @ 的 listen（只记背景、不回；approval 不看 listen）。 |
| 听／发 | `channel/reply`／`channel/replied` | 复用骨架纯文字适配器，转交程序并回传结果。 |
| 听 | `programs/channel-send-request` | approval 的 Outbound 带 `requestId` 和 `program` 调用。`action: 'draft'` 带 `draftId` 读取确切草稿。`action: 'send'` 带 `generation` 和已批准的 `call`，按原账号、聊天与正文提交。 |
| 发 | `programs/channel-send-result` | 以同一个事件 `requestId` 回 `{ draft }`、`{ receipt }` 或 `{ code, error }`。运输回执状态为 `sent`、`failed` 或 `uncertain`，可带 `reason`。外置程序的发件写操作超时回 504，提示核对原意图状态。 |

这组事件由 `listenChannelSend` 挂在 programs。

- 草稿回执带实例代次、渠道、账号、聊天和原文。
- 发件 `call.requestId` 是外置程序用的持久业务号。
- 批准提供 `approval.id`、`state` 和 `expiresAt`。
- 提交前核对
  - 目标宿主仍就绪。
  - 渠道及代次与批准一致。
  - 批准未过期。
- 外置结果未知时回 `uncertain`，本人可凭原意图核对。
- 实例密钥只用于程序间请求头。

[事件类型 · `ChannelSendRequest` · ChannelSend.ts:70](ChannelSend.ts#L70) · [代次与期限核对 · `callProgram` · ChannelSend.ts:129](ChannelSend.ts#L129)

资源事件类型定义在`ResourceGuard.ts`。消费者通过`utils/RequestEvent.ts`的requestEvent等待配对回执；无人接单、超时、取消或错误应由消费者保守拒绝，不能默认允许。旧设计的`resource/state`、`need/mb`载荷不是本版接口，避免按尚未实现的草案接线。

- `heavy` 不影响准入：CPU 限制已停用（用户 #442/#444），CPU 再高、读不到都不拒绝。
- `vram_mb` 缺省表示不加载显卡模型。需要 GPU 时必须给预计新增 MiB 数，目标 `gpu` 缺省为 0。
- `owned_vram_mb` 是调用方已经驻留的自有显存，缺省为 0。它不是显卡整卡读数，也不是调用方权限凭证。
- `who` 只用于预算标签，不用于鉴权。为 voice 时，自有显存、本次需求和该调用方未过期预留合计不得超过 8 GiB。

sample 字段

- `at` 为 Unix 毫秒。
- `cpu` 为百分比或 null。
- `memory` 和 `totalMemory` 为字节或 null。
- `gpus` 为 `[{index,used,total}]` 或 null。`used` 和 `total` 也是字节。没有显卡或探针失败时用未知值。

插件卸载按顺序进行

1. 取消探针与定时器。
2. 等待当前有界任务结束。
3. 关停自有 Host。卸载后不会自动恢复或重新拉起程序。

## 内部函数

- `Spec.readPrograms(config)` 校验配置类型、名称和挂载路径唯一性，并补齐默认值。`Spec.getLaunch(root, spec)` 解析路径、参数和子进程环境。
- `Protocol.waitReady(reader, spec, signal)` 等待并校验就绪行。启动时用 `info` 验证程序身份，就绪后每 3 秒查一次 `health`，单次最多等 2.5 秒。
- `Host.start()` 运行单个监督任务。
  - 程序文件不存在时每 30 秒检查一次。
  - 连续 5 次健康检查失败后重启。
  - 崩溃退避从 3 秒开始，每次翻倍，最多 60 秒。
  - 10 分钟内累计 5 次失败转为 `failed`，等待再次启动。
- `Host.stop()` 取消监督和重试。对已确认身份的进程
  1. 请求退出接口，最多等 1 秒收到回执。
  2. 再给 `exit_wait_ms` 收尾。
  3. 仍未退出时，Windows 按自己保留的 PID 调 `taskkill /F /T`，然后等待退出通知。
- `Programs.openUi(request, reply)` 在 `/programs/:name` 路由收到请求时调。
  1. 按名字找宿主。
  2. 核对 ready 且报了界面。
  3. 补尾斜线，交给 forward。
- `forward(host, prefix, request, reply)`：mount 和界面入口收到请求时调，按上面“两种转发共用”的规则向已就绪的程序转发方法、路径、业务头和请求体，并流式返回响应。
- `getLocation(location, base, prefix)`：forward 回写响应头时调，把程序的跳转地址换回主站前缀。
- `Host.getUiUrl()`、`Host.getUiPath()`：status() 和 openUi 调；只有当前实例 ready 且 info 报了界面才给值，停止、健康异常时立即为 null。
- 渠道桥接
  - `ChannelBridge.mount(app)` 登记入站。
  - `getCallbackUrl(spec, signal)` 等主 HTTP 监听并生成子进程回调前缀。
  - 入站先由 `accept(owner, inbound)` 合并重发，再由 `dispatch(owner, inbound, messageId)` 发事件。
  - 出站回复和历史由 `call(host, route, body, timeoutMs)` 调当前实例。

## 资源守卫配置与动作

`plugins[programs].config.guard`可省略，入口`Spec.readGuard`一次校验；所有G按GiB（1024³字节）解释，nvidia-smi的MiB按1024²换算。

| 配置 | 默认值与约束 |
|---|---|
| cpu_percent / cpu_resume_percent | 已停用（用户 #442/#444）；老配置写了照收不报错，不生效。 |
| memory_gb / resume_gb | 60 / 55；达到60进入高位，严格低于55才恢复。55至60保持原高位。 |
| vram_gb / vram_resume_gb | 15.5 / 14.5；逐卡硬线取配置与该卡总量较小者；退出线还不高于该卡有效上限的95%。 |
| interval_ms | 5000；整数100至2147483647。 |
| nvidia_smi | nvidia-smi；PATH命令名或可执行文件路径；不套shell。 |

- 改阈值时同时保持进入线和恢复线的大小关系。
- guard 段的未知字段、null、非对象、非有限数或非法定时器值直接拒绝。
- 单个程序新增 `closable` 为布尔，默认 false，拒绝 null。
- `heavy` 沿用既有布尔配置。

### 采样与显存准入

- CPU 忙碌率（只读给页面看，不参与准入、档位和通知）
  1. `sumCpuTimes` 取 `os.cpus()` 所有逻辑核累计 user、nice、sys、idle 的区间增量；irq 只在非 Windows 加，Windows 上 libuv 的 sys 已是“内核时间减空闲”，中断时间已在里面。
  2. 用 `(总增量 - idle 增量) / 总增量` 算忙碌率，取最近最多 3 个有效区间的均值。首次、空核或无有效增量时记 null。
  3. 默认周期下三段约 15 秒。额外准入采样也推进 CPU 区间，实际窗口随请求频率变化。
  4. 口径接近 Windows 计数器 `% Processor Time`；任务管理器显示的是 `% Processor Utility`（按睿频折算），通常更高。11-21 实测同一窗口：本算法 38.5%，Processor Time 24–34%，Processor Utility 38–50%。
- 内存是`os.totalmem()-os.freemem()`的已用物理内存，不是本进程RSS，也不把所有缓存当额外已用。Windows可用物理内存口径已在设计中的独立探针核过；本轮不重复做真实高负载实验。
- 显存读取
  1. 运行 `nvidia-smi --query-gpu=index,memory.used,memory.total --format=csv,noheader,nounits`，设 `windowsHide=true`、2 秒超时，继承卸载取消信号。
  2. 取不到、输出 N/A 或非法时静默标记 GPU 未知。
  3. 不加载显卡模型的请求不因此拒绝。GPU 申请拒绝并说明取不到数据。多卡不拼接空闲量。
- 每次准入
  1. 获取新快照，并发准入共享正在执行的采样。
  2. 检查 `已用+未过期预留+本次需求+512MiB余量` 是否超过目标卡有效上限。超出时拒绝，理由包括已用、预留、本次需求和上限。
  3. 检查和登记之间不 await。每次放行保守预留 60 秒，届满释放，不是永久配额或长期占用锁。已反映到驱动的需求在 60 秒内可能重复计算，不承诺满载利用率。
- voice的8GiB是自己的预算，不是让所有程序合计只用8GiB。未来voice接线须准确上报owned_vram_mb和新增估算，并在自己内部维护已加载累计值；本版守卫不跨插件查询模型对象，也不猜测文件大小。memory、voice等消费者尚未接入，不能宣称已经阻止它们现有的全部模型加载。
- 超过max(10秒,3个采样间隔)的旧快照或未来异常时间戳按未知处理；内存未知不清除高位、不触发错误恢复。即使调用者传入heavy=false，内存未知也拒开。

### 内存高线与恢复

1. 60GiB进入高位，发pressure high和通知；对所有当前ready且明确声明pause能力的本插件Host请求`POST /jmbots/v1/pause`，只暂停后台重活，不做OS挂起。只有`{ok:true,paused:true}`确认才记为本守卫暂停成功；失败不冒称已暂停，后续周期可重试。
2. 每一次采样（包括事件准入）都维护连续达到60GiB的时段；降到60以下或读数未知会重置30秒计时，但仍须低于55才解除高位。
3. 连续 30 秒后，等暂停请求完成，再次采样确认仍不低于 60 GiB，才选 RSS 最大的候选走 `Host.stop()`。候选必须同时满足
   - `closable:true`
   - 有自有子进程
   - 状态为 ready 或 unhealthy
   - RSS 有效且新鲜

   每个 60/55 迟滞周期最多关闭一个，避免批量清掉用户后台。无候选就不关闭，不按程序名或 PID 扫描猜测。
4. 排名来自已核对name/protocol的health自报rssMb（本接口约定MiB），新鲜度max(10秒,3个守卫间隔)。不枚举tasklist/PowerShell；外部程序须同口径报告，不保证其自报数字绝对可信。原本手动暂停且非守卫所暂停的项不参与关闭。
5. 严格低于55GiB后，恢复本守卫确实暂停或关闭且generation仍相同的项。用户手动stop/restart使代次变化，不会被守卫拉回；原本停止/暂停的程序保持不动。正常停止超时仍持有句柄、状态failed的项不会强行再拉一份。
6. 每个恢复动作都重查最新读数；恢复HTTP等待期间若重新高位/变未知，会撤回本轮恢复并重新请求暂停，不继续拉起其它项。重启的Host还须过新一轮CPU/内存准入。恢复通知即使没有可控宿主也发一次，不把所有后台程序都宣称成已恢复。

只允许操作构造时由本插件自己创建的Host。stop沿用既有正常退出→等待→必要时仅回收自有句柄/PID树的流程；不按资源总量停jmbots、用户进程或其它插件进程。其它插件监听pressure的接线不在本版范围。

## 通知、数据与边界

- `GuardNotices.send(key,text,now)`把完整小正文先写.tmp，再原子改为`integrations/feishu/outbox/<时刻>_guard_<随机ID>.md`。这里只是入队，实际投递仍由既有飞书发件箱负责，不能把入队写成用户已收到。
- 正文固定四行，用户一眼看懂
  1. `【jmbots 资源提醒】<哪项超了>`
  2. `- 现在：<现在多少、线多少、降到多少算恢复>`
  3. `- jmbots 做了：…`
  4. `- 你可以：…`
  - 容量按 GiB 两位小数写。
- 同类键和什么时候发：

| 键 | 什么时候发 | 正文要点 |
|---|---|---|
| `memory-high` | 内存进入高位（≥60GiB），暂停请求都回来后 | 已用/总量；已让谁暂停后台，或“jmbots 没有拉起能暂停的程序”；按内存排序关大程序，多半不是 jmbots 拉起的 |
| `memory-shed` | 连续 30 秒仍超线，关掉一个 closable 程序后 | 关了谁、它自报多少 MiB、降到 55GiB 以下自动拉回 |
| `memory-recovered` | 严格低于 55GiB 后（跨过恢复线，或这一轮真恢复了程序） | 已恢复谁，或没有要恢复的 |
| `vram-high:<卡号>` | 这张卡达到硬线，或有 GPU 加载因显存不足被拒 | 已用/总量/线；不再放行新显卡模型加载 |
| `crash:<名字>` | 程序 10 分钟内连续失败 5 次、放弃自动重启 | 最后一次原因；看 `data/logs/<名字>.log` |
| `license:<名字>` | 程序自报授权 expired | 只提醒，不停程序、不删数据 |

  同类成功入队滑动10分钟最多一次，所以持续高位每10分钟提醒一次。去重记录为`data/programs/guard-notices/<事件键sha256>.json`，内容为上次成功入队Unix毫秒，插件重载可沿用。无新增数据库表。
- 生产环境写进运行时 `integrations/feishu/outbox/`，由 feishu 插件的发件箱每 5 秒扫一次发出（发给应用最近私聊的人）。测试一律注入假出口，不写真实发件箱。
- Host 的授权状态
  1. info 验证身份后读取 license。
  2. 健康周期中每 60 秒更新。读不到保持未知，明确为 expired 才通知，过期不终止程序或删除数据。
- 连续 5 次崩溃放弃时，按显式 gaveUp 标志通知。
- 通知入口的文件写失败只记录诊断，不把资源拒绝改成允许，也不阻断Host关停。去重保证是正常成功入队/持久记录后的窗口；进程恰在正文入队与去重落盘之间崩溃、磁盘损坏等故障无法提供跨飞书的exactly-once送达保证。
