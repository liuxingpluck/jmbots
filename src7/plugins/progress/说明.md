# progress v1.1.17

1.1.17 构造函数只做登记（服务、四个事件、进度请求、卸载清定时器），处理挪成方法：`onChange`（session/change）、`onBeforeModel`（session/before-model）、`onDecided`（approval/decided）、`onRequest`、`onRequestError`（progress/request）。行为不变。

1.1.16 用户点终止（`act` 的 stop）时先清报时、到点和长跑提醒三个定时器，和限时叫停 `stop` 共用 `clearTimers`：会话停下前不会再报一次“到点会先停下”。合并推送的定时器照留，终止后的进度照常推。

1.1.15 审核、交接、复盘、模型目录和群日报请求分别处理业务回执 `reply` 与缺回执原因 `why`。本机请求等处理方回执，卡片、交接和决策等得慢时记一条警告；模型请求的时限由 decision 管。无人接单时沿用文字提示、缺项默认值和原有失败反馈。

1.1.14 群日报的 `session/before-tool` 先看 `gate.deny`：前面的关口已经拒了就不动，不覆盖别人写的理由（云端 19 第 3 条附带）。

机器人名单和目录等只读值由 utils/Bots.ts 读取。

以下操作使用请求退回原因判断结果是否确定。仅在明确失败时走各自的失败路径。

- 长跑卡
- 复盘送审
- 会话转交

插件负责

- 跟踪会话一轮进度和长跑提醒。
- 管理限时、延长和交接。
- 登记超时，在空闲时自动写复盘存入公共记忆（已并入原 review）。

## 飞书群每日进度

1. 同时挂载 `feishu`、`progress` 和 `memory`。
2. 在飞书插件 `groups` 的目标群里填 `daily: { at: "17:30", bot: 周小灵, prompt: "应汇报成员：小林、小周。按交付、阻塞、明日安排汇总。" }`。
   - `at` 用运行机器所在时区。重启错过的当天不补。
   - 机器人有多个有效应用时填 `daily.app_id`。
   - 启用日报时未填 `listen` 的群默认用 `all`。普通成员回复照常进本群记忆。

把应汇报成员的准确群名片姓名写进 `prompt`，汇总时才能对照名单提醒未汇报的人。

1. `GroupDaily.ts` 的 `dispatchReport` 在预定时刻发请求事件 `bot/request`（`action: 'hand'`，带该群指定的机器人 `bot`、日报指令 `text`、`origin: {}`、当天单开的前台 `sessionId`、指向本群的 `replyTo`），等 `bot/result`（超时 10 秒）。没交成（没有这个机器人、前台没定下、超时）就抛错，由定时器记日志。
   - `replyTo` 是 `{ channel: 'feishu', accountId: 应用号, chatId, chatType: 'group', address, key, sender }`。`address` 是本群的飞书地址，按外人算（不受信），带 `scheduled: 'daily-progress'` 标记；`key` 是 `daily-progress:<群>:<日期>`，同一天重发时 bots 认得出来不再排；`sender` 是群进度定时任务。
   - 不拼假的群消息、不经渠道事件：approval、memory、网页时间线都看不到这段交办的话。
2. 使用当天独立的前台轮，按 `memory_get` 读上次计划时刻到本次的群记录。
3. 用 `channel_reply` 回原群。飞书发送时把已知群成员或 `people` 里登记的 `@姓名` 转成真实提及，未识别的名字保留为文字。

## 设计要点

- 限时、报时、长跑询问留在插件，骨架只提供状态、消息、请求、停止等通用口。
- 带渠道的 work 即使有 parent 也要受进度管理，内部小会话不纳入，避免漏掉前台交办的后台。
- 报时只改请求副本。
- 卡片由 approval 和 feishu 承载。
- 会话结束或取消之后还有收尾。
- 会话上持久的 progress 和进程内 timers 分开；重启能延续计时不代表完整过程已恢复。
- 复盘（Review）
  1. 在进度空闲且没有待审复盘时挑超时记录，避免工作中再发起重模型任务。
  2. 先写 reviewedAt，避免反复提醒。
  3. 再生成复盘。模型出错不保证自动重试。
- 复盘建议
  1. 通过可选 `filesMirror.getDir` 取记录位置，镜像插件和文件都可能缺席。
  2. 只归纳已记录的工作过程。预计提速仍按估算表述。
  3. 将建议交给 approval。
  4. 本人确认后写共享 `memory/复盘`。
