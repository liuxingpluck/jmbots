## 回话时按归属带记忆

`MemoryKey.getMemoryAccess` 按本轮不可变来源快照确定权限。

- 本人在非群聊或 `trusted: true` 的受信群可读私人记忆、知识库与当前机器人的全部历史分区。
- 其余群聊使用该群的键。
- 非本人私聊使用该人的键。
- 缺少可信来源的会话跳过召回。

`recall_history` 在后台开场和受限前台本轮开始时检索获准的往来。

- 前台只在同一轮复用召回。
- 后台缓存带生成时的归属。
- `memory_search` 和 `memory_get` 共用同一权限。受限模型无法改查别人或别的群，原文和相邻段也核对归属。
- 私人文件和未补标的旧往来只供本人读取。
- 本人的 Rust 分区目录不可读时退回当前客户检索，渠道索引仍可用。

## 记忆服务由 programs 拉起（1.6.0）

Rust 记忆服务 `jmbots-memory` 登记在 `config.example.yaml` 的 programs 段。

- programs 负责拉起、握手、守护、暂停和退出。
- 自带界面在 `/programs/jmbots-memory/`。
- 本插件按 `service_url`（默认 `http://127.0.0.1:30087`）调用 HTTP 接口。

- 发给记忆服务的请求都经 `Backend.ts` 的 `fetchMemory`。
  - 连不上报“记忆服务没在线（地址）：原因”。
  - 超时报“记忆服务超时没回”。
- 记忆服务没在线时各入口如下。
  - `GET /api/memory/health` 回 `ok:false`，带同一句原因。
  - 统一检索把对应来源放进 `unavailable`、原因放进 `warnings`。记忆页显示“提示”，`memory` 工具旧动作也带“提示：”一行。
  - `memory/request` 三种动作都回 `ok:false` 带 `error`。
- 已删的模块或入口
  - `Services.ts`（拉起、守护、端口顺延、日志）
  - 配置 `services`
  - 主端口 `/memory/*` 转发
  - `GET /api/memory/services`
  - 旧 vgr 条目

  进程状态看 programs 的 `GET /api/programs`。

`Search.find` 分别查四个来源。

- Rust 聊天往来
- Rust 知识库
- 渠道 SQLite 索引
- 本地记忆卡片

四路按排名倒数折算分数，分数相同时新记录在前。

- `unavailable` 是未响应或未启用的来源。
- `skipped` 是因范围或权限跳过的来源。
- `semantic` 在 Rust 返回中保留向量命中，渠道和卡片仍按字面搜。
- 时间筛选分别使用渠道索引、卡片文件修改时间和 Rust 已返回的最多 50 条候选。

- Rust 的单次历史查询必须有客户号。
- 受限模型的 Rust 客户号和渠道索引归属由来源自动指定，模型提供的其他客户号会被拒绝。
- `memory_get` 读取每条引用时重新验权。
- 前台两种新工具共用每轮三次配额。

HTTP 和内部 `search` 事件的归属参数至多传 `customer`、`person`、`group` 中的一项。

- `person` 可为 `person=person:<渠道>:<发话人ID>` 或 `person=owner`。
- `group` 可为 `group=group:<渠道>:<聊天号>`。
- 归属查询精确匹配渠道索引和 Rust 客户分区，知识库和记忆卡片列在 `skipped`。
- 同时查 `channel` 和 `history` 时，渠道消息通过索引返回一次。
- 事件调用方确认请求人的权限。

网页归属列表合并渠道索引和记忆服务同机库中的已标记段落。

- 个人名优先取最近的 `sender_name`，群用聊天号，本人显示“本人”。
- 同一批渠道消息在索引和 Rust 均出现时，按渠道索引计一次。

- 网页的“全部”沿用原有演示客户和公共知识库选择。

## 渠道消息索引（1.2.0，`ChannelIndex.ts`）

各渠道的消息按聊天记进表 `memory_channel_messages`，能按“渠道 + 聊天 + 时间范围 + 关键词”查。配置 `channel_index`（布尔，不写是开）。

建表直接含以下字段，各字段沿用原有默认值。

- `mentioned_bots`
- `rust_state`
- `memory_key`

[建表 · `ChannelIndex.constructor` · ChannelIndex.ts:116](ChannelIndex.ts#L116)

- **听的事件**
  - `channel/direct`、`channel/mention`、`channel/listen` 是用户的话（私聊、群里叫了机器人、只听的），三个事件由 `applyChannelIndex` 用同一个处理（`onInbound`，`prepend`）挂上，飞书、微信、网页、命令行、语音先落盘再发，键为 `messageId`；只听的、没登记的群也记。`getMessageRow` 遇到 `routing.partial === true`（语音半句）返回 undefined 不记，键和整句一样，先记半句整句会被 `INSERT OR IGNORE` 挡掉，等同一消息号的整句再记。
  - `channel/replied` 是机器人回复，只有回执状态为 `sent`、`partial` 才记；正文取回执带的请求，文字片段连起来，聊天照请求的来源快照，键为 `replyRequestKey`。`getReplyRow` 没有来源快照的（旧路自动回话、relay 回信、主动发件）不记。

- **模型读写范围**
  - memory_search 可按渠道、聊天、关键词、发言人和时间查，单查渠道最多 200 条。
  - memory_get 省略 ref 时默认当前账号和聊天，回执的 nextCursor 可传给 before 继续翻页。
  - 受限会话的查询及邻段都按已核定的账号、聊天和归属过滤。
- **接口** `GET /api/memory/channel?channel=&chat=&since=&until=&q=&limit=` → `{ hits }`（令牌由 http 统一查，按本人全量）。统一查询返回的 `id` 参数可定位一条消息，回 `{ anchor, before, after }`。

  - `msg_key`（唯一）
  - `channel`
  - `account`（飞书应用号、微信号；网页、命令行 local）
  - `chat`（飞书 chat_id、微信会话名、`http:本机`、`cli:本机`）

## Rust 渠道消息与后台回填

- 渠道事件先落 SQLite 索引，再由实时队列送入 Rust。旧 SQLite 行及归档历史通过手动回填发送。
  - `rust_state` 0：历史待入。
  - `rust_state` 1：实时待入。
  - `rust_state` 2：Rust 已确认。
  - 重启从待入行继续，重试使用同一 Rust 来源键。
- 写入 Rust 的归属
  - 新记录把 `memory_key` 写进 `customer`，发言人键写进 `session`。
  - 原消息键保留在 `jmbots-channel:<消息键>` 来源里。
  - 缺归属的旧记录保留原 `jmbots-channel:` 客户分区和幂等写入键。
  - 关系空间按 `h:<customer>` 划分，当前渠道批次沿用关闭关系抽取的设置。
- 回填配置和恢复
  - `backfill.enabled` 默认 `false`，决定首次启动是否回填。
  - `batch_size` 默认 25，范围 1～100。
  - `interval_ms` 默认 2000，范围 1～600000。
  - 手动选择和归档扫描完成状态原子写进 `memory/channel-backfill.json`。
  - 扫描中重启会重读归档，已确认行直接跳过。
- 回填的资源守卫
  - 每批发 `programs/resource-request`，载荷为 `{action:'can-start', heavy:true, who:'memory-backfill'}`，收到 `programs/resource-result` 放行才继续。
  - 收到 `programs/pressure` 的 `high` 时停发新批，收到 `ok` 后允许继续。
  - 手动暂停优先。
- 回填接口
  - `GET /api/memory/backfill` 回 `{done,total,running,scanning,reason}`。`total` 为已发现消息数，扫描时会增加。
  - `POST /api/memory/backfill` 接 `{running:boolean}` 并回新状态。
  - 记忆页同一路径轮询并提供开始、暂停。

### 只读核对历史回填覆盖率

```powershell
Invoke-RestMethod -Method Get -Uri 'http://127.0.0.1:30086/api/memory/backfill' |
  Select-Object done, total, running, scanning, reason
```

`total > 0` 时，用 `done / total` 算已发现消息的 Rust 确认比例。检查归档是否扫完时同时读 `reason`。显示「回填完成」且 `done = total`，才说明已扫描的归档没有待发项。下面的归属统计单独衡量已存段落的身份标记覆盖率。

### 统计旧段落的归属覆盖率

```powershell
bun.cmd ztools/memory/Count_Memory_Keys.ts --data <运行时目录> [--store <记忆库文件>]
```

脚本只读打开 `data/jmbots7.db` 和 `data/memory/memory.db`。memsvc 使用别的库时用 `--store` 指定。脚本只输出计数。

- `total`：总段落。
- `tagged`：已标归属。
- `recoverable`：渠道依据足够，可后续补标。
- `reasons`：无归属的知识段、缺渠道来源或索引行、未知聊天类型、缺渠道或群号，或私聊对话对象缺失、有歧义。

### 给渠道索引和旧段落补归属

```powershell
bun.cmd ztools/memory/Backfill_Memory_Keys.ts --data "<运行时目录>"
bun.cmd ztools/memory/Backfill_Memory_Keys.ts --data "<运行时目录>" --write
```

预览只输出计数，支持 `--store "<记忆库文件>"`。

- `channelIndex.empty`：空键渠道行数。
- `recoverable`：能算出键的行数。
- `planned`：核对 Rust 后可补的空键行数。
- `existingCopies`：可协调的已有 Rust 副本数。
- `reasons`：归属不明的行数。
- `conflicts`：重复副本、空间或归属不符、索引原键不符。
- 顶层计数统计 Rust 段落。旧 `session:`、`bot-log:` 仅在回话地址明确且旧客户吻合时作为会话候选。

写入在一个事务中重新扫描，先补渠道再补会话。

- 找到唯一且归属相容的 Rust 副本时原地补归属，将索引的 `rust_state` 标为 2，避免重复入库。
- 仅有索引的行保留回填状态。
- 归属不明或冲突的记录保留原值。
- 段落保留正文、编号和向量。
- 旧图挂接解绑，已允许抽取的段落由记忆服务在新归属下重建。

正式迁移由中控依次执行。

1. 停 jmbots 主服务和 `jmbots-memory` 的写入。暂停历史回填后实时队列仍可写入。
2. 成对备份 `data/jmbots7.db` 与实际 Rust 库。
3. 保持服务停止，复跑预览，再带 `--write` 写入。
4. 核对 `indexed`、`moved`、`confirmedCopies` 和冲突，复跑预览应没有新的可补项。

- 事务内报错会撤销两边更新。
- 异步断电等中断时，SQLite WAL 模式不保证跨库提交同时落盘。
- 回滚时保持两边停写，从同一时点成对恢复备份，再启动服务。

## 前台往来归档

`memory_channel_messages` 统一持有前台往来正文。

- 标准消息键已知、方向及正文匹配时，同一条渠道消息可关联多个机器人会话。
- 缺可靠渠道身份或经过会话处理的内容标 `front_only=1`，只按前台会话范围读。
- 渠道检索、归属补标和 Rust 渠道同步只处理渠道可见的行。

`memory_channel_front` 保存以下关联字段。

- `id`：归档编号
- `archive_key`：重放识别键
- `msg_key`：索引消息键
- `bot`：机器人
- `session_id`：会话
- `time`：原记录时间

正文由渠道表保存。查询按机器人及当前会话范围过滤，原 `bot-log:编号` 引用仍可用。

旧表停写后按阶段读取。

- 尚未迁移的往来仍由 memory 按相同会话范围读。
- 停写窗口执行 `M14` 后重启，历史统一从渠道索引读。
- 旧向量由记忆服务分批重算，离线时保留字面检索。

## 数据

### 数据库表

`memory_chunks` 存本地记忆库的片段：聊天记录按句切、知识库文件按段切，给 memory 工具搜；一行是一个片段。外部记忆服务（memory.backend_url）开着也照样先写这张表。

| 列名 | 类型 | 能不能空 | 意思 | 谁写、什么时候写 |
|---|---|---|---|---|
| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | 否 | 片段号 | `LocalBackend.ingest` 插入时自增 |
| `source` | TEXT NOT NULL | 否 | 来源：`session:<会话号>` 或知识库文件绝对路径；按它整批删了重建 | `ingest` |
| `scope` | TEXT NOT NULL | 否 | `history` 聊天记录 / `knowledge` 知识库 | `ingest` |
| `bot` | TEXT NOT NULL | 否 | 机器人；公共知识是空串 | `ingest` |
| `customer` | TEXT NOT NULL | 否 | 客户；knowledge 是空串 | `ingest` |
| `session` | TEXT NOT NULL | 否 | 会话号；knowledge 是空串 | `ingest` |
| `title` | TEXT NOT NULL | 否 | “用户说” / “机器人答” / 文件名 | `ingest` |
| `text` | TEXT NOT NULL | 否 | 片段原文 | `ingest` |
| `at` | INTEGER NOT NULL | 否 | 消息时间或文件 mtime，毫秒 | `ingest` |
| `start_at` | INTEGER NOT NULL | 否 | 出处起点：聊天是 0 起的消息序号，知识库是 1 起的行号 | `ingest` |
| `end_at` | INTEGER NOT NULL | 否 | 出处终点 | `ingest` |

片段写入和删除由以下方法处理。

- `Store.ingestSession` 在 `session/new-message` 时把新消息切片收进来。
- `Store.indexFile` 在知识库文件变化时先 `remove` 再 `ingest`。
- `Store.syncKnowledge` 发现文件没了就 `remove`。
