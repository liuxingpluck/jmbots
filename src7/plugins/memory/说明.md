# memory v1.10.3

1.10.3 保留记忆服务超时和连接失败时的请求异常链。

提供记忆文件工具、按客户隔离的检索、关系图和渠道消息索引。

## 回话时按归属带记忆

`MemoryKey.getMemoryAccess` 根据本轮不可变来源快照确定权限。本人在非群聊或 `trusted: true` 的受信群可读私人记忆、知识库与当前机器人的全部历史分区。其余群聊使用该群的键，非本人私聊使用该人的键。缺少可信来源的会话跳过召回。

`recall_history` 在后台开场和受限前台本轮开始时检索获准的往来。前台只在同一轮复用召回，后台缓存带生成时的归属。`memory_search`、`channel_search`、`memory_get` 共用同一权限。受限模型无法改查别人或别的群，原文和相邻段也核对归属。只有本人可读私人文件和未补标的旧往来。本人的 Rust 分区目录不可读时退回当前客户检索，渠道索引仍可用。

## 记忆服务由 programs 拉起（1.6.0）

Rust 记忆服务 `jmbots-memory` 是 programs 插件的一个条目（`config.example.yaml` 的 programs 段），由 programs 拉起、握手、守护、暂停和退出，自带界面在 `/programs/jmbots-memory/`。本插件不再托管进程，只按 `service_url`（默认 `http://127.0.0.1:30087`）调它的 HTTP 接口。

- 所有发给记忆服务的请求都经 `Backend.ts` 的 `fetchMemory`：连不上报“记忆服务没在线（地址）：原因”，超时报“记忆服务超时没回”。
- 记忆服务没在线时：`GET /api/memory/health` 回 `ok:false` 带这句；统一检索把对应来源放进 `unavailable`、原因放进 `warnings`（记忆页显示成“提示”，`memory` 工具旧动作也带“提示：”一行）；`memory/request` 三种动作都回 `ok:false` 带 `error`，不再悄悄交回空的。
- 删掉的：`Services.ts`（拉起、守护、端口顺延、日志）、配置 `services`、主端口 `/memory/*` 转发、`GET /api/memory/services`、旧 vgr 条目。进程状态看 programs 的 `GET /api/programs`。

## 统一记忆搜索

| `GET /api/memory/owners` | 只读，无查询参数，沿用 HTTP 令牌规则。 | `{ owners: [{ key, kind, name, count }] }`，`kind` 为 `owner`、`person` 或 `group`。 |
| `memory_search` | 模型按会话确定可查范围。`range=session` 限这场会话。用 `front=true` 翻本场前台归档，可按 `who`、`since/until`、`before/after` 编号或 `from_earliest` 限定。`mentions=true` 查 @，可省 `q` 并用 `before` 游标翻当前渠道。 | 普通检索的命中结构包含 `source,id,title,snippet,score,at,ref,via,customer,bot`。前台归档和原渠道 @ 分页保留各自的回执。 |
| `memory_get` | `ref`（含 `#编号` 或 `bot-log:编号`）。省略 `ref` 可按 `channel/chat`、`before` 游标或 `senderId` 翻页，或用 `since/until` 从渠道索引截取时间段。微信本人可用 `wechat_skip` 读原归档。 | 段落原文及前后文、卡片命中行附近文本，或渠道原档页与 `nextCursor`。Rust 原文来自 `/passages/:id`，同一出处的邻段由本地只读库补。 |

`Search.find` 独立查询 Rust 聊天往来和知识库、渠道 SQLite 索引、本地记忆卡片。四路按排名倒数折算分数，分数相同时新记录在前。`unavailable` 是未响应或未启用的来源，`skipped` 是因范围或权限跳过的来源。`semantic` 从 Rust 返回中保留向量命中，渠道和卡片仍按字面搜。渠道时间筛选在索引中执行，卡片按文件修改时间筛，Rust 时间筛选在已返回的最多 50 条候选内执行。

Rust 的单次历史查询必须有客户号。受限模型的 Rust 客户号和渠道索引归属由来源自动指定，模型提供的其他客户号会被拒绝。`memory_get` 读取每条引用时重新验权。前台两种新工具共用每轮三次调用配额。

HTTP 和内部 `search` 事件可传 `person=person:<渠道>:<发话人ID>`、`person=owner` 或 `group=group:<渠道>:<聊天号>`。`customer`、`person`、`group` 三项至多传一项。归属查询精确匹配渠道索引和 Rust 客户分区，知识库和记忆卡片列在 `skipped`。同时查询 `channel` 和 `history` 时，渠道消息通过索引返回一次。事件调用方负责确认请求人的权限。

网页归属列表合并渠道索引和记忆服务同机库中的已标记段落。个人名优先取最近的 `sender_name`，群用聊天号，本人显示“本人”。同一批渠道消息在索引和 Rust 均出现时按渠道索引计一次，Rust 同机库未挂载时仍返回渠道归属。检索命中携带归属键供网页显示。网页的“全部”使用原有演示客户和公共知识库选择。

模型在挂载 memory 后使用 `memory_search`、`memory_get`，本人的 `memory` 文件操作仍可用。`memory/history-tool` 可把本人的原归档请求交给 bots 或 wechat，保留编号、游标和旧回执。受限模型查询已归属的索引与往来，不直接进入未标记的原始归档。计划 2026-11-25 清理兼容入口，由中控在提示词、技能和旧调用完成迁移后执行。

记忆页与图谱页由同一 `GET /api/memory/search` 检索，记忆状态由 `GET /api/memory/health` 直探 Rust。开场先搜、本地知识库文件增量同步、新导入和统一查询使用同一 Rust 地址。升级沿用现有 SQLite 备份和索引进度，尚未入 Rust 的历史数据不在此步批量重收。

## 渠道消息索引（1.2.0，`ChannelIndex.ts`）

各渠道的消息按聊天记进表 `memory_channel_messages`，能按“渠道 + 聊天 + 时间范围 + 关键词”查。配置 `channel_index`（布尔，不写是开）。

建表直接包含 `mentioned_bots`、`rust_state` 和 `memory_key`。各字段沿用原有默认值。 [建表 · `ChannelIndex.constructor` · ChannelIndex.ts:114](ChannelIndex.ts#L114)

- **听的事件**：`channel/message`（用户的话；飞书、微信、网页、命令行都是先落盘再发）→ 键 `messageId`；`channel/reply`（机器人的回复，文字片段连起来，聊天照来源快照）→ 键 `replyRequestKey`。`INSERT OR IGNORE`，同一条不重复；记不上只打日志，不挡别人。
- **工具 `channel_search`**（front、work）：`channel`、`chat`、`since`、`until`（`2026-11-17`、`2026-11-17 08:30` 或毫秒）、`query`（空格分开的关键词都要有，LIKE 子串，`%`、`_` 照字面）、`limit`（默认 50，最多 200）；新的在前，一条一行“[时间] 渠道·聊天 发言人：正文”。范围照这一轮的来源快照（`frontTask.sourceSnapshot ?? activeSourceSnapshot`）用 `bots/ChannelProtocol.ts` 的 `isHistoryOwner` 判断：本人（不是外人、不在群里）全都能查；别的只查快照里这个聊天，写了别的聊天、别的渠道直接拒。approval 的只读名单里有它（外人也能查自己这个聊天）。
- **接口** `GET /api/memory/channel?channel=&chat=&since=&until=&q=&limit=` → `{ hits }`（令牌由 http 统一查，按本人全量）。统一查询返回的 `id` 参数可定位一条消息，回 `{ anchor, before, after }`。
- **表** `memory_channel_messages`：`id`、`msg_key`（唯一）、`channel`、`account`（飞书应用号、微信号；网页、命令行 local）、`chat`（飞书 chat_id、微信会话名、`http:本机`、`cli:本机`）、`chat_type`（p2p、group、local；补旧不知道是空串）、`direction`（user、bot）、`sender_id`、`sender_name`、`bot`、`text`、`at`（毫秒）；索引 `(channel, chat, at)`、`(at)`。不用 FTS5：中文没分词，unicode61 整句一个词、trigram 查不了两个字的词。
- **提及字段** `mentioned_bots` 是可信渠道解析出的被 @ 的机器人名数组（JSON）。旧行沿用空数组。
- **归属字段** `memory_key` 由 `MemoryKey.ts` 统一计算，并以 `(memory_key, at)` 建索引。私聊话归对话对象，群聊话归群，本机网页和命令行归 `owner`。旧行和缺少归属依据的行留空。
- **补旧** `bun src7/plugins/memory/Backfill_Channel_Index.ts --data <运行时目录> [--run yes] [--wechat_channel wechat]`：默认只数不写；读飞书 `channels/feishu/chats/<应用号>/<聊天号>.jsonl`、`wechat_messages`、`web_messages`（只取 channel='http' 的和它的 replies）、`channels/cli/*.jsonl`；键照各渠道 `channel/message` 的拼法，拼不出的（机器人回复、命令行）按同渠道同聊天同方向同正文两分钟内去重；可以反复跑。
- **历史来源**：微信未发事件的消息、飞书只落归档的消息，可用后台回填收录。机器人 `workspace/inbox/` 保存附件。

## Rust 渠道消息与后台回填

- 渠道事件先落 SQLite 索引，再由实时队列送入 Rust。旧 SQLite 行及归档历史通过手动回填发送。`rust_state` 为 0（历史待入）、1（实时待入）、2（Rust 已确认），重启时从待入行继续，重试使用同一个 Rust 来源键。
- 新记录把 `memory_key` 写进 Rust 的 `customer`，发言人键写进 `session`。原渠道消息键保留在 `jmbots-channel:<消息键>` 来源里。缺归属的旧记录保留原 `jmbots-channel:` 客户分区和幂等写入键。Rust 的关系空间按 `h:<customer>` 划分，当前渠道批次沿用关闭关系抽取的设置。
- `backfill.enabled` 默认 `false`，决定首次启动是否回填。`batch_size` 默认为 25，范围 1～100。`interval_ms` 默认为 2000，范围 1～600000。手动选择和归档扫描完成状态原子写进 `memory/channel-backfill.json`。扫描中重启会重读归档，已确认的行直接跳过。
- 每批发送 `resource/request`，载荷为 `{action:'can-start', heavy:true, who:'memory-backfill'}`，收到 `resource/result` 放行才继续。收到 `resource/pressure` 的 `high` 停止发新批，收到 `ok` 后允许继续，手动暂停优先。
- `GET /api/memory/backfill` 返回 `{done,total,running,scanning,reason}`。`total` 是当前已发现消息数，归档扫描期间会增加。`POST /api/memory/backfill` 接收 `{running:boolean}` 并返回新状态。记忆页同一路径轮询并提供开始、暂停操作。

### 统计旧段落的归属覆盖率

```powershell
bun.cmd src7/plugins/memory/Count_Memory_Keys.ts --data <运行时目录> [--store <记忆库文件>]
```

脚本以只读方式打开 `data/jmbots7.db` 和 `data/memory/memory.db`。若 memsvc 使用另外的库路径，用 `--store` 指定。输出 `total`（总段落）、`tagged`（已标归属）、`recoverable`（有足够渠道依据可后续补标）以及 `reasons`（其余原因）。原因包括无归属的知识段、缺渠道来源或索引行、未知聊天类型、缺渠道或群号，以及私聊对话对象缺失或存在歧义。脚本只输出计数。

### 给渠道索引和旧段落补归属

```powershell
bun.cmd src7/plugins/memory/Backfill_Memory_Keys.ts --data "<运行时目录>"
bun.cmd src7/plugins/memory/Backfill_Memory_Keys.ts --data "<运行时目录>" --write
```

预览只输出计数。报告中 `channelIndex.empty` 为空键渠道行数，`recoverable` 为能算出键的行数，`planned` 为核对 Rust 后可补的空键行数，`existingCopies` 为可协调的已有 Rust 副本数。`reasons` 统计归属不明的行，`conflicts` 统计重复副本、空间或归属不符、索引原键不符。顶层计数统计 Rust 段落，旧 `session:` 和 `bot-log:` 仅在回话地址明确且旧客户吻合时列为会话候选。支持 `--store "<记忆库文件>"`。

写入在一个事务内重新扫描，先补渠道再补会话。已找到唯一且归属相容的 Rust 副本时，原地补段落归属，并把索引的 `rust_state` 标为 2，避免后台重复入库。仅有索引的行保留回填状态。归属不明和冲突的记录保留原值。段落保留正文、编号和向量。旧图挂接解绑，已允许抽取的段落由记忆服务在新归属下重建。

正式迁移由中控执行。先停 jmbots 主服务和 `jmbots-memory` 的写入，成对备份 `data/jmbots7.db` 与实际 Rust 库。暂停历史回填后实时队列仍可写入。保持服务停止，复跑预览再带 `--write` 写入。核对写入报告的 `indexed`、`moved`、`confirmedCopies` 和冲突，复跑预览应没有新的可补项。事务内报错会撤销两边的更新。遇到异步断电等中断时，SQLite 的 WAL 模式不保证跨库提交同时落盘。需要回滚时保持两边停写，从同一时点成对恢复备份，再启动服务。

## 前台往来归档

`memory_channel_messages` 统一持有前台往来正文。已知标准消息键且方向、正文匹配的，同一条渠道消息可关联到多个机器人会话。缺乏可靠渠道身份或经过会话处理的内容用 `front_only=1` 标记，仅按前台会话范围读取。渠道检索、归属补标和 Rust 渠道同步只处理渠道可见行。

`memory_channel_front` 保存归档编号 `id`、重放识别键 `archive_key`、索引消息键 `msg_key`、机器人 `bot`、会话 `session_id` 和原记录时间 `time`。不在关联表复制正文。查询按机器人与当前会话范围过滤，原 `bot-log:编号` 引用仍可用。

停写旧表的版本上线后，尚未迁移的往来仍由 memory 按相同会话范围读取。停写窗口执行 `M14` 并重启后，历史统一从渠道索引读取。旧向量由记忆服务分批重算，离线时保留字面检索。 [迁移说明](../../../ztools/migrate-legacy/说明.md)
