**可信目录**（1.1.1，用户 11-18 #169）取配置 `trusted_dirs` 和这场会话的授权目录。以下路径解开后都须落在可信目录里。

- 命令的执行目录
- 开头 `cd` 到的目录
- 命令里写的每个绝对路径
- 带 `..` 往上走或从盘根算的相对路径（`\` 开头、只写盘符）

满足目录条件且未命中 `mustAsk` 时，程序规则直接放行，`by: 'rule'`、原因“可信目录”。以下情况沿用各自规则。

- 删系统、删注册表、删数据、格式化命中 `mustAsk`。
- 写了环境变量（`%X%`、`$X`、`${X}`、`~`）的命令算不出落在哪，不能按可信目录放行。
- 碰密钥文件先拒。
- builder 让跑的命令（`confined`）使用受限目录规则。

**审批卡片说清楚**（1.1.2，用户 11-18 #172）：命令要问用户时，卡片正文（`card.reason`）固定三行，飞书卡片顶上、网页审批面板一眼看完：
1. `要做什么：` 按以下顺序取命令执行完的结果。
   1. 审核小会话写的 `what`，不复述命令。
   2. 决策模型顺带写的 `what`。1.1.6 起 `askDecision` 带 `want: ['what']`，`decision/judge-result` 回的 `what` 在决策模型拿不准、继续往下走时才用得上。
   3. 都没有就写“说不清会做成什么（命令：<命令>）”，照旧问用户。
   - 这句用于显示。可信目录、mustAsk、决策模型阈值和审核小会话 safe 仍各按原规则判断。
2. `动哪些：` 依次整理涉及的路径。
   1. 先列命令里解析出的绝对路径。
   2. 再列审核给的 `paths`，去重后最多 5 个，多了写“等 N 个”。
   3. 都没有就写执行目录。
3. `为什么问你：` `review` 记录每档未放行的原因（`asks`）。
   - mustAsk 的原因
   - `getUntrusted` 的原因（没配可信目录 / 某路径不在可信目录里 / 写了环境变量）
   - 决策模型拿不准的原话（真答过才写）
   - `审核小会话：<risk 原文>`

审核说明有以下规则。

- 审核小会话没写 risk，或不放行却写“无”时，`getReviewReason` 一律写“审核没给出理由”。
- `card.risk.text` 也用同一句理由。
- 每行最多 160 字。
- 审核提示词要求 what、risk 写具体的路径、操作和后果。

**授权目录（grants）**按消息一路带到审批。回话地址的 `grants.dirs` 有三个来源：

1. 本人或中控（`from: 'claude'`）发 `POST /api/message` 时可带 `grants: { dirs: [绝对路径…] }`，web-api 入口用 `utils/Checks.ts` 的 `checkGrants` 查一次并规范化。
2. 渠道进来的话按人、按群从 `approval_grants` 查到的（`Grants.applyMessage`，见「目录授权」）。
3. 本人这一轮说的当轮授权（`dir_grant`），按这一轮的 `replyRoundKey` 记在内存里（`Grants.getTurnDirs`）。

`bots` 认领时抄地址记到 `session.row.address`，交办的后台会话带着同一个地址。approval 审 exec 时用 `getReviewDirs`：

- 本人（不是 confined）：配置的 `trusted_dirs`，地址是 `owner: true` 的再加这一轮的授权目录（地址里的 + 当轮的），原因写“可信目录”。
- 外人（confined，exec 给非本人那一轮的命令）：这一轮有授权目录时，认执行目录（他这一轮的工作目录）加授权目录，在里面原因写“授权目录”，**出了这些规则直接拒**（不问模型、不出卡片）；这一轮没授权目录的照旧交给决策模型、审核小会话，审不过拒。`trusted_dirs` 是本人的，不给。
- 地址不是本人、又不是 confined：只有 `trusted_dirs`。

地址跟着最后一句带渠道的话换。后来的消息没带 grants、库里也没有，授权就没了。

## 目录授权（Grants.ts，用户 #292、#297、#301）

本人把某个人、某个群绑到一个或几个目录：这些目录和下面的子目录里读写、跑命令（命令照样过密钥、mustAsk 规则）、发文件都不用再问本人；出了这些目录照旧。

- **谁**：人是个人身份（飞书 `feishu:<open_id>`，别的渠道是客户号），群是群的客户号（`feishu:group:<chat_id>`），都照 `Rules.ts` 的 `getSpeaker` 算。
- **进来的话**（`channel/direct`、`channel/mention`、`channel/listen`，`prepend: true`，在 bots 认领、抄地址之前）：`index.ts` 的入站监听调 `applyMessage`（direct、mention 先认批复再调它），按群（只在群里）、按人查表。
  - 外人地址里原有的 `grants` 第一步就删掉（只有本人的网页消息能带），这步不碰库。
  - 查库出错（锁住、坏了）：`getDirs` 只打一行日志、交回空，这一轮当没有授权；不往外抛，因为入站是 `ctx.serial` 挨个问，抛了这条话就到不了任何机器人。
  - 本人：原来带的 `grants`（网页、中控）加上库里的，档位、工作区不动。
  - 外人：查到了就把 `role` 改成 builder、`owner: false`、消息的 `role` 也改；工作区换成群绑的第一个目录（群里谁说话都在群的目录里干活，收到的附件也落进去）；没有群绑的，原来是 guest 的换到他自己的第一个授权目录，原来就是 builder 的留在他登记的目录。
  - 顺带记下见过的人和群（内存，最多 300 个，重启清空），给按名字授权、网页挑人用。
- **本人说的当轮生效**：`dir_grant` 设的（存表的、`once` 的都算）马上写进这场会话现在的地址；再按这一轮的 `replyRoundKey`（前台读 `activeSourceSnapshot`，后台读 `frontTask.sourceSnapshot`）记下（内存，最多 200 轮）。`session/before-model` 每一步先 `applyTurn` 补进地址；审命令时 `getReviewDirs` 另从 `getTurnDirs(meta)` 取（`sessions.find` 读的是库里的记录，内存里补的它看不到）。地址已经换成外人的不补。
- **提示词**：这一轮有授权目录时，`session/before-model` 加一句 `grantPrompt`：列出目录，跑命令先 `cd /d 目录 && 命令`，群里只说文件名或相对路径。
- **用到授权目录的地方**：approval 审命令（`getReviewDirs`）；file-tools 读写、飞书发文件（`utils/Bots.ts` 的 `resolveSessionPath`）；hand_session 选工作区（`bots/DispatchTools.ts` 的 `getWorkspace`，授权目录可以直接当后台的工作区）。
- **命令开头 cd**：`Rules.getUntrusted` 照真正跑命令的目录查（开头 `cd X &&` 了就是 X，原来的执行目录不再查），授权目录在工作区外面时模型照提示先 cd 过去。

## 本人确认渠道发件

外置客服页在主站 `/programs/<程序名>/_approval/` 准备及确认草稿。只有 HTTP 核对过的本人请求可以操作。下面的动作各走原入口。

- 普通命令确认
- 模型回复
- 决策规则
- 客户的“同意”文字

草稿从准备到发出有以下步骤。

1. 从程序读取原草稿，固定程序名、实例代次、渠道、草稿号、账号、会话及正文的 SHA-256 摘要。
2. 客服页展示原文和目标，确认时交回意图号、所见摘要和交互号。
3. 主站重新读取草稿核对，十分钟内才接受待确认意图。
4. 确认成功后一次性记下批准时刻和十分钟有效期，再交 programs 按原值运输。

同草稿的重复请求及在途记录复用原业务请求号。

`approval_outbound` 保存在主站库。

- 每行包含意图号 `id`、永久业务号 `send_id`、永久外置批准号 `approval_id`、程序、代次、渠道、草稿号、目标及原文和摘要。建表时包含可空的 `target_bot`。
- 批准证据记录在 `approved_at`、`expires_at`、`interaction_id`。
- 外置 `sent/failed/uncertain` 回执原样存入 `receipt`。通用 `channel/replied` 把 failed 表达为 `rejected`。
- 主站中断后在途记录转为 uncertain，客服页可查原状态并填人工核对结果。
- 飞书提示只尝试投递一次给配置中明确登记为本人的私聊。
- 发件账不存启动密钥，也不会自动重发或换号。

本功能使用以下事件。

- `approval/outbound-request` 接收发件请求。
- `approval/outbound-result` 返回结果。
- `programs/channel-send-request` 和 `programs/channel-send-result` 连接外置草稿读取和发送。回执中没有程序密钥。

主站主动发件复用同一个持久账。

- 主动行的 `program` 为 `@channel`，`draft_id` 为 `0`，`generation` 保存入口填入的来源。
- 调用方通过 `approval/outbound-request` 提交 `action: 'prepare-channel'`、`program: '@channel'`、受信入口确定的 `actor` 和 `message: { channel, account, chat, text, from }`。
- 工具入口可以给 `toolKey`，同一次调用复用原意图。
- 准备阶段返回意图号、确切目标、原文和摘要。

本人确认后的发件流程如下。

1. 核对意图号、所见摘要、交互号和期限。
2. 成功占位后，`Outbound.submitChannel` 经 `requestTextReply` 发 `channel/reply`。
   - `target` 为 `{ channel: row.channel, chat: row.chat, address }`。
   - 飞书 `address` 为 `{ appId: account, chatId: chat, messageId: '', openId: '', chatType: '' }`。
   - 网页（channel `http`）`address` 为 `{ reminder: 意图号 }`。
   - 轮键为 `'approved-send:' + send_id`，请求键为 `getReplyRequestKey(轮键, send_id)`，同一笔重试时渠道按它去重。
   - `kind` 为 `final`，`bot` 为提醒记录的 `target_bot`，没有则为空串。
3. 渠道照 `target.address` 发出，经 `channel/replied` 回执。

业务插件通过 Outbound 提交和确认意图，由 Outbound 触发发送。

渠道回执折成 `ProviderReceipt`。

- `ok` 为 `sent`。
- `rejected`（含渠道没挂）为 `failed`。
- 其余为 `uncertain`，保留原发送号等核对。
- 原因放在可选的 `receipt.reason`。

等渠道回执不掐表：飞书每个开放接口请求自己限时 60 秒、到点回 uncertain，等 30 秒还没回只报警；外置程序的发件由 programs 的 HTTP 自己限时 90 秒。拿到结果后按下列顺序结算。

1. 把结果写入账。
2. 主站自己的主动发件到此为止：渠道自己已发过 `channel/replied`，不再补。
3. 外置程序的发件由 `Outbound.publish` 补一条 `channel/replied`，请求由渠道、聊天、正文和 `payloadHash` 拼出。

重复确认、超时和重启都可按原意图号查询，已占位的发送只结算一次。

定时提醒使用内部 `approval/reminder-send { reminderId }`。

1. Outbound 经 `assist/reminder-read` 取得到期、已占位的记录，核对创建时的本人确认。
2. 用同一发件账发送（经 `channel/reply`）。网页提醒的原机器人写入 `approval_outbound.target_bot` 并参与发送摘要。
3. 提醒回执经 `approval/reminder-sent` 回到 assist。

- 飞书普通外发仍走申请和确认流程。
- HTTP 和模型无法直接调用定时入口。

提醒确认卡使用 `assist-reminder` 种类。

- 飞书本人可点卡片或明确回复编号。
- 网页只接受核验通过的请求。
- `approval/request` 的 `reminder-card` 动作按机器人和提醒号查询持久卡片，用于去重和恢复。

#### GET /api/approvals

- 定义在 `src7/plugins/approval/index.ts` 的 `routes`。
- 网页待审核批次
  1. SQLite 按号升序取最早一批，`WEB_WAITING_LIMIT` 设为 200。
  2. 返回数组附最近 10 分钟已定的长跑提醒。
  3. 处理前排记录后，下一次轮询补进后续待审核。
  - 内部审批事件和批量处理仍可查完整的待审核集合。
- 待审核页收到满一批时补查 `GET /api/approvals/overflow`，显示批次之外的条数。两个 GET 都经现有 HTTP 鉴权。

#### POST /api/channel/send

本机或带有效令牌的远端请求可用。HTTP 插件记录的 `isVerified` 是本路由的身份依据，受信网关的免令牌浏览规则只用于浏览。

- 申请用 `{ action: 'prepare', channel: 'feishu', account, chat, text }`，也可以省略 `action`。
  - `account` 为飞书应用 ID。
  - `chat` 为原聊天 ID。
  - `text` 按输入原样保存。
- 查询用 `{ action: 'status', intentId }`。页面取得 `intent` 后展示账号、聊天和正文，把 `intent.digest` 留给用户点击确认时使用。
- 确认用 `{ action: 'confirm', intentId, observedIntentDigest, interactionId, decision: 'approve' }`。每次明确确认操作生成一个 `interactionId`。发送采用已保存的目标和正文，待确认意图有效期为十分钟。
- 成功响应为 `{ intent }`。
  - `intentId` 是查询号。
  - `requestId` 是固定业务号。
  - `status` 可为 `waiting`、`sending`、`sent`、`failed` 或 `uncertain`。
- 错误响应
  - 参数无效返回 400。
  - 未核验请求由鉴权拦截。
  - 未知意图返回 404。
  - 不支持的渠道、过期或摘要不符返回 409。

主站和外置客服页共用 `Outbound.requestOutbound`。

- 不掐表：真走网络的读草稿（5 秒）、外置发送（90 秒）、飞书发送（60 秒）各自限时，外面几层不叠加。
- 写操作回执不确定返回 504，提示按原意图核对。
- 查询回执缺失返回 503。

### 模型工具

`channel_send` 接受 `{ text }`，给当前飞书聊天创建待确认发件并返回 `{ intentId, status }`。

- 前台读取本轮 `activeSourceSnapshot`。
- 后台可读取所领任务的 `sourceSnapshot`。
- 模型只填写正文，目标由快照固定。
- 工具权限只向本人开放，确认由本人通过上述 HTTP 接口完成。

`dir_grant`（前台、后台都有；不在 `READ_ONLY_TOOLS`、`BUILDER_TOOLS` 里，外人拿不到、执行前也挡，run 里再核一次 `isOwnerTurn`）：

| 参数 | 说明 |
|---|---|
| action | `list` 列全部授权；`grant` 设；`revoke` 按号撤 |
| dir | grant：目录，绝对路径（`checkGrantDir` 查：要在） |
| person | grant：给最近见过的这个名字的人（先找这个聊天里的，再找全部；没见过、重名都报错）；不写是给这个聊天（群里就是整个群，名字用群名） |
| once | grant：true 只管这一轮和这一轮交办的后台，不存表；不写是一直有效，直到 revoke |
| id | revoke：list 里的号 |

交回 JSON：list `{ ok, items }`；grant `{ ok, grant }` 或 `{ ok, once: true, dir }`；revoke `{ ok, removed }`。设的（存表的、once 的）当轮就生效。

## 设计要点

- 判断和执行分开：approval 只给结论和持久的待确认，exec、runs、update-watch 等提问者自己执行。
- 审核从规则、可选的 decision、审核小会话到本人确认逐档推进。
  - 必须人审的危险操作不能被模型放行。
  - builder 不能自己审批自己的越权请求。
- 目录授权只放开本人点名的目录：外人地址里的 `grants` 只认 approval 按库查出来写的，自己带的删掉；`dir_grant` 只有本人那一轮能用；本人的 `trusted_dirs` 不给外人。
- 卡片是渠道对 CardData 的渲染；渠道和文字回复按实际 customer、actor、群权限核对。
