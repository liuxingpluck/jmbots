# feishu v1.3.9

1.3.9 联动 `relay` 占位撤回与发件箱健壮性升级：新增请求-回执事件 `feishu/recall-message` ↔ `feishu/recall-message-result`（调 `Recall.recallBotMessage` 温和撤回机器人自己发出的占位消息，缺权限、超时或过时限仅记日志回 `ok: false` 绝不抛错）；`Feishu.sendText` 与 `Reply.onChannelReply` 补齐 `atFiles: true` 场景下的文本 `messageId` 回传；发件箱（`outbox/Outbox.ts`）单份 `.md` 发送异常时自动移入 `integrations/feishu/failed/` 隔离不阻断同批后续文件，并支持可选 `---` 文件头（`app_id` / `bot` / `chat_id`）及 `plugins.feishu.outbox` 默认多应用路由。

1.3.8 修复飞书 `post` 富文本消息对本机器人的 `@名字` 未剥除的问题：`Inbound.getFacts` 除剥除占位符 `@_user_N` 外，对命中本应用机器人的 `@` 同步剥除 `@名字`（保留对其他群成员的 `@名字`，`rawText` 仍留完整平台全文）；`Media.postText` 在 `at` 节点缺 `user_name` 时回退 `user_id`，已有前导 `@` 时不再叠成 `@@`。

1.3.7 拆文件，行为不变：配置校验（`checkConfig`、`getPeople`、`getGroups`、`getGroupDaily`）和配置类型（`FeishuApp`、`FeishuPerson`、`FeishuGroup`、`FeishuConfig`）、`GUEST_DIR`、拉历史条数上下限搬进 `Config.ts`；app_id、app_secret、role、listen、relay、trusted、judge_threshold、history_on_join 改用 `utils/Checks.ts` 的公共校验，报错说法随之统一（如“只能是 …”“要写成 true 或 false”）。`Feishu` 构造函数只做登记，建表（`createTables`）、建 SDK 客户端（`createClients`，共用 `getHttpInstance`）、发文件请求（`onSendFile`、`onSendFileError`）、关长连接（`closeConnections`）挪成方法；`ctx.on` 和 `onRequestEvent` 仍在构造函数里。

1.3.6 `groups` 每项可写 `judge_helper`（非空文字，relay 的 helpers 里的名字，可不写；#318）：`listen: judge` 的群里只听的话，地址带 `judgeHelper`；bots 的群攒批判定要接话时，这一批记成背景后转给这个外部助手（bots `DispatchClaim.relayBatch` → relay 认 `relayHelper`），不由机器人自答。不写的群照旧。

1.3.5 飞书是真走网络的那一层，自己限时（云端 19 第 1、2 条）：`index.ts` 建 SDK 用的 `httpInstance` 时设 axios `timeout`（`HTTP_TIMEOUT_MS`，60 秒），发消息、上传、拉历史、send-file 等每个开放接口请求都算；到点 axios 断开，`Api.call` 抛普通 Error（不是 `NotSent`），回执照旧是 uncertain。等飞书的插件（channels 回话、relay 发文件）不用再自己掐表。点卡片交给 approval、progress 改 requestEvent 新写法，本机的一问一答不掐表：没人接单是明确没办成，接单后出错提示结果不确定；删 `APPROVAL_TIMEOUT_MS`、`PROGRESS_TIMEOUT_MS`。

1.3.4 `Feishu.sendText` 的返回类型叫 `SendTextReceipt`。它记录文字和 `@路径` 附件的发送结果。

1.3.3 新工具 `feishu_recall`（`Recall.ts`）：撤回机器人自己在当前聊天发过的消息，参数 `count`（最近 N 条）或 `messageIds`（飞书消息号）二选一；只撤聊天日志里 `direction=bot` 的记录，用 SDK `im.v1.message.delete`，撤成功在日志记录上写 `recalled: true`（`ChatLog.markRecalled`）。谁能用由 approval 的工具表管：只有本人那一轮。`feishu_doc` 在群里建好文档后，再把这个群加成协作者给阅读权限（`drive.v1.permissionMember.create`，`member_type: openchat`、`perm: view`），没给成写进结果、不算失败，缺的权限写在错误里（`docs:permission.member:create`）；`feishu_doc`、`feishu_send_file` 的说明里加一句：群里要文件的优先生成 Word（.docx）用 `feishu_send_file` 发进群。撤回缺权限提示 `im:message:recall`（开 `im:message` 或 `im:message:send_as_bot` 也行）。不加事件。

1.3.2 是不是群（回话不带卡片、群里隐去本机路径、群里 @ 人）、点卡片的是不是本人，改问 channels 协议插件的 `isGroup`、`getSpeakerRole`（从 `utils/Workspace.ts` 挪过去的），判断不变。

1.3.1 文档路径按本轮机器人名和回话地址定位工作区，发文件时继续校验本轮授权目录。

1.3.0 拉群聊历史（`HistoryPull.ts` 的 `FeishuHistoryPull`）：用 SDK 的 `im.v1.message.list`（`container_id_type=chat`，按时间从新到旧翻页，一页 50 条）拉一个群最近 N 条，每条交 `FeishuInbound.onHistory`（认人认群认 @、附件下载进渠道附件目录、写聊天日志，都照实时消息；不挂表情、不补引用转发、不记去重表），再按时间从旧到新一页一批发 `channel/history` 给 memory 补记，不触发会话、不回话。聊天日志里已有的消息号、机器人自己发的话（`sender_type` 是 `app`，已由 `channel/replied` 记进记忆）、已撤回的跳过。触发两种：`POST /api/feishu/history`，和机器人新进群（`im.chat.member.bot.added_v1`，拉最近 `history_on_join` 条）。权限不够时报错写明要给应用开 `im:message.group_msg`、`im:message:readonly`，再发布一次版本，机器人还要在这个群里；进群自动拉失败只打控制台日志，不往群里说。

1.2.3 群里回话（`mentioned`）先把本机绝对路径换成最后一段（`utils/Text.ts` 的 `hideLocalPaths`，用户 #301：群里不报本机路径；私聊不动）；`feishu_send_file` 除了这一轮的工作区，也认这一轮的授权目录（`utils/Bots.ts` 的 `resolveSessionPath`），群里那一轮照旧发回这个群。

登记的 builder 和 guest 工作区用 `utils/Files.ts` 的 `ensureDir` 创建。

人员身份按 `people[].role` 判断，缺省为 `guest`。配置里出现 `people[].owner` 时提示改成角色写法。

所有发出去的话只走 `channel/reply` → `channel/replied`，回执带整份请求（正文、来源快照、目标）。

收到的一条话只发一个事件（经 channels 的 `emitInbound`），分法见 [channels 说明](../channels/说明.md)。

- 私聊：`channel/direct`，投给本应用的全部机器人，算叫了。
- 群里叫了机器人：`channel/mention`，只投被叫到的机器人。叫了是指 @ 了它、@ 了本应用时算默认机器人、或引用的那条是它发的（`getQuotedBot` 按 `parent_id` 查聊天日志里 `direction` 为 bot 的那条）。
- 群里没叫：`channel/listen`。登记了 `listen: all` / `judge` 的群投给本应用的全部机器人（记背景，judge 的群再问决策模型要不要接）；没登记的群 `targetBots` 空，机器人不收，记录类插件（memory 等）照记，流水 outcome 写“只记”。
- 叫了机器人的才挂“敲键盘”表情，出错才往聊天里回一句；只听的不挂表情，出错只记流水和日志。


飞书卡片提交审批决定或控制进度时，业务插件接了单却出错（没有回执）提示核对；不掐表，approval、progress 都在本机办。

审批占用保留到明确收到结果。

- 确认 `im.message.recalled_v1` 后把原话和撤回时刻交给 bots；随后回这条消息时直发原聊天。

- 审批与进度卡片。

- `prompt` 登记日报提示。

本人批准的主动发件（approval）经 `channel/reply` 来，带确切地址 `{ appId, chatId }`，发到指定群或私聊。

- 正文保留 `@路径` 等普通文字（不带 `atFiles`）。
- 按应用号 + `replyRequestKey` 去重，不带飞书 uuid。
- 回执按结果区分
  - 飞书明确拒收回 `rejected`。
  - 传输结果无法确认回 `uncertain`。
  - 已受理回 `sent`。
- 成功后写入聊天历史，历史写入故障只打日志，回执照旧 `sent`（免得同键重试重发）。

## 文件分工

渠道收发按职责分文件（1.1.13 起）。后四个各是一个 class，由 `Feishu` 构造时建好，构造只登记各自的事件，运行时目录交后续流程处理。

- `feishu.inbound`
- `feishu.reply`
- `feishu.history`
- `feishu.contacts`

| 文件 | class | 管什么 |
|---|---|---|
| `index.ts` | `Feishu` | 对外类型、`feishuCustomer`、长连接（connect/start/mark/findSelf）、群名缓存（`chats`、`chatNames`）、别的插件调的发送口（`sendText`、`sendCard`、`updateCard`、`sendFile`）、`apply` |
| `Config.ts` | 函数 | 配置类型（`FeishuApp`、`FeishuPerson`、`FeishuGroup`、`FeishuConfig`）、`GUEST_DIR`、拉历史条数上下限、入口配置校验（`checkConfig`、`getEntries`、`getPeople`、`getGroups`、`getGroupDaily`） |
| `Inbound.ts` | `FeishuInbound` | 长连接推来的收消息、撤回、点卡片：去重、`handleInboundMessage` 的 6 步、经 `emitInbound` 发 `channel/direct`、`channel/mention`、`channel/listen`、发 `channel/recall` |
| `Reply.ts` | `FeishuReply` | 只响应 `channel/reply`：定发到哪（确切地址、跨聊天认目标、来源快照的原消息）、回复去重、发出、写聊天日志 |
| `ChatLog.ts` | FeishuChatLog | 读写飞书聊天日志，供撤回核验和回复目标定位 |
| `HistoryPull.ts` | `FeishuHistoryPull` | 拉群聊历史：`pull`（翻页拉、去重、拼标准消息、发 `channel/history`）、`onJoin`（机器人新进群自动拉） |
| `Contacts.ts` | `FeishuContacts` | 来往流水 `data/logs/feishu-contacts.jsonl` 的记和读，听 `bot/judged` |
| `Media.ts`、`Api.ts`、`cards/`、`doc/`、`outbox/` | 函数 | 媒体收发、SDK 调用重试、卡片、云文档、发件箱（没变） |

  - DocNode.level：heading等级1–9
  - DocNode.language：围栏代码语言文本，toBlocks实际输出language固定1未映射此值
  - DocNode.rows：table二维string[][]
  - TextRun.content：行内文字
  - TextRun.style.bold/italic/inline_code/link.url：可选样式与链接
  - Block.block_type 的本地枚举
    - text：2
    - heading：从 3 起
    - bullet：12
    - ordered：13
    - code：14
    - quote：15
    - image：27
    - table：31
  - Block其他字段：按类型生成text/headingN/bullet等elements与style；接口索引签名unknown，不预定完整SDK schema

## 设计要点

- 以下模块共用同一个应用身份和客户端，作为一个平台插件分工。
  - SDK
  - 素材
  - 卡片
  - 云文档
  - 发件箱
- 渠道处理群 @、监听与身份，把平台地址交给 bots。
  - 审批和进度卡片桥接独立的业务服务。
  - 群或私聊的受众与 role 是权限输入。

当前边界

- 每个应用按配置投递给单个机器人。
- 发送异常可能只记日志。平台确认仍以平台回执为准。
