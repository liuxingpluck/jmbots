## 2026-11-14 07:15 EST：点停止时工具怎么停？

**结论：** 喊停时会话掐模型请求用的那个停止信号，现在也交给工具；要等很久的工具（搜索、生图、`exec`、子任务）听到就马上断开，写文件这类快工具照常做完，已经做了的不回滚。

**细节：**
1. 网页 `POST /api/sessions/:id/stop`、飞书点停止，最后都调 `session.stop(谁)`：状态改成 `stopped`，再 `aborter.abort()`。
2. 这一轮的 `AbortController` 是 `Session.run` 建的，它的 `signal` 一份给模型请求（`ChatRequest.signal`），一份经 `tools.execute(call, session, signal)` 交给工具的 `run(args, session, signal)`。
3. 慢工具把 `signal` 交给 `fetch`、`spawn`，或者听 `abort` 事件，收到就断开并抛错。`Tools.execute` 看到 `signal.aborted` 就把结果记成“已停止：点了停止，工具没做完”，`isError` 是 false，不当工具出错报。
4. 快工具不用管它，老工具不写第三个参数也照样能用（只是停不下来，要等它自己做完）。
5. 想恢复已经改了的东西，就让 AI 再改回来。
6. 顺带修了一个卡住的问题：以前喊停后慢工具还在跑的那段时间，同一场会话又来一句话，`run()` 看到还在转就直接返回；等这一轮收尾时，因为状态是 `stopped`，“有新话就再转一轮”那句不转，新话就一直排着，要等下一句话来才处理。现在把“被喊停的不再转”那个条件删了，收尾时有排着的话就接着转。

**代码位置：**
- `src7/Tools.ts`：`ToolSpec.run` 的第三个参数 `signal`；`Tools.execute` 收 `signal`、传给工具，`catch` 里看 `signal.aborted` 记“已停止”。
- `src7/Sessions.ts`：`Session.loop` 里 `this.ctx.tools.execute(call, this, signal)`；`Session.run` 收尾时 `if (this.inbox.length > 0)` 再转一轮；`Session.stop` 的说明。

## 2026-11-14 05:50 EST：为什么调 cli 的 `this.receive` 会走到 bots 里的 `receive`？

**结论：** 这条路上有两个同名的 `receive`，中间靠继承和一次直接调用连起来，没有事件，也没有魔法。
- `cli` 调的 `this.receive`，其实是父类 `Channel.receive`：`Cli` 继承 `Channel`，自己没写 `receive`。
- `Channel.receive` 里先找到对应的机器人 `Bot`，再直接调 `target.receive(message)`，也就是 `Bot.receive`。

**细节：**
1. `class Cli extends channelModule.Channel`。`Cli` 没有自己的 `receive`，所以 `this.receive` 用的是继承来的 `Channel.receive(bot, text)`。
2. `Channel.receive` 依次做这几件事：
   - 用 `this.ctx.bots.get(bot)` 拿到机器人对象 `Bot`；
   - 发一条 `trace`；
   - 把这句话存进 `channels/cli/<日期>.jsonl`；
   - `await target.receive(message)`，这一步调的是 `Bot.receive(message)`。
3. `Bot.receive` 再用 `ctx.serial('bot/receive', event)` 问各插件：这条消息该进哪场会话？前台插件 `bot-front-desk` 会回答。

**调试提示：** 在 `cli/index.ts:69` 按 F11 会先进 `Channel.ts:39`，再在 `Channel.ts:57` 按 F11 进 `bots/index.ts:153`。

**代码位置：**
- `src7/plugins/cli/index.ts:22`：类定义。
- `src7/plugins/cli/index.ts:69`：调 `this.receive`。
- `src7/plugins/bots/Channel.ts:39-58`：`Channel.receive`。
- `src7/plugins/bots/index.ts:153-156`：`Bot.receive`。

## 2026-11-14 05:45 EST：插件依赖的服务没人提供时，`await app.plugin(...)` 会不会一直卡住？

**结论：** 不会卡住。`await` 会马上返回，插件只是不开工，所以 `Main.ts` 后面那段“没开工”的检查能跑到，也能打出提示。

**细节（Cordis 4.0.0-rc.12）：**
1. `app.plugin()` 返回的东西带一个 `then`。`await` 它，等的是 `fiber.await()`。
2. `fiber.await()` 只在插件“正在加载”或“正在卸载”时等。这时 `inertia` 里有一个还没完成的任务，等它做完就结束。插件 `apply` 抛错的话，`await` 也会把错误抛出来。
3. 插件挂上去时会调 `_refresh()`。它发现 `inject` 里有服务没人提供，就把状态记成“不开工”（`INACTIVE`）。
4. 状态本来就是“不开工”，`_setEpoch` 发现没变化，直接返回，不会去加载插件。
5. 所以 `inertia` 一直是空的，`await()` 一进去就返回。插件挂上了但没有执行 `apply`。
6. 以后哪个插件提供了这个服务，它会自动开工。

**代码位置：**
- `node_modules/cordis/lib/index.js:1489-1505`：`plugin()`，返回值带 `then`。
- `node_modules/cordis/lib/index.js:659-665`：`await()`。
- `node_modules/cordis/lib/index.js:574-585`：`_refresh`。
- `node_modules/cordis/lib/index.js:586-601`：`_setEpoch`。
- `src7/Main.ts:59-65`：检查没开工的插件。

## 2026-11-13 16:58 `this.ctx.emit('trace', ...)` 标红：“trace”的参数不能赋给“keyof Events”？

**结论**：代码没错，是 VS Code 用错了 tsconfig。已加 `src7/tsconfig.json`，重启 TS 服务后红线消失。

**细说**

1. `'trace'` 这个事件是在 `utils/Trace.ts` 里用 `declare module 'cordis'` 加到 Cordis 的事件表（`Events`）上的。
2. 编辑器打开一个文件时，会往上找最近的 `tsconfig.json`。原来 src7 里没有，就用了根目录那个，而根目录的不包含 `src7/**`，于是 `Trace.ts` 的声明没被读进来：编辑器眼里 Events 里没有 'trace'，就标红了。
3. 命令行 `tsc -p tsconfig.src7.json` 会把整个 src7 读进来，所以能过；bun 运行时不查类型，所以也能跑。
4. 解决：`src7/tsconfig.json` 只管 src7，编辑器打开 src7 的文件就用它。改完后 Ctrl+Shift+P →“TypeScript: Restart TS Server”。

**代码**：`src7/utils/Trace.ts`；`src7/tsconfig.json`。

## 2026-11-13 16:57 调试时一步步往下走，老是钻进 node_modules，bun 能屏蔽吗？

**结论**：bun 的 VS Code 调试器目前不支持 `skipFiles`（官方 issue [oven-sh/bun#9396](https://github.com/oven-sh/bun/issues/9396) 还开着），屏蔽不了，只能换个走法。

**细说**

1. 钻进去的原因：`this.ctx.bots`、`this.ctx.sessions` 这些不是普通属性，而是 Cordis 用 Proxy 拦下来，再去服务表里查。所以连读一个 `ctx.xxx`，“单步进入”都会跳进 `node_modules/cordis`。
2. 走法：
   - 用 **F10 单步跳过**，不用 F11 单步进入。F10 照样执行这一行，只是不进函数。
   - 想看的函数，**直接在里面下断点再按 F5**，不用一步步跟进去。
   - 不小心进了 node_modules，按 **Shift+F11 单步跳出**，回到自己的代码。
3. 网上有人改用 `"type": "node"` 加 `runtimeExecutable: bun` 来用 skipFiles，但 bun 的调试协议和 Node 不同，断点不一定好使，不推荐。

## 2026-11-13 16:57 config.yaml 里没写“助手”机器人，为啥会有一个？

**结论**：`config.yaml` 里**整个没写 `bots` 段**时，骨架默认给一个叫“助手”的机器人。

**细说**

1. 读配置时，`checkConfig()` 是这样写的：`root['bots'] ?? [{ name: '助手' }]`。`??` 的意思是“左边没有（undefined/null）才用右边”。
2. 所以只要 `bots` 段写了（哪怕只写一个别的名字），就不会再有“助手”。
3. 命令行不写 `--bot` 时，用名单里的第一个机器人：`plugins/cli/index.ts` 的 `start()` 里 `this.ctx.bots.list()[0]`。

**代码**：`src7/utils/Checks.ts` 的 `checkConfig()`（bots 那几行）；`src7/plugins/cli/index.ts` 的 `start()`。

## 2026-11-13 16:51 `main()` 里没有 await，为啥能一直等到对话结束？

**结论**：`main()` 其实没在等，它早就返回了；进程不退出，是因为后台还有没完成的异步活；真正让程序退出的是 cli 插件的 `exitWhenIdle()`。

**细说**

1. bun（和 Node 一样）的规矩：只要还有没完成的异步活（等模型回答的网络请求、计时器、读命令行输入），进程就不会结束。`main()` 返回不等于程序结束。
2. `Main.ts` 里 `app.emit('ready', args.rest)` 是同步通知：cli 渠道收到后开始收这句话 → `bot.receive` → `session.run()`。`run()` 是异步的，没人 await，它就在后台转。
3. `void app.sessions.open(row.id).run()` 也是同理。`void` 的意思是“故意不等它”，不写的话 eslint 会报“漏了 await”。
4. 会话在后台调模型、执行工具，这些 Promise 没结束，进程就一直活着。
5. 退出：`plugins/cli/index.ts` 的 `exitWhenIdle()`。每次会话状态变了，它都看一下库里还有没有 `running` 的会话，一个都没有了就 `process.exit()`。

**为什么这么设计**：`main` 只管把东西挂上，什么时候结束由渠道决定。命令行一句话模式跑完就退；以后的 HTTP、飞书渠道应该一直跑着，不退。

**代码**：`src7/Main.ts` 的 `main()`（ready、恢复 running 会话那几行）；`src7/plugins/cli/index.ts` 的 `exitWhenIdle()`。

## 2026-11-13 16:49 Cordis 插件的 `apply` 是什么意思？

**结论**：`apply` 就是插件的 `main()`。Cordis 挂这个插件时调它一次，交给它一个专属的 `ctx`。

**细说**

1. `Main.ts` 里 `app.plugin(插件模块, 配置)`：Cordis 给这个插件建一个专属的子 `ctx`。
2. 插件 `inject` 里写的服务（比如 `sessions`、`tools`）都就绪后，Cordis 调一次 `apply(ctx, 配置)`。
3. 插件在 `apply` 里通过 `ctx` 做事：`ctx.on(...)` 听事件，`ctx.tools.register(...)` 登记工具，`new Cli(ctx)` 起渠道。
4. 这个 `ctx` 记得插件登记过的东西，插件被拔掉（dispose）时自动撤掉，所以插件不用写卸载代码，可以热插拔。

**类比**：`apply` 是插件的 `main()`，`ctx` 是它拿到的“遥控器”，插件拔掉时遥控器上按过的东西一起作废。

**代码**：`src7/plugins/Index.ts` 的 `PluginModule.apply` 注释；每个 `src7/plugins/*/index.ts` 的 `apply`。
