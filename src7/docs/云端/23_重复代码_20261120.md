## 一页结论

**判断**：上一遍那种“同一个对象手拼十几次”的重复已经基本清掉了，11 号提的 10 条做了 9 条（第 7 节）。逐字比对，6 行窗口在不同文件之间只撞上 4 处。

这一遍剩下的重复换了样子：**同一件事有两三种写法并存**。新写法加进来了，旧写法还留着，或者写下的东西根本没人读：

- 入站消息里有一个字段，7 个渠道每条消息都在算，可整个项目没有一处读它；
- “请求写错了，回 400”有四种写法；
- `requestEvent` 新旧两种返回方式都还在；“结果不确定”的判断有现成的函数，却在 10 处各手写一遍；
- usage 并进 model-catalog 以后，插件里面还在走事件总线问自己。

### 1.3 为什么不顺手给入站消息做一个构造函数

上一遍第 1 条给回执做了构造函数。入站消息看起来是同样的情况：7 处、每处约 30 行的字面量。但这两件事不一样：

- 回执出问题，是**值的算法**走了样（`ok` 有三种算法）。入站消息除了 `visibility`，没有要算的值；剩下的固定值只有 `v: 1`、`replyTo: null`、`origin.channel` 三样；
- 字段齐不齐，TypeScript 已经管着：`ChannelMessage` 每一项都是必填，漏写编译不过；
- 删掉 `visibility` 以后，做构造函数净省约 10 行，却多一层要跳过去看的函数。

所以删字段就够了，不另建函数。

## 2. “请求写错了”：四种写法

### 2.1 现状

| 写法 | 处数 | 位置 |
|---|---|---|
| `throw new Failure(400, …)` | 83 | 各插件 |
| 普通 Error 加 `statusCode: 400` | 7 | `utils/Checks.ts:496-497`、`:518-519`、`:526-527`、`:557-558`、`:578-579`、`:586-587`；`journal/index.ts:397` |
| exec 自己的类 | 1 类、4 处抛 | `exec/Runs.ts:74` 定义 `class BadInput extends Error {}`；`:182`、`:187`、`:194`、`:198` 抛；`:520-528` 接住转 400 |
| 抛普通 Error，路由 try/catch 一律转 400 | 8 处 + 1 个包装 | `memory/index.ts:954-959`（写知识库）、`memory/ChannelIndex.ts:735-738`、`memory/Search.ts:187-192`、`journal/index.ts:583-587`、`desktop/index.ts:155-159`、`model-catalog/Notes.ts:468-473`；`model-catalog/index.ts:443-450` 的 `answer`（`:399`、`:416` 两处用） |

第二种写法，`Checks.ts:488` 的注释写着“Fastify 自己的错误处理、web-api 的 setErrorHandler 都照 statusCode 回 400”。可 web-api 的 setErrorHandler 已经并进了 http 的全局出错处理（`http/index.ts:134-151`），这句注释也过时了。

第四种写法的副作用：`memory/index.ts:955` 的注释写着“失败（名字不合法之类）回 400”。可 try 里面的 `store.writeKnowledge` 还会写盘、建索引，这些出错也一样回 400。`journal/index.ts:586` 用的是 `(error as Error).message`，抛出来的不是 Error 时，回的就是 undefined。

### 2.2 根因

CLAUDE.md 的“外部入口校验一次”只规定了**在哪里**校验，没规定校验不过时**抛什么**。所以 `Checks.ts` 抛普通 Error，因为它也要给启动时的配置校验用；desktop 的 `parse`（`desktop/index.ts:49-76`）、memory 的 `Store.writeKnowledge`（`memory/Store.ts:128-129`）也抛普通 Error。路由只好自己包一层，把错误翻成 400，结果把别的错也一起翻了进去。

`Failure` 继承自 Error，启动时的配置校验接到它，和接到普通 Error 一样（插件照样挂不上，提示的话也一样）。所以校验函数直接抛 Failure，对两类调用方都成立。

### 2.3 改后

`utils/Checks.ts:494-498` 改前：

```ts
  //G 不是只有数字 → 抛带 400 的错。
  if (!COUNT_PATTERN.test(value)) {
    const failure = new Error(`${key} 要是非负整数`);
    throw Object.assign(failure, { statusCode: 400 });
  }
```

改后（`Checks.ts` 加一行 `import * as failureModule from './Failure.ts';`）：

```ts
  //G 不是只有数字 → 400。
  if (!COUNT_PATTERN.test(value)) throw new failureModule.Failure(400, `${key} 要是非负整数`);
```

`memory/Store.ts:128-129` 两处校验改抛 `Failure(400, …)`，然后 `memory/index.ts:954-959` 改前：

```ts
      try {
        //M 写一篇知识库文件并马上收进记忆库，成功交回文件路径；失败（名字不合法之类）回 400 并带原因。
        return { file: await store.writeKnowledge(bot, body['name'], body['content']) };
      } catch (error) {
        return reply.code(400).send({ error: textModule.getErrorMessage(error) });
      }
```

改后：

```ts
      //M 写一篇知识库文件并马上收进记忆库，交回文件路径。名字不合法时 writeKnowledge 抛 Failure(400)。
      const file = await store.writeKnowledge(bot, body['name'], body['content']);
      return { file };
```

其余几处照这个样子改：先把被调函数里“填错了”的 `throw new Error` 换成 `Failure(400, …)`，再删掉路由的 try/catch。要换的被调函数：`desktop/index.ts` 的 `parse`、`model-catalog/Checks.ts` 的 `checkRating`、journal 的 `query`，memory `ChannelIndex.ts` 的 `getQuery` 和 `Search.ts` 的 `find` 里面的时间、参数校验（**待核**：这两处具体在哪几行抛）。exec 删掉 `BadInput`，`Runs.ts:182-198` 的 4 处改抛 Failure，`:520-528` 的 try/catch 删掉。model-catalog 删掉 `answer`。它那 3 个接口里，表单校验改抛 Failure；探测上游失败会变成 500（**待核**：设置页是不是按 400 判断“填错了”。`web/src` 里只有 401、404、≥500 三种判断，看起来不受影响）。

### 2.4 不在这条里的

还有 105 处 `return reply.code(4xx).send({ error })`，其中回 400 的 49 处。它和 `throw new Failure(…)` 回出去的东西完全一样，都是 `{ error }` 加状态码，两边都是一行，换写法不省行。**不建议批量改**。只是以后新写的统一抛 Failure（第 8 节）。

### 3.2 改后

`RequestEvent.ts:15-24` 换成：

```ts
/**
 * 结果不确定：请求发出去了，没等到回执，又不是没人接单（超时、被喊停、对方出错）。
 * 对方可能已经做了，不能当没做去重发。只有 unhandled 能确定没做。
 * @param asked requestEvent 交回的结局。
 * @returns 不确定是 true。
 */
export function isUnsure(asked: { why?: FallbackReason }): boolean {
  if (asked.why === undefined) return false;

  return asked.why !== 'unhandled';
}
```

  const getFallback = (reason: FallbackReason, detail?: string): Answer => {

## 8. 防止再长出来

这一遍的四条大的，长出来的路子各不一样，但都是两种情况之一：**加新的没删旧的**，或者**写了没人读**。

| 条 | 怎么长出来的 | 能自动查的 |
|---|---|---|
| 1 visibility | 设计协议时先写了字段，注释说由权限插件计算。后来权限走了“地址加 `isOwnerTurn`”这条路，字段没删。每个新渠道都照着旧渠道抄字面量 | 协议类型（`ChannelMessage`、`SourceSnapshot`、`ReplyReceipt`）的每个字段，除了写它的地方，在 `src7/` 里至少要有一处读。脚本对每个字段名 grep `.字段名` 这种读法，一处都没有就报 |
| 2 四种 400 | 校验函数没约定抛什么，各插件自己想办法 | grep `statusCode: 400`；grep 路由 catch 里的 `code(400)` |
| 3 两种返回方式 | 迁移分两个阶段走，第二阶段做完没回头删第一阶段留的兼容 | grep `onFallback`，0 处才算迁完 |
| 4 自己问自己 | 两个插件并成一个，原来跨插件的请求事件留下了 | 同一个插件里既 `onRequestEvent` 又 `requestEvent` 同一个事件就报（第 9 节那段扫描） |

建议加进 CLAUDE.md 的三句（中控定，推荐至少加第一句）：

> - **校验不过一律 `throw new Failure(400, 一句话)`**（`utils/Failure.ts`），挂在“外部入口校验一次”下面。路由不包 try/catch，不把别的错翻成 400。
> - **同一个插件内部直接调，不走自己的请求事件**，挂在“插件之间尽量只靠事件”下面。并插件时，把原来的请求事件改成直接调用。
> - **新写法替旧写法，最后一步是删旧写法**，挂在“相似的函数合成一个”下面。旧写法在正式代码里没人用了就删，不为测试留着。

上面 4 条检查可以合成一个 `ztools/check-dups/Check_Dups.ts`，约 60 行，照 `ztools/check-lines` 的样子写，阶段验收时跑一遍。
