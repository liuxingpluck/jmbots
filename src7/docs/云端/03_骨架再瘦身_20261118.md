# 03 骨架再瘦身（2026-11-18）

- 写的人：云端后备优化顾问。只读代码，没改任何文件。行号以 main 的 `ae9686f` 为准。
- 方法：
  - A（第一性原理）：让一条消息走通，最少需要什么？
  - F（反方）：先假设我的方案是错的，站在最强反对者的角度找反例，再重新评估。
- 口径：下面说的“代码行”都不算注释和空行，和 `src7/README.md` 的口径一样。

## 一、一页结论

**现状**：骨架（`src7/` 下 `plugins/` 以外的文件）共 2,607 行代码，分两块：

- **主线**：`Main.ts`、`Resources.ts`、`Sessions.ts`、`Tools.ts` 四个文件，共 672 行。逐个看下来，已经接近该有的样子（见第 4 节）。
- **共享库**：`Channels.ts`（605 行）和 `utils/`（1,330 行），共 1,935 行。

**判断**：骨架长在共享库里，不在主线上。病根有两条规矩：

- 插件之间不许 import 代码，所以两个插件要共用的东西，只能放进 `utils/`；
- “检查函数放 `utils/Checks.ts`”这条，被套到了所有插件头上。

结果，**只有一个插件用、甚至原来的理由已经不在了的代码**，也留在了骨架里。把它们挪回各自的插件，骨架能少约 630 行，主线一行不用动。

| # | 改什么 | 为什么 | 预计省 | 风险 |
|---|---|---|---|---|
| 1 | `Checks.ts` 里只有一个插件用的校验，挪回那个插件：外部 AI 任务协议的校验挪进 relay，评分校验挪进 model-notes | `Checks.ts:383-657` 是任务协议的类型和校验，只有 relay 用；`:44-67`、`:326-382` 是评分校验，只有 model-notes 用 | 骨架约 200 行代码（文件约 330 行） | 低：只挪文件，函数名不变 |
| 2 | `Versions.ts` 里的版本说明改成数据文件，代码只留读和打印 | 这个文件 234 行代码里，约 215 行是 43 个版本的更新说明，是数据，不是逻辑。它占了 `utils/` 的六分之一 | 骨架约 215 行 | 低：`version` 子命令打印的 JSON 格式不变，基地照常认 |
| 3 | 只有一个插件用的共享代码挪回插件：`Snapshot.ts` 挪进 tutorial，`requestChannelHistory` 挪进 bots，`getRoundId` 挪进 wechat。另加一个检查脚本，防止再长回来 | `Snapshot.ts` 头注写着“放 utils 是因为 boot-trail 和 flow 都用”，可这两个插件 11-17 已经并成了 tutorial，理由不在了。另外两个函数也各只有一个插件在用 | 约 215 行；以后不再长回来 | 低 |
| 4 | README 分开写两个数：主线（目标 ≤ 600 行）、共享库（规矩是“只放两个以上插件用的”）。不再拿一个总数去比 NamiDSH 的 300 行 | 用户要的是“一眼读得懂一条消息怎么走”。读主线就够了，共享库是查字典时才翻的。把两者混成一个数，既比不出好坏，也找不到该瘦哪里 | 少一个误导人的数字 | 低。反方意见见第 5 节 |

做完前三条，骨架从 2,607 行降到约 1,980 行，其中主线 672 行、共享库约 1,305 行。

**要用户定的一件事**：骨架以后按“主线 + 共享库”两个数来说，可以吗？可以的话，第 4 条连同第 3 条的检查脚本一起写进 CLAUDE.md（这要本地 AI 改）。

后面是证据和方案细节，用户不用读。

### 1. Checks.ts 里的插件私货（结论第 1 条）

用一个小脚本数 `Checks.ts` 的每个导出被哪些文件用：

| 行 | 导出 | 谁用 |
|---|---|---|
| 68 | `checkArgs` | Main、tutorial |
| 138 | `checkConfig` | Main、settings、tutorial |
| 44、326、346 | `RatingInput`、`checkModelId`、`checkRating` | **只有 model-notes** |
| 383-548 | `ReturnMode`、`AgentAbilities`、`AgentHello`、`checkAgentHello`、`TaskResult`、`checkTaskResult`，以及它们用到的 `RESULT_STATUSES`、`CHECK_OUTCOMES`、`ActualSubagent` 等 | **只有 relay** |
| 658 | `checkCount` | journal、web-api |
| 682 | `checkVersion` | `plugins/Index.ts`、journal |

**反方意见（F）**：CLAUDE.md 写着“检查函数放 `utils/Checks.ts`”，挪走就违反了规矩。

**重新评估**：

- 同一份 CLAUDE.md 第一条还写着：“HTTP、配置文件、工具参数等新的外部输入仍须在各自边界首次校验。”
- 任务协议的边界是 relay 的 `/api/agents*`；评分的边界是 model-notes 的 `POST /api/model-notes/rate`。
- “检查函数放 Checks.ts”是 0.4 时的写法（原文写的还是 `src/utils/Checks.ts`），那时没有插件。
- 两条规矩可以这样同时满足：挪进插件后，文件**也叫 `Checks.ts`**，即 `relay/Checks.ts`、`model-notes/Checks.ts`。约定“检查函数放 Checks.ts”不变，只是从骨架搬到了边界上。

改后：

```ts
// relay/TaskRoutes.ts，改前
import * as checks from '../../utils/Checks.ts';

// relay/TaskRoutes.ts，改后
import * as checks from './Checks.ts';
```

`relay/` 已经有 `TaskProtocol.ts`（334 行）讲任务协议。直接并进它也行，但新建 `Checks.ts` 更好找。

### 2. Versions.ts 是数据（结论第 2 条）

- `Versions.ts:6` 是 `VERSION = '0.7.42'`；`:8` 起是 `VERSIONS = [...]`，43 项，每项有 version、date、changes。
- 用它的地方有三处：`Main.ts:40-43` 的 `version` 子命令打印 JSON 给基地，tutorial 显示，web-api 显示。

改后有两种写法：

| 方案 | 做什么 | 代价 |
|---|---|---|
| 甲：JSON（推荐） | 新建 `src7/版本.json`，`Versions.ts` 改成 `import data from '../版本.json' with { type: 'json' }`。Bun 编译成单文件时会把 JSON 一起打进去，不用经过 `Embedded.ts` | 写更新说明时要守 JSON 的引号和逗号 |
| 乙：Markdown | 新建 `src7/版本.md`，写成 `## 0.7.42（2026-11-18）` 加 `- 一条说明` 的格式，`Versions.ts` 用二十来行解析 | 多了解析代码，但人写起来最顺手 |

改后的 `Versions.ts` 大约是这样：

```ts
import data from '../版本.json' with { type: 'json' };

/** 版本说明，新的在前；数据在 src7/版本.json。 */
export const VERSIONS = data as VersionEntry[];

/** 现在的版本号：版本说明里的第一项。 */
export const VERSION = VERSIONS[0].version;
```

这样也顺手去掉一个隐患：现在的 `VERSION` 常量和 `VERSIONS` 第一项要手动对齐。

### 3. 只有一个插件用的共享代码（结论第 3 条）

| 代码 | 行（代码行） | 谁用 | 挪到哪 |
|---|---|---|---|
| `utils/Snapshot.ts` 整个文件 | 134 | 只有 tutorial（`tutorial/State.ts` 等） | `tutorial/Snapshot.ts` |
| `Channels.ts:847` 的 `requestChannelHistory`（约 `:840-929`） | 69 | 只有 bots（`bots/ChannelTools.ts`） | `bots/ChannelTools.ts` 或 `bots/History.ts` |
| `Channels.ts:517` 的 `getRoundId`（约 `:510-537`） | 11 | 只有 wechat | `wechat/` |

**Snapshot 是“原因已经不在了”的典型**：头注 `Snapshot.ts:4` 写着“boot-trail 和 flow 都用这里；放 utils 是因为插件之间不互相 import”。可 boot-trail 和 flow 在 11-17 已经并成了 tutorial（`plugins/Index.ts:74`）。

**防止再长回来**：在 `ztools/` 加一个检查，列出“骨架里只有一个插件 import 的导出”。做法就是我这次用的脚本：

1. 扫 `src7/` 下的非测试文件；
2. 对 `Channels.ts`、`utils/*.ts` 的每个 `export`，找出 import 了这个文件、又在正文里提到这个名字的文件；
3. 把它们按插件归类。只归到一个插件、骨架自己也不用的，就报出来。

全仓库跑一次不到 1 秒。这条检查也是主题 11“返工根因”要的那类自动化。

**看过、但不建议挪的**（F：先当成该挪，再找反例）：

- **`utils/Trace.ts`**（129 行）：journal 和 tutorial 都用 `dispatchLine`、`getCallSite`，两边要拼出一模一样的跟踪行。挪进任何一家，另一家就得 import 它，违反规矩。留着。
- **`utils/Card.ts`**（48 行）：approval、progress、feishu 和网页共用卡片的数据结构，这是协议。只有 `getRiskLevel`、`getCardText` 两个函数只给 approval 用，省 20 来行，不值得拆。
- **`Channels.ts` 的其余部分**：大部分是事件载荷的类型。发的一方和听的一方都要用，拆开反而看不全协议。主题 1 的第 1 条如果做了（查历史合成一个工具），`ChannelHistory*` 这一组还能再缩，到时再看。
- **`utils/RequestEvent.ts`**（102 行，有 12 个插件在用）：留不留、怎么简化，取决于主题 5“事件化的二阶影响”。

### 4. 主线四个文件：基本到位（第一性原理）

**让一条消息走通，最少需要**：

- 读配置、开库、认供应商：`Resources`；
- 会话的记录和循环，加上发一次模型请求：`Sessions`；
- 工具的登记、列出和执行：`Tools`；
- 把插件挂上、发 `ready`、接着跑没跑完的会话：`Main`。

四样都在，每个文件里也没有和主线无关的大块代码：

- `Sessions.ts`（320 行代码）：
  - `create`、`open`、`find`、`ask`（`:319`，6 个插件在用，用户 11-17 点头放进骨架）；
  - `chat`（`:349-412`：拼上下文、思考档、重试、发 `model/failed`）；
  - 循环（`:476-592`，四个关口）；
  - 另有 `stop`、`save`。
  - 唯一的重复是重试：`chat()` 有重试，model-catalog 的 Fallback 也在 `session/request` 上换模型。但两者管的事不同：前者重试同一个模型的临时错，后者是限流时换模型。而且没挂 model-catalog 时，主线照样要能重试，所以留着。
- `Main.ts`（109 行代码）里能商量的只有一块：`:79-137` 的挂载记录，约 45 行，写进 `resources.pluginStatus`，给 `/api/health` 和教程页用。
  - 反方意见（F）：这块挪进 tutorial，没挂 tutorial 时，health 就报不出“哪个插件没挂上”；挪进 http，http 又不是第一个挂的，Cordis 不补发之前的事件，它看不到前面的插件。
  - 结论：留在 Main。
- `Resources.ts`、`Tools.ts`：没找到可以挪的。

主线 672 行比 NamiDSH 的约 300 行多，主要多在三处：中文注释要求写全的 JSDoc 类型（`Sessions.ts:63-192` 一段就是接口定义）、四个关口、`ask`。这些都是用户要的。主线不建议再压。

### 5. 反方意见：“只数主线是在换口径”（F）

- **最强的反对**：用户说的是“骨架少之又少”。把 `Channels.ts`、`utils/` 叫成“共享库”不算进去，等于换了个口径，看上去瘦了，代码一行没少。
- **重新评估**：这条反对是对的，所以第 4 条不能单独做，要和第 1 到 3 条一起做：先真把共享库里只有一个插件用的挪走（约 630 行），再分开报两个数。
- 两个数分开报，各有各的用处：
  - 主线的数，回答“新人多快能看懂一条消息怎么走”；
  - 共享库的数，回答“插件之间共用的约定有多重”。
- 共享库要守的规矩是“只放两个以上插件用的”，由第 3 条的检查脚本守住。
- **还有一种做法**：把 `Channels.ts` 和 `utils/` 搬进一个新目录，比如 `src7/shared/`，让目录名就说明它不是主线。我不推荐：要改约 190 处 import，又和用户 #147“渠道协议挪进骨架”的决定正面冲突，付出比收获大。

## 三、怎么扫出来的（复查用）

- **行数**：去掉空行，以及 `//`、`/*`、`*` 开头的行，剩下的就是代码行。
- **导出谁在用**：用 node 脚本读目标文件的 `export function|const|class|interface|type 名字`。在 `src7/` 的非测试文件里，找 import 了这个文件、正文里又出现这个名字的，按插件目录归类。
- **主线结构**：`grep -nE "^  (async |private )*[a-zA-Z]+\(|^export" src7/Sessions.ts src7/Resources.ts src7/Tools.ts src7/Main.ts`。
