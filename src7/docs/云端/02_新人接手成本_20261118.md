# 02 新人接手成本（2026-11-18）

- 写的人：云端后备优化顾问。只读代码，没改任何文件。行号以 main 的 `593a17d` 为准。
- 方法 H：假设明天来一个能力很强、但完全没见过这个项目的工程师。他手里只有 git 仓库，和我现在一样：没有 `docs/`、`config.yaml`、记忆库，也看不到正在跑的服务。估一估他要付出多少理解成本，再找出命名乱、抽象多、职责不清的地方，给出简化方案。

## 一、一页结论

**判断**：新人最贵的成本不是代码难，而是**文字和代码说的不是一回事**。他会先读入口、README 和插件地图，可这三处有一半已经过时：

- 默认命令跑的是冻结了的 0.4；
- “一条消息怎么走”有三种说法；
- 插件地图里的版本号，30 个有 18 个对不上。

他得先花一天分辨哪句话还算数，才能开始读代码。下面 5 条，按“先消掉误导，再降词汇量”排序。

| # | 改什么 | 为什么 | 预计省 | 风险 |
|---|---|---|---|---|
| 1 | `package.json` 的默认命令换成 src7。0.4 的命令加后缀保留；7 处指向不存在目录的命令删掉或改掉。`lint` 加上 src7 | `dev`、`start`、`test`、`typecheck` 跑的都是 0.4，或者指向 `src6/`、`tests6/`、`scripts6/`、`testpage/`，这几个目录仓库里都没有。`lint` 根本不查 src7 | 新人第一小时的错路；概念上少一个“现在到底哪一版” | 低。要先确认 DSH、基地、任务书里没人按旧名字调这些命令（待核） |

**要用户定的两件事**：

1. 第 1 条：默认命令换成 src7 以后，用户、本地 AI 和 DSH 任务书里写的 `bun run test`、`bun run typecheck` 就会改去跑 src7。这样可以吗？还是加一个 `src7:` 前缀，旧名字原样留着？
2. 第 4 条：`docs/` 不进 git 是 11-02 定的。代码里的设计出处，是改指同目录的说明.md（推荐），还是把 `docs/src7插件设计/` 加进 git 白名单？

## 二、证据和方案

### 0. 模拟新人的第一天

| 时间 | 他读什么 | 卡在哪 |
|---|---|---|
| 第 1 小时 | 根目录 `CLAUDE.md`（约 200 行） | 约四成在讲 AI 分工（130、131、132、DSH、Grok、Codex、Antigravity）和 Windows 运维，夹着几十条带日期的用户原话。“jmbots 是什么”一节说入口是 `src/entries/Main.ts`，“以后由 Cordis 版 `src6/` 接手”，可 `src6/` 不在仓库里。“命令”一节的 `bun run test` 跑的是 0.4 |
| 第 1 小时 | `package.json` | `bun run dev` 起的是 0.4（`src/entries/Main.ts`）。`bun run test` 要跑 `./tests6`，`typecheck` 要读 `testpage/tsconfig.json`，这两个都不存在。版本号写 0.6.0，可 `src7/utils/Versions.ts` 已经到 0.7.42 |
| 第 2 小时 | `src7/README.md` | 第一行让他去读 `docs/src6开发/骨架和插件_进度.md`，仓库里没有。“骨架里没有机器人、渠道……这些词”，可骨架里有一个 1,078 行的 `Channels.ts`，专讲渠道。“约 465 行”，实际 1,277 行 |
| 第 3 小时 | README 的“一条消息怎么走” | 照着读到 `Bots.receive → bot/receive → frontDesk.receive`，再去对飞书的代码，发现飞书走的是另一条路：`channel/message → 认领 → channel_reply` |
| 第 4 小时 | `src7/docs/插件地图.md` | 版本号、事件清单和代码对不上，他开始不信这份地图 |
| 第 2 天 | 插件代码 | 文件头的“设计：docs/src7插件设计/xxx.md”一个都打不开。`kind`、`customer`、`frontDesk`、`flow`、`http` 这几个词，在不同地方意思不一样（见第 5 节） |

**按第一性原理看**：新人要的是“现在是什么样”。过去怎么来的，留给想追究的人去 git 和说明.md 里找。所以凡是“写着过去、却放在新人必读路径上”的东西，都是成本。

### 1. 入口指错版本（结论第 1 条）

`package.json` 里有问题的命令：

| 命令 | 现在跑什么 | 问题 |
|---|---|---|
| `dev`、`start` | `src/entries/Main.ts` | 0.4，已冻结 |
| `test` | `bun test ./tests ./tests6` | `tests/` 是 0.4 的；`tests6/` 不存在 |
| `typecheck` | 含 `tsc -p testpage/tsconfig.json` | `testpage/` 不存在 |
| `lint` | 查 `src/`、`web/`、`testpage/`、`scripts6/`、`src6/`、`tests6/`、`learn/` 等 | 不查 src7；里面有 4 个目录不存在 |
| `serve6`、`release6`、`swap6`、`guard6` | `src6/`、`scripts6/` 下的入口 | 目录不存在 |
| `build:testpage` | `testpage/Build.ts` | 目录不存在 |

**还有一处坑**：`eslint.config.mjs:94` 写着 `curly: ['error', 'all']`。照这条规则，CLAUDE.md 要的“单句 return 的 if 写成一行、不加大括号”会报错。所以现在的 lint 规则直接套到 src7 上会和约定打架，加 src7 之前要先改这一条。（怎么自动查 src7 的写法约定，留给主题 11。）

改后示意：

```json
"dev": "bun --watch src7/Main.ts",
"test": "bun run test:src7",
"typecheck": "bun run typecheck:src7",
"dev:04": "bun --watch src/entries/Main.ts serve",
"test:04": "bun test ./tests",
"typecheck:04": "tsc -p tsconfig.check.json && tsc -p web/tsconfig.json"
```

另外三种做法：

- 只删 7 个指向不存在目录的命令，默认名字不动：最稳，但“默认是 0.4”这个误导还在。
- 给 src7 的命令统一加 `src7:` 前缀，旧名字原样留着：不影响任何人的习惯，但新人还是会先敲 `bun run test`。
- 推荐上面的改后示意。前提是先核一遍：本地任务书、DSH、`approval/Rules.ts` 的 `isProjectCheck` 里，有没有写死旧命令名。

### 2. “一条消息怎么走”有四种说法（结论第 2 条）

| 出处 | 说法 |
|---|---|
| `src7/README.md`“一条消息怎么走” | 只有一条路：`Bots.receive → bot/receive → frontDesk.receive → session.run`，一轮结束由 `session/change` 自动发回 |
| `src7/docs/插件地图.md` 的 bots 一节 | 两条路：飞书走 `channel_tool`；命令行、网页、微信走 `legacy_auto` |
| `bots/index.ts:42`（1.4.1 的改版记录） | “网页、命令行、微信也走 channel_tool（去掉 deliveryMode）” |
| `bots/ChannelTools.ts:519` 的注释 | “兼容 legacy_auto 会话（网页、命令行、微信）” |

**代码现在的样子**：

- `Dispatch.ts:410-418` 仍然先把 deliveryMode 设成 `legacy_auto`；
- 只要有来源快照，就改成 `channel_tool`；
- `Dispatch.ts:72`、`:144`、`:180` 三处类型里都还留着这个字段；
- `ChannelTools.ts:162`、`:192`、`:229-232`、`:295`、`:510-519` 都在按它分情况。

**两个要先核的问题**：

- 问一：bots 1.4.1 以后，还有哪种消息会走到“没有来源快照”？推测有两种：升级前存下来的旧会话，和外部 AI 交回的结果（`AgentTasks` 调 `acceptResult` 时传不传 sourceSnapshot）。待核。
- 问二：如果只剩旧会话，能不能启动时给旧会话补一个快照，然后把 `legacy_auto` 整条分支删掉？

改后的 README 这一节，只写一条路：

```text
渠道收到一句话，先落盘                     ★ channel/message（approval 先认“同意 3”）
  bots 认领：按来源找这个机器人对这个客户的前台   Dispatch.claimChannelMessage
  排进前台，session.run()                   （下面是骨架，和现在 README 的骨架部分一样）
  模型调 channel_reply                       ★ channel/reply → 渠道发出 → ★ channel/replied
  一次没调就把最后的话当回复                  routing.autoFinal
```

### 3. 手写的地图一天就过时（结论第 3 条）

拿插件入口 `index.ts` 的 `version`，和插件地图、说明.md 对比（2026-11-18）：

- 插件地图对不上的有 18 个：approval、base-bridge、bots、cli、context-fit、decision、feishu、http、journal、memory、model-catalog、progress、relay、settings、tutorial、usage、web-api、wechat。例如 bots 的代码是 1.4.5，地图写 1.4.0；relay 的代码是 1.3.0，地图写 1.1.0。
- 说明.md 落后的有 6 个：base-bridge、desktop、fake-model、files-api、image-gen、web-search。
- README 写着“骨架 5 个文件不算注释和空行约 465 行，`utils/` 约 115 行”。实际按同样口径数，5 个文件是 1,277 行（`Channels.ts` 一个就 605 行），`utils/` 是 1,330 行（`Versions.ts` 占 234 行）。

**病根**：地图里大部分是能从代码读出来的东西，比如版本、inject、听和发的事件、工具、HTTP 路径、会话字段。人手抄一遍，代码一改就过时。

**两版方案**：

| 方案 | 做什么 | 代价 |
|---|---|---|
| 甲：教程页生成（推荐） | tutorial 已经有 `Code.ts`，能列函数、HTTP、工具；`Boot.ts` 记得每个插件多出了哪些服务和工具。再加一页“插件一览”，从代码和启动记录里生成这些机械列。手写的地图只留每个插件一句话用途和分类 | 教程页多一个视图，约 100–150 行；没跑起来时看不到 |
| 乙：脚本生成 Markdown | 写一个 `ztools/` 脚本扫代码，生成插件地图的机械部分，提交前跑一次 | 要有人记得跑；离线也能看 |

README 里写死的行数直接删掉。要说“骨架小”，就让教程页现算。

### 4. 代码注释里指向不存在的文件、留着改版痕迹（结论第 4 条）

我扫了 `src7/` 下 122 个非测试源文件，结果是：

- 指向 `docs/*.md` 的有 49 处，其中 48 处在仓库里没有。分布：`docs/src7插件设计/` 37 处，`docs/开发进度/` 9 处，`docs/协作/` 2 处。原因是 `.gitignore` 白名单不放 `docs/`（用户 11-02 定）。
- “照 0.4 src/…”这类出处有 69 行。`src/` 还在仓库里，这些引用能打开，但它们把新人引到一份已经冻结的旧代码。
- 改版记录式的 `//M x.y.z：……` 有 24 行，`bots/index.ts` 就占 8 行（`:39-47`）。
- 注释里带 `11-xx` 日期的有 138 行。

**改法**：

- 文件头只写职责和为什么；
- “设计：docs/…”改成“细节见同目录说明.md”；
- `//M 1.4.1：……` 这类挪进说明.md 的“版本”一节，代码里不留；
- 用户原话和日期只留在规则本身需要出处的地方，比如“用户 #113：插件之间只靠事件”。

改前（`bots/index.ts:40-42` 一带）：

```ts
//M 1.4.0：并进 prompt（Prompt.ts，默认开）、reply-tool（ReplyTool.ts，默认关）；legacy_auto 渠道的 channel/message 在这里交前台，去掉渠道里的过渡监听。
//M 1.4.1：渠道统一第 3、4 步——routing.sessionId 指定会话；网页、命令行、微信也走 channel_tool（去掉 deliveryMode）；
```

改后：代码里删掉这两行，说明.md 的版本一节写：

```markdown
- 1.4.1：网页、命令行、微信也走 channel_tool。
- 1.4.0：并进 prompt、reply-tool。
```

### 5. 词汇：一个意思几个词，一个词几个意思（结论第 5 条）

**一个意思几个词**

| 概念 | 代码和文字里的叫法 |
|---|---|
| Windows 上的常驻程序 | 基地（src7 里出现 193 次）、壳子（12 次）、`jmbots.exe`、`local/`（Rust 源码）、`engine.index_url`（配置）、`ctx.base`（服务）、`base-bridge`（插件）、30085 |
| 教程和调试插件 | 插件名 tutorial；服务 `ctx.flow`（`tutorial/index.ts:323`）；路径 `/flow/`；目录 `data/flow/`；relay 里还叫它“flow 插件”（`relay/index.ts:386`） |
| 一条消息的执行记录 | trace（事件）、跟踪点、journal、流水、轨迹（`Trail.ts`）、追溯（`web-api/Trace.ts`）、泳道（`Lanes.ts`）、快照（`State.ts`）、boot（`Boot.ts`） |

**一个词几个意思**

| 词 | 意思 |
|---|---|
| `kind` | 会话种类（front、work、decision、summary……），待确认的种类（exec、run、long-run、update、review、wechat-send、progress-limit……），回话种类（progress、final），模型种类（chat、decision），消息片段种类（text、image），还有教程页、Markdown 块各自的种类。`review`、`decision`、`progress` 在两套以上的取值里同时出现 |
| `http` | 插件名（唯一的 Fastify），又是 web-api 这个渠道的渠道名 |
| `frontDesk` | 服务名，实现它的却是 `Dispatch` 类（`Dispatch.ts:255`）；`FrontDesk.ts` 里的 `FrontDesk` 类不是服务。共 21 处引用 |
| `relay` | 插件名（所有外部交办都在里面）、机器人配置 `relay: direct`、“转话机器人”。这三样不是同一件事 |
| `customer` | 在 `bots/index.ts:79` 起、`wechat/index.ts:55`、`memory/Store.ts:21` 三处各 declare 一遍 |

**会话字段**：骨架的 `SessionRow`（`Sessions.ts:139`）只有 9 个字段：id、kind、parent、model、thinking、state、reply、messages、updatedAt。插件用 `declare module` 往上加了 17 个，分在 8 个文件里：

| 文件 | 加的字段 |
|---|---|
| `bots/index.ts:79` | bot、channel、address、customer、quiet、sourceClaims、sourceScope、activeSourceSnapshot、recalledStop |
| `bots/Dispatch.ts:42` | frontTask、resultQueue、activeKey、workspaceId |
| `progress/index.ts:143` | progress |
| `progress/Review.ts:20` | reviewedAt |
| `context-fit/Summary.ts:13` | summary |
| `memory/index.ts:40` | recall |
| `memory/Store.ts:21` | customer（第二遍）、memoryIndexed |
| `wechat/index.ts:55` | customer（第三遍） |

新人想知道“一场会话身上有什么”，得读完这 9 个文件。

**配置散在两处**：

- `config.yaml` 顶层的 `engine` 是 0.4 留下的段，src7 有 6 个插件和 `Checks.ts` 还在读它（progress、model-catalog/Fallback、image-gen、memory、base-bridge、settings）。
- progress 的主配置读 `engine`，子配置读 `plugins[progress].config`（`progress/index.ts:38`）。同一个插件的配置分两处写。
- `config.example.yaml:41-60` 的 engine 段里，有些键 src7 已经不读了：`poll_ms`、`compress_at`、`exec_pass`、`vision_model`。src7 的前台看图模型在 `bots.front.vision_model`（`bots/index.ts:764`）。新人分不清哪些键还有用。

**Cordis 的一个坑**：

- 服务的方法被别的插件调用时，`this.ctx` 是调用方的 ctx。这件事写在 `Tools.ts:106`、`bots/index.ts:202`、`Dispatch.ts:235`、`workspaces/index.ts:164` 的注释里。
- 所以这三个服务另存了一个 `home`，方法里一律用它。
- 其余十几个服务（approval、memory、progress、journal……）的方法里都直接用 `this.ctx`。
- 新人看到两种写法，不知道哪种对。
- 待核：这些方法里，有没有在被别的插件调用时用 `this.ctx` 登记东西（on、定时器、tools.register）？有的话，登记的东西会挂到调用方身上，调用方一停就跟着撤掉。
- 框架本身是 `cordis 4.0.0-rc.12`（`package.json:44`），是候选版，中文资料以外几乎没有，这本身也是接手成本。

**改法**（按收益排）：

1. **会话字段表**：在教程页生成“会话字段”一栏，或者在 `Sessions.ts` 的 `SessionRow` 上方写一段注释，列出哪个插件加了哪些字段。`customer` 只留 bots 一处声明，wechat 和 memory 改成 `import type`。
2. **frontDesk 对齐**：服务改名 `dispatch`（21 处），或者 `Dispatch` 类改名 `FrontDeskService`。推荐前者，名字和文件对上。
3. **词汇表**：在 `src7/README.md` 末尾加一张十来行的表，写这一节列出的几组词，每个词一行“指什么、在哪”。
4. **Cordis 的坑**：在 `plugins/Index.ts` 的 `PluginModule` 注释里写一次规矩：“服务方法里要登记东西，用构造时存下的 ctx”，各个服务照着统一。

### 6. 不建议改的（先假设该改，再找反例）

- **全局改 `kind`**：涉及上百处，还牵涉存库的字段名和网页。付出远大于新人少想的那一下，用词汇表解释就够了。
- **插件改名**（比如 tutorial 改叫 flow，或者反过来）：要改每个人的 `config.yaml`。只把服务名 `ctx.flow` 在说明.md 里写清楚就行。
- **删掉 `src/`（0.4）**：会让 69 处“照 0.4”的出处全部失效，牵涉也大。这是主题 4“历史包袱”的事，这里不动。
- **把 CLAUDE.md 拆成“给人的”和“给 AI 的”两份**：方向对，但 CLAUDE.md 只能本地改，而且用户把它当成规则的单一来源。这里只指出：“jmbots 是什么”和“命令”两节已经和 src7 对不上，请本地 AI 照第 1 条一起改。

## 三、怎么扫出来的（复查用）
