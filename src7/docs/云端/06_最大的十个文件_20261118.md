# 06 最大的十个文件（2026-11-18）

- 写的人：云端后备优化顾问。只读代码，没改任何文件。行号以 main 的 `ca212da` 为准。
- 方法：
  - A（第一性原理）：这个文件为什么大？是一件事本来就大，还是好几件事挤在一起？
  - H：一个没见过项目的人，要打开几个函数才看得懂？
- 范围：`src7/` 下非测试源文件，按行数取前十。
- 口径：“代码行”不算注释和空行；“函数长度”从签名那一行数到收尾的大括号。

## 一、一页结论

**判断**：十个最大的文件，大的原因只有两种。

- **好几件事挤在一个文件里**：`feishu/index.ts` 和 `bots/Dispatch.ts`，一个文件 2,300–2,600 行，里面有 11 个函数超过 80 行，最长的 355 行。
- **同一件事别处已经做过一遍**：飞书自己写了一套历史分页；前台为查历史登记了 3 个工具。

剩下的文件，approval、progress、relay、wechat、AgentTasks，函数长度基本在 80 行以内，结构已经合理，不建议动。

### 1. 飞书自己写了一套历史分页（结论第 1 条）

- 命令行、网页、微信都调 `Channels.ts:664` 的 `paginateChannelHistory`（主题 3 的导出盘点：它的使用方是 cli、web-api、wechat）。这个函数的头注写着：“按渠道标准协议校验翻页游标、按模式过滤、按 (createdAt, messageId) 升序稳定分页并生成下一页签名游标”。
- 飞书的 `onChannelHistory`（`feishu/index.ts:1590-1793`）前半段在解析应用号和聊天号，这是飞书特有的，要留。后半段是：
  - `:1708` 起调 `protocol.decodeHistoryCursor` 校验游标；
  - `:1732` 起按 mentions、visible 过滤；
  - `:1743` 起排序、截取；
  - 最后拼出下一页游标。

  这正是 `paginateChannelHistory` 做的事。

改后：

```ts
//M 读出这个聊天落盘的原始记录，换成标准历史条目（@我 的先在条目上标好，过滤交给骨架）。
const entries = this.readChatEntries(appId, chatId, botOpenId);

//M 游标、模式过滤、排序、分页，和别的渠道用同一套。
const result = protocol.paginateChannelHistory({
  request,
  channel: this.name,
  accountId: appId,
  chatId,
  entries,
});
this.ctx.emit('channel/history-result', { ...result, requestId: request.requestId });
```

待核：`paginateChannelHistory` 怎么过滤“@我”这个模式？要看 `ChannelHistoryItem` 上有没有标记字段。没有的话，加一个 `mentionsBot` 字段，由各渠道在拼条目时填好。

### 2. feishu/index.ts 怎么拆（结论第 2 条）

**现在**：

- 文件里一个 `Feishu` 类，外加 `apply`；
- 已经有 4 个子文件夹或子文件：`cards/`、`doc/`、`outbox/`、`Media.ts`；
- 收消息、查历史、回话、找聊天、来往流水这几块，还都在 `index.ts` 里。

**改后的文件**（照别的渠道的样子）：

| 文件 | 放什么 | 约多少行 |
|---|---|---|
| `index.ts` | `apply`、配置校验、`Feishu` 类的构造函数和长连接 | 600 |
| `Inbound.ts` | 收消息：`handleInboundMessage` 拆出来的 6 步，加上 `resolveOutcome`、`getAllowedBots` | 550 |
| `History.ts` | `onChannelHistory`（改用 `paginateChannelHistory` 以后约 110 行），加上读本地聊天日志 | 200 |
| `Reply.ts` | `onChannelReply`、`getReplyTargetAddress`、发送去重 | 450 |
| `Contacts.ts` | `feishuCustomer`、来往流水 `data/logs/feishu-contacts.jsonl`、`/api/feishu/contacts` | 300 |

**`handleInboundMessage` 拆成 6 步**（`feishu/index.ts:835-1189`，按现有的 `//M` 段落分）：

```ts
private async handleInboundMessage(appId: string, app: AppState, data: ReceiveData): Promise<void> {
  //M 1. 这条消息 @ 了哪些机器人（本应用允许投递的名单里挑）。
  const targets = this.getTargets(app, data);

  //M 2. 换成文字，去掉 @ 占位符。
  const text = this.getText(data, targets);

  //M 3. 认人、认群、定客户号和角色。
  const who = this.identify(appId, app, data);

  //M 4. 群里没 @ 也没登记只听的：只落盘、记一行流水，不交给机器人。
  if (this.shouldDrop(who, targets)) return this.keepRaw(appId, data, who);

  //M 5. 收到了先点表情；引用、转发、附件补齐。
  const extras = await this.collectExtras(appId, app, data, who);

  //M 6. 落盘、发 channel/message、记去重、汇总认领结果。
  await this.deliver(appId, data, text, who, targets, extras);
}
```

**注意**：

- 现在整个方法包在一个 `try` 里，出错时登记失败流水（`:1174` 起）。拆完这个 `try` 留在外层不动。
- 第 4 步的 `return this.keepRaw(...)` 返回 `void`，符合“`if` 加提前 return”的写法。
- 拆成的方法都是这个类的私有方法，不新建接口，也不加转发层，符合 CLAUDE.md“不为一次用途另建接口”。

- `Channels.ts` 加一个 `pickChat(要找的, 候选清单)`，返回唯一命中的那个，或者一句原因。

## 三、怎么量的（复查用）

- **函数长度**：用 node 脚本找方法的起点，有两种写法：类方法是“两个空格缩进、名字、括号”，顶层函数是 `function 名字`。终点分别是同缩进的 `}`。签名跨多行的也认得。先用正则粗扫过一遍，把接口里的方法签名误认成了函数（比如 `progress` 的 `ask`），这次已经去掉了。
- **飞书分页**：读 `feishu/index.ts:1590-1793`，对照 `Channels.ts:621-743` 的 `PaginateHistoryInput` 和 `paginateChannelHistory`。
- **按名字找聊天**：`grep -n "getReplyTargetAddress" src7/plugins/*/index.ts`。
