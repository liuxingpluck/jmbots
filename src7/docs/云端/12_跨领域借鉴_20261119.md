## 一、一页结论

**判断**：翻了九类系统（打包器的插件钩子、Linux 内核、systemd、Emacs、VS Code、Koishi、D-Bus、LSP、游戏引擎 ECS），它们在“插件多还不乱”这件事上做法一致，有两条：

1. **钩子按活分种类**：改东西的、先答先得的、只通知的，各用各的钩子，不挤在同一个钩子里；
2. **先后靠声明，不靠名单里的位置**：依赖写在插件自己身上（`After=`、`inject`），同一个钩子里的先后用 `pre` 这类标记；用户能改的名单，顺序不带意思。

jmbots 第 2 条借到了一半：`inject` 和 `ctx.inject` 在用。第 1 条没借到：`session/request` 一个事件里同时干三种活，改请求、量尺寸、替骨架调模型。结果是 `config.yaml` 里插件的位置成了程序逻辑。模板里写了 **12 条“写在谁前面、后面”**，插件一合并，监听的先后就悄悄变了（`bots/index.ts:1064-1065` 自己写着）。

| # | 改什么 | 借自哪里、为什么 | 预计省 | 风险 |
|---|---|---|---|---|
| 1 | 把“调模型”从 `session/request` 里拆出来，加一个骨架事件 `session/chat`：先答先得。换模型（Fallback）挪过去；context-fit 的裁剪也挪过去，用 `prepend` 排在最前；假模型加一行“已有回答就不管” | 打包器（webpack、Rollup）分“依次改”和“先答先得”两种钩子。现在 Fallback 必须在 `config.yaml` 里排最后，否则排在它后面的插件改的请求，模型根本看不到；裁剪要量最终的提示词，也必须排在所有加东西的插件后面，这一条哪里都没写 | 先后约束少 4 条，6 处注释不用再写；骨架加 1 个事件、循环多 2 个 `if` | 中低：动骨架主线 3 处，换模型的逻辑一行不改 |

| 3 | 外部程序的渠道名只写一处：programs 拉起程序时，把渠道名放进环境变量（和密钥、回调地址一样），不再要求 `args` 里的 `--channel` 和 `channels` 写成同一个名字 | systemd 把套接字名经环境变量交给服务（`LISTEN_FDNAMES`），LSP 握手时由主机把配置交给服务端。现在两处写得不一样，启动时不报错，要等到收消息才回 403 | 少 1 处重复配置，少一类“配对了才能用”的坑 | 低：程序那一侧不在 git 里，待核 |
| 4 | （要用户定）各插件的配置要不要能在设置页直接改 | Koishi、VS Code 都是插件声明配置项，界面自动出表单。Cordis 4 自带这个口子（`cordis:292-304`），jmbots 没用 | 要的话：校验挪到挂载前，说明.md 的配置表和设置页表单都能自动出 | 要的话中：要引一个校验库 |

**不借的**：ECS 那种按组件拆开存、VS Code 的懒加载、数字优先级、洋葱式中间件、单独发一个公开 API 包。理由见第五节，都是“现在的规模用不上，或者和 Fallback 的写法冲突”。

**要用户定的一件事**：设置页要不要能直接改每个插件的配置（按插件自动出表单）？

- 要：借 Koishi 的写法，每个插件导出 `Config`，Cordis 挂载前自动校验（第 4 条，方案 C）；
- 不要：第 4 条不做，前 3 条照做。

## 二、九类系统各怎么做（方法 E）

| 系统 | 它靠什么做到“插件多还不乱” | jmbots 现在 | 借不借 |
|---|---|---|---|
| webpack（Tapable）、Rollup、Vite | 钩子分种类：依次改值的、先答先得的、并行的；同一钩子里的先后用 `stage`、`enforce: 'pre' \| 'post'`、`order` 声明 | 四个关口都是“挨个问”；`session/request` 一个事件里有改请求、量尺寸、替骨架调模型三种活 | 借：第 1 条拆钩子，第 2 条用 `pre` |
| Linux 内核 | 启动分级（early → core → … → late）；驱动缺依赖时返回 `-EPROBE_DEFER`，依赖到了再挂；netfilter 的钩子按优先级数字排，每个钩子回一个裁决（放行、丢弃、自己接手） | `ctx.inject` 就是“依赖到了再挂”，6 处在用，2 处还在当场取（`ctx.get`）；`request.answer` 相当于“自己接手” | 借统一用 `ctx.inject`（第 2 条）；数字优先级不借 |

| Emacs、Neovim | `add-hook` 带深度参数（-100 到 100）定先后；autocmd 按组整组撤掉 | Cordis 只有 `prepend`（`cordis:784-785`）；插件拔掉时监听整组撤掉，已经有了 | 只用 `pre` 这一档，已经够了（第 2 条）；数字深度不借 |

| D-Bus、GObject | 跨进程的调用带序号，回信带 `reply_serial` 配对；进程内的信号靠 accumulator，第一个处理者返回 TRUE 就不再往下问 | 进程内也用请求号配对（`utils/RequestEvent.ts`）；跨进程走 HTTP（programs） | 进程内照 GObject 用返回值，即主题 5 的第 1 条，本篇不重复 |
| LSP | `initialize` 握手：服务端报能力，主机用 `initializationOptions` 把配置交过去；JSON-RPC 用 id 配对 | 就绪行加 `info` 核对身份（`Protocol.ts:196-226`），已经借到 | 渠道名改成由主机交给程序（第 3 条） |

**共同的一条**：先后永远写在插件或钩子自己身上，从不写在用户能改的名单里。名单的顺序一旦带意思，两件不相干的事就会互相牵连：

- 用户在 `config.yaml` 里挪一行；
- 本地 AI 把两个插件合成一个。

这两件事都会悄悄改掉会话的行为。

## 三、证据和改法

### 1. 拆出 `session/chat`：谁来调模型

#### 1.1 现在一个事件干三种活

`session/request`（`Sessions.ts:550` 发，挨个问）上挂着 18 个监听（`Sessions.ts:40-59` 的“谁接”）。按干的活分三种：

| 干的活 | 谁 | 对先后的要求 |
|---|---|---|
| 改请求：加提示词、换对话、收窄工具 | Prompt、FrontDesk、memory、skills、progress、file-tools、approval、ChannelTools、relay（非直转）…… | 整段换对话的要在前面（见第 2 节），别的大多互不影响：收窄工具都是 `filter`，谁先谁后结果一样 |
| 量尺寸：按模型的窗口裁对话 | context-fit 的裁剪（`context-fit/index.ts:211-245`） | 要量最终的提示词、工具和对话（`:239` 用的是 `estimate(request.system)`、`estimate(request.tools)`），所以必须在所有加东西的插件**后面**。这一条哪里都没写 |
| 答：直接给回答，或者替骨架调模型 | fake-model（`fake-model/index.ts:28`）、relay 直转（`relay/index.ts:734-788`）、DispatchTools 暂停（`bots/DispatchTools.ts:603-607`）、Fallback（`model-catalog/Fallback.ts:165`） | Fallback 必须**最后**；relay 必须在 fake-model **后面**（fake-model 不看有没有回答，直接覆盖） |

**二阶影响**：Fallback 是在 `session/request` 里面真调模型的（`Fallback.ts:183`、`:219`、`:233`）。排在它后面的插件：

- 往请求里加的东西，模型看不到；
- 收窄的工具，模型已经拿着全量的清单答完了。

approval 给外人收窄工具（`approval/index.ts:393-410`）就是这样的插件。好在执行前还有一道拦截（`:413`），不会真执行，但模型会答应做不了的事。

**三阶影响**：这种顺序要求，只能写成注释和模板说明来守。现在写了 6 处：

- `Fallback.ts:3`、`:7`、`:164`；
- `model-catalog/index.ts:5`；
- `relay/index.ts:1615`；
- `config.example.yaml:282`。

插件合并也会改先后，`bots/index.ts:1064-1065` 写着：

> 并进来之前它排在 relay、memory 后面，现在排到它们前面

这是主题 1 合并插件带出来的副作用。

#### 1.2 Cordis 现成的能力

- `ctx.serial` 依次 await，**第一个返回了值的就停**，并把这个值交回来（`cordis:754-760`）；“有值”的判断在 `cordis:692-694`：不是 `undefined`、`null`、`false`。这正是“先答先得”。
- `{ prepend: true }` 用 `unshift` 插到最前面（`cordis:784-785`），不看挂载先后。

所以“先量、后答”在一个新事件里就能分开：量尺寸的用 `prepend`，答的不返回就让给下一个。

#### 1.3 改法

骨架 `Sessions.ts`，加一个事件（声明写在 `Events` 里，返回值的类型写法待核）：

```ts
    /**
     * 真要调模型了：请求已经改完（session/request 问完了），也没有插件直接给回答。照先后一个个 await。
     * 量尺寸、裁剪的插件挂的时候写 { prepend: true }，排在最前，不返回值；
     * 替骨架调模型的插件（换模型）返回回答，后面的就不再问；都不返回，骨架自己调 chat()。
     * 谁发：src7/Sessions.ts 的 Session.loop
     * 谁接：
     *   src7/plugins/context-fit/index.ts 的 apply（prepend，裁剪）
     *   src7/plugins/model-catalog/Fallback.ts 的 ModelFallback.constructor（换模型）
     */
    'session/chat'(request: ChatRequest): Promise<piAi.AssistantMessage | undefined>;
```

`Session.loop`，改前（`Sessions.ts:571-575`）：

```ts
      //M 调模型（Sessions.chat，就在本文件上面）。插件已经给了回答（假模型）就不发请求。
      let answer = request.answer;
      if (answer === undefined) {
        answer = await this.ctx.sessions.chat(request);
      }
```

改后：

```ts
      //G 问插件的时候被喊停了（插件自己调了 session.stop）→ 不调模型。
      if (this.row.state !== 'running') return;

      //M 插件已经给了回答（假模型、转话机器人）就不调模型。
      let answer = request.answer;

      //M 真要调模型了：先交给插件（session/chat）。量尺寸的先裁，替骨架调模型的（换模型）交回回答。
      if (answer === undefined) {
        answer = await this.ctx.serial('session/chat', request);
      }

      //M 没有插件替骨架调：骨架自己调（Sessions.chat，就在本文件上面）。
      if (answer === undefined) {
        answer = await this.ctx.sessions.chat(request);
      }
```

第一行守卫的来由：DispatchTools 暂停时，先 `session.stop('暂停中')`，再塞一个空回答（`DispatchTools.ts:605-606`）。塞空回答，只是因为骨架在这个位置不查状态，不塞就会接着调模型。加了守卫，这个空回答就可以删，或者改成写 `request.stop = '暂停中'`，那正是 `request.stop` 本来的用处（`Sessions.ts:552-556`）。

`model-catalog/Fallback.ts`：

```ts
    //M 听 session/chat：请求已经改完、也没人直接给回答。这里替骨架调模型，限流、超长时换着试，交回回答。
    ctx.on('session/chat', (request) => this.onChat(request));
```

`onRequest` 改名 `onChat`，返回 `Promise<piAi.AssistantMessage>`：

- `:174` 的 `if (request.answer !== undefined) return;` 删掉，骨架已经保证没有回答；
- `:183`、`:219`、`:233` 三处 `request.answer = await this.attempt(...)` 改成 `return await this.attempt(...)`；
- `attempt`、冷却、排队一行不动。

`context-fit/index.ts:210-211`：

```ts
  //M 听 session/chat，排最前（prepend）：请求已经改完，按要调的模型量一量，超了就裁。
  //M   不返回值，模型由后面的插件（换模型）或骨架去调。
  ctx.on('session/chat', async (request) => {
    // ……函数体原样
  }, { prepend: true });
```

`fake-model/index.ts:28` 后面加一行，这样它和 relay 谁先谁后都一样：

```ts
    //G 前面已经有插件给了回答（转话机器人）→ 不管。
    if (request.answer !== undefined) return;
```

删掉这几处先后说明：`Fallback.ts:3`、`:7`、`:164`；`model-catalog/index.ts:5`；`relay/index.ts:1615` 的“写在 fake-model 后面，model-fallback 前面”；`config.example.yaml:134` 的“fake-model 后面”和 `:282` 整句。README 的关口表加一行 `session/chat`。

**预计省**：

- 先后约束少 4 条：Fallback 排最后；relay 在 fake-model 后面；relay 在 Fallback 前面；裁剪在所有加东西的插件后面；
- 6 处注释删掉；
- 转话机器人、假模型的每一步不再裁剪，所以也不再问一次模型目录（`context-fit/index.ts:220` 最多等 3 秒，`:60`；平时是进程内往返，耗时很小）；
- 骨架多 1 个事件声明（约 10 行），循环多 2 个 `if`。

#### 1.4 反方（方法 F）

- **“骨架多一个事件，违背骨架少。”** 多的是 1 个事件、6 行代码，换掉的是散在 6 处的一条隐含规矩，外加一条哪里都没写的规矩。CLAUDE.md 允许给骨架加事件，只要改动最少；“会话每一步都有关口事件”这一条，也正好要求“调模型”这一步对插件可见。
- **“启动时查一下 model-catalog 是不是排最后，不就行了？”** 只查得到 `config.yaml` 的顺序，有两种情况查不到：
  - 写在 `ctx.inject(...)` 回调里的监听，要等服务出现才挂上，排到当时的最后；
  - 插件内部的先后：合并以后重新排过（`bots/index.ts:1064`），有的还写着“必须在 Memory 之后注册”（`memory/GraphRoutes.ts:174`）。

  查顺序只治表面。病根是一个事件干了三种活。
- **“用 Cordis 的 `waterfall`（洋葱式）更漂亮：Fallback 包住 `next()`。”** 不行。`next()` 只准调一次，第二次调会抛错（`cordis:776`）。而 Fallback 每换一个模型，都要另起取消信号、另占一个排队名额（`Fallback.ts:248-273`）。洋葱式装不下“重试好几次”，“先答先得”装得下。
- **“relay 直转和假模型还用 `request.answer`，不是又成了两条路？”** 是故意留的。它们决定的是“这一步不调模型”，和 `request.stop` 一样，属于改请求。挪进 `session/chat` 的话，裁剪（`prepend`）会排在它们前面，转话机器人每一步又要白量一次。

#### 2.2 同一件事两种写法：当场取 http 和等 http

已经在用 `ctx.inject(['http'], …)` 的有 6 个插件：

- `journal/index.ts:519-520`
- `progress/index.ts:1344`
- `exec/index.ts:425`
- `model-catalog/index.ts:546`
- `programs/index.ts:526`
- `tutorial/index.ts:4`（注释里说明了做法）

还在 `apply` 里当场 `ctx.get('http')` 的有 2 处：`feishu/index.ts:1243`、`relay/index.ts:313`。http 写在它们后面，接口就悄悄不登记了。relay 自己往下三行就用 `ctx.inject(['flow'], …)`，注释写着“flow 前后挂都接得上”（`relay/index.ts:315-316`）。可见写法是知道的，只是 http 这一处没跟上。

`feishu/index.ts:1242-1249`，改前：

```ts
  //M http 挂了（写在 feishu 前面）才有来往流水的接口：GET /api/feishu/contacts?limit=（默认 50，最多 1000），新的在前。
  const http = ctx.get('http');
  if (http !== undefined) {
    http.app.get<{ Querystring: { limit?: string } }>('/api/feishu/contacts', (request) => {
      const limit = textModule.getNumber(request.query.limit, 50, 1, 1000);
      return { items: feishu.contacts.list(limit) };
    });
  }
```

改后：

```ts

  //M   GET /api/feishu/contacts?limit=（默认 50，最多 1000），新的在前。
  void ctx.inject(['http'], (sub) => {
    const route = '/api/feishu/contacts';
    sub.http.app.get<{ Querystring: { limit?: string } }>(route, (request) => {
      const limit = textModule.getNumber(request.query.limit, 50, 1, 1000);

  });
```

`relay/index.ts:312-313`，改后：

```ts

    void this.ctx.inject(['http'], (sub) => {
      routesModule.routes(sub.http, this);
    });
```

`routesModule.routes` 里除了 http 还碰不碰别的东西（`relay/TaskRoutes.ts:163-165` 用的是 `ctx.http`），待核。

Fastify 在开始监听以后就不能再加路由，这一点不受影响：http 等 `ready` 才开始监听，而 `ready` 在所有插件都发起挂载之后才发（`Main.ts:212`）。`ctx.inject` 的回调在挂载阶段就会跑，赶得上。

#### 2.3 压缩从 `row` 重拼，会冲掉前面插件的改动（待核）

`context-fit/Compress.ts:110`：

```ts
    request.messages = [note, ...row.messages.slice(done.upto)];
```

它从 `row.messages`（库里的原文）重拼，不是从 `request.messages`（前面插件改过的副本）接着改。管道的规矩（Unix 管道、webpack 的依次改值钩子都一样）是：每一段只读上一段的输出，不回头读源头。这一行违反了它。

后果按模板的顺序推（实际的 `config.yaml` 看不到，所以待核）：

- file-tools 写在 `:126`，context-fit 写在 `:207`，file-tools 的监听先跑；
- 看图模型的请求里，file-tools 把用户 @ 的图片接进对话（`file-tools/BaseTools.ts:181`）；不看图的模型，它在末尾加一句“别自己写识图脚本”（`:176`）；
- 后台会话压缩过一次以后（`Compress.ts:86`，只压 work），这两样每一步都被冲掉。用户在长任务里 @ 一张图，模型收不到图。

progress 的报时提醒原来也会被冲掉，所以它在 `progress/index.ts:284` 写了“要写在 compress 后面”。

改法：压缩是“整段换掉对话”的，让它排最前（相当于 Vite 的 `enforce: 'pre'`）。

`context-fit/Compress.ts:75`，改后：

```ts
    //M 排最前（prepend）：这里把整段对话换成“摘要 + 后半段原文”。
    //M   要在别的插件接图片、加提醒之前换，不然会把它们的改动冲掉。
    this.ctx.on('session/request', (request) => this.onRequest(request), { prepend: true });
```

排最前时，`request.messages` 还是 `row.messages` 的原样副本，`:110` 那行不用改。

README 关口表里补一句规矩：**整段换掉 `messages` 的监听写 `{ prepend: true }`；别的只在上一段的基础上改，不回头读 `row`。**

#### 2.4 反方（方法 F）

- **“几个插件都 `prepend`，彼此谁先？”** `prepend` 用的是 `unshift`，后挂的反而排前面（`cordis:785`）。现在整段换对话的只有两个：FrontDesk 只管 front，压缩只管 work，管的会话不重叠，谁先都一样。以后再加第三个，也要求按会话种类错开。写进上面那句规矩就够，不用上数字优先级。
- **“注释删了，新人怎么知道谁依赖谁？”** 依赖写在 `inject` 里，插件地图是脚本生成的。留着已经过时的“写在谁后面”，反而让人以为名单的顺序处处带意思。

### 3. 外部程序的渠道名只写一处

#### 3.1 现状

- 程序的 `channels` 在 config 里登记（`programs/Spec.ts:228-246`）；
- 同一个名字，还要在程序的启动参数 `--channel` 里再写一遍，模板专门提醒了两次（`config.example.yaml:257`、`:260`）；
- 两处写得不一样，启动时不报错。要等程序交进第一条消息，`ChannelBridge.onInbound` 才回 403“渠道没有登记给程序”（`programs/ChannelBridge.ts:229-233`）；
- 密钥和回调地址已经是主机经环境变量交给程序的（`programs/Host.ts:380-389`，常量在 `programs/Protocol.ts:10`、`:12`）。

#### 3.2 改法

照 systemd 的 `LISTEN_FDNAMES`、LSP 的 `initializationOptions`：名字由主机交给程序，程序不自己再记一份。

`programs/Protocol.ts`：

```ts
/** 登记给这个程序的渠道名，逗号隔开（如 wechat）；程序照它收发，不再从启动参数读 --channel。 */
export const CHANNELS_ENV = 'JMBOTS_CHANNELS';
```

`programs/Host.ts:383` 后面（和 `CALLBACK_ENV` 一样先删旧值）：

```ts
      delete env[protocolModule.CHANNELS_ENV];

      //M 登记了渠道的程序：渠道名也放进环境。名字只在 config 的 channels 里写一次，args 里不用再写 --channel。
      if (this.spec.channels.length > 0) {
        const names = this.spec.channels.map((channel) => channel.name);
        env[protocolModule.CHANNELS_ENV] = names.join(',');
      }
```

程序这一侧（`external/wechat/Main.ts`）不在 git 里，读环境变量那几行由本地改，**待核**。模板 `:257`、`:260` 两句提醒随之删掉。

#### 3.3 反方

**“将来程序要自报能力（LSP 那样双向协商）。”** 现在只有外置微信一个程序，等第二个程序真需要时再加。环境变量这一步不挡以后的协商。

### 4. 插件配置：要不要借 `Config`（要用户定）

#### 4.1 现状

- Cordis 4 支持插件导出 `Config`：挂载前调它的 `~standard.validate` 校验，校验通过的值交给 `apply`，不通过就挂载失败（`cordis:292-304`；`:1497` 读 `plugin.Config`）。这里认的是 Standard Schema 接口，不绑定哪个校验库；
- jmbots 没用这个口子。各插件在 `apply` 里手写校验，单看 `index.ts` 里 `throw new Error` 的个数：feishu 32、voice 24、memory 17、web-search 15、model-catalog 14、bots 13（子文件里的没算）；
- 设置页（`settings/index.ts`）不知道插件有哪些配置项；
- 32 份 `说明.md` 的“配置”表是手写的。

#### 4.2 三个方案

| 方案 | 做什么 | 得到 | 代价 |
|---|---|---|---|
| A 不动 | — | — | — |
| B 只换位置 | 写一个约 15 行的适配函数，把现有的检查函数包成 `Config` 导出 | 校验在挂载前跑，`apply` 直接拿到带类型的配置，正合 CLAUDE.md 的“入口校验一次” | 得到的很少，`说明.md` 和设置页都还是手写 |
| C 声明式 | 引一个校验库（比如 zod，它能导出 JSON Schema），每个插件把配置项写成声明 | 设置页按插件自动出表单；`说明.md` 的配置表自动生成；默认值写在一处 | 多一个依赖、多一个概念，32 个插件逐个改写 |

#### 4.3 反方

用户说过不要过度抽象。B 收益太小，不值得单独做。C 只有在“设置页要能改插件配置”时才划算。所以这件事不该由顾问定，挂到决策图上，问用户要不要。

### 5. 考虑过、不借的（方法 F 的结论）

| 借什么 | 最强的支持理由 | 为什么不借 | 什么时候再看 |
|---|---|---|---|
| ECS：按组件拆开存（每个插件一张表，按会话号对上） | 插件往 `SessionRow` 上加的字段有 18 个，散在 8 个文件（`src7/docs/词汇表.md:56`），拆开存，谁的字段归谁 | ECS 图的是成千上万个实体逐帧遍历时的缓存命中，会话没这个量；`sessions.find` 现在一条 SQL 就能跨字段查，拆开要连表、要迁移。“谁加了什么”已经由词汇表 1.2 列着 | 会话多到 `find` 变慢时 |
| VS Code：用到才激活（懒加载） | 33 个插件全在启动时挂，有的要等（`Main.ts:177-191` 的超时） | 自带插件几乎都是一开就要用的渠道和关口；启动慢不慢，没有数据 | 启动时间成了问题时，先看 tutorial 的启动录像 |
| 数字优先级（Emacs 的深度、netfilter 的优先级） | 想排多细排多细 | 数字最后会变成一张要背的表。做完第 1、2 条，只剩“最前”和“默认”两档，Cordis 的 `prepend` 就够了 | 出现第三个整段换对话、又不能按会话种类错开的插件时 |
| 洋葱式中间件（Koa、Cordis 的 `waterfall`）当 `session/chat` | 写法漂亮，前后都能插手 | `next()` 只准调一次（`cordis:776`），Fallback 要换着模型重试好几次 | — |
| 单独的公开 API 包（像 `@types/vscode`） | 外部插件要单独编译（用户 #161），不能 import 内部文件，事件类型得有个地方拿 | 收费插件走进程插件，只认 HTTP 接口，用不着 TypeScript 类型；仓库外的开源 JS 插件现在只有模板里一个示例（`config.example.yaml:293`） | 第一个仓库外的开源 JS 插件动手写时 |
