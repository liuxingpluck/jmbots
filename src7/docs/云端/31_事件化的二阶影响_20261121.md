## 一、一页结论

**判断**：事件化的成本，已经从“发请求的一方”挪到了“旁听的一方”。

- 插件之间只靠事件以后，要看清一条消息怎么走，只能在旁边听：journal 记流水，tutorial 打印、拍快照、录载荷。
- 这些旁听者跑在**发事件的那一行里**：Cordis 先同步发 `internal/dispatch`，再调业务监听，而且 `emit` 不接异常。
- 所以旁听层现在既是性能的大头，也是一个没人注意到的单点：它一抛错，正事就停。

## 二、证据和改法

### 1. 旁听者不许拦正事（结论第 1 条）

**Cordis 怎么发事件**（`lib/index.js`）：

- `_resolve`（`:727-736`）：事件名不是 `internal/` 开头、又有人听 `internal/dispatch` 时，**先同步** `this.emit("internal/dispatch", type, name, args, thisArg)`，再取这个事件的监听列表；
- `emit`（`:750-753`）就是一个 for 循环挨个调，没有 try；`serial`（`:754-760`）也一样，只是挨个 await；
- 所以 `internal/dispatch` 的任何一个监听抛错，异常从 `_resolve` 一路冒到发事件的那一行，原来那个事件的业务监听**一个都没被调到**。第五节的小脚本实测了这一点。

**谁在旁听**：

| 旁听的事件 | 监听在哪 | 每次干什么 | 有没有 try |
|---|---|---|---|
| `internal/dispatch` | `journal/index.ts:263-276` | 拼事件行、取调用栈、**同步写 SQLite**（`:313`） | 没有 |
| `internal/dispatch` | `tutorial/Print.ts:60-62` | 拼事件行、取调用栈、打控制台、`fs.appendFileSync`（`:145`） | 没有 |
| `internal/dispatch` | `tutorial/State.ts:127-160` | 有 `#调试` 消息时拼事件行、拍整个运行时的快照 | 没有 |
| `internal/dispatch` | `tutorial/Payload.ts:1056-1066` | 15 个核心事件：拼事件行、取调用栈、深拷贝、算差异 | 没有 |
| `trace` | journal `:232`、Print `:55`、State `:102`、Payload `:1037`、`tutorial/Boot.ts:248` | 记一行、打一行、对号 | 都没有 |

`trace` 也是 `ctx.emit` 发的，旁听者抛错同样冒到发跟踪点的业务代码里，比如 `Bot.receive`。

**二阶影响：一个调试插件成了整个服务的单点**。

- journal 每个事件都同步 `INSERT` 一次。库只要有一次写不进去（磁盘满、外部工具打开库持有写锁、I/O 错），**每一个**事件都会在 `_resolve` 里抛错，所有消息全停；
- `trace_file: true` 时，Print 的 `appendFileSync` 也一样；
- 报错的调用栈落在发事件的地方（`Session.loop`、`emitInbound`），看日志的人会先去查业务代码；
- 这和 CLAUDE.md 的“渠道发来的东西都要接住”正面冲突：19 号第 3 条刚把 Grants 读写库出错挡 bots 认领的路堵上，旁听层留着同样的口子，而且更大。

**三阶影响：同一件事算好几遍**。

- Cordis 交给每个 `internal/dispatch` 监听的 `args` 是**同一个数组**（第五节实测），可现在每个旁听者各拼一次 `buildDispatchLine`（读 `_hooks`、扫参数），journal、Print、Payload 还各取一次调用栈（`utils/Trace.ts:344-363`，每次 `new Error().stack` 再逐行正则）；
- 一个核心事件在 journal 加 tutorial 都开着时：事件行 2～4 次，调用栈 2～3 次；
- 四个监听开头都抄了同一句过滤：`typeof event !== 'string' || event === 'trace' || event.startsWith('internal/')`（journal `:264`、Print `:93-95`、State `:133`、Payload `:1057`）。

**改法**：`utils/Trace.ts` 已经是 journal 和 tutorial 共用的旁听工具（`buildDispatchLine`、`getCallSite` 都在这里），在这里加一个挂旁听的函数，四个旁听者都改用它。

```ts
/** 旁听交给每个监听的事件行：事件行本身，加上是哪一行代码发的。 */
export type SharedLine = DispatchLine & { site: string };

/** 一次派发只拼一次事件行。键是 Cordis 交给每个旁听者的同一个 args 数组，派发完自然释放。 */
const sharedLines = new WeakMap<unknown[], SharedLine>();

/**
 * 旁听 Cordis 的每次派发：journal 记库、tutorial 打印、拍快照、录载荷都从这里挂。
 * 旁听者跑在发事件的那一行里，Cordis 的 emit 不接异常，所以这里出错只打一行日志、不往外抛。
 * @param ctx 旁听插件的 ctx。
 * @param who 旁听者的名字，写进出错日志。
 * @param handler 拿到事件行和原始参数；跟踪点自己、Cordis 内部的事件不交过来。
 */
export function onDispatch(
  ctx: cordis.Context,
  who: string,
  handler: (line: SharedLine, args: unknown[]) => void,
): void {
  ctx.on('internal/dispatch', (mode, event, args) => {
    //G 跟踪点自己、Cordis 内部的事件不算。
    if (typeof event !== 'string') return;
    if (event === 'trace') return;
    if (event.startsWith('internal/')) return;

    //M 同一次派发，第一个旁听者拼事件行、取调用栈，后面的直接拿。
    let line = sharedLines.get(args);
    if (line === undefined) {
      const built = buildDispatchLine(ctx, mode, event, args, SHARED_VAR_MAX);
      const site = getCallSite(OBSERVER_DIRS);
      line = { ...built, site };
      sharedLines.set(args, line);
    }

    //M 旁听者出错只记一行：调试插件坏了，不能把这条消息一起拦下。
    try {
      handler(line, args);
    } catch (error) {
      const reason = textModule.getErrorMessage(error);
      console.error(`${who} 旁听 ${event} 出错，已跳过：${reason}`);
    }
  });
}
```

- `OBSERVER_DIRS` 是 `['plugins/journal/', 'plugins/tutorial/']`：两边原来各跳自己的文件夹，合起来跳两个，取到的就是业务代码那一行。只有 journal、tutorial 自己发事件时取到的位置会变（待核影响哪几个事件，估计只有 `journal/result` 这类）。
- `SHARED_VAR_MAX` 取 200：journal 的 `VAR_MAX`（`journal/index.ts:191`）和 Print 的默认 `trace_var_limit`（`tutorial/index.ts:272`）都是 200；State、Payload 原来传 1，是因为它们不看正文，多截一点不影响。用户把 `trace_var_limit` 配得比 200 大时，Print 显示会变短，可以改成取两者里大的那个。
- `trace` 的 5 个旁听照同样的写法加一个 `onTrace`（只有过滤和 try/catch，不用共享），或者和 `onDispatch` 合成一个函数用参数分两种，交给写代码的一方定。

journal 改后（`journal/index.ts:262-276`）：


Payload 的 `extractEventRefs`（`:890`）和 `onWhitelistedDispatch` 里的 `getCallSite`（`:1244`）都改成用传进来的 `line`；`PayloadItem.site` 的注释本来就写着“取自对应 journal 行的 site”（`:48`），改完才名副其实。

**F：最强的反对意见**

| 反对 | 重新评估 |
|---|---|
| 吞掉旁听者的错，bug 就藏起来了 | 不是吞：每次都打一行日志，写明是谁、哪个事件。比起现在“调试插件一坏，整个机器人停掉、报错还指向业务代码”，这是更容易查的状态。旁听者自己的测试直接调 handler，照样能测出错 |

3. `RequestEvent.ts` 删上表里的东西。剩下的等待选项：

```ts
/** 发请求时的等待选项。 */
export interface RequestWaitOptions {
  /** requestId 前缀，如 'apr'、'dec'、'cat'；不给默认 'req'。 */
  prefix?: string;
  /** 等了这么久还没回执，就在日志里报一句，接着等。 */
  warnAfterMs?: number;
  /** 不想等了就中止：撤掉回执监听，交回 aborted。要限时就传 AbortSignal.timeout(毫秒)。 */
  signal?: AbortSignal;
}

/** 没拿到回执的原因：没人接、调用方不等了、处理方抛错。 */
export type FallbackReason = 'unhandled' | 'aborted' | 'error';
```

收回执那一段从 5 行变成 1 行，`getFallback` 从 10 行变成直接 `finish({ why: reason, detail })`；函数只剩一个签名，返回类型固定是 `Promise<Asked<EventArg<ResKey>>>`。

4. 11 个测试文件里的 `onFallback` 改成读 `asked.reply`/`asked.why`，和生产代码同一个形状。

**F：反方意见**——“删了 `timeoutMs`，以后真要限时的只读请求怎么办？”

- 传 `signal: AbortSignal.timeout(毫秒)`，一行。要让处理方也停下，就把同一个信号放进请求里（exec 审命令就是这么做的，`exec/Runs.ts`），这正是 19 号说的“限时要么处理方自己做，要么调用方限时的同时让处理方也停下”；
- 两种限时（掐表、信号）合成一种，读的人只要认一个概念。

### 3. 载荷录制按引用比（结论第 3 条）

**默认配置**（`tutorial/index.ts:275-284`）：每条消息都录（`payload_record: all`），单份 256KB，单条消息 8MB，留最近 20 条。CLAUDE.md 要求教程插件一定开着，所以这是常驻开销。

**每步拷几份历史**：

- 每步的请求都带整段历史：`messages: [...this.row.messages]`（`Sessions.ts:730`）；
- 关口一 `session/before-model` 发出时，Payload 深拷一份 before（`Payload.ts:1227`）；
- 关口二 `session/after-model` 的参数是 `{ ...request, answer }`（`Sessions.ts:848`），浅展开，`messages`、`tools`、`system` 还是同一批数组；
- 关口二发出的那一刻，Payload 先给关口一补拷 after（`settlePreviousEntries` → `finalizeEntry`，`:1274-1340`），紧接着给关口二拷 before：**同一刻、同一批数组，拷了两遍**；
- 下一个同会话事件（`session/new-message`）到来时，再给关口二补拷 after；
- 合计每步 4 份整段历史，外加 4 份工具定义。

**按下标截断，先丢最新的**：

- 数组按下标从前往后拷，撞到预算就停，后面写“[已截断 剩 N 项]”（`Payload.ts:441-452`）；
- 对象按字段顺序拷，撞到预算就停，后面写“[已截断 后续字段省略]”（`:499-516`）；
- 请求对象的字段顺序是 `session, model, thinking, system, tools, messages, signal`（`Sessions.ts:724-732`），after-model 再在最后加 `answer`；
- 所以历史加工具超过 256KB 时，丢掉的是 `messages` 末尾**最新的几条**，after-model 连 `answer`（这一步模型回了什么）都会被省略。整条消息到 8MB 以后，`bucket.capped`，后面的步不再录（`:1220-1239`）。

按历史 100KB 估：一步约 400KB 以上，20 步左右到 8MB 封顶；历史一旦过 256KB，每份都截断，8 步左右封顶。`watch_think_max_steps` 的样例是 40 步（`config.example.yaml:108`），长任务正好落在录不全的区间。**实际大小待核**：本地看 `data/flow/*.payload.json` 的文件大小，数一数里面 `truncated: true` 的条目和 note 里写“超上限”的文件。

**改法**：两个模型关口的顶层数组按引用比。

- 现在改数组的监听者，都是整个换数组（`context-fit/index.ts:342`、`context-fit/Compress.ts:343`、`bots/FrontDesk.ts:349`、`:363`、`:389`）、往后 push（`progress/index.ts:337`），或者 `map` 出新数组（`file-tools/BaseTools.ts:181`）；
- 每条消息对象本身没看到有人原地改（**待核**：按 `session/before-model`、`session/after-model` 的监听逐个核一遍，原地改单条的就照旧深拷那一条）；
- 所以发出时只要留一份浅拷（每条消息的引用，几乎不占地方），补拷 after 时逐条按引用比，就知道这一步加了哪几条、换了哪几条、删了哪几条，只深拷这几条。

示意（数据形状，改前改后）：

```text
改前 before.messages = [m0, m1, …, m99]        整段深拷；超 256KB 时 m90 之后被截掉
改后 before.messages = { count: 100 }           只记条数
     diff = [
       { path: 'messages[100]', kind: 'add',    after: '工具结果：……' },
       { path: 'messages[0..60]', kind: 'remove' },   ← context-fit 压缩换掉的前 61 条
       { path: 'messages[0]', kind: 'add',      after: '（前情摘要）……' },
     ]
```

- `tools` 同样按引用比：一步里通常不变，变也是 approval 按权限过滤掉几项；
- `system` 是字符串数组，按值比；
- 关口二的 before 不用再拷：它的数组就是关口一 after 的那一批，只多一个 `answer`；
- 顺带把对象字段改成“小的先拷”：`answer`、`stop`、`model` 这些放在 `messages` 前面，单份撞上限时也不会丢掉 `answer`。

**F：反方意见**——“按引用比，看不到某个插件原地改了第 5 条消息的内容。”

- 对。所以要先核上面那条待核；核到有，就把那个插件改成换一条新对象（插件里一行），或者给那一个事件保留整段深拷。
- 就算不改，现在长会话的问题更大：它录不到最新的几条和 `answer`，等于这一步什么都看不到。
