## 三、第 1 条：同一条底线，三处各判各的

### 3.1 三个判断，两份来源

| 谁在判 | 读的是什么 | 微信联系人算什么 |
|---|---|---|
| 工具关口：`approval/index.ts:409-426`（调模型前删工具）、`:429-454`（执行前再拦） | `getSpeakerRole(row.address)`（`utils/Workspace.ts:18`）：先看地址上的 `role`，再看 `owner === false` | 地址上两样都没有，返回 `''`。`Rules.ts:55-59` 的 `toolsFor('')` 返回 `undefined`，也就是**不限** |
| 记忆：`memory/MemoryKey.ts:133-150` | 来源快照的 `snapshot.role === 'owner'`（`:139`） | 快照的 role 由 `Channels.ts:1086` 的 `resolveLegacyRole` 推出来，没写 owner 一律给 `'guest'`，所以算**外人** |
| 历史：`Channels.ts:755-771` 的 `isHistoryOwner` | 先看地址，再看快照的 role 和渠道 | 不是 http、cli，也不是 owner，算**外人** |

会话的回话地址就是渠道给的那份原样：`bots/index.ts:836` 的 `session.row.address = origin.address`。微信造这份地址时只写了 4 个字段，见 `wechat/index.ts:390`：

```ts
const address: WechatAddress = { account, chat: row.chat, name: row.name, customer: `wechat:${row.chat}` };
```

`Workspace.ts:14` 的注释写着“都没写的渠道（网页、命令行、微信）和小会话是 ''，照旧不限”。也就是说，**当初是把微信和网页、命令行归成一类“本机渠道”的**。可微信里会触发机器人的消息，全是别人发的：

- 自己发的消息会跳过：`wechat/index.ts:386` 的 `msg.from_self === true`；
- 测试里也把“微信客户”算作外人：`bots/ChannelHistoryCross.test.ts:562`。

### 3.2 现在漏在哪

- 微信联系人发一句话，起的前台会话、派出去的后台会话，用的都是这份地址；
- 工具关口不拦，所以 exec、write、edit、memory（会写记忆）、notify_user、agent_task、reply 都在；
- exec 只有“删系统、删注册表、删数据、格式化”这四样要人审（`Rules.ts:339-366` 的 `mustAsk`），别的命令交给决策模型判（待核：哪些命令会被直接放行）。

缓冲有两层，但都不是保证：

1. 微信默认只起草不发（`wechat/index.ts:10-11`、`:723`）。可 `send: true` 加“自动发”是现成的配置。
2. 记忆、历史两处已经按外人挡住了。

### 3.3 改前、改后

第一步：微信的地址写明不是本人。造地址的有 3 处：`:390`（收消息）、`:534-539`（按聊天找地址）、`:843`（客服页“让 AI 起草”）。三处合成一个函数（三处用、长得一样，照 CLAUDE.md“相似的函数合成一个”）：

```ts
/** 微信的回话地址，记在会话的 row.address 上。customer 给 memory 认客户。 */
export interface WechatAddress {
  account: string;
  chat: string;
  name: string;
  customer: string;
  /** 微信里会交给机器人的话都是联系人、客户说的，不是用户本人：固定 false。 */
  owner: false;
}

/**
 * 造微信的回话地址。收消息、按聊天找地址、客服页起草三处共用。
 * @param account 本机微信账号。
 * @param chat 聊天号。
 * @param name 聊天显示名；没有就用聊天号。
 */
function getWechatAddress(account: string, chat: string, name: string): WechatAddress {
  //M owner: false 让工具关口（approval）、记忆、历史三处都按外人算。
  const address: WechatAddress = {
    account,
    chat,
    name,
    customer: `wechat:${chat}`,
    owner: false,
  };
  return address;
}
```

改完后：

- `getSpeakerRole` 返回 `'guest'`，工具只剩白名单（`Rules.ts:30-37`）；
- `getWorkspace` 没有 `workspace` 字段，照旧落在机器人的工作区（`Workspace.ts:73-79`）。所以起草时还能读工作区里的资料，比如报价单；
- `resolveLegacyRole` 照旧给 `'guest'`，三处判断从此一致。

第二步（不急）：“这一轮是不是本人”只留一个函数，放在 `utils/Workspace.ts`，三处都调它。它要同时写清两条：网页、命令行默认算本人；其他渠道不写 owner 就算外人。

### 3.4 反方意见

- **“微信只起草，草稿要用户自己点复制，限制工具反而让草稿变差。”**
  - 起草要用的是读资料、搜本聊天，这两样还在；
  - 拿掉的是 exec、write、写记忆、通知用户、派外部任务，回一句话用不上这些；
  - 而且“只起草”只是个配置开关，不是保证。
- **“客服页上点‘让 AI 起草’的是用户本人。”**
  - 对，`:843` 那一处是用户点的；
  - 可它和联系人的消息落进的是同一场前台会话（`wechat/index.ts:191`“是同一场”）。地址要是跟着谁说话来回变，工具清单也会跟着来回变；
  - 起草的内容是联系人的对话，按外人处理更稳。
- **“老会话库里存的地址没有 owner。”**
  - 每来一句话，地址就重写一次（`bots/index.ts:836`），所以下一句就对了；
  - 对不上的只剩已经排队、还没跑的那几轮（待核）。

## 七、第 5 条：手写的“谁接”已经在漂

### 7.1 怎么查的

- 对每一份 `谁接：` 清单，取出里面列的文件；
- 再 grep 所有非测试的 `.ts`，找真正在听的文件，认四种写法：
  1. `.on('名'`；
  2. `.once('名'`；
  3. `onRequestEvent(ctx, '名'`；
  4. 名字先存进变量再用；
- 两边比对。

结果：95 份里有 5 份对不上，逐个核过以后，3 份是脚本误报（名字存进变量后再传给 `requestVoice` 一类的函数），**2 份是真的漂了**：

| 在哪 | 清单写的 | 实际 |
|---|---|---|
| `Main.ts:28-45`（ready） | 17 个，没有 context-fit | `context-fit/index.ts:285` 有 `ctx.once('ready', …)`。0.7.69 新加的“窗口没登记的启动时列出” |
| `Sessions.ts:40-58`（session/before-model） | 第 47 行写着 `context-fit/Compress.ts 的 Compress.constructor` | Compress.ts 里已经没有 `ctx.on`。0.7.69 把压缩并进了 `context-fit/index.ts:288` 的同一个监听；`358e7fa` 时 Compress.ts:75 还在听 |

两处都在骨架里，都出在同一个提交 `1bc784c`。也就是改监听的那一刻，清单就没跟上。

教程页的“谁在听（grep 现查）”这次是对的，见 `骨架逐行/Main.json` 的 `r-main-02`，里面有 context-fit。

### 7.2 改法

不改写法，只加检查。用户靠 VS Code 悬停看清单，这个习惯保留。脚本约 40 行，放 `scripts/`，挂进第 5 节的 CI。思路：

```ts
//M 每一份“谁接”清单：列的文件 和 真在听的文件 两边比。
for (const block of whoListens) {
  //M 真在听的：代码里（不算注释）出现 on、once、onRequestEvent 带这个事件名的文件。
  const actual = getListenerFiles(block.event);

  //G 清单漏了的：报出来，写明在哪一行补。
  const missing = getDifference(actual, block.files);
  if (missing.length > 0) {
    problems.push(`${block.site} 的 ${block.event} 少了：${missing.join('、')}`);
  }

  //G 清单多了的：那个文件已经不听了。
  const extra = getDifference(block.files, actual);
  if (extra.length > 0) {
    problems.push(`${block.site} 的 ${block.event} 多了：${extra.join('、')}`);
  }
}
```

事件名存在变量里的（`relay/index.ts:949-950`、`decision-map/Routes.ts:139-140`、`screen/Screen.ts:244-245`），要么在脚本里认这种写法，要么改成直接写字面量。后者正好也合 CLAUDE.md“一眼看出在调哪个事件”的意思。

### 7.3 反方意见

- **“又多一个脚本。”** 它守的是 95 份清单，而用户调试时最依赖的就是它们（`CLAUDE.md:200`“我都没法跟踪”）。清单错了比没有更糟：F12 跳过去，看到的是错的。
- **“干脆别手写，全交给教程页。”** 那样用户就得离开 VS Code 去开网页。用户的习惯是在编辑器里读，所以留着手写，配上检查。
