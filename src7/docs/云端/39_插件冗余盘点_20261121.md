2. **记忆页的“导入文档”留不留？** 它写的是 memory 的 `knowledge/` 文件夹（`web/src/Memory/MemoryPage.tsx:349`），同一页上的“存入知识库”按钮写的是 knowledge 插件（`:200`）。我推荐把“导入文档”改成建知识库文档，memory 的 `knowledge/` 文件夹只留给人直接往里丢文件。
3. **内置微信什么时候退场？**（第三轮第 1 条，还挂着）推荐不变：外置微信在 programs 下跑满一周、没退回内置的，就删内置的 `wechat-kefu`。

- **frpc 不并进 programs**。看着都是“管一个外部 exe”，但生命周期正好相反：programs 的子进程跟着 jmbots 一起关（`programs/Host.ts:549`），frpc 是脱离出去的独立进程（`frpc/Process.ts:313` 的 `detached: true`），换后端版本时外网不能断。programs 还要求子进程打就绪行（`programs/Protocol.ts:185`），原版 `frpc.exe` 不会打。硬并要么写包装程序，要么给 programs 加脱离模式，都比现在重。frpc 要改的是写死的本机默认值，见第 6 节第 1 条；

## 二、证据和方案

### 0. 动手前先问自己的三个问题（方法 C）

**问题一：插件这一轮多了两个，该不该多？**

- knowledge：用户叫得出名字（“知识库”），有自己的页面 `/knowledge/`，该单独存在；
- frpc：用户叫得出名字（“外网隧道”），有自己的页面 `/frpc/`，和 programs 的模型不同（见“不建议动的”），也该单独存在。

所以问题不是插件个数，而是新插件和老插件的**边界**画在哪。这一轮就扫边界：新插件写到了谁的目录、谁的工具名、谁的概念上。

**问题二：怎么找边界上的重叠？**

三个角度：
- 同一个目录有没有两个插件在写或扫（找到 `knowledge/`，第 1 节）；
- 模型手里同一类能力有几个工具（找到三个搜知识库的入口，第 1、2 节）；
- 同一张对照表写了几遍（找到 tutorial 的七张，第 3 节）。

**问题三：重复的那份有没有存在的理由？**（方法 F 的反面检验）

- memory 收知识库镜像：有一个**意外的好处**：kb 自己只会按字匹配（`knowledge/Store.ts` 的 `LIKE`），镜像被 memory 收进去以后，等于白得了语义检索。所以第 1 条不能简单地“挪走就完”，要先问用户要不要这份语义检索（要用户定第 1 件）；
- `memory` 工具的三个旧 action：注释写的是“兼容”（`memory/index.ts:376`），可模型看不到它们，兼容的对象只剩历史里的旧调用（待核）；
- DataFlow 的长解释：比 journal 的短名好懂，有价值；但应该写进 journal 那一张，而不是另起一张、还把 journal 的盖掉。

### 1. 两个“知识库”（结论第 1 条）

**1.1 两套各是什么**

| | memory 的“知识库” | knowledge 插件的“积木知识库” |
|---|---|---|
| 是什么 | 运行时 `knowledge/` 和 `bots/<机器人>/knowledge/` 下的 `.md`、`.txt`，切成 800 字一段送进 Rust 检索服务（`memory/Store.ts:4`、`:154-157`） | SQLite 表 `kb_dirs`、`kb_docs`、`kb_tags`、`kb_doc_tags`、`kb_links`，人在网页上或用 `kb_save` 写 |
| 怎么更新 | 每次搜之前最多 30 秒扫一次（`Store.ts:33`、`:148-149`），按修改时间和大小比 | 写文档时同步更新，再导出磁盘镜像 |
| 给模型的工具 | `memory_search`（`sources` 含 `knowledge`，`memory/Search.ts:260-264`）；旧的 `memory` 工具 `action: 'knowledge'`（`memory/index.ts:142`，模型看不到，见第 2 节） | `kb_search`、`kb_disambiguate`、`kb_save`（`knowledge/Tools.ts:70`、`:237`、`:439`） |

**1.2 撞在哪**

- **同一个目录**：knowledge 的镜像默认就是 `<运行时>/knowledge`（`knowledge/index.ts:75`），每篇文档写成 `<日期>/<id>_<标题>/content.md` 加 `meta.json`（`DiskMirror.ts:129-151`）。memory 扫 `<运行时>/knowledge/**/*.{md,txt}`（`Store.ts:154`、`:256-259`），镜像的 `content.md` 全被当成资料文件收进去，标题取文件名（`Store.ts:192` 的 `title: path.basename(file)`），所以每篇都叫 `content.md`；
- **镜像本来不是给 memory 的**：`DiskMirror.ts:4` 写的用途是“供外部算力机只读协同与灾难恢复”，说明.md、组块阅读 12 里都没提 memory 会扫它。这是意外，不是设计；
- **结果里重复**：`kb_search` 带关键词时，先查本库，再经 `searchMemoryBridge` 问 memory 的 knowledge 范围，最多补 4 条，标成 `M1.`、`M2.`（`knowledge/Tools.ts:164-171`）。memory 那边命中的，很可能就是这篇文档自己的镜像。HTTP 的 `GET /api/knowledge/search` 也一样（`Routes.ts:456`）。实际出现的比例**待核**（本地跑一次 `kb_search` 就能看到）；
- **反方向也挡住了**：FolderSync 专门跳过镜像目录（`FolderSync.ts:234-236`）。因为镜像目录就是整个 `knowledge/`，记忆页“导入文档”写进去的文件，就算用户把 `knowledge/` 配进 `localWatchDirs`，也永远进不了 kb；
- **模型怎么选**：三个入口都挂在前台和后台会话上（`memory/Search.ts:280`、`knowledge/Tools.ts:74`、`memory/index.ts:150`）。系统提示词只写了“memory_search（搜往来、渠道、知识库）”（`prompts/zh/10_机器人.md:44`），没提 `kb_search`。

**1.3 三版方案**

| 方案 | 做什么 | 代码 | 代价 |

### 2. memory 工具里藏着的三个 action（结论第 2 条）

**2.1 一个工具两份定义**


模型每一步看到的都是后一份（只有 list、read、write、delete）。可是：
- `run` 里那三个 action 的分支还在：`:345-353`（外人走 search、history）、`:377-381`（search 搜卡片、技能、知识库）、`:384`（history、knowledge 交给 `cite`）；
- `cite()`（`:318-337`）只被这一处调；
- 教程页插件地图读的是登记时那一份，显示的参数和模型实际看到的对不上。

**2.2 改法**

```ts
// 改后：登记时就是模型看到的样子；before-model 里那段替换删掉
ctx.tools.register({
  definition: {
    name: 'memory',
    description: FILE_DESCRIPTION,
    parameters: FILE_PARAMETERS,
  },
  sessionKinds: ['front', 'work'],
  run: (args, session) => this.run(args, session),
});
```

`run` 里删掉三个 action 的分支，`cite()` 一起删。外人（`!access.full`）原来走 search、history 的那条路，改成直接抛“私人记忆文件仅本人可访问”，他们要搜往来用 `memory_search`，那边已有同样的权限口径（`canQueryChannel`）。

动手前要核一件事：最近一周有没有会话还在调 `memory` 工具带这三个 action（模型照历史里的旧调用学）。journal 的 `journal_lines` 能查，待核。
