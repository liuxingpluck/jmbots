## 一、一页结论

**判断**：事件化的方向是对的，但现在的底座**重新造了一遍 Cordis 已经有的东西**。

Cordis 的 `ctx.serial(事件名, 参数)` 的行为（`cordis/lib/index.js:754-760`）：

- 按挂载先后依次调用监听者，每个都 await；
- 返回第一个不是 undefined、null、false 的返回值；
- 没人回答就返回 undefined；
- 返回值的类型照事件声明推出来（`events.d.ts:15`）。

`RequestEvent.ts` 为了“发请求、等回执”另外做了好几样东西：请求号、回执事件、`handled` 标记、等回执的定时器、四种退回原因。这些 `serial` 的返回值已经全有了。

多出来的这一层，带来几个二阶、三阶影响：

- 每个能力要声明两个事件、两个信封类型；
- 每个调用点要写一个“退回值”，还要靠 `requestId === ''` 这样的魔法值认出“没人回答”；
- 出错时调用栈丢了；
- 流水把请求和回执各记一行。看轨迹这个动作本身，就会往轨迹的取数窗口里塞行。

## 二、证据和方案

### 0. 现在一次“请求—回执”要做什么

`requestEvent`（`utils/RequestEvent.ts:76-148`）每调用一次，依次做这些事：

1. 生成请求号：`prefix_ + randomUUID`；
2. 在回执事件上挂一个临时监听，按请求号认自己的回执；
3. 起一个 `timeoutMs` 的定时器；
4. 发 `serial(请求事件)`，等所有监听者跑完；
5. 跑完没人把 `handled` 置成 true，就退回 `unhandled`。

`onRequestEvent`（`:154-186`）在处理的一方做这些事：

1. 先置 `handled = true`；
2. await 业务函数；
3. 带上请求号，`emit(回执事件)`；
4. 抛错时，有 `onError` 就发一个失败回执，没有就把错误抛给 `serial`。

**关键事实**：处理一方的监听是 `async`，而且会 await 完业务函数才 emit 回执（`:172-178`）。`serial` 本身又会 await 每个监听（Cordis 源码 `:756-758`）。所以回执**一定在 `serial` 返回之前就发出了**。也就是说，“回执事件”和“serial 的返回值”在时间上完全重合，前者是多出来的一层。

另外核过：8 个回执事件，除了发请求的那一方自己挂的临时监听，没有任何别的监听者（主题 1 第 2 节的事件盘点）。所以删掉回执事件，不会影响任何第三方。

| 请求事件 | 回执事件 | 处理的一方 |
|---|---|---|
| `base/request` | `base/result` | `base-bridge/index.ts:92` |
| `decision/judge` | `decision/judge-result` | `decision/index.ts:140` |
| `feishu/send-file` | `feishu/send-file-result` | `feishu/index.ts:545` |
| `http/request` | `http/result` | `http/index.ts:159` |
| `journal/request` | `journal/result` | `journal/index.ts:417` |
| `model-catalog/request` | `model-catalog/result` | `model-catalog/index.ts:149` |
| `progress/request` | `progress/result` | `progress/index.ts:282` |
| `usage/list` | `usage/list-result` | `usage/index.ts:163` |

### 1. 改用 serial 的返回值（结论第 1 条）

**改前**，settings 核对模型（`settings/index.ts:189-206`）：

```ts
const lookup = { action: 'find', model } as const;
const options = {
  timeoutMs: CATALOG_TIMEOUT_MS,
  onFallback: () => ({ requestId: '' }),
};

//M 通过事件核对模型。没有应答时沿用只查供应商的行为。
const result = await requestEventModule.requestEvent(
  this.ctx,
  'model-catalog/request',
  'model-catalog/result',
  lookup,
  options,
);
if (result.requestId === '') return;

//G 收到明确回执时，未找到的模型仍回 400。
if (result.info === undefined) throw new failureModule.Failure(400, `模型清单里没有 ${model}`);
```

**改后**：

```ts
//M 问模型清单这个模型在不在；没挂 model-catalog 时没人回答，只查供应商就算过。
const found = await this.ctx.serial('model-catalog/find', model);
if (found === undefined) return;

//G 清单里明确没有这个模型 → 400。
if (found.info === undefined) throw new failureModule.Failure(400, `模型清单里没有 ${model}`);
```

**处理的一方，改前**（`decision/index.ts:138-147`）：

```ts
super(ctx, 'decision');
onRequestEvent(ctx, 'decision/judge', 'decision/judge-result', async (request) => {
  const judgement = await this.judge(request);
  const out: Omit<DecisionJudgeResult, 'requestId'> = { verdict: judgement.verdict, reason: judgement.reason };
  if (judgement.score !== undefined) out.score = judgement.score;
  return out;
});
```

**改后**：

```ts
//M 有人要判断一道是非题：交给 judge，返回值就是答案（serial 拿到第一个非空的返回值就停）。
ctx.on('decision/judge', (input) => this.judge(input));
```

**事件声明，改后**：一个事件就够了，类型照返回值推出来：

```ts
declare module 'cordis' {
  interface Events {
    /**
     * 判断一道是非题，交回 allow / deny / unsure。
     * 接的：src7/plugins/decision/index.ts 的 Decision.judge。没挂 decision 时 serial 返回 undefined。
     */
    'decision/judge'(input: JudgeInput): Promise<Judgement>;
  }
}
```

**几个细节**：

- **多个处理方、各管一部分**（原来 `filter` 的用法）：管不着的监听者 `return undefined`，`serial` 就接着问下一个。和原来“不置 `handled`”的效果一样。
- **超时**：调用方真要限时，就把 `signal` 放进参数，处理方照常用它中止。base 自己已经有 15 秒的超时（`base-bridge/index.ts` 的 `TIMEOUT_MS`）。外面再套一层“等回执的定时器”是重复的，还会引出第 3 节那种状态对不上。
- **出错**：处理方抛错，`serial` 就把错抛给调用方，调用栈原样保留。原来的做法是把错误变成 `onFallback('error', 一句话)`，调用方拿到的只是一个退回值，查问题时看不到栈。这也符合 CLAUDE.md“内部漏传……由正常执行错误直接暴露，不静默补救”。
- **名字**：回执没了，`xxx/request` 里那个 `action` 字段可以拆成几个具体的事件，比如 `model-catalog/find`、`journal/message-lines`。一个事件一件事，类型也不用写成联合类型。拆不拆可以以后再定，不拆也能用 `serial`。

**省多少**：

- `RequestEvent.ts` 整个文件：186 行；
- 8 对事件里的回执声明，加上请求和回执的信封类型：约 150 行（`journal/index.ts:41-72`、`base-bridge/index.ts:26-49`、`decision/index.ts:32-35` 和 `:67-75`、`feishu/index.ts:82-84` 和 `:386-400` 等）；
- 14 个调用点：每处少写 `options`、`onFallback` 和魔法值判断，约 5–10 行。

**F：最强的反对意见**

| 反对 | 重新评估 |
|---|---|
| 用户 #113 原话就是“等别人回一个事件” | 用户要的是解耦：“自己不管别人怎么做、做多久”。用 `serial` 的返回值，调用方照样不知道谁在回答、怎么做的，解耦没少。少的只是一个没有第三方在听的回执事件。所以列为“要用户定的”，不擅自改 |
| 流水里看不到回答了：`internal/dispatch` 只带参数，不带返回值 | 原来的回执行，也只是把 vars 截短了记下来。真要看的回答（比如决策模型的结论），处理方本来就发 `trace`，`decision` 插件就有。取数类的回答（流水行、用量行）记进流水反而有害，见第 4 节 |
| 处理方卡住了，调用方就一直等 | 现在会卡的只有发网络请求的几家，它们自己都带了超时。要兜底，就在调用点用参数里的 `signal`，不用全局的回执定时器 |
| `channel/reply` ↔ `channel/replied` 也是这个模式（`Channels.ts:754` 起），要不要一起改？ | 不一样：`channel/replied` 有第三方在听（bots、web-api，见主题 1 的事件盘点），它是一个真正的通知。可以保留 `channel/replied` 当通知，发请求的一方改拿 `serial` 的返回值。待核：飞书发消息的监听会不会 await 到发完，这决定能不能拿到返回值 |

### 2. 三种关系，三种写法（结论第 2 条）

| 关系 | 写法 | 例子 |
|---|---|---|
| 必须有（写在 `inject` 里） | 直接调服务，F12 能跳到实现 | `ctx.resources`、`ctx.sessions`、`ctx.tools`、`ctx.http`、`ctx.bots`；exec 调 `ctx.approval.review` |
| 可选、不在乎谁来做 | `await ctx.serial('名字', 参数)`，undefined 表示没人管 | 决策模型、基地、模型清单、流水、用量、进度、飞书发文件 |
| 通知（发生了什么） | `ctx.emit` | `approval/decided`、`session/change`、`channel/replied`、`progress/update` |

**照这条规则，现在要改的地方**（数据来自主题 1 第 2 节的表）：

- 可选、现在却走服务的，迁到事件：
  - `ctx.get('base')` 7 处：settings、web-api、base-bridge 的 Notify 和 UpdateWatch、memory 的 Recall（其中 Recall 的 2 处按主题 4 第 1 条直接删掉）；
  - `ctx.get('decision')` 3 处：approval、progress、bots 的 FrontDesk；
  - `ctx.get('feishu')` 1 处：relay；
  - `ctx.get('modelCatalog')` 2 处：bots 的 Dispatch。
- 必须有、现在却走事件的，改成直接调：settings 请 http 关监听。settings 的 `inject` 里写了 http，却走 `http/request`，还带 10 秒超时（`settings/index.ts:289`、`:361`）。
- 迁完以后，decision、base、usage、journal、progress、model-catalog 就不用再挂成 Cordis 服务了：没人 inject 它们。这几个插件的 `declare module 'cordis' { interface Context { … } }` 和 `extends cordis.Service` 都可以去掉，插件内部用普通 class。

**二阶影响**：

- `ctx.get('decision') as decisionPlugin.Decision | undefined` 这样的强转一起消失（13 处 `ctx.get` 里有 6 处带强转）；调用方也不用再 `import type` 对方的 class。
- 主题 2 第 5 节说的“服务方法里 `this.ctx` 是调用方的 ctx”这个坑，碰到的服务从十几个降到 5、6 个。
- 主题 1 第 4 条说的“`model-notes` 和 `model-catalog` 被 Dispatch 拼着用”：迁到事件以后，Dispatch 只发一个 `model-catalog/levels` 之类的事件，拼接留给模型那边做，正好和主题 1 的合并方向一致。

**F：反方意见**——“规则一多，又是一层抽象”。

- 重新评估：现在实际上已经有两套写法了，只是没有规则说什么时候用哪套，才长出了双入口。这条规则不新增写法，只说清已有的写法什么时候用。
- 可以写进 CLAUDE.md“插件之间尽量只靠事件”那条的下面，作为它的细则（要本地 AI 改）。

### 3. 会改东西的请求不能“超时当没做”（结论第 3 条）

- `settings/index.ts:280-298`，请 http 关监听：
  - 等 10 秒没回执，打一行 trace“HTTP 关闭未获回执，继续重启”，然后接着重启；
  - 但没回执可能只是还没关完。这时新进程起来抢端口，旧的监听还没放，会撞上 EADDRINUSE（待核：基地是先杀旧进程再起新的，还是反过来）。
- 同类的还有：`progress/request` 的 act（停一场会话）、`base/request` 的 POST（`/update/apply`）、`feishu/send-file`。
  - 超时退回后，调用方以为没做，可能再做一次：重复发文件、重复申请换版；
  - 也可能告诉用户“失败了”，其实已经成功了。
- 改成 `serial` 的返回值后，只剩两种结局：拿到结果，或者处理方抛错。不再有第三种“不知道做没做”。真要限时，限时的那一刻也要中止处理方（传 `signal`），不能只是调用方不等了。

### 4. 流水把“看流水”也记进去（结论第 4 条）

- **流水记什么**：`journal/index.ts:185-186` 在 `internal/dispatch` 上，除了 `trace` 和 `internal/*` 以外的每个事件都记一行，vars 截到 `VAR_MAX`。
- **谁会去取流水**：
  - 教程页取轨迹：`tutorial/Files.ts:252`、`tutorial/index.ts:596` 发 `journal/request`；
  - 聊天页取追溯：`web-api/Trace.ts:240` 发 `journal/request`，`:247` 发 `usage/list`；
  - 每发一次，流水多 2 行（请求和回执各一行），追溯一次多 4 行。
- **怎么按消息取**：`journal/index.ts:251-255` 先找到这条消息 `web-api/received` 那一行，再取 `id >= 起点` 往后的 `limit` 行，然后交给调用方去筛。
- **三阶影响**（待核实际规模）：
  - 页面每轮询一次，就往表尾写几行；
  - 对一条较早的消息来说，“它之后的 N 行”里，越来越多是别人、包括调试页自己写的行；
  - 一旦超过 `limit`，这条消息后半段的轨迹就取不到了。
  - 越想看清一条消息，看的次数越多，它的轨迹反而越可能被截断。
- **改法**：
  1. journal 跳过取数事件：名字以 `/request`、`/result`、`/list`、`/list-result` 结尾的不记。做完第 1 条以后，只剩请求事件，按名字跳过就行。
  2. 取轨迹的 SQL 加上过滤：`WHERE id >= ? AND (message_id = ? OR session_id IN (这条消息涉及的会话))`。这样窗口里只有这条消息的行。

### 5. 调试可读性（结论第 5 条）

- **用户在意的**：用户 11-07 调试时说过：“由于 receive 函数本身也是传入的参数，我都没法跟踪。”README 也写着：“主线全是直接调用，按 F12 能一路跳到实现；事件只留给插件接进来。”
- **事件化在这上面付的代价**：插件之间每多一处事件，F12 就少一处能直接跳到的地方。
- **已经有的补救**：流水里每一行事件都记了“听的人”（`listeners`，`utils/Trace.ts` 的 `dispatchLine`），教程页能看到运行时是谁接的。
- **还缺的一样**：写代码时看不到谁接。补法是：每个 `interface Events` 里的事件，JSDoc 最后一行写“接的：文件 的 类.方法”。通知类的写“听的：插件名、插件名”。在调用点 F12 跳到事件名，就能看到这一行。
- 这件事可以由主题 3 说的检查脚本顺带查：事件声明里没写“接的/听的”就报出来。

## 三、怎么核的（复查用）

- **Cordis 的行为**：在草稿目录 `npm pack cordis@4.0.0-rc.12`，解开后读：
  - `package/lib/index.js:754-760`（`serial`）、`:761-766`（`bail`）；
  - `:692-694`（`isBailed`：不是 null、false、undefined 才算回答了）；
  - `package/lib/events.d.ts:15`（`serial` 的返回类型是 `Promisify<ReturnType<Events[K]>>`）。
- **谁发请求、谁接**：用 node 脚本扫 `requestEvent(` 和 `onRequestEvent(` 的多行调用，得到 14 个调用点、8 个处理点。
- **回执有没有第三方在听**：同一个事件盘点脚本数 `.on('xxx/result'`，结果是 0。
