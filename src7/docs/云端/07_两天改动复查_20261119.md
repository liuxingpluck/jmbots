## 二、证据和改前改后

### 1. 拆文件的对照：没有发现行为变化

**做法**：取拆分前的旧文件（`git show <提交>^:<旧路径>`）和拆分后的新文件，按方法名逐个抽出函数体，去掉注释、统一空白，再一对一做 diff，不看 diff 统计。拆出来的小函数，和旧函数里对应的那一段逐行对上。飞书那部分交给一个子代理逐分支对照，我抽查了它的关键结论。

**Dispatch 第一次拆分（e153ed5，抽出 DispatchTools）**：只有 `hand` 里一段 16 行，挪成了 `getPlan`（`DispatchTools.ts:179`），内容一字不差，调用位置也在原处。

**Dispatch 第二次拆分（150ca3a，抽出 Claim、Recall、Results）**：

- `acceptResult`、`claimChannelMessage`、`finishChannelFront`、`drain` 里抽出的 `getResultItem`（`DispatchResults.ts:270`）、`getClaimItem`、`persistClaim`、`getClaimRecord`、`recordChannelOutcome`（`:600`）、`startQueuedUser`（`:881`），和原来内联的代码逐行相同。事务里先存、抛错时还原内存的写法也原样保留了。
- 挂监听的先后：旧的是 DispatchTools → `session/change` → `ready` → `channel/recall` → `channel/reply`。新的 `Dispatch.ts:51-62` 先 `new DispatchTools`，再 `results.listen()`（前两个），再 `recall.listen()`（后两个），顺序一致。`onChannelJudgeAllow` 回调挪到了 `DispatchClaim.ts:19`，挂的时机没变。
- `onChannelRecall` 拆成了三段（`DispatchRecall.ts:108`、`:130`、`:192`、`:233`）。旧代码里有一个变量 `matchedAuthorized`，初值是 `isOwner`，三段扫描都会往里写。新代码改成三段各回一个布尔值，最后再和 `ownerRecall` 合起来。**用方法 F 反查**：如果旧变量在三段中间被读过，拆开就会出错。查下来，它只在最后一个 `if` 里读，所以两种写法等价。三段里单独调的 `rememberRecalled` 也都还在原位。

**飞书入口拆分（e153ed5）和“接住前半段报错”（150ca3a）**：

- `handleInboundMessage` 拆成了 12 个方法。提及、认人认群、投递对象、丢弃分支、附件、拼标准消息、撤回分支、`serial('channel/message')` → `markSeen` → 流水 → 撤表情，这些的先后都一致。外层 `try` 的范围也没变。

  - **待核**（极端情况）：配置的群或流水里有一条 chatId 为空串、而名字刚好对上时，旧代码会接着往后面的来源找，新代码会直接返回一个 chatId 为空的地址（`Reply.ts:355-358`）。正常数据碰不到。

**以前就有、这次没引入的（只记一笔）**：`Inbound.ts:736` 的 `serial('channel/message')` 在 `markSeen` 前面。如果有监听者抛错，飞书重推时会把同一条再分发一遍。bots 有 `sourceClaims` 按认领键去重，会话不会重复开，可其他监听者（approval、memory 渠道索引、web-api）会再收到一次。

### 4. 第 3 条：18 处“结果不确定”，三种写法、两种规则（f100372）

**现状**：`requestEvent` 退回的原因有四种：`unhandled`、`timeout`、`aborted`、`error`（`RequestEvent.ts:13`）。退回值由调用方的 `onFallback` 拼出来，结果里不带原因，所以每个调用点只好自己记下“这次是不是超时”：

| 写法 | 在哪里 |
|---|---|
| 比对哨兵字符串：`if (reply.error === uncertain)` | `progress/index.ts:551`、`:990`，`progress/Review.ts:336`，`settings/index.ts:177`、`:359`，`web-api/index.ts:863`，`relay/index.ts:953`，`assist/Reminders.ts:355`、`:400`，`base-bridge/UpdateWatch.ts:262` |
| 闭包里改标志：`let timedOut = false` | `feishu/cards/Cards.ts:389`、`:434`，`relay/index.ts:1387`，`relay/AgentTasks.ts:47`，`screen/Screen.ts:722` |
| 模块常量加 `getDelivery` | `decision-map/Routes.ts:366` |
| 除 `unhandled` 外都算不确定 | `approval/Outbound.ts:503`、`:536`，`assist/index.ts:304` |

**规则不一（方法 F）**：只认 `timeout` 的那 16 处有一个隐含的假设：“对方抛错，就是没做”。可抛错可能发生在做到一半的时候。`approval/Outbound.ts` 和 `assist/index.ts` 明确不信这个假设：除了 `unhandled`，都按不确定处理。两种规则并存，以后新加一个调用点照着抄，抄到哪种算哪种。

还有更深一层，**待核**：`bot/request` 配了 `onError`（`bots/index.ts:395-399`），处理时抛的错会变成一个正常回执 `{ ok: false, error }`，根本不会走退回。所以 `settings` 的 add、`progress` 的 hand、`web-api` 的 save-file，这几件会改东西的事如果做到一半抛错，调用方看到的是“明确失败”。要不要把这种情况也标成不确定，得在接活的那一方定。

**改后示意**

```ts
// utils/RequestEvent.ts：requestEvent 里四处 finish(options.onFallback(...)) 改成同一个函数
const fallBack = (reason: FallbackReason, detail?: string): void => {
  const result = options.onFallback(reason, detail);
  //M 退回值带上原因，调用方不用再比字符串、记标志。
  finish({ ...result, fallback: reason });
};

/**
 * 会改东西的请求，等不到回执时算不算“结果不确定”。
 * 只有“没人接”能确定没做；超时、出错、中途喊停时，对方可能已经做了。
 */
export function isUnsure(reply: { fallback?: FallbackReason }): boolean {
  if (reply.fallback === undefined) return false;

  return reply.fallback !== 'unhandled';
}
```

### 5. 第 4、5 条：发件的等待时间，和“先落盘再发”的三套写法

#### 5.1 等待时间一层套一层

| 层 | 位置 | 数字 |
|---|---|---|
| assist 等提醒发完 | `assist/index.ts:304` | 95 秒 |
| └ Outbound 读提醒行 | `approval/Outbound.ts:225` | 1 秒 |
| └ Outbound 等内置渠道发完 | `approval/Outbound.ts:536` | 90 秒 |
| 网页、客服页等确认结果 | `approval/ChannelSend.ts:49`、`programs/ChannelSend.ts:266` | 105 秒 |
| └ Outbound 重读外置草稿 | `approval/Outbound.ts:316` | 6 秒 |
| └ Outbound 等外置程序发完 | `approval/Outbound.ts:503` | 95 秒 |

现在的数是对的：95 > 1 + 90，105 > 6 + 95。可这层大小关系哪里都没写下来。

**三阶影响**：哪天有人把渠道的 90 秒改成 120 秒，assist 会先在 95 秒时把提醒记成 uncertain；Outbound 到 120 秒时收到回执，又把 `approval_outbound` 记成 sent。提醒列表显示“不确定”，客服页显示“已发”，本人去核对时看到两个答案。

**改后示意**

```ts
// approval/Outbound.ts 顶上
/** 读外置草稿最多等多久。 */
export const DRAFT_WAIT_MS = 6000;
/** 内置渠道发一条最多等多久。 */
export const CHANNEL_WAIT_MS = 90_000;
/** 外置程序发一条最多等多久。 */
export const PROGRAM_WAIT_MS = 95_000;
/** 外层比里层多留的时间：里层先给出结果，外层才不会先记成“不确定”。 */
const MARGIN_MS = 4000;
/** 到点提醒：读提醒行 1 秒，加内置渠道发送，再加余量。assist 等 approval/reminder-sent 用。 */
export const REMINDER_WAIT_MS = 1000 + CHANNEL_WAIT_MS + MARGIN_MS;
/** 网页和客服页等确认：重读草稿，加外置发送，再加余量。 */
export const CONFIRM_WAIT_MS = DRAFT_WAIT_MS + PROGRAM_WAIT_MS + MARGIN_MS;
```

算出来正好是现在的 95 秒和 105 秒，行为不变。**代价**：assist 和 programs 要从 approval 引一个常量。它们本来就要引 approval 的事件类型，这不算多一层依赖；仓库外的插件不能 import，照事件声明里写的秒数用就行。

#### 5.2 三套“先落盘再发”能不能合一

| | 先落什么 | 怎么发 | 等不到回执 | 重启时 |
|---|---|---|---|---|
| Outbound（主动发件） | `approval_outbound` 一行：waiting → sending → 终态 | `channel/send` 或外置程序，带固定 `send_id` | 记 uncertain，只核对、不重发 | `recover`（`Outbound.ts:618`）：sending → uncertain |
| 到点提醒 | `assist_reminders` 一行：pending → sending → 终态 | 交给 Outbound | 记 uncertain | `start`（`Reminders.ts:175`）：sending → uncertain |
| 决策图 | 图节点和历史（`Store`） | 投给 relay 收件，按节点号或“节点号#留言号”去重 | 回 `delivery.error`，中控可以轮询 `/changes` 补看 | 不用管：图是事实，收件丢了可以轮询 |

**方案对比（方法 C、F）**

- **A. 抽一个通用 Outbox 类，三处共用。** 最强的反对理由：三者护的是不同的东西。Outbound 护“本人批准过的这段原文只发一次”；提醒护“到点”；决策图护的是“中控别漏看”，而且有轮询兜底，根本不需要发件账。硬并成一个类，等于给决策图加一本用不上的账，正是用户说的“过度抽象”。**不推荐。**
- **B. 维持现状。** 代价是提醒和 Outbound 两本账记的是同一次发送：同一个 sending，两处各标一次 uncertain。重启时还有一个误判：如果 assist 已经占了位，但还没把活交给 Outbound 就退出了，这条提醒其实没发，重启后也会被标成“不确定”，要本人去核对一条根本没发的消息。
- **C（推荐）. 只去掉重复的那一半。** 提醒表只管排期，“发没发出去”以 Outbound 为准。重启时把卡在 sending 的提醒再交一次 `approval/reminder-send`。Outbound 用 `assist-reminder:<编号>` 算出固定的发送号（`Outbound.ts:237`，`prepareChannel` 里按它取回原意图），已经占过位的只交回原来的结果，不会重发。

**改后示意（C）**

```ts
// assist/Reminders.ts:171 start，改前
const sql = "UPDATE assist_reminders SET state = 'uncertain', reason = ? WHERE state = 'sending'";
this.db.query(sql).run(UNCERTAIN);

// 改后：drain 循环体里“发一条、存回执”的那段抽成 deliver(row)，重启和到点共用
//M 上次停在 sending 的，交回 Outbound 再问一次：固定发送号去重，发过或在途的只交回原结果，不会再发。
const stuckSql = "SELECT * FROM assist_reminders WHERE state = 'sending'";
const stuck = this.db.query<Row, []>(stuckSql).all();
for (const row of stuck) {
  void this.deliver(row);
}
```

`deliver` 要用表里已经冻结的 `send_text`。不能先把行改回 pending 再走 `drain`：`drain` 的 SQL（`Reminders.ts:544`）会重新拼一次“补发提醒（原定……）”前缀，正文一变，摘要就对不上，`prepareChannel` 会回 409。

#### 5.3 推演 C 的边界（方法 F）

- Outbound 已经占位（state 是 sending 或终态）：`confirm` 直接交回原记录（`Outbound.ts:430`），不重发。结果和现在一样。
- Outbound 还没有这一行（assist 占位后、交给 Outbound 前就退出了）：这次会真的发出去，现在则是记“不确定”。这正是 C 要修的。
- Outbound 这一行还是 waiting（准备了、还没确认就退出了）：10 分钟内重启就照常发；过了 10 分钟会回“待确认意图已过期”，提醒记成 failed，意思是“没发”，也是对的。
- 两个插件的 `ready` 谁先跑（**待核**）：assist 先问时，Outbound 那一行可能还是 sending，交回的回执是空的，就走 `UNKNOWN`，记成 uncertain，和现在一样。Outbound 先跑 `recover` 时，assist 拿到的就是 uncertain。两种先后都不会重发。

#### 5.4 顺带看到的（不进一页结论）

- 提醒走 Outbound 时，`sendReminder`（`Outbound.ts:223-252`）先 `prepareChannel`，再拿自己刚读到的摘要去 `confirm`。所以对提醒来说，“核对展示过的摘要”这一步永远成立；真正的批准是建提醒时那张确认卡。Outbound 在这里只是一本带去重键的发件账。这样用没问题，可 `sendReminder` 的注释最好写明“批准来自提醒确认卡，摘要核对对提醒不起作用”，免得读的人以为这里还有第二道关。
- `Outbound.notify`（`:629-660`）用 `ctx.get('feishu')` 直接调 `feishu.sendText`（`:656`），不符合“插件之间尽量只靠事件”。另外它只在外置程序发件结果不确定时提醒本人（`Outbound.ts:573` 的 `row.program !== DIRECT_PROGRAM`）。主动发件和提醒结果不确定时，本人收不到提醒，**待核**是不是有意的。
- `approval/ChannelSend.ts:45-61` 的 `requestOutbound` 和 `programs/ChannelSend.ts:264-276` 几乎一模一样：都是 105 秒，退回写法相同，只有报错文字差几个字。等第 4 条把等待时间收拢以后，可以一起合成一份。
- 决策图的 `decision-map/upsert`、`decision-map/status`（`Routes.ts:172-189`）是 async 监听，`store.put` 校验不过会抛错。现在仓库里没人发这两个事件，等以后有插件发了，抛错会变成一个没人接的 rejection（**待核** Cordis 对 async 监听抛错怎么处理）。
