## 一、一页结论

**判断**：这三件事有同一个毛病：**同一件事有一条新路、一条旧路，新代码随手挑一条。**

- 建表：db 插件有带版本的迁移账本，13 个插件照旧自己 `CREATE TABLE IF NOT EXISTS`。账本建好以后新写的工作决策，又回到旧路，手写查列、补列；
- 调试记录：采集已经收拢成 `utils/Trace.ts` 一个入口，可三份记录之间仍然按“时刻差 50 毫秒以内”来猜谁对谁；
- 配置：Cordis 4 自带“插件导出 `Config`，挂载前自动校验”，没人用；每个插件手写校验，一个键要写 4 到 6 遍。

成熟系统的做法是**只留一条路，而且让这条路就是最省事的那条**。

## 二、借的是哪几样（方法 E）

| 别处的做法 | 解决的是什么 | 对应 jmbots 的哪里 |
|---|---|---|
| Django 的 migrations、Rails 的 `db/migrate`、Android Room 的 `Migration(1, 2)` | 表结构只能经一条带版本的路改；“表在不在”和“列对不对”分开管 | 第 1 条：db 插件的 `ctx.db.migrate`（已有，带 `adoptColumn`），对面是 13 个插件里的 `CREATE TABLE IF NOT EXISTS` |
| 绞杀者模式（Strangler Fig） | 旧系统不一次重写，新代码先走新路，旧的碰到哪块换哪块 | 第 1 条第二步：旧表碰到再迁 |
| OpenTelemetry 的 trace id、span id；Kafka 的 offset；数据库 WAL 的日志序号 | 同一件事的多份记录靠源头发的编号连起来；时间戳只用来显示，不用来配对 | 第 2 条：`Trace.ts` 已经是唯一的采集入口，缺的只是编号 |
| Koishi 的 Schemastery（控制台照 schema 自动画配置表单）；VS Code 的 `contributes.configuration`（设置页照 JSON Schema 生成）；Home Assistant 的 config flow | 配置的形状、默认值、说明只写一次，校验、表单、文档都从这一份来 | 第 3 条：Cordis 4 的 `Config` 钩子（项目用的这一版就有，已核），TypeBox（24 个文件已经在用它写工具参数） |

**已经借到、做得好的**（不用再改）：

- 插件地图的机械信息由代码生成（`ztools/plugin-map/Gen_Plugin_Map.ts`），和 VS Code 从 `package.json` 读插件贡献点是一个思路；
- 插件页面按约定挂在 `/<插件名>/`（`http/Static.ts:41-50`），不用一张中央路由表；
- 旁听只有一个采集入口，`onDispatch`、`onTrace`（`utils/Trace.ts:147`、`:185`）；同一次派发只拼一次事件行（`:134`、`:161-167`）。这和 OpenTelemetry 的 SDK 一样：采集一处，用的人各取所需。第 2 条就是在这个好底子上补一个编号。

**“可有可无”的 db 带来两个分支和一条先后**：

- knowledge：有 db 就记一笔账，没有就靠 Store 自己建（`knowledge/index.ts:62-67`），两条路都走一遍；

**一个现成的毛病**：

- 默认插件表是 `['workspaces', 'bots', 'cli', 'file-tools', 'context-fit']`（`utils/Checks.ts:43`），里面没有 db；

**旧路的坑**：`CREATE TABLE IF NOT EXISTS` 只管“表在不在”，不管“列对不对”。

- 谁往这 29 张表里加一列，只改建表语句，用户机器上的旧库不会变；
- 测试用的都是新建的库，照样全过；
- 只在用户真跑时报 `no such column`；
- CLAUDE.md 定了“只跑改到的测试，不跑全量”，这个坑更不容易早发现。

> 新表、新列一律写成 `migrations/000N_说明.sql`，交给 `ctx.db.migrate`。不许在插件代码里写 `CREATE TABLE`、`ALTER TABLE`。

#### 1.3 反方（方法 F）

- **“db 是可选插件，强制依赖它违背插件化。”** db 只有 217 行，包的就是 Resources 已经开着的同一个连接（`db/说明.md` 第一段）。这 13 个插件都在用 `ctx.resources.db`，依赖早就有了，可选的只是记账那一半。
- **“`IF NOT EXISTS` 幂等，够用了。”** 只对建表幂等，对加列不幂等。work-decision 已经为了加一列手写了查列和补列，这正是第二条路长出来的样子。
- **“有的表不在主库里。”** 待核：`memory/Backend.ts`、`wechat/read/Store.ts` 用的是不是主库的连接。不是主库的，照 `ChannelSchema.ts:36-40` 的写法，对那个连接 `new Db` 跑同一套账本，规矩不变。
- **“迁移出错会把启动卡住。”** 现在建表出错也一样卡住。账本还多一道保护：同一版的 SQL 改了，哈希对不上会报错（`db/说明.md` 的“迁移哈希”一行），不会悄悄跑两遍。

### 2. 调试记录按编号对齐，不按时刻猜

#### 2.1 现状

采集已经收在一处：

- journal 写库、教程拍快照、录载荷都从 `onDispatch`、`onTrace` 挂（`journal/index.ts:230`、`:262`；`tutorial/State.ts:103`、`:129`；`tutorial/Payload.ts:740`、`:760`）；
- 同一次派发，三家拿到的是同一个事件行对象（`Trace.ts:161-167`）。

但事件行里没有编号（`Trace.ts:93-114` 的 `DispatchLine`），所以教程页把三份记录拼到一起时只能对时刻：

- 快照对流水：种类、名字、会话、消息号都一样，再加时刻差在 50 毫秒以内（`State.ts:24-26` 的 `MATCH_MS`，`:300-318` 的 `getMatched`）。注释写明了：“两边各自取 `Date.now()`”；
- 载荷对流水：名字一样、时刻差在 200 毫秒以内（`Payload.ts:149-150` 的 `ROW_MATCH_MS`，`:536-575` 的 `assignTrailSteps`）。对不上，再按时间段找步骤（`:508` 的 `findStepByWindow`）。

**会对错的情况**：

- 同名事件连着来。比如几个工具接连跑完，`session/before-tool`、`session/after-tool` 一串，会话、消息号都一样，时刻差几毫秒。只要前面漏掉一行，后面就整串错位：游标往前走，不回头；
- journal 有意不记一些事件（`journal/index.ts:264` 的 `READ_EVENT_NAMES`），快照那边不跳，两边的行数本来就不一样多；
- journal 每条同步写 SQLite。慢一点，两边的时刻就会差出 50 毫秒，这一步的快照就丢了（待核：真机上多常见）。

对错的后果：教程页显示的“这一步的变量”是别的步骤的。这是给开发自己看的调试插件，用户要求全量原样（CLAUDE.md 用户 11-17），可它原样显示的是一份配错的数据。

`data/flow/` 里改版前存的旧文件没有号，就不对齐了。这是调试数据，重新拍一次就有。

#### 2.3 反方

- **“为了对齐调试数据，加一列、改三个插件，值吗？”** 时间窗口是猜。猜错的时候，教程页把别的步骤的变量挂到这一步，人照着它去调，方向就错了。改动是三处对齐代码各删十几行，换成按号取，加起来还是净删。

- **“二阶影响：号进了数据库，以后有人拿它当业务主键。”** `DispatchLine` 的注释写明只给旁听对齐用。它和 `journal_lines.id` 一样，不出现在任何业务表里。

### 3. 插件配置只写一处（要用户定）

#### 3.1 现状

**配置交到插件手里是原样的 `unknown`**：

- `Resources.ts:61-67` 的 `PluginEntry.config` 注释写着“插件自己校验”；
- `Main.ts:150` 原样交给 `app.plugin(plugin, entry.config)`。

**每个插件各写一套**：

- feishu、voice 基本靠 `utils/Checks.ts`（`feishu/Config.ts:104` 起、`voice/Config.ts:83` 起）；
- memory、model-catalog、approval 多半手写 `typeof`（`memory/index.ts:857-882`、`model-catalog/Fallback.ts:543-600`、`approval/index.ts:1536-1546`）；
- http 读的是顶层的 `server` 段（`http/index.ts:564`）。

**一个键写几遍**。以 `fallback.max_tries` 为例，“默认 5”写了 6 处：

| 位置 | 写了什么 |
|---|---|
| `model-catalog/Fallback.ts:563-564`、`:595` | 校验，默认 5 |
| `config.example.yaml:301` | `max_tries: 5` |
| `model-catalog/说明.md:162` | 默认 5 |
| `settings/ConfigFile.ts:45` | 设置页后端白名单 |
| `web/src/Settings/Edits.ts:16` | 前端路径 |
| `web/src/Settings/Sections.tsx:659-660` | 表单，提示文字“默认 5”是手抄的 |
| `web/src/locales/en.json:677`、`fr.json:677`（还有 zh-TW） | 三份翻译，又各写一遍“默认 5” |

谁把默认值改成 3，要改 6 处；漏一处，设置页就在骗人。飞书的 `history_on_join` 也是 4 处（`feishu/Config.ts:157-159`、`config.example.yaml:183`、`feishu/说明.md`、`Config.ts:2` 的文件头）。

**设置页只能改 7 个插件键**：`settings/ConfigFile.ts:39-47` 的 `PLUGIN_FIELDS`。feishu、memory、voice、approval 这几十个键都只能手改 YAML。

**手边已经有的两样东西**：

- **Cordis 4 自带配置校验**。项目用的 `cordis@4.0.0-rc.12`（`package.json:39`）：插件类型上有 `Config?: StandardSchemaV1`（包里的 `lib/registry.d.ts:24`），挂载时调 `runtime.Config['~standard'].validate(config)`，有问题抛 `ValidationError`，没问题把校验后的值交给 `apply`（包里的 `lib/index.js:292-303`）。我从 npm 下载这个版本的包核对过。项目里没有一个插件导出 `Config`。这正是 CLAUDE.md 第一条说的“外部入口校验一次”，而且入口在 Cordis 里，不用自己写；
- **TypeBox 已经在用**。24 个文件用 `piAi.Type.Object(...)` 声明工具参数，带 `description`、`minimum`、`default`（例：`knowledge/Tools.ts:16-22`）。pi-ai 导出了 `Type`，它依赖 `typebox@1.3.27`。

#### 3.2 三个方案

| 方案 | 做法 | 得到 | 代价 |
|---|---|---|---|
| A 声明一次 | 插件用 TypeBox 写配置，导出成 `Config`；`utils/` 加一个约 25 行的 `toConfig`，把 TypeBox 包成 Cordis 认的格式；设置页从后端取各插件的声明，按类型画表单；`Gen_Plugin_Map --check` 顺带核对 `config.example.yaml` 有没有漏写的键 | 一个键只写一处；设置页覆盖全部插件键；校验和默认值不用每个插件手写 | `package.json` 显式加 `typebox`（版本跟 pi-ai 一致，不多装新东西）；每个插件的入口要改；跨字段的规则仍要手写 |
| B 只收设置页 | `PLUGIN_FIELDS` 每项加 `default`、`hint`，前端照它画，删掉 `Sections.tsx` 里手抄的提示 | 设置页那 7 个键不再手抄 | 插件里的校验和默认值照旧；默认值仍写两处（插件和白名单） |
| C 不动 | — | — | 每加一个能在设置页改的键，改 5 处再加 3 份翻译 |

**推荐**：用户要设置页能改全部插件配置，选 A，先拿 model-catalog 的 `fallback` 试；不要，选 B。

A 的样子（model-catalog，`Fallback.ts` 顶上）：

```ts
/** fallback 段：形状、默认值、说明只写这一处。Cordis 挂载前按它校验并补默认值，设置页按它画表单。 */
const FallbackConfig = piAi.Type.Object({
  chain: piAi.Type.Array(piAi.Type.String(), {
    default: [],
    description: '被限流后依次换的模型（供应商名/模型 ID）',
  }),
  max_tries: piAi.Type.Integer({
    minimum: 0,
    default: 5,
    description: '被限流后最多再试几个模型',
  }),
  include_siblings: piAi.Type.Boolean({
    default: true,
    description: '同一供应商价格为 0 的模型也试',
  }),
});
```

`model-catalog/index.ts`：

```ts
/** 交给 Cordis：挂载前校验，apply 收到的已经是补好默认值的配置。 */
export const Config = configModule.toConfig(piAi.Type.Object({
  fallback: piAi.Type.Optional(FallbackConfig),
}));
```

`readPositiveInt(rawMaxTries, …, 5, true)` 这类手写校验删掉，直接用 `config.fallback.max_tries`。

“并发没写就沿用顶层 `concurrency`”这种跨字段的规则（`Fallback.ts:566-590`），schema 写不进去，照旧留在 `apply` 里手写。

`utils/Config.ts`（新，约 25 行，**待核**：typebox 1.x 里补默认值、校验、取错误的函数名）大意：

```ts
/**
 * 把 TypeBox 的配置声明包成 Cordis 认的 Config（Standard Schema）：先补默认值，再校验。
 * 出错时每条带上字段路径和声明里的中文 description，报错照旧是中文。
 */
export function toConfig<T extends piAi.TSchema>(schema: T): Plugin.Config<T> { … }
```

设置页：

- `settings` 插件加一个接口，交回已挂载插件的声明。TypeBox 的声明本身就是 JSON Schema，不用转；
- 前端写一个通用的表单，只认整数、开关、文字、文字列表四种（约 60 行），换掉 `Sections.tsx` 里每个插件键的手写表单；
- `PLUGIN_FIELDS` 和 `Edits.ts` 的 `PLUGIN_PATHS` 删掉；
- 翻译的键改用声明里的 `description`。

#### 3.3 反方

- **“这就是用户最怕的过度抽象。”** 不是新建一层。`Config` 是 Cordis 自带的钩子，TypeBox 是 24 个文件已经在用的写法。新加的只有 `toConfig` 这 25 行，删掉的是每个插件手写的 `typeof`、默认值、报错文案。
- **“和 32 号第 5 条（配置校验统一用 `checkNumber` 这些）反着做？”** 不反。32-5 统一的是“怎么查”，这一条统一的是“写在哪”。A 做完，`checkNumber`、`checkFlag` 只剩 HTTP 请求体在用，和 35 号第 1 条（`Checks` 改抛 `Failure(400, …)` 给 HTTP 用）正好接上。
- **“报错会变成英文。”** `toConfig` 自己拼报错：字段路径加上声明里的中文 `description`，不用 TypeBox 的原文。待核：试点时看一眼真实的报错。
- **“`config.example.yaml` 是用户的说明书，生成会丢掉手写的注释。”** 不生成，只核对：声明里有的键，例子文件里也要有。照 `Gen_Plugin_Map --check` 的做法，过期就报。
- **“二阶影响：设置页能改全部配置，改错了服务起不来。”** 校验在 Cordis 入口，设置页存之前可以先拿同一份声明校验一遍，不对不存。这比现在手改 YAML、重启才发现要安全。插件配置改完仍要重启才生效（`Resources.ts` 的热重载只管 providers），这一点不变。
