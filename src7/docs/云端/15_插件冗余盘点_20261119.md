## 一、一页结论

**变化**：从第一轮到现在，插件从 30 个变成 32 个：新加 5 个（programs、voice、screen、decision-map、db），并掉 3 个（files-api、model-notes、usage）。插件代码从 40,007 行涨到 60,770 行，多了 52%。新加的 5 个就占了 11,142 行。

**判断**：插件个数不是现在的病根。现在的冗余是三种：

- 一件事拆在两个插件里，互相 import：主动发消息拆在 approval 和 programs；
- 同一件事有两套做法：问模型有两条路，建表有两种写法；
- 改成发事件以后，原来的服务入口没收：6 个服务只有自己在用。

/** 本进程签发过、还没用掉的发件凭证。 */
const tickets = new WeakSet<ApprovedChannelSend>();

export function issueTicket(call: ApprovedChannelSend): void {
  tickets.add(call);

export function takeTicket(call: ApprovedChannelSend): boolean {
  //G 普通对象、复制的对象、用过的凭证都不算数。
  if (!tickets.delete(call)) return false;

  return call.expiresAt > Date.now();
}

### 3. 第二阶段收尾：没人取的服务（结论第 3 条）

**3.1 现状**

改事件的第二阶段（调用方改成发请求事件）走得很快：第一轮说“没人发”的 3 个请求事件，现在都有人发了。

- `base/request` 有 2 处；
- `feishu/send-file` 有 2 处。

反过来，这些插件原来登记的 Cordis 服务，现在只有自己在用：

| 服务 | 登记在 | 别的插件取它 | 误导人的注释 |
|---|---|---|---|
| base | `base-bridge/index.ts:105` | 0（只有自己的 `Notify.ts:91`、`UpdateWatch.ts:161`） | — |
| exec | `exec/index.ts:104` | 0 | `:103`“别的插件以后用 ctx.exec.run 跑命令” |
| journal | `journal/index.ts:182-188` | 0 | `:43`“别的插件当可选依赖，用 ctx.get('journal') 现取” |
| filesMirror | `journal/FilesMirror.ts:82` | 0（只有 journal 自己在 `index.ts:260` 看它在不在） | `:19` |
| progress | `progress/index.ts:262` | 0 | `:130` |
| usage | `model-catalog/Usage.ts:161` | 0 | `:18` |

`flow` 是另一种情况：同一件事有两个入口。

- tutorial 既提供服务 `ctx.flow`（`tutorial/index.ts:433`），又听通知 `flow/state`（`:436`）。
- `flow/state` 的注释写着“谁发：暂无”（`:69` 附近）。
- 用服务的只剩 relay 一处（`relay/index.ts:317`）。
- 文件头 `:31` 还写着“relay、web-api 在用”，可 web-api 已经不用了。

**3.2 改法**

这 6 个类不再 `extends cordis.Service`，也不再 `super(ctx, '名字')`。插件里谁要用就把对象传给谁（CLAUDE.md：“需要谁就传谁”，`this.xxx.方法()` 按 F12 能跳到实现）。`declare module 'cordis' { interface Context { … } }` 里对应的那一行删掉。

改前改后（base-bridge 为例）：

```ts
// 改前：base-bridge/index.ts:105 登记服务，Notify.ts:91 再从 ctx 现取
constructor(ctx: cordis.Context, readonly url: string) {
  super(ctx, 'base');
}
// Notify.ts:91
const base = ctx.get('base');

// 改后：apply 里建好，直接传给要用的两处
//M 基地桥只在本插件里用，别的插件发 base/request。
const base = new BaseBridge(ctx, url);
notify.mount(ctx, base, settings.notify);
updateWatch.mount(ctx, base, settings.update);
```

flow 的改法：relay 改发 `flow/state`，然后 tutorial 撤掉 `ctx.provide('flow', …)`。这一步正好是任务书说的“先让被调方能听，再让调用方改发”的第二步，不是删监听。

**3.3 代价**

- 两份测试靠服务取对象：`exec/Exec.test.ts:202`（`ctx.exec.run`），`journal/Journal.test.ts:101-137`（`ctx.journal`、`ctx.filesMirror`）。要改成直接建对象来测。
- 这 6 个类有没有用到 Service 的 `start`、`stop` 这类生命周期：按行首搜没搜到，待核。
- `modelCatalog`（screen 在用）、`approval`（wechat 用 `ctx.inject`，`wechat/index.ts:1011`）、`feishu`、`decision`、`memory`、`workspaces`、`programs`（http 在用，`http/index.ts:263`）还有别的插件在取，这一轮不动。

### 4. 建表的两种写法（结论第 4 条）

**4.1 现状**

- db 插件 194 行，带 `drizzle-orm`、`drizzle-kit` 两个依赖（`package.json:40`、`:61`），引擎只支持 sqlite（`db/index.ts:170-171`）。
- 用它的只有 context-fit 一个插件、一张表 `compress_log`（`context-fit/Schema.ts:6`），两句查询（`Compress.ts:114`、`:192`），迁移在 `context-fit/index.ts:278`。
- 其余 12 个插件的 25 张表，加上骨架的 `sessions` 表，都是 `resources.db.exec('CREATE TABLE IF NOT EXISTS …')`。
- 改表结构靠手写的 `ALTER TABLE` 加 `PRAGMA table_info`，只有 3 处：journal、`memory/ChannelIndex.ts`、relay。

**4.2 先替 db 辩护（方法 F）**

- db 的长处是迁移有账：有版本号、有 hash、能回放。
- 可眼下手写 `ALTER` 的只有 3 处，这个痛还不明显。

**4.3 三版方案**

### 6. 不建议并的（先假设“该并”，再找反例）

- **decision-map 并进 relay**：decision-map 存的是文件（`graph.json`、`history.jsonl`，`decision-map/Store.ts:244-245`），relay 存的是表。decision-map 交给中控，是发 `decision-map/relay` 请求事件，由 relay 接（`relay/index.ts:325`）。它是 relay 的一个“渠道”客户，不是另一套 relay。

- **programs 拆开**：programs 一个插件管三件事：
  - 托管外部程序：Host、Spec、Protocol，约 1,400 行；
  - 外置渠道的收发：ChannelBridge、ChannelSend，约 1,090 行；
  - 资源守卫：ResourceGuard、ResourceProbe、GuardNotices，约 910 行。

  说明.md 第 22 行自己写着“一个外部程序都不配时守卫照样每 5 秒采样”，说明守卫不依赖托管。可拆出去就多 1 个插件，和“少插件”相反。

  建议只做两件小事：
  - 说明.md 第一行写明“三件事：托管、外置渠道、资源守卫”；
  - `GuardNotices.ts:38-47` 现在直接往 `integrations/feishu/outbox/` 写文件。发件箱本来是给“外面的程序”用的（`feishu/outbox/Outbox.ts:2`），插件之间不该靠目录约定说话。要不要改走 `base-bridge` 的通知或别的事件，待核：系统告警发给本人不该过审批，现在没有一个“不过审批、发给本人”的事件。
