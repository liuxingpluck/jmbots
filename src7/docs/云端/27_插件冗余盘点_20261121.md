## 二、证据和方案

### 0. 动手前先问自己的三个问题（方法 C）

**问题一：上一轮最大的问题（服务没人取）为什么更多了？**

因为第二阶段只做了一半：调用方都改成发请求事件了，提供方的 `super(ctx, '名字')` 却没撤。0.7.74 的提交说明写着“全插件 requestEvent 迁移完结”，所以这一步该收尾了（第 4 节）。

**问题二：怎么找“同一件事两套”？**

这一轮换了个角度：不扫跨插件 import，扫的是“同一份数据被写了几次”和“同一组路由被实现了几次”。
- 前者找到了说过的话存四份（第 2 节）；
- 后者找到了微信两套（第 1 节）。

跨插件 import 也重扫了一遍（第四部分）。按值 import 的大头现在是 channels，一共 33 处，这是设计上的“协议插件”，不算问题。

**问题三：“多出来的那套”有没有存在的理由？**（方法 F 的反面检验）

- 微信两套：过渡期有理由，长期没有（第 1 节）；
- MD 和记忆表：读者不同（人看文件，模型查表），两份都该有；但写入可以只有一个入口（第 2 节）；
- DataFlow 的手写表：函数名、字段说明已经有现成的来源，没理由手写（第 3 节）。

**2.2 A 和 C 是最该合的一对**

两者有四点一样：
- 事件一样：都听 direct、mention、listen、history、replied、recall；
- 时机一样：都是 `prepend: true`；
- 都跳过语音半句：`ArchiveListen.ts:30` 和 `ChannelIndex.ts:440` 各写了一遍；
- 都按消息号去重：A 用 `in:<messageId>`，C 的 `msg_key` 就是 messageId。

C 还依赖 A：附件路径要等 A 先复制完，才能从归档目录里取到（`ChannelAttachments.ts:8-18`）。所以 `memory/index.ts:831-834` 必须**先**登记 C、**后**登记 A，再靠 Cordis“prepend 的后登记先执行”让 A 先跑。注释 `:833` 写明了这一点，可是代码里看不出来，谁调换这两行就会出错。approval 的 Grants、Approval 也在同样的事件上 prepend（`channels/index.ts:18`），所以几个插件之间谁先谁后，还取决于挂载顺序，待核。

归属也是错开的：
- `channels/index.ts:3` 写着“不挂服务”，`channels/说明.md` 写着“本插件自己不挂监听”；
- 可 `ArchiveListen.ts` 是一组有状态的监听，生命周期跟着 memory 走；
- 而且它挂在 `if (channelIndex !== undefined)` 外面（`memory/index.ts:834`），关掉渠道索引时 MD 归档照样开着。这是有意的，但没写在说明里。

**2.3 改法：挪进 memory，合成一个监听**

```ts
// 改后：memory/ChannelRecord.ts（示意；原 channels/ArchiveListen.ts 和 ChannelIndex 的监听合一）
/**
 * 渠道里说过的话：先写聊天 MD，再写渠道索引。
 * 顺序写在这里，不靠 prepend 的登记先后。
 */
const onInbound = (message: protocol.ChannelMessage): void => {
  //G 语音半句不记，等同一消息号的整句。
  if (message.routing.partial === true) return;

  //M 先写 MD：附件原件复制进聊天目录，拿到它们在归档里的路径。
  const attachments = archive.writeInbound(message);

  //G 渠道索引关了，只留 MD。
  if (index === undefined) return;

  //M 再写索引：附件路径直接用上面这份，不再回头去归档目录里找。
  index.recordInbound(message, attachments);
};

ctx.on('channel/direct', onInbound, { prepend: true });
ctx.on('channel/mention', onInbound, { prepend: true });
ctx.on('channel/listen', onInbound, { prepend: true });
```

挪完以后，channels 只剩 `Message.ts`、`Reply.ts`、`Target.ts`、`TextReply.ts` 和事件声明，和它自己文件头说的“协议”对上了。`ChannelAttachments.ts` 那一圈“从归档目录反查路径”也能删掉，待核。

**2.4 B（飞书 jsonl）的两版**

| 方案 | 做什么 | 代价 |
|---|---|---|
| 甲：瘦身（倾向） | jsonl 只存平台消息号、方向、是否撤回、appId，不存正文。引用要正文时，查记忆表或调飞书接口取原消息 | 引用的正文多一步；老文件不用迁 |

还有一个小问题：`channels/Archive.ts:16` 写着账号目录“和 feishu/ChatLog.ts 的账号目录同一个”。实际上 B 是 `chats/<appId>`，A 是 `<账号名>_<appId>`，两者不同。这句注释要改。

**2.5 D（网页收件表）不建议动**
