## 一、一页结论

**判断**：事件化现在最贵的不是多一个回执事件，而是**调用方自己掐表**。

- 调用方给每个请求定一个 `timeoutMs`。到点就自己结案，可处理方还在办。
- 于是多出第三种结局“不知道做没做”（`isUnsure`）。它一路扩散：
  - 现在 26 个源文件里有 131 处 `uncertain` / `不确定`；
  - 网页上要提示“请核对后再操作”；
  - 外层超时得算成内层超时之和再加余量。
- 可 53 个请求点里，**35 个的处理方就在本进程里读写内存或 SQLite**。这些“超时”只说明处理方还没办完，并不说明出了什么事。

## 二、证据和改法

### 1. 谁走网络谁限时（结论第 1 条）

**53 个请求点按处理方分类**（子代理逐个查过，关键行我抽查过）：

| 处理方在哪 | 只读 | 会改东西 | 例子 |
|---|---|---|---|
| 本进程（内存、SQLite、文件） | 20 | 15（其中 14 个用了 `isUnsure`，`progress/GroupDaily.ts:118` 超时直接当失败） | approval 的 ask、decide、close、list；bots 的 add、hand、accept-result、save-file；model-catalog 查模型；journal 取流水；work-decision 的 note；progress 的 act、list |
| 走网络、子进程或模型 | 11 | 7 | decision 判断、approval 审命令（问模型）；飞书发文件；基地重启；外部程序发件；渠道发话 `channel/reply` |

- 没有一个处理方是“等人点”：approval 的 ask 只登记卡片就返回（`approval/index.ts:633-645`），用户点了以后走另一次 decide 请求。
- `timeoutMs` 是必填项（`utils/RequestEvent.ts:55`），所以 35 个本进程处理方的调用点全都写了超时，常见是 1500–10000 毫秒。

**本进程处理方的“不确定”是造出来的**。拿 settings 新建机器人举例（`settings/index.ts:155-168`）：

- bots 在同一个进程里登记机器人；
- 5 秒没回执，就报 504“实时登记结果不确定。请核对机器人列表后再操作”；
- 可这时 bots 还在办，过一会儿就登记好了。程序其实能自己知道结果，只要接着等。

**三阶影响：超时一层套一层，只能靠算术对齐**。`approval/Outbound.ts:12-27`：

```ts
const DRAFT_WAIT_MS = DRAFT_HTTP_WAIT_MS + 1000;
const PROGRAM_WAIT_MS = CHANNEL_WAIT_MS + 5000;
const RECEIPT_MARGIN_MS = 4000;
export const REMINDER_WAIT_MS = REMINDER_READ_WAIT_MS + CHANNEL_WAIT_MS + RECEIPT_MARGIN_MS;
const CONFIRM_WAIT_MS = DRAFT_WAIT_MS + PROGRAM_WAIT_MS + RECEIPT_MARGIN_MS;
```

- 外层掐表一旦比内层短，就会在内层还在发的时候判“不确定”；
- 所以每加一层，就得手工往外层加一段余量。改一个底层超时，要顺着链子把外层全改一遍。

**两层超时，其中一层是死的**：

- http 的关闭处理带一个可选的 `waitMs`，到点回“等待 HTTP 关闭超时”（`http/index.ts:58`、`:290-302`）；
- 全仓没有人传 `waitMs`（grep 只有声明和处理两处）。settings 只传 `{ action: 'close' }`（`settings/index.ts:304`），靠自己的 10 秒定时器；
- 所以 `settings/index.ts:326` 判断 `result.error === '等待 HTTP 关闭超时'` 永远走不到；
- 而且这还是拿一句中文原话来认结局。

**项目里已经有对的写法**：exec 审命令（`exec/Runs.ts:86-110`）。

- 到点时它不只是自己不等了，还用 `review.abort(cause)` 让审批那边也停下；
- 所以不会出现“调用方以为没审完，审批那边却登记了待确认”。

这说明：限时要么由处理方自己做，要么调用方限时的同时让处理方也停下。只是调用方自己不等，最容易把状态弄得对不上。

**改法**：

1. `RequestEventOptions` 去掉必填的 `timeoutMs`，换成可选的 `warnAfterMs`：到点只报警，不结案。`utils/RequestEvent.ts:153-159`，改前：

```ts
timer = setTimeout(() => {
  //M 等待回执超时，调用退回构造器收尾。
  finishFallback('timeout');
}, options.timeoutMs);
if (options.keepAlive !== true) {
  timer.unref?.();
}
```

改后：

```ts
//M 等久了只在流水里报一句，不结案：处理方还在办，调用方照样等它办完。
timer = setTimeout(() => {
  const vars = { request: String(requestEventName), waitedMs: warnAfterMs };
  ctx.emit('trace', 'requestEvent', 'trace.requestEvent.slow', '处理方还没回', vars);
}, warnAfterMs);
timer.unref?.();
```

2. 真走网络的 7 个处理方，自己给 HTTP 限时，限时到了自己回“不确定”。外部程序发件已经这么做了：`programs/ChannelSend.ts:119-124` 发送抛错就回 `{ receipt: UNKNOWN }`。照它补上飞书发文件、基地重启、渠道发话这几家。
3. `FallbackReason` 去掉 `'timeout'`。`'error'`（处理方抛错、又没写 `onError`）算不算不确定，交给处理方的 `onError` 定，因为只有它知道抛错时做到了哪一步。
4. `keepAlive` 选项跟着删：它只是为了让结案的定时器不被进程退出吃掉（`:56-57`、`:157-159`），报警的定时器不需要。

**F：最强的反对意见**

| 反对 | 重新评估 |
|---|---|
| 处理方卡死了，调用方就永远等着，网页的请求也挂着 | 现在处理方卡死，照样一直卡着，没有谁去中止它（除了 exec），调用方的超时只是把“卡死”变成一句“请核对”。改成报警以后，流水里有一行“处理方还没回”，教程页能直接看到卡在哪个插件。网页请求另有 Fastify 和浏览器的超时兜底（Fastify 的具体配置待核） |
| 以后有外部插件、收费插件，调用方不知道处理方在不在本进程，所以必须自己掐表 | 正因为调用方不知道，才不该由它定超时：它连处理方要走网络都不知道，定的数只能是猜。外部插件经 `Main.ts:241-256` 的 `loadExternalPlugin` 加载进同一个进程；真在进程外的只有 programs 托管的程序，它们本来就经 HTTP，属于第 2 步“自己限时”的那一类 |
| 事件循环被同步的 SQLite 卡住时，靠超时能发现 | 事件循环卡住时，定时器自己也跑不了，原来的超时同样发现不了 |
| 有的调用点确实要限时：问决策模型最多等 1800 毫秒，过了就不要了（`screen/Analysis.ts:75`） | 这属于“过时不候”，不是“不知道做没做”：它是只读的，结果晚了就不用。这类照 exec 的写法，传 `signal`、到点 `abort`，处理方跟着停。只读的点不会出现状态对不上 |

### 2. 交回 `{ reply }` 或 `{ why }`（结论第 2 条）

**改前**，`relay/AgentTasks.ts:39-53`：

```ts
const request = { action: 'accept-result', input } as const;
const options = {
  timeoutMs: 5000,
  onFallback: (reason: requestEventModule.FallbackReason, detail?: string) => {
    return { requestId: '', ok: false, error: detail ?? `结果投递未获回执（${reason}）` };
  },
};

//M 两个入口都以稳定键提交，只有确定收到入队回执才能标为已送。
const result = await requestEventModule.requestEvent(ctx, 'bot/request', 'bot/result', request, options);
if (requestEventModule.isUnsure(result)) return { ...result, uncertain: true, error: '结果投递状态不确定' };

return { ...result, uncertain: false };
```

**改后**（第 1、2 条一起改）：

```ts
const request = { action: 'accept-result', input } as const;

//M 请 bots 把结果排进派活会话的结果队列；bots 在本进程里写库，不掐表。
const asked = await requestEventModule.requestEvent(ctx, 'bot/request', 'bot/result', request);

//G 没挂 bots，或 bots 办的时候抛错：确定没排进去，调用方照常重试。
if (asked.reply === undefined) return { ok: false, error: `结果投递没人接（${asked.why}）` };

return asked.reply;
```

- 返回类型里的 `uncertain` 字段跟着删：`requestResultDelivery` 的两个调用方（`relay/index.ts:1125`、`relay/AgentTasks.ts:587`）各少一个分支（待核它们后面怎么用这个字段）。
- `work-decision/Routes.ts:199-204` 自己又写了一份同样的 accept-result 请求，也带 `uncertain`，同样改法；顺带可以直接调 `requestResultDelivery`，少一份重复。
- `RequestEvent.ts` 里，`getFallback`、`onFallback`、`RequestFallback`、`isUnsure` 一起删，换成一个类型：

```ts
/** 一问一答的结局：拿到回执，或者没拿到、写明为什么。 */
export type Asked<Res> =
  | { reply: Res; why?: undefined }
  | { reply?: undefined; why: 'unhandled' | 'aborted' | 'error'; detail?: string };
```

- 调用方只看一个字段：`reply === undefined` 就是没拿到，`why` 说为什么。不用再编假回执，也不用拿 `result.error` 的原话去比。

### 3. 入站事件的先后（结论第 3 条）

**`channel/direct` 的实际先后**（按 `config.example.yaml` 的插件顺序和 prepend 规则推出来，没跑起来验证）：

```
voice（prepend）→ 聊天归档（prepend）→ memory 渠道索引（prepend）
→ approval 认批复（prepend）→ Grants 目录授权（prepend）→ bots 认领 → web-api 绑会话
```

- memory 先调 `applyChannelIndex`（`memory/index.ts:821`）、后调 `applyChatArchive`（`:825`），所以聊天归档反而排在前面；
- approval 先 `new Grants`（`approval/index.ts:418`），后挂自己的监听（`:445-446`），所以 Grants 反而排在后面；
- web-api 排在 bots 后面，靠的是 `inject` 里写了 bots（`web-api/index.ts:53`），这一处是稳的。

也就是说，现在有三种东西在决定先后：`inject`、prepend、config 里的顺序。其中 prepend 的效果和直觉相反：先挂的后跑。

**新提交带进来的风险**（0.7.71，`approval/Grants.ts`）：

- `applyMessage` 第一步 `this.remember(...)` 就写库（`Grants.ts:110`、`:447` 起），整个函数没有 try/catch；
- 入站事件是 `serial` 派发的（`channels/Message.ts:290-301`）。前面的监听者一抛错，后面的 bots、web-api 都不再被调用；
- 所以：库写出错，这条话就到不了任何机器人。飞书入口在 `emitInbound` 抛错时不会写 `feishu_seen`（`feishu/Inbound.ts:763-768`），会不会重投待核；
- 对照：聊天归档和渠道索引都特意包了 try/catch，注释写的就是“别挡别人认领这条消息”（`memory/ChannelIndex.ts:608-619`）。

**但不能简单地把错误吞掉**：

- Grants 对外人做的第一件安全的事，是删掉地址里原有的 grants（`Grants.ts:137`）；
- 这一步排在写库之后。如果只是在外面包一层 try/catch，写库出错时这一步就被跳过了，外人地址里原有的 grants 会原样留下，等于出错时放行（待核：外人的地址里实际会不会带 grants）。

**改法**：

1. Grants 不再自己挂监听（删 `Grants.ts:97-99`）；
2. approval 每个入站事件只挂一个监听，先后写在函数里，并保持现在的实际先后：

```ts
//M 进来的话：先认批复（“同意 3”），再过目录授权（改地址，bots 认领时照抄）。
//M   两步在一个监听里，先后看代码就知道，不靠挂载顺序。
const onCalled = async (message, control) => {
  await this.onChannelMessage(message, control);
  this.grants.applyMessage(message);
};
ctx.on('channel/direct', onCalled, { prepend: true });
ctx.on('channel/mention', onCalled, { prepend: true });

//M 只听的话没叫机器人，不认批复，只过目录授权。
ctx.on('channel/listen', (message) => {
  this.grants.applyMessage(message);
}, { prepend: true });
```

3. `applyMessage` 里，外人那一路先删 grants 再读写库；读写库出错就打日志，按 guest 往下走：

```ts
//G 外人地址里原有的 grants 一律不认：先删，后面读写库出错也不会留下。
if (!protocol.isOwnerTurn(channel, address)) {
  delete address['grants'];
}

//M 记下见过的人和群、查授权目录。库出错只打日志：外人按 guest 往下走，不挡 bots 认领。
try {
  this.remember(speaker, address);
} catch (error) {
  console.error(`approval：目录授权记不下来：${textModule.getErrorMessage(error)}`);
  return;
}
```

查目录（`getDirs`）也是读库，可以一起放进 try。

**F：反方意见**——“要不要顺便把先后改成先过授权、再认批复，更符合直觉？”

- 先不改。`onChannelMessage` 读 `message.role` 和 `rules.getSpeaker(address)`（`approval/index.ts:1043-1047`），而 Grants 会改 `role` 和地址里的 `role`、`workspace`（`Grants.ts:143-146`）；
- 换顺序前，要核 `getSpeaker` 和 `allowed` 读不读这些字段。合并时保持原样，行为不变，换不换另说。

**附带一处同类问题（关口事件）**：

- `session/before-tool` 的三个监听者都写 `gate.deny`；
- approval 和 ChannelTools 都先查 `if (gate.deny !== undefined) return;`（`approval/index.ts:485`、`bots/ChannelTools.ts:58`），GroupDaily 没查（`progress/GroupDaily.ts:139-144`），会把前面写的拒绝原因盖掉；
- 仍然是拒绝，安全上没问题，只是模型看到的原因变了。补上那一行就行。

### 4. “谁接”按实际先后排（结论第 4 条）

- `channels/index.ts:44-51` 的“谁接”列表现在按文件路径字母排：approval/Grants、approval/index、bots、channels/ArchiveListen、memory、voice、web-api。实际先后见第 3 节，几乎是反过来的。
- 改法：
  - 按第 3 节的实际先后排；
  - prepend 的后面写“（prepend）”；
  - 文件头加一句“prepend 是插到最前面，几个都 prepend 时，后挂的先跑”。
- 怎么核：教程页的事件行里，`listeners` 就是 Cordis 监听数组的顺序（`utils/Trace.ts:171-177` 按 `_hooks` 原序取插件名），拿它和声明对一遍。
- `bot/receive` 也一样：tutorial 去关键词的注释写“排在管分派的插件前面”（`tutorial/State.ts:93`），但 approval 的 prepend 挂得更晚，排在 tutorial 前面。approval 那边在 `fromChannelEvent` 时直接返回（`approval/index.ts:1002`），所以只影响旧路，影响很小，注释改准就行。

### 5. 核过、不用改的

- **`serial` 误返回真值、截断后面的人**：
  - TypeScript 允许把返回非 void 的函数赋给返回 void 的监听类型，所以类型挡不住，这本来是个隐患；
  - 子代理逐个看了所有非请求类的 `serial` 事件（channel/*、bot/receive、session/before-*、channel/history 等），没有一个监听者会误返回真值；
  - 唯一返回值的是 `work-decision/decided`，它是故意的（见第一节“要用户定的”）。
  - 以后加监听，统一写块体 `{ ... }`、不写表达式箭头，就不会踩到。
- **`work-decision/note` 有两个处理方**：
  - `work-decision/Routes.ts:180` 只接 `action === 'reply'`，`relay/index.ts:351` 只接其余的，正好互补；
  - 两边都不接，只可能是对应插件没挂，回 unhandled，是对的。
- **`channel/history`（0.7.71 新加）**：两个监听者都是块体、都不 prepend，顺序无关，没问题。
