## 三、证据和改法

### 1. 收费授权：发行版不许换验签公钥

#### 1.1 现状

- 验签公钥有内置的一把（`external/wechat/License.ts:26`），但注释写着“测试可通过 `--license-pubkey` 注入临时公钥”（`:25`）；
- 解析时只要传了值就用传进来的（`License.ts:116-119`）；
- 命令行和环境变量都能传（`Main.ts:193`）：

  ```ts
  const licensePubkey = values['license-pubkey'] ?? env['JMBOTS_WECHAT_PUBKEY'];
  ```

- `--help` 里明写了这个参数（`Main.ts:101`：“可选覆盖验签公钥”）；
- 编 exe 时没有任何开关把它关掉（`Build.ts:91-96` 的 `Bun.build` 没有 `define`）；
- 冒烟测试恰恰靠这个口子，拿**发行版 exe** 激活授权（`SmokeExe.ts:314-318` 生成临时密钥对、带 `--license-pubkey` 启动；`:355-360` 自签授权、PUT 进去）。

**后果**：拿到 exe 的人照冒烟测试的六行做一遍，就能自签一份永不过期、不绑机器的授权。`说明.md:18-19` 写的“独立离线 Ed25519 收费授权门禁”就形同虚设。

#### 1.2 改法

`Main.ts` 文件头附近加一个常量：

```ts
/**
 * 是不是编进 exe 的发行版。Build.ts 用 define 把整个表达式换成 '1'，exe 里改环境变量也改不了它；
 * 源码跑（bun Main.ts、测试）时读真实环境，一般没有。
 */
const RELEASE = process.env.JMBOTS_WECHAT_RELEASE === '1';
```

`Main.ts:193`，改后：

```ts
  //M 换验签公钥只给源码跑的测试和另编的测试版用。
  const testPubkey = values['license-pubkey'] ?? env['JMBOTS_WECHAT_PUBKEY'];

  //G 发行版带了换公钥的参数 → 报错退出，不悄悄忽略（免得以为生效了）。
  if (RELEASE && testPubkey !== undefined) {
    throw new Error('发行版不接受 --license-pubkey');
  }
  const licensePubkey = testPubkey;
```

`Build.ts:91-96`，加一个 `--test-keys` 开关（冒烟测试用），默认编发行版：

```ts
    //M 默认编发行版：关掉换验签公钥的口子（Main.ts 的 RELEASE）。--test-keys 编给冒烟测试用的测试版。
    let define: Record<string, string> = { 'process.env.JMBOTS_WECHAT_RELEASE': '"1"' };
    if (testKeys) {
      define = {};
    }

    const buildRes = await Bun.build({
      entrypoints: [entryFile],
      target: 'bun',
      compile: { outfile: tempOutExe },
      files: { [silkLibrary]: silkContents },
      define,
    });
```

`SmokeExe.ts`：

- 解密、转语音那一段改跑测试版（`jmbots-wechat-testkeys.exe`）；
- 发行版只补一项：带 `--license-pubkey` 启动，要非零退出、报“发行版不接受”。

`License.ts:25` 的注释改成“只有源码跑和测试版能用 `--license-pubkey` 换公钥”；`Main.ts:101` 的帮助行同样注明。

`define` 换 `process.env.X` 是 Bun 文档里的标准写法（例子就是 `process.env.NODE_ENV`）。编进 exe 以后是不是真的换掉了，编一次、带参数跑一下就知道，**待核**。

#### 1.3 反方（方法 F）

- **“exe 本来就能被逆向、改字节，堵这个口子有什么用？”** 逆向要会打二进制补丁，现在只要照着 `--help` 加一个参数，门槛差了几个数量级。离线授权的共识是不留写进文档的后门，并不指望防住破解。
- **“冒烟测的就不是真正发出去的那个 exe 了。”** 两个版本只差一个 `define`。发行版另有一项专门的检查：确认这个口子是关着的。这一项正是现在缺的。
- **“环境变量 `JMBOTS_WECHAT_PUBKEY` 是给 programs 拉起时传的吗？”** 不是。`programs/Host.ts` 只往环境里放密钥和回调地址（`programs/Protocol.ts:10`、`:12`）；仓库里也没有别的地方设这个变量。

### 2. 外网门禁：失效时要关着

#### 2.1 现状

- 是不是外网，只看一个请求头：`X-External-Proxy: 1`（`http/WebAuth.ts:103-105`）。文件头写着：家里 127.0.0.1 和内网虚拟机直连没有这个头，“零打扰”（`WebAuth.ts:1-4`）；
- 判断本机先看这个头，再看 socket 地址（`http/index.ts:364-368`）：

  ```ts
  isLocal(request: fastify.FastifyRequest): boolean {
    if (webAuthModule.isExternalProxyRequest(request)) return false;
    const address = request.ip.replace(/^::ffff:/iu, '');
    return address === '::1' || address.startsWith('127.');
  }
  ```

- 本机来的直接记成“已核验”（`http/index.ts:416-420`）。这几处只认“已核验”：
  - 设目录授权（`approval/Grants.ts:315`）；
  - 批准主动发件（`approval/ChannelSend.ts:52`、`programs/ChannelSend.ts:222`）；
  - 换版（`base-bridge/UpdateWatch.ts:437`）；
  - 令牌管理只认本机（`http/Tokens.ts:120`）。
- 0.7.76 的说明写着“彻底告别丑陋浏览器 BasicAuth 弹框”（`src7/utils/Versions.json:7`）。看起来原来 nginx 那层的 BasicAuth 已经撤了，**门禁只剩后端这一道**（待核）。

**风险**：外网的请求怎么到家里这台机器，仓库里没有写（搜不到 nginx 和隧道的配置）。

- 如果是落在本机的反向隧道（frp、`ssh -R` 一类），后端看到的 socket 地址就是 127.0.0.1；
- 这时 nginx 那一行 `proxy_set_header X-External-Proxy 1` 只要漏一次（换服务器、改配置、加一条新的 location），外网请求就被当成本人：能设目录授权、批准发件、管令牌；
- 漏了也没有任何报错，网页照常打开，还更“顺”了。

这和用户唯一的底线正好冲突：不让外人看到个人数据和微信隐私。

#### 2.2 第一步：带代理头的一律不算本机（约 6 行）

`WebAuth.ts:19` 后面：

```ts
/** 反向代理会补的请求头：有一个就说明这条请求是代理转来的，不是坐在这台电脑前的人。 */
const PROXY_HEADERS = [EXTERNAL_PROXY_HEADER, 'x-real-ip', 'x-forwarded-for', 'forwarded'];
```

`WebAuth.ts:103-105` 旁边加一个：

```ts
/**
 * 这条请求是不是经过了反向代理（带了任何一个代理头）。
 * @param request Fastify 请求。
 * @returns 带了就是 true。
 */
export function isProxied(request: fastify.FastifyRequest): boolean {
  return PROXY_HEADERS.some((name) => request.headers[name] !== undefined);
}
```

`http/index.ts:364-368`，改后：

```ts
  isLocal(request: fastify.FastifyRequest): boolean {
    //G 经过反向代理的都不算本机。隧道落在本机时 socket 地址也是 127.0.0.1，只看地址会把外网当成本人。
    if (webAuthModule.isProxied(request)) return false;

    const address = request.ip.replace(/^::ffff:/iu, '');
    return address === '::1' || address.startsWith('127.');
  }
```

为什么是这几个头：`getClientIpKey` 本来就假定 nginx 会送 `X-Real-IP`、`X-Forwarded-For`（`WebAuth.ts:260-273`）。nginx 漏了 `X-External-Proxy`、却还带着这两个头，就会被这一步接住，落到“要令牌”那条路上，不再被当成本人。

`checkExternal`（`WebAuth.ts:341-352`）要不要也改用 `isProxied`，让这类请求看到登录页、而不是 401？可以改，对用户更友好，两种都是关着的。

**待核**：本机自己的工具会不会带这几个头。Vite 开发服务器的代理默认不加 `X-Forwarded-*`（`xfwd` 默认关），AOBB 是浏览器，也不加。真有带的，那个工具就要带令牌访问，不会出错，只是多一步。

#### 2.3 第二步（要用户定）：信任看入口，不看标记

- 隧道改接一个单独的端口（比如 30090），后端把从这个端口进来的连接一律当外网，不看任何请求头；
- 这样 nginx 怎么配都不会把门打开。这就是 Envoy、Kubernetes 的做法：管理入口和公开入口是两个监听；
- 写法（待核）：Fastify 只能 `listen` 一次，可以另起一个 `node:net` 服务器，把连接交给同一个 `app.server`（`emit('connection', socket)`），判断时看 `request.socket.localPort`。这个写法在 Bun 里能不能用，要先试。

#### 2.4 反方

- **“CLAUDE.md 说开发阶段不加限制，0.0.0.0 也不要加防护。”** 第一步不给用户加任何限制：本机直连、内网虚拟机直连都没有代理头，照旧免令牌。它只让用户 0.7.76 自己要的门禁在出错时关着，服务的正是“不让外人看到个人数据”这一条。
- **“nginx 是我们自己配的，不会漏。”** 那份配置不在 git 里，没有检查盯着，漏了也不报错。代码里的假设又写在三处（`WebAuth.ts:1-4`、`http/说明.md:4`、`config.example.yaml:78`），都是“nginx 一定会加”。
- **“`X-Forwarded-For` 的第一段是客户端能伪造的，限速会被绕过。”** 对，但这是另一件小事：`getClientIpKey` 先看 `X-Real-IP`，只要 nginx 用 `$remote_addr` 设它，就伪造不了。本篇不展开。

### 3. 先归档、后索引：写成一个监听里的两步

#### 3.1 现状

- `memory` 插件装了两组监听，都挂在 `channel/direct`、`channel/mention`、`channel/listen` 上，都写 `{ prepend: true }`：
  - 索引：`memory/ChannelIndex.ts:653-655`（`applyChannelIndex`，在 `memory/index.ts:831` 装）；
  - 聊天归档：`channels/ArchiveListen.ts:47-49`（`applyChatArchive`，在 `memory/index.ts:834` 装）。
- 索引要用归档刚复制好的附件，它去磁盘上找：

  ```ts
  //M 归档监听已经创建目录并复制附件，这里只确认目标文件存在。
  const directory = archive.chats.getDirectory(chat);
  ...
    if (!fs.existsSync(target)) continue;
  ```

  （`memory/ChannelAttachments.ts:33-41`）
- 归档其实已经算出了这些路径（`ArchiveListen.ts:148-161` 的 `copyAttachments` 返回 `附件/名字` 列表），只是用完就丢了；
- 谁先跑，靠的是 Cordis 的 `prepend` 用 `unshift`，后登记的反而排前面。`memory/index.ts:833` 写着：

  > prepend 后登记先执行。先复制 Markdown 附件，再写索引，接着交给机器人认领。

**后果**：有人觉得“先装归档再装索引更顺”，把 `:831` 和 `:834` 换个位置，或者把归档挪到别的插件里装，索引里的附件就全空了（`continue` 跳过），不报错。`channel/history` 那条路也一样（`ChannelIndex.ts:663`）。

现在这三个入站事件上，带 `prepend` 的有 approval、memory 的两组、voice 四家（`approval/index.ts:456-462`、`voice/Replies.ts:24-29`）。它们之间谁先，全看挂载顺序倒过来。`channels/index.ts:18` 的注释已经在给读的人解释这个反序了。

#### 3.2 改法

归档那边把“记一条用户的话”提成一个函数，交回复制好的附件路径（相对运行时根目录，和索引现在存的一样）。`ArchiveListen.ts:29` 的 `onInbound` 原样搬进去，最后多一行 `return`。

`memory/index.ts:826-834`，改后：

```ts
  //M 用户的话：先归档（复制附件），再拿归档交回的附件路径写索引。
  //M   两步写在一个监听里，不靠 prepend 的先后；索引没开就只归档。
  const onInbound = (message: protocol.ChannelMessage): void => {
    const attachments = chatArchive.recordInbound(message);
    channelIndex?.addInbound(message, attachments);
  };
  ctx.on('channel/direct', onInbound, { prepend: true });
  ctx.on('channel/mention', onInbound, { prepend: true });
  ctx.on('channel/listen', onInbound, { prepend: true });
```

- `channel/history` 照此改：循环里先 `recordInbound`，再交给索引；
- `ChannelIndex.ts:638-655` 的 `onInbound` 改名 `addInbound`，多收一个 `attachments` 参数，不再自己挂监听；
- `memory/ChannelAttachments.ts` 整个删掉（47 行）；
- `memory/index.ts:833` 那句注释删掉。

README 或 `src7/docs/Cordis用法/02_事件.md` 补一句规矩（照 Bevy：同一阶段里的系统默认无序，要有先后就显式 `chain`）：

> `prepend` 只保证排在不带 `prepend` 的前面。两个 `prepend` 之间谁先不许有依赖；真有依赖，写成一个监听里的两步。

#### 3.3 反方

- **“归档和索引合进一个监听，就绑在一起了。”** 现在已经绑着：索引靠 `existsSync` 读归档复制的文件，只是这层关系看不见。改完绑得明明白白，还少了一个 47 行的文件。
- **“发一个 `channel/archived` 事件，让索引去听，更解耦。”** 只有一个听众，又多一个事件，正是 CLAUDE.md 说的“为一次用途另建接口”。两组监听本来就在同一个插件里相邻两行装，一个函数里写两步最直白。
- **“approval 改地址（`Grants.applyMessage`）和归档谁先，要不要也管？”** 归档和索引都不读 `address.grants`，现在没有依赖，所以不用管（待核：以后归档要不要记授权）。

### 4. 进程插件的线上格式只写一份（要用户定）

#### 4.1 现状：两份，已经开始漂

#### 4.2 两个方案

把 `programs/Protocol.ts:1-103` 里两边都用的部分（三个常量、`AttachmentNote`、`InboundMessage`、`InboundReceipt`、`ReplyCall`、`ReplyCallStatus`、`isSameKey`，再加上 `PROTOCOL_VERSION` 和 `LicenseState`）拆成 `programs/Wire.ts`。只引 `node:crypto`，不引 `src7/` 别的文件。主程序这边的 `waitReady`、`readReport` 这些留在 `Protocol.ts`，自己引 `Wire.ts`。

| 方案 | 做法 | 得到 | 代价 |
|---|---|---|---|
| A 直接引 | 外置微信 `import * as protocol from '../../src7/plugins/programs/Wire.ts'`，删掉自己那份。Bun 编 exe 时会把它打进去，运行时不依赖 `src7/` | 删 87 行，只有一个源头 | 外置目录的“零跨目录引用”要给 `Wire.ts` 开个例外 |
| B 抄一份、加核对 | `external/wechat/Protocol.ts` 和 `Wire.ts` 逐字一样，`ztools/` 加个约 20 行的脚本比对两份文件（照 Go 的 `vendor/modules.txt`），并进现有的检查 | 外置目录照样自包含，搬出仓库也不受影响 | 多一个脚本；两份要一起改 |

外置插件要是还在仓库里，A 最省。用户 #161 说过外部插件、收费插件将来放到仓库外面单独编译；真要搬，就选 B，搬的时候把核对脚本一起带走。这件事要用户定。

不管选哪个，`readLicense` 和 `getLicenseLabel` 都改用 `LicenseState`；`programs/Protocol.ts:1` 的注释按选定的方案改成实话。

## 四、考虑过、不借的

| 借什么 | 支持的理由 | 为什么不借 | 什么时候再看 |
|---|---|---|---|
| HTTP 条件请求（ETag、304）代替 `/version` 探针 | 工作决策每 30 秒探一次 `/api/work-decision/version`（`work-decision/Routes.ts:470`、`web/src/DecisionMap/DecisionMapPage.tsx:33-34`）；用 ETag，“探”和“取”能合成一次 | 只有这一个页面这样做，最多省一个接口、十几行；用户禁了 SSE、WebSocket，ETag 不冲突，只是现在不值得 | 第二个页面也要探针时，统一换成 ETag |
| `@fastify/cookie`、`@fastify/rate-limit` 换掉 WebAuth 手写的部分 | `readCookieValue`（`WebAuth.ts:281`）、`formatSessionCookie`（`:302`）、`issueToken`（`:434`）、`recordFailure`（`:481`）都是常见轮子 | 加起来约 80 行，换库少写几十行，却多两个依赖；限速插件默认按 `request.ip` 计，隧道下大家都是同一个地址，还得另配 `keyGenerator`，省不了多少 | WebAuth 要加多用户、多种登录方式时 |
| 在线激活（授权服务器） | 能吊销、能查用了几台 | 离线 Ed25519 加机器指纹已经是常见做法，不依赖服务器、不怕断网；问题只在第 1 条那个口子 | 真要卖、要能吊销时 |
| Bevy 的“先后歧义”自动报警 | 两个插件都 `prepend`、又碰同一个字段时自动报出来 | 要靠静态分析看出谁改了哪个字段，做不准；第 3 条那句规矩加上教程页的 listeners 列表，现在够用 | `prepend` 的监听多到靠人看不过来时 |
