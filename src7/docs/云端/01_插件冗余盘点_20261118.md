## 二、证据和方案

### 0. 动手前先问的三个问题（方法 C）

**问题一：一个插件凭什么单独占一个文件夹？** 按第一性原理，我的标准是三条：

- 配置里会单独开关它；
- 一句话说得清它管什么；
- 别的插件用它时，只用它的一两个入口。

三条都不满足，或者用它的地方总得把它和另一个插件拼着用，就该并。

**问题二：用户嫌的“插件多”，到底是个数多，还是同一件事分在好几处？** 用户 #156 的原话是“是不是冗余、功能重叠，看不过来”，病根更像后者。所以结论里的第 1、2、3、5 条合并的是概念，只有第 4 条是减插件个数。

**问题三：消息正文到底该存几份？**

- 渠道自己的原始记录（微信的库、飞书的日志）不能省：里面有机器人没收到过的话。
- 会话记录（`sessions` 表）不能省：它是会话的真相。
- 其余都是为了“查”另建的副本，应该只剩一份索引。

**1.3 动手前要核的两个问题**

- **问一：微信的话进不进索引？** memory_channel_messages 只记 `channel/message` 和 `channel/reply`（`ChannelIndex.ts:2-3`）。微信里没勾“监听”的会话“只存不交”（`wechat/index.ts:6`、`:8`），这些话不会进索引。在手机上人工回的话进不进，待核。所以微信、飞书自己的原始记录要留着，`channel/history` 这条路也要留。
- **问二：并表缺什么？** bot_log 有 sessionId 列，前台用它圈出“本场前台和它交办的后台”（`FrontDesk.ts:747` 的 scopeIds）。memory_channel_messages 没有会话列（`ChannelIndex.ts:89-91`）。并表要加一列 session_id。

**1.4 顺带发现：微信前台的一次请求里拼了两段“最近 50 条”**

- 第一段：`bots/FrontDesk.ts:583-584`。前台每一步都拼最近 N 条往来，N 默认 50（`bots/index.ts:798`），来源是 bot_log。
- 第二段：`wechat/index.ts:634-647`。微信来的会话再拼一段最近 50 条，来源是 wechat_messages。
- 第二段末尾还写死了一句“你的回复只会存成草稿给人看，不会自动发出去”。可会话开了自动发（`wechat_watch.auto`，`wechat/index.ts:194`）时，这句话是错的。实际效果待核。

**1.5 三版方案**

| 乙：合工具，再并表 | 在甲的基础上，bot_log 并进 memory_channel_messages（加 session_id 列；谁说的用已有的 direction 列表示）。删掉 bot_log_vec 和本地余弦（`FrontDesk.ts:846-1015`），语义检索只走 `ctx.memory` | 再少 2 张表，再省约 250–350 行 | 没开记忆服务时，语义搜退成只按字搜 |

推荐乙，答完问一再做丙。

索引表放在哪：现在在 memory（`ChannelIndex.ts`），可天天用它的是前台。有两种放法：

- 留在 memory，bots 通过 `ctx.memory` 查。bots 本来就可选地依赖 memory（用 `ctx.inject`）。
- 挪进 bots，因为“往来”本来是 bots 的概念。

推荐第一种：不挪文件，改动最少。

改后的样子（只登记一个工具，照 CLAUDE.md 的写法）：

```ts
//M history：查往来的唯一工具。默认查本机索引（各渠道收发都记在 memory_channel_messages）；
//M   source 写 channel 时改问渠道自己（微信没交给机器人的话、飞书群的原始日志），走 channel/history。
this.ctx.tools.register({
  definition: {
    name: 'history',
    description: '查往来记录，新的在前。可按渠道、聊天、谁说的、@我、关键词、时间筛；要全文用 history_get。',
    parameters: HISTORY_PARAMETERS,
  },
  kinds: ['front', 'work'],
  run: (args, session) => this.history(session, args),
});
```

```ts
private async history(session: Session, args: Record<string, unknown>): Promise<string> {
  //M 问渠道自己：本机索引里没有的原始记录。
  if (args['source'] === 'channel') return this.askChannel(session, args);

  //M 默认查本机索引；外人只看这一轮来源快照里的这个聊天（判断在 Channels.ts 的 isHistoryOwner）。
  const query = this.getQuery(session, args);
  const rows = this.memory.searchChannel(query);
  return this.format(rows);
}
```

### 3. 给外部 AI 交活的三条路（结论第 3 条）

| 路 | 入口 | 存在哪 | 结果怎么回来 |
|---|---|---|---|

| 留言 | 工具 `note_claude`（`relay/NoteClaude.ts:21`） | `integrations/claude/inbox/*.md` | 不回 |

**按第一性原理看**：三条路都是“一件交办”，记的都是同几样东西：

- 交给谁；
- 谁交的（哪场会话、哪个渠道地址）；
- 正文和附件；
- 现在什么状态，回信是什么。

它们只在两个开关上不同：

- 外部方怎么拿到活：推给它（webhook），还是它自己来领；
- 回信怎么处理：原样发给用户（direct），还是交给前台整理。

这两个开关都是一条记录上的字段，用不着两套表。

**还有一处违反 CLAUDE.md**：“外部助手、机器人的名字也一样，代码里不写死”。可 `NoteClaude.ts:23-24` 的工具说明写死了“Claude”，目录 `integrations/claude/inbox` 也写死了。

| 甲：只并留言 | 删掉 `note_claude`。要给 Claude 留话，就用 `agent_task send`，执行端写 Claude，任务协议加一个 `reply: false`，表示不等回信 | 少 1 个工具、1 个目录约定，约 40 行；顺带去掉写死的名字 | `ztools/claude-link` 要改成读任务，这是本地 AI 的活 |

**名字**：并完以后叫 models 更准。但改名要改每个人 `config.yaml` 的 plugins 段，所以建议不改名，在说明.md 第一行写清：“模型：清单、换模型、介绍和评价、用量”。

**省多少**：每个插件的样板约 30–40 行（name、version、inject、配置校验入口、declare module、说明.md 开头），4 个合计约 150 行。插件地图和教程页也各少 4 项。

**要核的一处**：model-catalog 要写在 plugins 段最后，因为 Fallback 要在 `session/request` 上排最后。usage 并进去以后也跟着最后挂。usage 只听 `session/message` 和 `model/failed`，按理不受挂载先后影响，待核。

### 5. 轨迹整理有两份（结论第 5 条）

两份做的事：

- tutorial：`tutorial/Trail.ts:392` 的 getTrail 把 journal 行收成步骤，`Lanes.ts:180` 的 getLanes 再摆成泳道。数据由 `tutorial/Files.ts:252` 发 `journal/request`（message-lines）取。
- web-api：`web-api/Trace.ts:216` 的 trace() 发同一个 `journal/request` 取数（`:240`），另外再拼上 `usage/list`（`:247`）。

两边的起点也一样：都从 `journal/index.ts:251` 查到的 `name = 'web-api/received'` 那一行开始。

**两版方案**：

- **推荐**：把“行 → 步骤”放进 journal，因为数据归它管。`journal/request` 加一个 action steps；tutorial 在此之上加快照和泳道，web-api 在此之上加用量。约省 150–250 行，两边的步骤格式要先对一遍（待核）。
- **不推荐**：让 web-api 的追溯直接调 tutorial。tutorial 是可选插件，聊天页的追溯不该依赖它。

### 6. 不建议并的（先假设“该并”，再找反例）

- **decision 并进 approval**：三个调用方是 approval、progress（限时到了要不要延）、bots/FrontDesk（群里要不要接话）。后两个都不是审批，并进去会让 approval 名不副实。只删死事件（第 2 节）就够了。
- **approval/decided 按 kind 分发**（11-17 第 8 条）：现在有 7 个监听，6 个各在开头按 kind 过滤：`exec/index.ts:285`、`exec/Runs.ts:216`、`progress/index.ts:256`、`progress/Review.ts:146`、`base-bridge/UpdateWatch.ts:229`、`wechat/index.ts:863`。剩下 `feishu/cards/Cards.ts:66-70` 全收。改了每处只省一两行，不值得为此加一层。
- **desktop、image-gen、web-search**：各自单独开关，各接一个外部能力，一句话说得清，三条标准都满足。并成一个“外部工具”插件，只是换了个文件夹名，配置反而要分段写。
- **fake-model**（71 行）：离线测试要单独挂它。并进 model-catalog，会让测试用的假模型和真正调模型的代码混在一个插件里。
- **workspaces**：bots 依赖它，但它有自己的表、工具和配置开关。并进 bots，会让已经 5,300 行的 bots 更难读。
- **assist**：react、todo 和别处没有重叠。ask 和 `approval.ask` 形状不同：assist 是多个选项，答案当成用户的话发回；approval 是同意或拒绝。硬并要给 `approval.decide` 改签名，付出的比省下的多。
- **session/after-model**（`Sessions.ts:529`）：现在一个监听都没有，但它是用户 #113 定下的四个关口之一，留着。

**只留痕、没人听的事件**：

- 这三个事件没有业务上的监听，只靠 journal 在 `internal/dispatch` 上记一行：
  - `model/fallback`（`model-catalog/Fallback.ts:211`、`:227`）；
  - `workspaces/changed`（`workspaces/index.ts:615`）；
  - `web-api/model`（`web-api/index.ts:1005`）。
- 建议不删，但在各自说明.md 的“发的事件”里写一句“只留痕，没人听”，免得读的人去找监听者。
- `web-api/received` 不算这一类：journal 靠它找到一条消息的起点（`journal/index.ts:251`、`utils/Trace.ts:125`）。
