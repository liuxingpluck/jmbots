# 第四块：插件之间一问一答

读完这一块，你能说清楚：一个插件想让另一个插件办件事、并拿到结果，现在是怎么做的——发一个“请求事件”、等一个“回执事件”，怎么配对、谁接单、没人接怎么办、等太久怎么办。

只讲 5 个概念，都在 `src7/utils/RequestEvent.ts`（两百多行，两个主要函数）。这一块要先懂第一块的“挨个问（`ctx.serial`）和通知（`ctx.emit`）”，和第二块的 `channel/reply` ↔ `channel/replied`。决策图上待定的 q-ev-serial（另一种写法）不在这一块讲，两种写法的对照放在 `附录_一问一答两种写法.md`。

## 概念一：请求事件和回执事件——两个事件配成一对

**一句话**：插件 A 要插件 B 办事，不直接调 B 的函数，而是发一个“请求事件”；B 办完再发一个“回执事件”。一问一答 = 两个事件。比如 `context-fit` 插件要查模型的上下文窗口：发 `model-catalog/request`，等 `model-catalog/result`。A 不知道也不用知道谁来办。

**代码里**：提问的一方 `src7/plugins/context-fit/index.ts`

同一个插件里还有另一对：`Usage.ts:190` 的 `model-catalog/usage` ↔ `model-catalog/usage-result`。

这是 CLAUDE.md “插件之间尽量只靠事件”的落地：只发事件、收事件，不管别人怎么做、做多久。

**类比**：门诊医生开一张化验单送检验科（请求事件），检验科做完出一份报告（回执事件）。医生不用知道是哪位检验员做的、怎么做的。

## 概念二：`requestId`——靠单号认回执

**一句话**：同一时间可能有很多人在问。`requestEvent` 每次发请求都自动生成一个 `requestId`（带前缀，如 `apr_…`），回执必须原样带回；提问的人只认单号对得上的那份，别的回执当没看见。

**代码里**：`src7/utils/RequestEvent.ts`

```ts
// src7/utils/RequestEvent.ts
96	  const requestId = `${prefix}_${crypto.randomUUID()}`;
```

```ts
// src7/utils/RequestEvent.ts
124	    dispose = bus.on(String(resultEventName), (event: EventArg<ResKey> & ResultEnvelope) => {
125	      if (event.requestId !== requestId) return;
126	
127	      //M 收到匹配当前 requestId 的回执，结束本次请求等待。
128	      finish({ reply: event });
129	    });
```

注意顺序：先挂好“听回执”的监听（第 124 行），再发请求（第 143 行）。不然办事的人当场就回了，回执会漏掉。收完回执（或中止、出错）都会把监听撤掉，不留残渣（`finish`，第 111–121 行）。

**类比**：化验单上的条码。同时送了三份化验，报告上的条码对得上哪张单，就是哪份的。

## 概念三：`handled`——接单，传完一圈没人接马上退回

**一句话**：请求事件是用 `ctx.serial` 挨个问的，而 `serial` 会**等每个监听函数跑完**（连它里面的 `await`），才问下一个。所以接活的插件是当场办完、把回执发出去，才轮到下一个人。全部问完，提问方再看 `handled`：没人标，说明没人管，立刻退回，不用傻等超时。不是自己的活就别标（`filter` 返回 false），留给后面的人。

`onRequestEvent` 在第一个 `await` 之前就标好 `handled`，这是个保险：万一有人把活扔到后台不等，提问方也不会误判。另外要知道：办得慢的办事方，会把排在它后面的监听者都挡住。

**代码里**：Cordis 的 `serial`（`node_modules/cordis/lib/index.js`，cordis 4.0.0-rc.12）

```js
// node_modules/cordis/lib/index.js

757	      const result = await Reflect.apply(callback, thisArg, args);
758	      if (isBailed(result)) return result;
759	    }
760	  }
```

## 概念四：退回——没得到正常回执时拿什么

**一句话**：调用方直接拿 `{ reply }` 或 `{ why, detail? }`，没收到正常回执的原因有 3 种：`unhandled`（没人接）、`aborted`（外面叫停，包括调用方自己传 `AbortSignal.timeout(...)` 到点）、`error`（监听器抛错）。所以 `requestEvent` 总会返回一个结果对象，不会抛错。

**代码里**：`src7/utils/RequestEvent.ts`

```ts
// src7/utils/RequestEvent.ts
14	export type FallbackReason = 'unhandled' | 'aborted' | 'error';
```

```ts
// src7/utils/RequestEvent.ts
106	    const onAbort = (): void => {
107	      //M 外部信号中止（含调用方自己设的时限到了）时立即结束等待并清理监听。
108	      finish({ why: 'aborted' });
109	    };
```

注意，退回只是提问方不等了。办事方不知道，会接着办完，办完发的回执没人收（命令审批另外把停止信号传过去，退回时叫停审批那边，见第五块概念四）。所以写操作拿到退回时，只有 `unhandled`（没人接）能确定对方没做；别的两种（`aborted`、`error`），对方可能已经做了。

退回怎么处理，由业务决定。比如查不到模型的上下文窗口，就按没登记处理（`src7/plugins/context-fit/index.ts:222` 读 `result.reply?.info`，为空则窗口记 0）；`exec` 的命令审批没回就退回“拒绝”（`src7/plugins/exec/Runs.ts:107` 判 `asked.why !== undefined`）。

**类比**：化验单送出去，有四种等不到报告的情况：没有科室接这张单、等了太久、医生自己撤了单、化验时出了事故。每一种都要提前想好“那就……”。而且医生撤了单，检验科不一定知道，可能照样做完。

## 概念五：两个函数——`requestEvent` 提问，`onRequestEvent` 办事

**一句话**：提问的插件调 `requestEvent`（它包办单号、等回执、超时、中止、退回）；办事的插件调 `onRequestEvent`（它包办“接单 `handled`”、跑你的处理函数、把你返回的内容配上同一个 `requestId` 发成回执，出错时可转成失败回执）。两边各写业务那一小段，其余是公用的。


回执是 `emit`（通知），不是返回值：提问方是靠挂监听“听到”它的。如果请求里没带 `requestId`，办事方办完不发回执（相当于“发出去就不管了”的通知式指令）。

第二块那条 `requestChannelReply`（`src7/plugins/channels/Reply.ts`）也走这个工具：发 `channel/reply`、等 `channel/replied`，没渠道接单回 rejected，接单后出错回 uncertain。

**类比**：`requestEvent` 是标准化验单，`onRequestEvent` 是检验科的标准报告单。全院用同一套单子，不用每个科室各自发明。

## 读完自测

1. 为什么 `requestEvent` 要先挂“听回执”的监听，再发请求？
2. 办事的插件什么时候该标 `handled`？它办得很慢时，排在它后面的监听者和提问方各会怎样？
3. 提问方能拿到哪四种退回？为什么 `requestEvent` 不会一直挂着不返回？

<details>
<summary>答案</summary>

1. 办事方可能在被问的当下就发回执；如果先发请求再挂监听，回执会漏掉（`RequestEvent.ts:123` 注释，监听在第 124 行，发请求在第 143 行）。
2. 是自己的活就标，不是就不标（`filter`，第 58 行、第 180 行）。`serial` 会等它办完才问下一个，所以后面的人都得等。提问方若传了 `signal`（含 `AbortSignal.timeout(...)`）到点先拿退回；但办事方不会因此被叫停，还会接着办完（见概念四）。
3. `unhandled`（没人接）、`aborted`（外部叫停或限时信号到点）、`error`（监听器抛错），第 14 行。每种路径都会走 `finish` 交回 `{ why }`；传了 `signal` 会监听 `abort`（第 106–109、140 行），没人接有 `handled` 检查（第 144–147 行），所以无人接或传了限时信号时总会返回。

</details>
