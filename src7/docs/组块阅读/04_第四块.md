# 第四块：前台、后台和小会话

读完这一块，你能说清楚：骨架里“前台”“后台”“小会话”其实是同一种东西（一场会话），只是 `kind` 不同；前台怎么把活派给后台、后台做完结果怎么回来；插件想临时问模型一句（审批、压缩、总结）怎么开小会话；以及“喊停”在三种情况下各是什么效果。

只讲 5 个概念。要先懂第一块的“会话 = 一份记录 + 一个循环”和第二块的前台会话。结果怎么发回渠道的细节（队列、重试）这一块不管。

## 概念一：`kind`——会话的种类，决定它能用哪些工具

**一句话**：前台、后台、小会话在骨架眼里没有区别，都是 `SessionRow`，只有 `kind` 这个字符串不同。骨架不解释 `kind`，只拿它去对工具登记时写的 `kinds`：工具说“我给 `['front']` 用”，那后台会话就看不到、也调不了它。

**代码里**：`src7/Sessions.ts`（`kind` 字段）和 `src7/Tools.ts`（对 `kind` 筛工具）

```ts
196	  /** 种类。骨架不解释它，只拿它去对工具登记时写的 kinds；有哪几种由开会话的插件定。 */
197	  kind: string;
```

```ts
129	    const usable = all.filter((spec) => spec.kinds.includes(kind));
```

执行时也要再对一遍（`Tools.ts:160`），模型就算胡乱编一个工具名也调不动。

现在用到的几种（都是插件起的名字，不是骨架规定的）：

- `front`：前台，直接面对用户（`FrontDesk.ts:460`）；
- `work`：后台，前台派出去干活的（`DispatchTools.ts:238`）；
- `exec-review`、`compress` 等：小会话，一次性的（`approval/index.ts:311`、`context-fit/Compress.ts:145` 附近）。

比如 `hand_session`（派后台）登记的是 `kinds: ['front']`（`DispatchTools.ts:86`）：只有前台能派活，后台不能再往下派。

**类比**：公司里的工牌颜色。保安、前台、临时工谁能进哪个房间，看工牌颜色（`kind`），楼本身不管你叫什么名字。

## 概念二：前台——一个客户一场，找得到就沿用

**一句话**：一个机器人对一个客户（或一个聊天）只有一场前台会话。消息进来，先按“哪个机器人 + `kind: 'front'` + 客户号”去库里找，找到就打开接着聊，找不到才新开。

**代码里**：`src7/plugins/bots/FrontDesk.ts`

```ts
460	    const input: { bot: string; kind: string; customer?: string } = { bot, kind: 'front' };
```

```ts
466	    const found = this.ctx.sessions.find(input)[0];
```

对应骨架里两个函数：`Sessions.find`（`Sessions.ts:349`，只读记录、不带整场对话，最近动过的在前）和 `create`（`Sessions.ts:278`，新开一场）。`find` 能按插件自己加的项（比如 `bot`、`customer`）找，是因为记录的 `meta` 存成了 JSON，查询用 `json_extract`，不用改表。

**类比**：银行大堂经理。老客户来了先翻名册找“这位客户的专属经理”，找到就接着办；新客户才安排一位新的。

## 概念三：派后台——前台调 `hand_session`，后台做完结果回前台

**一句话**：用户的话是前台在接。前台模型觉得要慢慢干的活，就调 `hand_session` 工具：骨架新开一场 `kind: 'work'` 的会话，`parent` 指回这场前台，把话交给它、推它去跑，**不等**。后台做完后，结果先排回前台，由前台整理再回给用户，后台不直接对用户说话。

**代码里**：`src7/plugins/bots/DispatchTools.ts` 的 `create`

```ts
237	    const work = this.home.sessions.create({
238	      kind: 'work',
239	      bot: bot.name,
240	      parent: front.id,
```

```ts
256	    bot.hand(plan.text, workOrigin, work.id);
```

`bot.hand` 在 `plugins/bots/index.ts:956`：把话交进那场会话（记回话往哪送、`session.add`），然后推它跑，不等。后台那一轮做完会发 `session/change`，`DispatchResults.ts:187` 听到后在 `returnWork`（第 408 行）把结果排进前台的队列，前面补一句“（做完了）”之类的状态词，让前台好整理。

`hand_session` 的 `action` 有两种：`new` 新开，`append` 接着一场已有的（暂停了的也用 append 接着做）。正在跑的后台只能补话，换模型要先暂停（`DispatchTools.ts:285` 的 `running_model_change`）。

另外，**后台也能被“受管”**：记录里带 `frontTask`（`DispatchTools.ts:225` 起，记着是哪场前台派的、第几轮、有没有暂停），没有 `frontTask` 的是老式后台。

**类比**：前台是接待员，后台是车间师傅。接待员收到“修一下这台机器”，开一张工单扔给师傅就接着接待别人；师傅修完把结果放回接待员桌上，由接待员跟客户说。

## 概念四：小会话——`sessions.ask`，一次性的模型提问

**一句话**：插件有时只需要问模型一句话、拿一个答案（这条命令危不危险？把这段对话压成摘要）。不用自己拼模型请求，调 `ctx.sessions.ask(...)`：它新开一场小会话，说一句，跑到底，把“做没做完”和回答交回给你。小会话没有渠道，不会把话发给用户。

**代码里**：`src7/Sessions.ts`

```ts
374	  async ask(input: AskInput): Promise<AskResult> {
...
377	    const child = this.create(fields);
378	    child.add(text);
```

整个函数就是 `create → add → run` 连起来；最后 `ok` 只有状态是 `done` 才是 `true`（`Sessions.ts:392`）。调用方一定要处理 `ok === false`，比如压缩失败就这次不压（`context-fit/Compress.ts` 里 `if (!ok) return done`）。

调用方在 `AskInput` 里填：`kind`（自己起个名字，比如 `compress`）、`parent`（嵌在哪场会话里）、`text`、可选 `signal`（提问方被叫停，小会话也跟着停：`Sessions.ts:381–384`）。

用到它的有：命令审批的“第三档”（`approval/index.ts:605`）、压缩（`context-fit/Compress.ts:145`）、总结（`context-fit/Summary.ts:87`）、判断（`decision/index.ts:338`）、进度收尾和复盘（`progress/index.ts:1057`、`progress/Review.ts:306`）。

**类比**：开会时临时叫来一位专家，问一句、他答一句、他就走了；不留办公室，也不用给他派后续任务。

## 概念五：喊停 `stop`——三种场合同一个出口

**一句话**：喊停的出口只有一个：`Session.stop(by)`。它把状态改成 `stopped`，写 `reply = 已停止（by）`，同时 abort：正在等的模型请求马上掐断，慢的工具也拿到停止信号断开。已经停了或根本没在转，再喊就什么都不做（免得“已停止”被再发给用户一遍）。

**代码里**：`src7/Sessions.ts`

```ts
648	  stop(by: string): void {
```

```ts
659	    this.change('stopped', `已停止（${by}）`);
660	    aborter.abort();
```

谁会去调它：

- **关口上的插件写了 `stop`**：会话循环自己调（`Sessions.ts:556`、`588`、`636`，见第一块）；
- **前台的 `stop_session` 工具**：对后台，`DispatchTools.ts:359` 的 `pause`。受管后台先记 `task.paused = true` 并存库（第 381 行），再 `stop('前台暂停')`（第 384 行）。记暂停是为了：被停的这一轮结果不再交回前台（`DispatchResults.ts:413`），以后 `hand_session append` 再把 `paused` 改回 `false` 接着做。不受管的老后台只是直接 `stop('前台')`（第 376 行）；
- **小会话的提问方被叫停**：`ask` 里的 `signal` 一断，就 `child.stop('提问方停了')`。

注意：停的是“这一轮”，会话记录和已做的事都留着，不回滚；正在执行的工具可能还在收尾（`pause` 的回执里有 `inFlightMayBeFinishing`）。

**类比**：车间的急停按钮。按下后机器停转、已经做出来的零件留在台面上；要继续，再发一张“接着做”的单子。

## 读完自测

1. 为什么后台会话不能再调 `hand_session`？这个限制是在哪里写的、在哪里挡住的？
2. 前台派出一场后台以后，前台会等它做完吗？后台的结果怎么到用户手里？
3. 一个插件想问模型“这段话是不是广告”，该调什么？拿到 `ok === false` 是什么意思？

<details>
<summary>答案</summary>

1. `hand_session` 登记时写了 `kinds: ['front']`（`DispatchTools.ts:86`）；`Tools.list`（`Tools.ts:129`）不会把它列给 `kind` 是 `work` 的会话，`execute`（`Tools.ts:160`）也会因为 `kinds` 不含它而回“没有这个工具”。
2. 不等。`bot.hand` 把话交进后台就“推它跑，不等”（`index.ts:956`）；后台那一轮做完发 `session/change`，`DispatchResults.returnWork`（第 408 行）把结果排进前台队列，前台整理后再回给用户。
3. 调 `ctx.sessions.ask({ kind: '自己起的名字', parent, text, signal })`。`ok === false` 表示小会话没做完（出错或被停了），这时 `reply` 是原因而不是回答，调用方要自己决定怎么办（审批当“拿不准”，压缩就不压）。
