# 第七块：进程插件

读完这一块，你能说清楚：

- 收费插件为什么编成二进制、不装进主进程；
- 系统插件 `programs` 怎么把它拉起来、看住它、关掉它；
- 主程序怎么调它，它又怎么调回主程序、调到内部插件；
- 只发二进制为什么就够防破解；
- 外置微信 `external/wechat` 是怎么照这套走的。

只讲 5 个概念。要先懂第二块的 `channel/message` 和回复、回执，第四块的“请求事件 + 回执事件”。

## 概念一：为什么不装进主进程

**一句话**：插件分两种接法（用户 11-18 #178 定的，`docs/开发进度/外部插件规划_一页_20261118.md` “用户定了”第 2 条）：

- 开源插件：编成 JS，主程序直接加载，和 `src7/plugins/` 下的插件一样挂进 Cordis；
- 收费插件：编成二进制，走**进程插件**，由系统插件 `programs` 按 `config.yaml` 里写的可执行文件路径和参数拉起，作为一个独立进程运行。

二进制装不进主进程，原因有两条：

- 主程序挂插件是 `import` 一份 JS（第一块），二进制不是 JS 模块；
- 装进同一个进程就能互相读内存、拿到 `ctx`，收费插件的授权和代码都没法隔开。

所以收费插件和主程序之间**只隔一层本机 HTTP**，彼此只认接口。

**代码里**：`programs` 插件只在主程序就绪后拉起配置里的程序，`src7/plugins/programs/index.ts`

```ts
// src7/plugins/programs/index.ts
524	  //M 主服务就绪后才启动程序，HTTP 晚挂时也能补登记路由。
525	  ctx.on('ready', () => programs.startConfigured());
```

`startConfigured` 在第 172–184 行，`autostart` 为 `true` 的才拉起（第 182 行）。

**类比**：外院专家来会诊。他不进本院编制、不用本院的病历系统，只通过会诊单和本院打交道。

## 概念二：programs 怎么管它——拉起、认人、看住、重启、请它退出

**一句话**：一个程序一个 `Host`（`src7/plugins/programs/Host.ts`），按下面的顺序管：

1. 按 config 拉起：每次拉起都换一把新密钥，放进子进程环境，不套命令行外壳；
2. 读 stdout 报的端口：程序第一条带数字 `jmbots` 字段的 JSON 行就是就绪行；
3. 核对身份：就绪行的名字、协议版本，再问一次 `/jmbots/v1/info`，名字对得上才算这个程序；
4. 健康检查：每 3 秒问一次 `/jmbots/v1/health`，连续 5 次失败就重启；
5. 崩了退避重启：等 3 秒、6 秒、12 秒……最多 60 秒，10 分钟内崩 5 次就放弃；
6. 关的时候先请它自己退出：`POST /jmbots/v1/exit`，等不到再强制结束。

**代码里**：拉起和读就绪行，`Host.ts` 的 `runChild`

```ts

381	      const key = crypto.randomBytes(32).toString('base64url');
382	      const env: Record<string, string | undefined> = { ...this.launch.env, [protocolModule.KEY_ENV]: key };
...
401	      //M 不套命令行外壳，读子进程的 stdout 并隐藏 Windows 控制台。
402	      const child: Child = Bun.spawn(command, options);
...
424	      //M 就绪行报端口，info 身份正确后才能向该程序转发或请求退出。
425	      const ready = await protocolModule.waitReady(reader, this.spec, lifetime);
...
429	      const report = await protocolModule.readReport(url, this.spec.name, 'info', this.timing.healthMs, lifetime);
```

就绪行的样子：

```json
{"jmbots":1,"event":"ready","name":"wechat","version":"0.3.0","port":43121}
```

核对在 `src7/plugins/programs/Protocol.ts` 的 `parseReady`（第 196–226 行）：

- 协议版本不对抛 `UnsupportedProtocol`，不再自动重试；
- 名字不符、缺版本、端口不对都抛错。

其余几步的位置：

- 身份核对完才标 `ready`、发 `program/state`：`Host.ts:442–448`；
- 健康检查：`watchHealth`，`Host.ts:498–534`，间隔和次数在 `Host.ts:41`；
- 退避：`supervise`，`Host.ts:308–371`，算等多久在第 351 行，放弃在第 342–349 行；
- 请它退出：`releaseChild`，`Host.ts:537–569`，第 544 行调 `requestExit`，等不到再 `killTree`。

**类比**：外院专家到了先在门口登记（就绪行），保安打电话核对名字（info）；会诊期间护士隔一会儿看一眼他还在不在（health）；人突然走了就再请一次，请太多次就不请了；会诊结束先说一声“您可以走了”，不肯走才请保安。

## 概念三：主程序调它——发 HTTP 请求，带上这次的密钥

**一句话**：主程序要它办事，就往它报的本机端口发 HTTP：

- 管理接口：`health`、`info`、`license`、`exit`、`pause`、`resume`，都在 `/jmbots/v1/` 下；
- 渠道接口：`/jmbots/v1/channel/reply`（回一条话）、`/jmbots/v1/channel/history`（要一页历史），请求头 `x-jmbots-key` 带这次启动的密钥。

内部插件不直接调它。比如机器人要回微信，照常发 `channel/reply`；`programs` 的 `ChannelBridge` 发现这个渠道登记给了外部程序，就转成一次 HTTP。

**代码里**：`src7/plugins/programs/ChannelBridge.ts`

```ts
// src7/plugins/programs/ChannelBridge.ts
599	    //M 带上这次启动的密钥：程序据此认出是主程序在调，不是本机别的进程。
600	    const headers = { 'content-type': 'application/json', [protocolModule.KEY_HEADER]: key };
...
606	    const response = await fetch(`${url}/jmbots/v1/channel/${route}`, options);
```

程序这边先核对密钥，例如外置微信 `external/wechat/ChannelLink.ts:166–170`：密钥不对回 401。

**类比**：本院要外院专家看一个病人，开一张会诊单送过去，单子上盖着今天的章。

## 概念四：它调主程序——回调接口带密钥，programs 核对后转成内部事件

**一句话**：

1. 拉起时，`programs` 往子进程环境里放两样：
   - `JMBOTS_PROGRAM_KEY`：这次启动现发的密钥；
   - `JMBOTS_CALLBACK_URL`：回调前缀，例如 `http://127.0.0.1:30086/api/programs/wechat`。只有登记了渠道的程序才给。
2. 程序要找主程序时，往回调前缀下的接口 POST，请求头带同一把密钥。
3. `programs` 用 `isSameKey` 核对：这个名字的程序此刻在运行、密钥是它这次的。
4. 核对通过，再转成内部事件或内部处理：
   - `/channel/message`：转成标准 `channel/message`，和内置渠道一样挨个问，bots 认领；
   - `/channel/draft`：客服页手动起草，只调文字模型；
   - `/channel/approval`：发件确认，交给主站同一份批准账。

程序退出后密钥立刻作废，带旧钥匙的回调一律拒。

**代码里**：密钥和回调前缀放进环境，`Host.ts:385–390`；回调前缀怎么算，`ChannelBridge.ts` 的 `getCallbackUrl`（第 179–203 行）。三个回调接口：

```ts
// src7/plugins/programs/ChannelBridge.ts
104	    //M 程序把渠道消息交进来。
105	    const route = '/api/programs/:name/channel/message';
...
108	    //M 客服页手动起草经当前程序回调，只调用文字模型。
109	    const draft = '/api/programs/:name/channel/draft';
```

```ts
// src7/plugins/programs/ChannelSend.ts
233	  const callback = '/api/programs/:name/channel/approval';
```

核对密钥再转事件，`ChannelBridge.ts` 的 `onInbound`（第 211–243 行）：

- 程序不在或密钥不对回 401；
- 渠道没登记给它回 403；
- 通过后在第 371 行 `ctx.serial('channel/message', message, control)`。

密钥比较用固定时间比较：`Protocol.ts` 的 `isSameKey`（第 125–134 行），常量名在第 10–14 行。

**类比**：外院专家写好意见，交到本院的会诊办（回调接口）。会诊办核对今天发给他的章（密钥）对不对，对了才把意见转进本院流程（内部事件），交给对应科室。

## 概念五：防破解——只发二进制，主程序只认接口

**一句话**：

- 收费插件只发二进制，不发源码；
- 主程序不加载它的代码，只认几样东西：就绪行、`/jmbots/v1/` 接口、回调里带的密钥；
- 授权由插件自己管，主程序只问 `/jmbots/v1/license`，显示“已授权 / 过期”（规划第 4 条）。过期不杀程序，只发通知（`Host.ts:438–440`）。

反过来，主程序也防着它：

- 它只能调自己登记的回调，渠道名只能是 config 给它登记的（`ChannelBridge.ts:230–233`，不对回 403）；
- 经主站转发打开它的界面时，`/jmbots/v1` 下的管理接口一律 404（`programs/说明.md` “外部接口”）。

**类比**：外院专家用自己的方法看诊，本院不看他的笔记本，只收会诊单；本院也只给他看这一个病人的资料。

## 实例：外置微信 `external/wechat`

外置微信是第一个照这套走的进程插件，说明在 `external/wechat/说明.md`。对应上面五个概念：

- 拉起：`programs` 按配置拉起它，配置里登记 `channels`，名字和启动参数 `--channel` 一致；
- 读密钥：启动时读 `JMBOTS_PROGRAM_KEY`、`JMBOTS_CALLBACK_URL`，读完立刻从环境删掉，不传给读微信的 Python 进程（`external/wechat/Main.ts:55–59`）；
- 报就绪：监听上端口后打印就绪行（`Main.ts:177–180`），管理接口在 `Main.ts:155–163`；
- 它 → 主程序：新消息 POST 回调 `/channel/message`（`external/wechat/ChannelLink.ts:131–132`），发件确认 POST `/channel/approval`（`external/wechat/KefuRoutes.ts:120–124`）；
- 主程序 → 它：机器人的回复经 `/jmbots/v1/channel/reply` 回来，默认只存成草稿。

3. 外置微信收到一条新私聊，要交给机器人。它发什么请求、带什么头？主程序核对通过后发的是哪个内部事件？程序重启后，它手里的旧密钥还能用吗？

<details>
<summary>答案</summary>

1. 主程序挂插件是加载一份 JS 模块，二进制不是 JS；装进同一个进程也隔不开授权和代码。进程插件只隔一层本机 HTTP，靠这几样认对方：
   - 主程序认它：就绪行和 `info` 里的名字、协议版本（`Protocol.ts:196–226`，`Host.ts:429`）；
   - 它认主程序、主程序认它的回调：每次启动现发的密钥，请求头 `x-jmbots-key`（`Host.ts:381`，`Protocol.ts:125`）。
2. 崩了以后，`supervise` 退避重试：3 秒、6 秒、12 秒……最多 60 秒（`Host.ts:351`）。10 分钟内崩满 5 次，状态改成 `failed`、`gaveUp` 记成 `true`，不再自动拉起，等用户手动启动（`Host.ts:342–349`）。
3. 它 POST `<JMBOTS_CALLBACK_URL>/channel/message`，头里带 `x-jmbots-key`（`ChannelLink.ts:131–132`）。`ChannelBridge.onInbound` 核对程序、密钥、渠道之后，发标准 `channel/message`，挨个问（`ChannelBridge.ts:371`）。旧密钥不能用：每次拉起换新的，进程一退就清掉（`Host.ts:472–473`），带旧钥匙的回调回 401。

</details>
