# 第二块：一条消息从渠道进来、回到渠道

读完这一块，你能说清楚：用户在飞书（或网页、命令行、微信）发一句话，它怎么变成一条标准消息、被哪个机器人认领、排进哪场前台会话；模型想回话时，话又怎么经渠道发回去、怎么知道发成没发成。

只讲 4 个概念。README“一条消息怎么走”有 11 步，这里只挑最要紧的 4 样讲透；审批、关口、后台这些在后面几块。先读过第一块（尤其“挨个问和通知”）。

## 概念一：`channel/message`——渠道把消息变成标准格式，喊一声

**一句话**：飞书、网页、命令行、微信各自收消息，存好之后，都发同一个事件 `channel/message`，带一份标准的 `ChannelMessage`（消息号、渠道、聊天、谁发的、要找哪几个机器人 `targetBots`、正文）。后面的插件不用关心消息是从哪个平台来的。

**代码里**：飞书入站 `src7/plugins/feishu/Inbound.ts`

```ts
736	    const control: protocol.ChannelMessageControl = { claims: [] };
737	    await this.ctx.serial('channel/message', channelMessage, control);
```

标准消息的类型在 `src7/Channels.ts:131` `ChannelMessage`。它是“挨个问”（`serial`），所以第二个参数 `control` 是一张共用的单子：谁认领了、谁已经把这条消息消费掉了（`approvalHandled`），都写在上面（`Channels.ts:196`）。

**类比**：收发室。不管包裹是顺丰、邮政还是同城跑腿送来的，收发室都拆开、登记、贴上统一的标签，再喊一声“有一件到了”，楼里各部门按标签领。

## 概念二：机器人认领——`bot/receive` 先问一圈，没人要的进前台

**一句话**：`bots` 插件听 `channel/message`，对 `targetBots` 里每个机器人各认领一次：先发 `bot/receive`（挨个问）问一圈“有谁要特别处理这条？”（比如 relay 转给外部助手）；没人认领，才交给这个机器人的前台。每个机器人有自己的去重键（消息号 + 机器人名），渠道重发同一条不会处理两遍。

**代码里**：`src7/plugins/bots/index.ts`

**类比**：前台小姐收到一封信，先在群里问一句“这是不是谁的专属件？”；有人举手就给他，没人举手才放进本部门的公共收件篮。

## 概念三：前台会话——话排进队，轮到了才 `add` 和 `run`

**一句话**：每个机器人对每个聊天有一场“前台”会话。认领后，话先排进这场前台的队列（存下消息和原回话地址），轮到它时才用第一块讲的 `Session.add` 加 `Session.run` 转起来。前台正在转时来的新话先排着，不会插队。

## 概念四：回复和回执——`channel/reply` ↔ `channel/replied`

**一句话**：模型想回话，调工具 `channel_reply`，工具发 `channel/reply`（请求：往哪个渠道、发什么、这轮第几条）；对应渠道的插件把话发出去，再发 `channel/replied`（回执：发成了、被拒了，还是不确定）。发的人按 `requestId` 对号收回执。这是“发请求、等回执”的第一个实例；它怎么配对、没人接怎么办，留到第三块讲。

## 读完自测

1. 飞书、网页、命令行为什么都发同一个 `channel/message`，对后面有什么好处？
2. 一条消息 `targetBots` 里有两个机器人，会不会处理两遍？渠道把同一条重发了一次又会怎样？
3. `channel/reply` 发出去后，发的人怎么知道是“它的”那份回执？为什么回执用 `emit` 而不是 `serial`？

<details>
<summary>答案</summary>

1. 渠道各自的差别都收在渠道插件里，变成同一份 `ChannelMessage`；机器人、审批、前台只认标准格式，加新渠道不用改它们（`Channels.ts:131`）。
2. 每个机器人各认领一次，所以两个机器人各处理一遍，互不挡路（`bots/index.ts:469` 起的循环）。重发的那条因为去重键（消息号 + 机器人名）已经记过，被记成 `duplicate`，不会再入队（`DispatchClaim.ts` 同键判断）。
3. 请求里带了 `requestId`，回执里原样带回，发的人只收 `requestId` 相同的那份（`Channels.ts:824`）。回执是“已经发生的结果”，不用别人改、不用依次传阅，通知出去、谁要谁听就够，所以用 `emit`。

</details>
