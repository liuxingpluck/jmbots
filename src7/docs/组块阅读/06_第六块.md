# 第六块：资源、存库和看路

读完这一块，你能说清楚：`config.yaml` 是怎么被读进来、只校验一次、之后谁用谁直接取的；插件为什么用 `ctx.resources.raw` 读自己那一段、自己校验；会话和别的数据存在哪张表、怎么存、怎么按“插件自己加的项”查；以及想看一条消息走过哪些模块、哪些函数、哪些事件，现在靠什么（跟踪点 `trace`），教程页上的泳道图又是怎么来的。

只讲 4 个概念。前三个讲“数据从哪来、存哪去”，最后一个讲“怎么看见代码走了哪条路”。要先懂第一块的启动顺序（先资源、再工具、最后会话）。

## 概念一：`config.yaml` 只校验一次，校验完是 `ctx.resources.config`

**一句话**：`Resources` 是骨架最底下一层，管四样：配置、数据库、模型供应商、运行时目录。这一节只讲配置：读 `config.yaml`、解析、**校验一次**，然后把骨架自己要用的那几项（默认模型、供应商、插件名单、思考档、重试）整理成一份 `JmbotsConfig`，放在 `ctx.resources.config`。以后谁要用直接读，不再检查、不再补默认值，这是 CLAUDE.md “外部入口校验一次，内部直接使用”的落地。

**代码里**：`src7/Resources.ts` 的 `readConfig`（构造函数首次读入和配置热更新共用）

```ts
// src7/Resources.ts
187	  const config = checks.checkConfig(written);
```

校验函数 `checkConfig` 在 `src7/utils/Checks.ts:121`（骨架的检查放 `utils/`，`Resources` 里只留这一行主线）。它会给没写的项补默认值（比如没写 `api_key` 是空串，没写 `api` 是 `openai-completions`，没写的模型用 `MODEL_DEFAULTS`，`Checks.ts:43`），写错了就抛错，**错误信息只说哪一项不对，不带配置原文**，因为里面有密钥。YAML 自己解析出错也只报“第几行附近”（`readConfig` 里的 `broken` 那几行）。

另外两个相关的函数：`getModel(name)`（`Resources.ts:412`）把“供应商名/模型 ID”拼成 pi 要的模型对象；`ensureRuntimeDir(...)`（`Resources.ts:388`）给出运行时目录下的文件夹、没有就建。

**类比**：入院时在登记处核对一次身份、戴上腕带；以后各科室看腕带就行，不会每进一个科室都重新登记。

## 概念二：`ctx.resources.raw`——插件读自己那一段，自己校验一次

**一句话**：`config.yaml` 里有很多段是骨架不认识的（`bots`、`server`、`channels`、`decision`、`paths`……）。骨架把**整份解析结果原样**留一份在 `ctx.resources.raw`，哪个插件要用哪一段，就自己取、自己校验一次。骨架不替插件校验，也不规定别人的段怎么写。

**代码里**：`src7/Resources.ts`

```ts
// src7/Resources.ts
188	  const raw = written as Record<string, unknown>;
```

插件这一侧，比如 `src7/plugins/http/index.ts`：

```ts
// src7/plugins/http/index.ts
511	  const server = (ctx.resources.raw['server'] ?? {}) as {
512	    port?: unknown; token?: unknown; host?: unknown; trusted_ips?: unknown;
513	  };
```

后面几行就是它自己的校验：没有 `server.port` 就抛错，`port` 必须是 1 到 65535 的整数，`token` 必须是字符串。`bots` 插件也一样：`src7/plugins/bots/index.ts:1020` 取 `raw['bots']`，整段不写就当一个叫“助手”的机器人。

`Resources.ts:150` 的注释写着：`raw` 里有密钥，不许打印。

**类比**：每个科室都拿到整份病历的复印件，但只看自己那一页，并且自己核对那一页写得对不对；内科不替外科审外科的单子。

## 概念三：`sessions` 表——一场一行，分“元信息”和“对话”两块

**一句话**：会话存在 SQLite 数据库 `data/jmbots7.db`（`Resources` 开的，`ctx.resources.db`）里的 `sessions` 表。一场会话一行，三列：`id`、`meta`、`messages`。`messages` 是整场对话的 JSON；`meta` 是记录里**除了对话以外所有的项**的 JSON（种类、状态、模型……连同插件自己往记录里加的项，比如 `bot`、`customer`）。拆成两块，是为了列清单时不用把整场对话读出来。

**代码里**：`src7/Sessions.ts`

```ts
// src7/Sessions.ts
328	    const sql = 'CREATE TABLE IF NOT EXISTS sessions'
329	      + ' (id TEXT PRIMARY KEY, meta TEXT NOT NULL, messages TEXT NOT NULL)';
```

存（每次对话多一条、状态改变都会调，`Session.save`）：

```ts
// src7/Sessions.ts
893	    const sql = 'INSERT OR REPLACE INTO sessions (id, meta, messages) VALUES (?, ?, ?)';
```

找（`Sessions.find`）：

```ts
// src7/Sessions.ts
459	      sql += ' AND json_extract(meta, ?) = ?';
```

因为 `meta` 是 JSON，`find({ bot: '助手', kind: 'front' })` 用 `json_extract` 一项项比，所以**插件给记录加了新项，不用改表就能拿来找**（第三块的前台、后台都是这样找的）。别的插件需要自己的表，也是用同一个 `ctx.resources.db` 自己建，比如 `approval` 的待确认表 `approval_pending`（`approval/index.ts:358`）、`journal` 的流水表 `journal_lines`（`journal/index.ts:185`）。数据库开了 WAL 模式（`Resources.ts:191`），被拔掉时自动关（构造函数里的 `ctx.effect`）。

**类比**：病历柜。每场就诊一个病历袋，袋子封面写着病人、科室、状态（meta），里面是全文（messages）；翻封面就能找到想要的那袋，不用把每袋全文都抱出来。

## 概念四：跟踪点 `trace`——代码走到关键处记一笔，打印、记库、画泳道图都用它

**一句话**：想看“一条消息从头到尾走过哪个模块、哪个函数、哪个事件”，不靠断点，靠**跟踪点**：骨架和插件在关键的地方各发一个 `trace` 事件，带四样东西——哪个模块的哪个函数、一句人话、一句代码、关键变量。它只是通知，谁也不许靠它改流程。发了没人听，等于没发。

**代码里**：一个跟踪点就是两行（代码约定里用 `//T` 开头的注释标出来）。比如命令行收到一句话，`src7/plugins/cli/index.ts`：

```ts
// src7/plugins/cli/index.ts
155	    //T 跟踪：命令行收到一句话，转成统一事件发出。
156	    const vars = { bot: bot, sequence: this.seq, length: sentence.length };
157	    this.ctx.emit('trace', 'Cli.submitLine', 'trace.cli.submitLine', "ctx.serial('channel/message')", vars);
```

会话循环调模型前也有一个（`Sessions.ts:558–569`，`Session.loop`）。事件的声明在 `src7/utils/Trace.ts:80`，文件头注释写了用法。

听它的有四个（`utils/Trace.ts` 第 70–74 行“谁接”）：

- `tutorial/Print.ts` 打到控制台或文件：配置 `trace_console: true` 打控制台，`trace_file: true` 写文件，两样都没开就不挂监听（`tutorial/Print.ts:9`）；
- `journal` 把它连同 Cordis 事件记进数据库的 `journal_lines` 流水表（`journal/index.ts:202`）；
- `tutorial/State.ts` 在要拍的消息上拍运行时变量快照；
- `tutorial/Boot.ts` 的 `BootTrail` 记启动的每一步。

两个细节：

- **会话的几个事件不用另发跟踪点**：Cordis 每发一个事件会自己先发一个 `internal/dispatch`，打印插件顺带打出“发了哪个事件、怎么发的（挨个问 / 通知）、谁在听”（`tutorial/Print.ts:50`）；
- **打印不是骨架的事**：原来的 trace 插件 11-17 已经并进了 `tutorial`（`plugins/Index.ts:76` 注释），拔掉它骨架照常跑。

打出来是一步一行，格式写在 `tutorial/Print.ts` 文件头（第 4–8 行）：函数行是“时间 函数 模块.函数 │ 人话 │ 代码 │ 变量名=值 │ 文件:行号”，事件行是“时间 事件 事件名（挨个问、通知）听的人：插件、插件 │ 这个事件带着什么 │ 文件:行号”。最后的“文件:行号”是打印插件从调用栈里自己找的，发的人不用写。

教程页 `/tutorial/` 的泳道图，就是拿 `journal` 记下的这些行，先整理成“一步一步”（`journal/Trail.ts`），再摆进格子（`tutorial/Lanes.ts`）：一道（行）是一个插件或骨架的某个服务（`main`、`resources`、`tools`、`sessions`），一列是一个阶段（启动、收到、存、分给机器人、会话第几步、回复）。所以**新加插件、新加关键函数时，记得补一个跟踪点**，不然图上这一步是空的。

**类比**：护理记录。每到关键一步记一笔“几点几分、谁、做了什么”；不记也照样看病，但事后要按时间把整个就诊过程排成一张时间线，就全靠这些记录。

## 读完自测

1. 为什么 `Resources` 里只有一行 `checks.checkConfig(raw)`，而不是把校验写在构造函数里？以后某个插件要用 `providers` 里的密钥，应该读 `raw` 还是 `config`？
2. 一个插件想加一个新的会话项 `urgent: true`，并且想“找出所有 `urgent` 的会话”，要改数据库的表结构吗？为什么？
3. 想让教程页的泳道图上多出“某个新函数这一步”，要做什么？它会不会影响业务流程？

<details>
<summary>答案</summary>

1. 校验函数放骨架的 `utils/Checks.ts`，调用处只留主线（CLAUDE.md 的约定）。骨架要用的项（含 `providers`）读 `ctx.resources.config`，那是校验过的、补过默认的；`raw` 是整份原样，只给插件读自己那一段（`Resources.ts:148、144`）。
2. 不用。`meta` 是 JSON，`find({ urgent: true })` 用 `json_extract(meta, '$.urgent') = ?` 比（`Sessions.ts:348–357`）。插件只需在自己文件里用 `declare module '../../Sessions.ts'` 给记录加上这一项的类型。（`bot`、`customer`、`frontTask` 这些项就是这样来的，看 `plugins/bots/index.ts:135` 的 `declare module`；`kind` 是骨架自带的，`Sessions.ts:198`。）
3. 在函数里发一个跟踪点：`//T` 注释加 `const vars = {…}` 和 `this.ctx.emit('trace', '类.函数', '一句人话', '一句代码', vars)`。它只是通知，不许靠它改流程；没挂 `tutorial` 或 `journal` 时发了等于没发。

</details>
