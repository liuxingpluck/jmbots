# 第六块：资源、存库和看路

读完这一块，你能说清楚：`config.yaml` 是怎么被读进来、只校验一次、之后谁用谁直接取的；插件为什么用 `ctx.resources.raw` 读自己那一段、自己校验；会话和别的数据存在哪张表、怎么存、怎么按“插件自己加的项”查；以及想看一条消息走过哪些模块、哪些函数、哪些事件，现在靠什么（跟踪点 `trace`），以及教程页上的画布是怎么画出来的。

只讲 5 个概念。这一块最简单的读法是：前三个讲“数据从哪来、存哪去”，后两个讲“怎么看见代码走了哪条路”。要先懂第一块的启动顺序（先资源、再工具、最后会话）。

## 概念一：`config.yaml` 只校验一次，校验完是 `ctx.resources.config`

**一句话**：`Resources` 是骨架最底下一层，启动时只做一件事：读 `config.yaml`、解析、**校验一次**，然后把骨架自己要用的那几项（默认模型、供应商、插件名单、思考档、重试）整理成一份 `JmbotsConfig`，放在 `ctx.resources.config`。以后谁要用直接读，不再检查、不再补默认值，这是 CLAUDE.md “外部入口校验一次，内部直接使用”的落地。

**代码里**：`src7/Resources.ts` 的构造函数

```ts
183	    this.config = checks.checkConfig(raw);
```

校验函数 `checkConfig` 在 `src7/utils/Checks.ts:121`（骨架的检查放 `utils/`，`Resources` 里只留这一行主线）。它会给没写的项补默认值（比如没写 `api_key` 是空串，没写 `api` 是 `openai-completions`，没写的模型用 `MODEL_DEFAULTS`，`Checks.ts:42`），写错了就抛错，**错误信息只说哪一项不对，不带配置原文**，因为里面有密钥。YAML 自己解析出错也只报“第几行附近”（`Resources.ts` 构造函数里的 `broken` 那几行）。

另外两个相关的函数：`getModel(name)`（`Resources.ts:258`）把“供应商名/模型 ID”拼成 pi 要的模型对象；`dir(...)`（`Resources.ts:246`）给出运行时目录下的文件夹、没有就建。

**类比**：新员工入职的体检。入职时统一体检一次，合格了就发工牌；以后各部门看工牌就行，不会每次开门都重新体检。

## 概念二：`ctx.resources.raw`——插件读自己那一段，自己校验一次

**一句话**：`config.yaml` 里有很多段是骨架不认识的（`bots`、`server`、`channels`、`decision`、`paths`……）。骨架把**整份解析结果原样**留一份在 `ctx.resources.raw`，哪个插件要用哪一段，就自己取、自己校验一次。骨架不替插件校验，也不规定别人的段怎么写。

**代码里**：`src7/Resources.ts`

```ts
186	    this.raw = raw as Record<string, unknown>;
```

插件这一侧，比如 `src7/plugins/http/index.ts:482`：

```ts
482	  const server = (ctx.resources.raw['server'] ?? {}) as {
483	    port?: unknown; token?: unknown; host?: unknown; trusted_ips?: unknown;
484	  };
```

后面几行就是它自己的校验：没有 `server.port` 就抛错，`port` 必须是 1 到 65535 的整数，`token` 必须是字符串。`bots` 插件也一样：`src7/plugins/bots/index.ts:1011` 取 `raw['bots']`，整段不写就当一个叫“助手”的机器人。

注意 `raw` 里**有密钥**，不许打印（`Resources.ts:144` 的注释）。这也是为什么调试插件要小心，不能把 `raw` 随便 dump 出去。

**类比**：公司给每个部门一份公司手册的完整复印件，但每个部门只照自己那一章办事，并且自己负责检查自己那一章写得对不对；人事部不替销售部审销售章程。

## 概念三：`sessions` 表——一场一行，分“元信息”和“对话”两块

**一句话**：会话存在 SQLite 数据库 `data/jmbots7.db`（`Resources` 开的，`ctx.resources.db`）里的 `sessions` 表。一场会话一行，三列：`id`、`meta`、`messages`。`messages` 是整场对话的 JSON；`meta` 是记录里**除了对话以外所有的项**的 JSON（种类、状态、模型……连同插件自己往记录里加的项，比如 `bot`、`customer`）。拆成两块，是为了列清单时不用把整场对话读出来。

**代码里**：`src7/Sessions.ts`

```ts
263	    const sql = 'CREATE TABLE IF NOT EXISTS sessions'
264	      + ' (id TEXT PRIMARY KEY, meta TEXT NOT NULL, messages TEXT NOT NULL)';
```

存（每次对话多一条、状态改变都会调，`Sessions.ts:676`）：

```ts
676	    const sql = 'INSERT OR REPLACE INTO sessions (id, meta, messages) VALUES (?, ?, ?)';
```

找（`Sessions.ts:356`）：

```ts
356	      sql += ' AND json_extract(meta, ?) = ?';
```

因为 `meta` 是 JSON，`find({ bot: '助手', kind: 'front' })` 用 `json_extract` 一项项比，所以**插件给记录加了新项，不用改表就能拿来找**（这是第四块 `find` 的底子）。别的插件需要自己的表，也是用同一个 `ctx.resources.db` 自己建，比如 `approval` 的待确认表 `approval_pending`（`approval/index.ts:355`）、`journal` 的流水表 `journal_lines`（`journal/index.ts:185`）。数据库开了 WAL 模式（`Resources.ts:191`），被拔掉时自动关（构造函数里的 `ctx.effect`）。

**类比**：档案室的卡片柜。每场会话一个抽屉，抽屉里一张“目录卡”（meta）、一叠“全文”（messages）；翻目录卡就能找到想要的抽屉，不用把每个抽屉的全文都抱出来。

## 概念四：跟踪点 `trace`——代码走到关键处，喊一嗓子

**一句话**：想看“一条消息从头到尾走过哪个模块、哪个函数、哪个事件”，不靠断点，靠**跟踪点**：骨架和插件在关键的地方各发一个 `trace` 事件，带四样东西——哪个模块的哪个函数、一句人话、一句代码、关键变量。它只是通知，谁也不许靠它改流程。发了没人听，等于没发。

**代码里**：一个跟踪点就是两行（代码约定里用 `//T` 开头的注释标出来）。`src7/Sessions.ts:560–571`：

```ts
	      //T 跟踪：调模型；插件已经给了回答（假模型）就写明没有调。
	      const vars = {
	        会话: this.id,
	        第几步: step,
	        模型: request.model,
	        对话几条: request.messages.length,
	      };
	      ...
	      this.ctx.emit('trace', 'Session.loop', doing, 'ctx.sessions.chat(request)', vars);
```

事件的声明在 `src7/utils/Trace.ts:80`，文件头注释写了用法。两个细节：

- **会话的几个事件不用另发跟踪点**：Cordis 每发一个事件会自己先发一个 `internal/dispatch`，打印插件顺带打出“发了哪个事件、怎么发的（挨个问 / 通知）、谁在听”（`tutorial/Print.ts:50`）；
- **打印不是骨架的事**：`src7/plugins/trace/` 现在没有，CLAUDE.md 里提到的那个“打印执行路径的插件”已经并进了 `tutorial`（`plugins/Index.ts:76` 注释说 11-17 由 flow、boot-trail、trace 合成）。真正打印的是 `plugins/tutorial/Print.ts`，在配置里写 `trace_console: true` 才打；拔掉它骨架照常跑。

打出来的样子，是 `src7/README.md` 第 283–300 行那段：

```text
16:43:58.553 函数 Bots.receive │ 渠道收到一句话，存下来，推给机器人 │ bot.receive(message) │ 渠道=cli 机器人=助手 字数=5 │ src7/plugins/bots/index.ts:270
16:43:58.555 事件 bot/receive（挨个问）听的人： │ src7/plugins/bots/index.ts:419
```

最后的“文件:行号”是打印插件从调用栈里自己找的，发的人不用写。

**类比**：高速公路上的收费站摄像头。每过一个关键路口，摄像头记一笔“几点几分，哪辆车，从哪个口进”。摄像头可以拆掉，路照样通车。

## 概念五：教程画布——同一批跟踪点，除了打印，还记进库、画成泳道图

**一句话**：跟踪点有好几个“听的人”（`utils/Trace.ts` 事件声明注释里的“谁接”）：`tutorial/Print.ts` 打到控制台；`journal` 把它连同 Cordis 事件记进数据库的 `journal_lines` 流水表；`tutorial/State.ts` 在要拍的消息上拍运行时变量快照。教程页 `/tutorial/` 的“泳道图”就是拿 `journal` 记下的这些行，先整理成“一步一步”（`journal/Trail.ts`），再摆进格子（`tutorial/Lanes.ts`）：一道（行）是一个插件或骨架的某个服务（`main`、`resources`、`tools`、`sessions`），一列是一个阶段（启动、收到、存、分给机器人、会话第几步、回复）。

**代码里**：

```ts
// src7/plugins/journal/index.ts:202  journal 听 trace，记一行
    ctx.on('trace', (where, text, code, vars) => {
```

`Trail.ts` 文件头（第 1–10 行）讲了“跟踪行 → 一步一步”这一步，`Lanes.ts` 文件头（第 1–10 行）讲了怎么排格子。一行归到“发它的那一段代码”头上（看 `site`：`plugins/<名字>/` 是插件，`Sessions.ts`、`Tools.ts` 是骨架服务）。

这就是为什么 CLAUDE.md 要求“打印执行路径的插件一定要有”：它不是只给人调试，教程画布、`/flow/` 的快照、聊天页的回话追溯，都靠同一批跟踪行。所以**新加插件、新加关键函数时，记得补一个跟踪点**，不然画布上这一步是空的。

**类比**：把摄像头一天的录像，按“谁、几点、过哪个口”整理成一张地铁线路图：每条线是一个模块，每站是一个阶段，圈出一辆车走过的所有站。

## 读完自测

1. 为什么 `Resources` 里只有一行 `checks.checkConfig(raw)`，而不是把校验写在构造函数里？以后某个插件要用 `providers` 里的密钥，应该读 `raw` 还是 `config`？
2. 一个插件想加一个新的会话项 `urgent: true`，并且想“找出所有 `urgent` 的会话”，要改数据库的表结构吗？为什么？
3. 想让教程画布上多出“某个新函数这一步”，要做什么？它会不会影响业务流程？

<details>
<summary>答案</summary>

1. 校验函数放骨架的 `utils/Checks.ts`，调用处只留主线（CLAUDE.md 的约定）。骨架要用的项（含 `providers`）读 `ctx.resources.config`，那是校验过的、补过默认的；`raw` 是整份原样，只给插件读自己那一段（`Resources.ts:141、144`）。
2. 不用。`meta` 是 JSON，`find({ urgent: true })` 用 `json_extract(meta, '$.urgent') = ?` 比（`Sessions.ts:350–359`）。插件只需在自己文件里用 `declare module '../../Sessions.ts'` 给记录加上这一项的类型。（再说明：`SessionRow` 里写了 `kind`、`bot` 等项就是这样来的。）
3. 在函数里发一个跟踪点：`//T` 注释加 `const vars = {…}` 和 `this.ctx.emit('trace', '类.函数', '一句人话', '一句代码', vars)`。它只是通知，不许靠它改流程；没挂 `tutorial` 或 `journal` 时发了等于没发。

</details>
