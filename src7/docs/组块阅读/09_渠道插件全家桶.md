# 第九块：渠道插件全家桶（channels、feishu、wechat、relay）

读完这一块，你能说清楚：

1. 四个插件各管什么：`channels` 是接线板，`feishu`、`wechat` 是两条进线，`relay` 是半路的转接台；
2. 飞书群里的话分哪三种去向，`listen: mention / all / judge` 和 `judge_helper` 各改了哪一步；
3. 用户发“cc …”“哈基米 …”时，这句话怎么绕开模型、转到外部助手手里，回信又怎么回到原聊天；
4. 工作决策页的留言怎么经 relay 到中控、中控回话又怎么写回节点；
5. 出门前要拍板的三处可以理顺的地方。

先读过第二块（`emitInbound`、`bot/receive` 截走 / 改道、`channel/reply` ↔ `channel/replied`）。第二块讲的是“一条消息怎么走”，这一块换个角度：站在每个渠道插件里看，它们各干哪段活。行号对的是 0.7.76 的源码。

## 插件一：`channels`——总接线板

**一句话**：`channels` 不收消息、也不发消息，它只定规矩：标准消息长什么样（`ChannelMessage`），进来发哪个事件（`getInboundEvent`），回话请求和回执长什么样（`channel/reply`、`channel/replied`）。它是“依赖型插件”，不挂服务、不进 `config.yaml`，别的插件直接 `import`。

**代码里**：七个事件都声明在 `src7/plugins/channels/index.ts`（`'channel/direct'` 第 58 行，`'channel/reply'` 第 111 行，`'channel/replied'` 第 123 行）。分法只有一处：

```ts
// src7/plugins/channels/Message.ts
263	export function getInboundEvent(chatType: ChannelChatType, called: boolean): InboundEvent {
264	  if (!called) return 'channel/listen';
265	
266	  if (chatType === 'group') return 'channel/mention';
267	
268	  return 'channel/direct';
269	}
```

几样要记住的：

- `emitInbound`（`src7/plugins/channels/Message.ts:280`）照上面的分法用 `ctx.serial` 发三个事件之一，所有渠道都经它发，事件名不在渠道里写；
- 回话一律走 `requestChannelReply`（`src7/plugins/channels/Reply.ts:196`）：发 `channel/reply`，等 `channel/replied`。只发纯文字的渠道（网页、命令行、微信、外置程序）不用自己写响应器，调 `registerTextReply`（`src7/plugins/channels/TextReply.ts:49`）挂一个就行；
- 谁是本人只问 `isOwnerTurn`（`src7/plugins/channels/Message.ts:399`）。飞书照 `people[].role` 写，微信一律外人，网页和命令行算本人。

**类比**：插线板的国标。插头（渠道）各家都不一样，插座只有一种；电器（机器人）只认插座，不管电从哪来。

## 插件二：`feishu`——最忙的一条进线

**一句话**：一个飞书应用一条长连接（SDK 的 `WSClient`，不用公网回调）。收到一条话，`FeishuInbound` 走 6 步：认人认群认 @ → 拼回话地址 → 挂“敲键盘”表情 → 下附件 → 写聊天日志 → 经 `emitInbound` 交出去。回话、卡片、撤回、拉群历史、发件箱、云文档也都在这个插件里，因为它们共用同一个应用身份。

**连上**：`Feishu.start`（`src7/plugins/feishu/index.ts:576`）给每个应用建一个分发器，登记收消息（`im.message.receive_v1`）、撤回（`im.message.recalled_v1`）、点卡片（`card.action.trigger`）和机器人进群（`im.chat.member.bot.added_v1`）。每个开放接口请求限时 60 秒（`HTTP_TIMEOUT_MS`，第 236 行）。

**进来**：`handleInboundMessage`（`src7/plugins/feishu/Inbound.ts:214`）就是那 6 步。最要紧的是“投给谁、算不算叫了”，在 `getTargets`：

```ts
// src7/plugins/feishu/Inbound.ts
492	    //M 私聊：本应用允许的机器人都收，算叫了。
493	    if (!group) return { targetBots: [...allowedBots], called: true };

506

```

翻成大白话，群在 `groups` 里登记的 `listen` 决定没被叫到时怎么办：

| `listen` | 有人 @ 或引用机器人 | 没人叫 |
|---|---|---|
| 不登记 / `mention` | `channel/mention`，被叫的回 | `channel/listen`，`targetBots` 空，只给记录类插件记 |
| `all` | 同上 | `channel/listen`，本应用的机器人都记背景，不回 |
| `judge` | 同上 | 同 `all`，再问决策模型要不要接话 |

`judge` 还多两个可选项，都写在回话地址上，由 `getAddress`（`src7/plugins/feishu/Inbound.ts:536`）贴：

```ts
// src7/plugins/feishu/Inbound.ts
553	    //M 只听的话、这个群登记了 listen: judge：标上 judge 和把握线，前台记完问决策模型要不要接。
554	    if (listen && registered?.listen === 'judge') address.judge = true;
555	    if (listen && registered?.listen === 'judge' && registered.judgeThreshold !== undefined) {
556	      address.judgeThreshold = registered.judgeThreshold;
557	    }
558	    //M 登记了 judge_helper 的 judge 群：标上转给哪个外部助手，群攒批判定要接话时转给它。
559	    if (listen && registered?.listen === 'judge' && registered.judgeHelper !== undefined) {
560	      address.judgeHelper = registered.judgeHelper;
561	    }
```

`judge_helper` 的意思是：判定这一批该接话时，不让机器人自己答，转给某个外部助手。转交在 bots 里做：`GroupBatch` 看到地址带 `judgeHelper`（`src7/plugins/bots/GroupBatch.ts:334`），调 `DispatchClaim.relayBatch`（`src7/plugins/bots/DispatchClaim.ts:290`），把 `listenOnly` 去掉、写上 `relayHelper`，再问一遍 `bot/receive`，relay 就接住了（见插件四）。

**发出去**：`FeishuReply.onChannelReply`（`src7/plugins/feishu/Reply.ts:74`）只接 `channel` 是飞书的请求，接了先标 `handled`：

```ts
// src7/plugins/feishu/Reply.ts

76	
77	    request.handled = true;
```

同一个回复键内容不一样就拒（`reply_conflict`，第 107 行），发完由 `emitReplied` 回回执（第 201 行）。

**发件箱**：AI 要主动通知你，往 `<运行时>/integrations/feishu/outbox/` 放 `.md` 就行。`Outbox.ts` 每 5 秒扫一次（`OUTBOX_INTERVAL_MS`，`src7/plugins/feishu/outbox/Outbox.ts:14`），按文件名顺序发给第一个应用最近私聊的人，发完挪进 `integrations/feishu/sent/`：

**其余几样，一句话各一**：

- 撤回：`FeishuInbound.onRecall`（`src7/plugins/feishu/Inbound.ts:889`）只认本人或原发信人撤的，核定后发 `channel/recall`，bots 把排着的那条拿掉；
- 拉群历史：`HistoryPull.ts` 翻页拉最近 N 条，发 `channel/history` 给记忆补记，不触发会话；机器人新进群自动拉 `history_on_join` 条；
- 卡片：审批卡、进度卡在 `cards/`，点卡片走 `onCard`（`src7/plugins/feishu/Inbound.ts:972`），只有本人点才算；
- 来往流水：`Contacts.ts` 每条入站记一行 `data/logs/feishu-contacts.jsonl`，网页的“联系人”看它。

## 插件三：`wechat`——客服模式，默认只起草

**一句话**：`wechat` 不连微信服务器，它读**本机**微信的数据库（经 `wechat_cli` 引擎），每 3 秒看一遍监听名单里的会话，有私聊或群里 @我 的新话，先存表，再经 `emitInbound` 交给机器人起草。模型的回话默认只存草稿，要本人点头才发；配置里 `send: true` 才真发。

**代码里**：轮询入口 `Wechat.poll`（`src7/plugins/wechat/index.ts:307`，定时器在第 268 行），存表在 `store`（第 384 行），交出去在最后：

```ts
// src7/plugins/wechat/index.ts
475	      //M 交下来的都是叫了机器人的（私聊、群里 @我）：私聊发 channel/direct、群里发 channel/mention。
476	      //M   bots 按来源范围排进这个客户的前台；一轮里 channel_reply 几次进几条发件，一次没调就把最后的话进发件。
477	      const control: protocol.ChannelMessageControl = { claims: [] };
478	      await protocol.emitInbound(this.ctx, channelMessage, true, control);
```

`called` 恒为 `true`：交下来的都是叫了机器人的，所以只会是 `channel/direct` 或 `channel/mention`；`routing.autoFinal` 表示这一轮模型一次 `channel_reply` 都没调时，把最后一句话当回复。回话用的是 `registerTextReply`（`src7/plugins/wechat/index.ts:229`），每条回话进发件表，等你审批。

**和外置微信的边界**：`external/wechat/` 是另一回事——一个纯 Bun 编的单文件 exe（`jmbots-wechat.exe`），由 `programs` 插件拉起，自己解密微信库，新消息 POST 回调主程序，主程序再经 `emitInbound` 发事件。它是收费插件的样板，细节在第七块。主站里的 `wechat` 插件和它不互相调用，只是读的是同一份本机微信。

**注意名字**：目录和渠道名是 `wechat`，`config.yaml` 里插件注册名是 `wechat-kefu`。

**类比**：代写回信的秘书。翻你的信箱，把要回的挑出来拟稿，放你桌上等你签字；你说了“以后不用问我”（`send: true`）才直接寄。

## 插件四：`relay`——把话转给外部助手的转接台

**一句话**：`relay` 在 `bot/receive` 上截话（第二块讲的“改道”），把它存进收件表 `relay_items`，外部助手（Claude、Antigravity、Codex……）来取、来回信；回信再经 `channel/reply` 发回原聊天，前面署上助手的展示名。配置写了 `helpers` 才挂转话。

**认前缀**：`prefixed`（`src7/plugins/relay/index.ts:538`）先跳过附件标记和引用块，再按 `helpers` 的顺序找第一个前缀对上的助手：

```ts
// src7/plugins/relay/index.ts
560	    const hits = (prefix: string): boolean => {
561	      const head = prefix.trim();
562	      if (said.slice(0, head.length).toLowerCase() !== head.toLowerCase()) return false;
563	      //M 中文前缀（如“哈基米”）没有空格分词，后面紧跟英文字母或数字也算命中；英文前缀照旧防 cc123/ccache 误判。
564	      if (/\p{Script=Han}$/u.test(head)) return true;
565	
566	      const next = said.charAt(head.length);
567	      return next === '' || /\p{Script=Han}/u.test(next) || !/[\p{L}\p{N}_]/u.test(next);
568	    };
569	
570	    //M 按配置顺序选第一个前缀命中的助手。
571	    return this.config.helpers.find((helper) => helper.prefixes.some(hits));
```

所以“哈基米a 帮我看下”算命中（中文前缀后面紧跟字母也行），“ccache 坏了”不算（英文前缀要词边界）。每个助手可以写 `title` 当展示名，回执和署名用 `getTitle`（第 496 行），库里和接口筛选仍用 `name`。

**三种进 relay 的路**，都在 `onReceive`（`src7/plugins/relay/index.ts:752`）：


1. **群攒批转交**：地址带 `relayHelper`（上面插件二讲的 `judge_helper` 那条路），直接进 relay 会话；
2. **前缀**：只听的话、或者不是“直转”的机器人，话要以助手前缀开头才进 relay 会话；

**外部助手怎么取、怎么回**：

- 取：`GET /api/relay/inbox?helper=Claude&state=pending`（`src7/plugins/relay/Routes.ts:24`）；
- 回：`POST /api/relay/reply {id, text}`（`src7/plugins/relay/Routes.ts:41`），交给 `accept`（`src7/plugins/relay/index.ts:628`）写进 `relay_replies`，`done` 默认 true，收件改成 `replied`；
- 超时：`checkLate`（`src7/plugins/relay/index.ts:1386`）默认 15 分钟提醒一次，120 分钟放下，晚回的照收。

**工作决策页的留言闭环**：

1. 你在 `/work-decision/` 给节点留言 → `POST /api/work-decision/note`（`src7/plugins/work-decision/Routes.ts:371`）；
2. work-decision 发 `work-decision/note`（`action: deliver`，第 411 行 `requestRelay`），relay 的 `receiveDecision`（`src7/plugins/relay/index.ts:1078`）插一条收件，按“节点号#留言号”去重；
3. 中控照常从 `/api/relay/inbox` 取到它，用 `POST /api/relay/reply` 回；
4. relay 的 `queueDecisionReply`（`src7/plugins/relay/index.ts:1116`）再发一次 `work-decision/note`（`action: reply`），work-decision 写进节点（`src7/plugins/work-decision/Routes.ts:188`），收到成功回执才标已送。

**另一半：任务通道**。`AgentTasks.ts` 管 `agent_task` 工具派的活：执行端登记、领取、交回，`reply: false` 是单向留言、领走即送达。它和转话共用一个插件，但走 `/api/agents/...` 那 7 个接口，不进 `bot/receive`。

**类比**：总机转接。你拨“cc”分机，总机不自己答，记一张转接单给那个人；那人回电话时总机替你接回原来的线，先报一句“XX 回话：”。

## 常见踩坑和可以理顺的地方（出门拍板用）

1. **`judge_helper` 写错名字会悄悄转给默认助手**。飞书配置只查它是非空文字（`src7/plugins/feishu/Config.ts:280–281`），不查是不是 relay 的 `helpers` 里有的名字；到 relay 那边找不到就落到第一个助手（`src7/plugins/relay/index.ts:824–826`）。建议：relay 启动时对一遍飞书群配置里的 `judge_helper`，对不上打一行警告。
2. **发件箱一份发不出，后面的全卡住**。`Outbox.ts` 发给“第一个应用最近私聊的人”，没人私聊过就抛错（`src7/plugins/feishu/outbox/Outbox.ts:41–44`），整轮停下，下一轮还是同一份卡在最前面。多个飞书应用时也只走第一个应用。建议：允许文件头写收件人；发不出的挪进 `failed/`，不挡后面的。
3. **relay 的 `index.ts` 有 1948 行，转话三条路挤在一个函数里**。`onReceive` 用 `relayHelper`、`listenOnly`、`getMode` 三个条件交叉判断（`src7/plugins/relay/index.ts:764–771`），转话、回信投递、决策图回信、超时、文件回信都在一个 class 里。建议：照 feishu 的做法，把“决策图回信”和“超时提醒”拆成同目录的文件，`onReceive` 的三条路各写成一个提前 return 的 `if`。

<details>
<summary>答案</summary>

1. 发 `channel/listen`，`targetBots` 是空的（`getTargets` 最后一行），机器人谁都不收，不回；记忆和聊天归档照样记。

4. 微信默认只起草：回话进发件表等你审批，`send` 不是 `true` 不真发。还有一种：带会话号的旧路回话，那一轮没跑完（出错、被停）就不发给客户。
