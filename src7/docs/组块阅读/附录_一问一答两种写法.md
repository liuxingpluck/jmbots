# 附录：一问一答的两种写法（现在的做法 vs 决策图上的 q-ev-serial）

这份是给拿主意用的材料，不是读懂骨架必需的。先读第四块“插件之间一问一答”。这里只摆两种长什么样、按代码事实列差别，不替用户做决定。

## 两种长什么样

**现在：请求事件 + 回执事件**（提问方，加办事方）

```ts
// 提问方：发 model-catalog/request，等 model-catalog/result；没人接、超时、中止、出错都走 onFallback
const result = await requestEvent(ctx, 'model-catalog/request', 'model-catalog/result',
  { action: 'find', model }, { timeoutMs: 3000, onFallback: () => ({ requestId: '' }) });

// 办事方：只写业务，handled、requestId、回执由 onRequestEvent 包办
onRequestEvent(ctx, 'model-catalog/request', 'model-catalog/result',
  (request) => ({ info: find(request.model) }));
```

**q-ev-serial：一个事件，答案从返回值拿**（示意，现在代码里没有 `model-catalog/find` 这个事件）

```ts
// 提问方：serial 挨个问，第一个返回“算数”的值就是答案，后面的不再问
const info = await ctx.serial('model-catalog/find', model);

// 办事方：直接 return 答案；不是自己的活就不 return
ctx.on('model-catalog/find', (model) => find(model));
```

“算数”的意思：Cordis 的 `isBailed` 是“不是 `null`、不是 `false`、不是 `undefined`”（`node_modules/cordis/lib/index.js:692–694`）。办事方返回 `false` 或 `null`，`serial` 也会接着问下一个人。

## 差别（按代码事实）

- **事件个数、代码量**：现在一问一答要声明两个事件（请求、回执），两边各带 `requestId`、`handled` 这些信封字段；q-ev-serial 只一个事件，办事方直接 `return`，提问方直接 `await`。
- **没人接**：现在有明确的 `unhandled` 退回；q-ev-serial 没人返回时拿到的是 `undefined`，提问方自己判断。
- **等多久、能不能叫停**：现在 `requestEvent` 通过 `signal`（如 `AbortSignal.timeout(...)`）支持中止与限时；`serial` 本身没有限时和中止，要的话得自己再包。
- **要跟现有规矩一致**：README 说过“挨个问”的监听函数不许有返回值，有了返回值 Cordis 就不再问后面的人了。q-ev-serial 正是把这一条反过来利用，所以只能给“答案只需一个人出”的事件用；一个事件的监听者不能同时既当“关口改数据”又当“返回答案”。

## 一条供决策参考的事实

按 `onRequestEvent` 的写法，办事方是在 `serial` 里被等完的（监听函数是 `async`，里面 `await handler(request)`，`src7/utils/RequestEvent.ts:178–190`），回执在 `serial` 结束之前就已经发出了。`requestId` 配对和单独的回执事件，真正派上用场的是两种情况：

1. 办事方把活扔到后台、过一会儿才回执；
2. 别的插件也想旁听回执（如第二块的 `channel/replied`：前台和 web-api 都在听）。
