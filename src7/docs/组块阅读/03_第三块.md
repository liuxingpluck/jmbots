# 第三块：前台、后台和小会话

读完这一块，你能说清楚：骨架里“前台”“后台”“小会话”其实是同一种东西（一场会话），只是 `kind` 不同；前台怎么把活派给后台、后台做完结果怎么回来；插件想临时问模型一句（审批、压缩、总结）怎么开小会话；以及“喊停”在三种情况下各是什么效果。

只讲 4 个概念。要先懂第一块的“会话 = 一份记录 + 一个循环”和第二块的前台会话。结果怎么发回渠道的细节（队列、重试）这一块不管。

> **先回顾（不算新概念）**：前台怎么找、话怎么排队，第二块概念三讲过：`FrontDesk.findOrCreateFrontByScope`（`src7/plugins/bots/FrontDesk.ts`）按“渠道 + 账号 + 聊天”找，找不到再按客户号沿用旧前台，都没有才新开。

## 概念一：`kind`——会话的种类，决定它能用哪些工具

**一句话**：前台、后台、小会话在骨架眼里没有区别，都是 `SessionRow`，只有 `kind` 这个字符串不同。骨架不解释 `kind`，只拿它去对工具登记时写的 `sessionKinds`：工具说“我给 `['front']` 用”，那后台会话就看不到、也调不了它。

**代码里**：`src7/Sessions.ts`（`kind` 字段）和 `src7/Tools.ts`（对 `kind` 筛工具）

```ts
// src7/Sessions.ts
244	  /** 种类。骨架不解释它，只拿它去对工具登记时写的 kinds；有哪几种由开会话的插件定。 */
245	  kind: string;
```

```ts
// src7/Tools.ts
157	    const usable = all.filter((spec) => spec.sessionKinds.includes(kind));
```

执行时也要再对一遍（`Tools.ts:160`），模型就算胡乱编一个工具名也调不动。

现在用到的几种（都是插件起的名字，不是骨架规定的）：

- `front`：前台，直接面对用户（`FrontDesk.findOrCreateFrontByScope` 里按 `kind: 'front'` 找）；
- `work`：后台，前台派出去干活的（`DispatchTools.ts:239`）；
- `relay`：转给外部助手的会话（`relay/index.ts` 的 `openOrCreateSession`，第 719 行起）；
- `exec-review`、`compress` 等：小会话，一次性的（`approval/index.ts:311` 的 `REVIEW_KIND`、`context-fit/Compress.ts:140`）。

比如 `hand_session`（派后台）登记的是 `sessionKinds: ['front']`（`DispatchTools.ts:87`）：只有前台能派活，后台不能再往下派。工具登记的 `sessionKinds` 全仓库只有三种写法：`['front', 'work']`、`['work']`、`['front']`。小会话的种类（`exec-review`、`compress`……）没有哪个工具登记过，所以它们天然一个工具都没有，第五块说的“不带工具的小会话”就是这么来的。

**类比**：门诊医生、住院部医生、会诊医生都是医生（会话），胸牌上的科室（`kind`）不同，能开的检查（工具）就不同。医院不管你叫什么名字，只看胸牌。

## 概念二：派后台——前台调 `hand_session`，后台做完结果回前台

**一句话**：用户的话是前台在接。前台模型觉得要慢慢干的活，就调 `hand_session` 工具：新开一场 `kind: 'work'` 的会话，`parent` 指回这场前台，把话交给它、推它去跑，**不等**。后台做完后，结果先排回前台，由前台整理再回给用户，后台不直接对用户说话。

**代码里**：`src7/plugins/bots/DispatchTools.ts` 的 `create`

```ts
// src7/plugins/bots/DispatchTools.ts
238	    const work = this.home.sessions.create({
239	      kind: 'work',
240	      bot: bot.name,
241	      parent: front.id,
```

```ts
// src7/plugins/bots/DispatchTools.ts
257	    bot.hand(plan.text, workOrigin, work.id);
```

`bot.hand`（`plugins/bots/index.ts:967`）把话交进那场会话（记回话往哪送、`session.queueUserMessage`），然后推它跑，不等。后台那一轮做完会发 `session/change`，`DispatchResults.ts:185` 听到后在 `returnWork`（第 408 行）把结果排进前台的队列，前面补一句“（做完了）”之类的状态词，让前台好整理。

`hand_session` 的 `action` 有两种：`new` 新开，`append` 接着一场已有的（暂停了的也用 append 接着做）。

`SessionRow` 里 `parent` 的注释（`Sessions.ts:200`）写着：后台指回派活的前台（上面第 241 行），小会话指回发起提问的会话。

**类比**：门诊医生开单把病人转去住院部，自己接着看下一位；住院部做完，把结果送回门诊，由门诊医生跟病人说。

## 概念三：小会话——`sessions.ask`，一次性的模型提问

**一句话**：插件有时只需要问模型一句话、拿一个答案（这条命令危不危险？把这段对话压成摘要）。不用自己拼模型请求，调 `ctx.sessions.ask(...)`：它新开一场小会话，说一句，跑到底，把“做没做完”和回答交回给你。小会话没有渠道，不会把话发给用户。

**代码里**：`src7/Sessions.ts`

```ts
// src7/Sessions.ts
481	  async ask(input: AskInput): Promise<AskResult> {
482	    //M 要问的话和停止信号不进记录，其余原样拿去开会话。
483	    const { text, signal, ...fields } = input;
484	    const child = this.create(fields);
485	    child.queueUserMessage(text);
```

整个函数就是 `create → add → run` 连起来；最后 `ok` 只有状态是 `done` 才是 `true`（`Sessions.ts:390`）。调用方一定要处理 `ok === false`，比如压缩失败就这次不压（`context-fit/Compress.ts:150` 的 `if (!ok) return done;`）。

调用方在 `AskInput` 里填：`kind`（自己起个名字，比如 `compress`）、`parent`（嵌在哪场会话里）、`text`、可选 `signal`（提问方被叫停，小会话也跟着停：`Sessions.ts:377–380`）。

用到它的有：命令审批的“第三档”（`approval/index.ts:628`，kind `exec-review`）、对话太长时压缩（`context-fit/Compress.ts:147`，kind `compress`）、后台做完写总结（`context-fit/Summary.ts:87`，kind `summary`）、判断（`decision/index.ts:338`，kind `decision`）、进度收尾和复盘（`progress/index.ts:1053`、`progress/Review.ts:306`，复盘的 kind 是 `review`）。

**为什么要有小会话**：插件要“借模型想一下”，但这段一问一答

- 不该塞进用户正在聊的那场对话：会弄乱对话，下一轮模型还会把它当成上下文；
- 不该让用户看到：小会话没有渠道，回答只交回给调用的插件；
- 也不用插件自己再拼一套模型请求：小会话走的是同一个循环，模型和思考档的选择、四个关口、跟踪全都照旧，提问方被喊停它也跟着停。

所以单独开一场、问完就扔，`parent` 记着是哪场会话发起的，回头查得到。

**类比**：看诊时医生转头问一下药师“这两种药能一起吃吗”，问完回来接着看；病人那份病历里不记这段，药师也不跟病人说话。

## 概念四：喊停 `stop`——三种场合同一个出口

**一句话**：喊停的出口只有一个：`Session.stop(by)`。它把状态改成 `stopped`，写 `reply = 已停止（by）`，同时 abort：正在等的模型请求马上掐断，慢的工具也拿到停止信号断开。已经停了或根本没在转，再喊就什么都不做（免得“已停止”被再发给用户一遍）。

**代码里**：`src7/Sessions.ts`

```ts
// src7/Sessions.ts
866	  stop(by: string): void {
```

```ts
// src7/Sessions.ts
877	    this.change('stopped', `已停止（${by}）`);
878	    aborter.abort();
```

谁会去调它：

- **关口上的插件写了 `stop`**：会话循环自己调（`Sessions.ts:553`、`585`、`633`，见第一块）；
- **前台的 `stop_session` 工具**：对后台，是 `DispatchTools.ts:360` 的 `pause`。前台派的后台（带 `frontTask`，`DispatchTools.ts:224` 起，记着是哪场前台派的、第几轮、有没有暂停）先记暂停再停：`task.paused = true` 并存库（第 382–383 行），再 `stop('前台暂停')`（第 385 行）。记暂停是为了：被停的这一轮结果不再交回前台（`DispatchResults.ts:413`），以后 `hand_session append` 再把 `paused` 改回 `false` 接着做。别的插件开的后台（比如 voice，`voice/index.ts:1529–1530`）没有 `frontTask`，没有暂停可记，直接 `stop('前台')`（第 377 行）；
- **小会话的提问方被叫停**：`ask` 里的 `signal` 一断，就 `child.stop('提问方停了')`。

注意：停的是“这一轮”，会话记录和已做的事都留着，不回滚；正在执行的工具可能还在收尾（`pause` 的回执里有 `inFlightMayBeFinishing`）。

**类比**：今天这次看诊到此为止。病历留着、已经做的检查结果也留着；要继续，下次挂号接着看。

2. 前台派出一场后台以后，前台会等它做完吗？后台的结果怎么到用户手里？
3. 一个插件想问模型“这段话是不是广告”，该调什么？拿到 `ok === false` 是什么意思？

<details>
<summary>答案</summary>

1. `hand_session` 登记时写了 `sessionKinds: ['front']`（`DispatchTools.ts:87`）；`Tools.listToolsForSessionKind`（`Tools.ts:154`）不会把它列给 `kind` 是 `work` 的会话，`execute`（`Tools.ts:160`）也会因为 `sessionKinds` 不含它而回“没有这个工具”。
2. 不等。`bot.hand` 把话交进后台就“推它跑，不等”（`bots/index.ts:967`）；后台那一轮做完发 `session/change`，`DispatchResults.returnWork`（第 408 行）把结果排进前台队列，前台整理后再回给用户。
3. 调 `ctx.sessions.ask({ kind: '自己起的名字', parent, text, signal })`。`ok === false` 表示小会话没做完（出错或被停了），这时 `reply` 是原因而不是回答，调用方要自己决定怎么办（审批当“拿不准”，压缩就不压）。
