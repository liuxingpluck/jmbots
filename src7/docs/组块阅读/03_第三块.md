# 第三块：插件之间一问一答

读完这一块，你能说清楚：一个插件想让另一个插件办件事、并拿到结果，现在是怎么做的——发一个“请求事件”、等一个“回执事件”，怎么配对、没人接怎么办、等太久怎么办；以及决策图上待定的 q-ev-serial 想改成什么样、两种各长什么样。

只讲 5 个概念，都在 `src7/utils/RequestEvent.ts`（共一百八十多行，两个函数）。这一块要先懂第一块的“挨个问（`ctx.serial`）和通知（`ctx.emit`）”，和第二块的 `channel/reply` ↔ `channel/replied`。

## 概念一：请求事件和回执事件——两个事件配成一对

**一句话**：插件 A 要插件 B 办事，不直接调 B 的函数，而是发一个“请求事件”；B 办完再发一个“回执事件”。一问一答 = 两个事件。比如 `usage` 要查模型价格：发 `model-catalog/request`，等 `model-catalog/result`。A 不知道也不用知道谁来办。

**代码里**：`src7/plugins/model-catalog/Usage.ts`（提问的一方）

```ts
249	    const result = await requestEventModule.requestEvent(
250	      this.ctx,
251	      'model-catalog/request',
252	      'model-catalog/result',
253	      lookup,
254	      options,
255	    );
```

办事的一方 `src7/plugins/model-catalog/Usage.ts`（另一对：`usage/list` ↔ `usage/list-result`）

```ts
192	    requestEventModule.onRequestEvent(ctx, 'usage/list', 'usage/list-result', (request) => {
193	      //M 沿用 list 的排序和截断规则。
194	      return this.list(request);
195	    });
```

这是 CLAUDE.md “插件之间尽量只靠事件”的落地：只发事件、收事件，不管别人怎么做、做多久。

**类比**：在公司群里发需求单“请财务查一下这个模型的价格”（请求事件），财务查完在群里回“单号 123：每百万 3 美元”（回执事件）。你不用知道谁是财务、怎么查的。

## 概念二：`requestId`——靠单号认回执

**一句话**：群里可能同时有很多人在问。`requestEvent` 每次发请求都自动生成一个 `requestId`（带前缀，如 `apr_…`），回执必须原样带回；提问的人只认单号对得上的那份，别的回执当没看见。

**代码里**：`src7/utils/RequestEvent.ts`

```ts
 90	  const requestId = `${prefix}_${crypto.randomUUID()}`;
```

```ts
116	    dispose = bus.on(String(resultEventName), (event: EventArg<ResKey> & ResultEnvelope) => {
117	      if (event.requestId !== requestId) return;
118	
119	      //M 收到匹配当前 requestId 的回执，结束本次请求等待。
120	      finish(event);
121	    });
```

注意顺序：先挂好“听回执”的监听（第 116 行），再发请求（第 132 行）。不然办事的人同步就回了，回执会漏掉。收完回执（或超时、中止）都会把监听撤掉，不留残渣（`finish`，第 104–113 行）。

**类比**：快递单号。你同时寄了三件，回执单上的单号对哪份存根，就是哪件的。

## 概念三：`handled`——办事的人先“举手”，没人举手马上退回

**一句话**：请求事件是用 `ctx.serial` 挨个问的。办事的插件一看是自己的活，就**立刻同步**把 `request.handled = true`（举手，必须在第一个 `await` 之前）；全部问完还没人举手，说明没人管，提问方立刻拿到退回，不用傻等超时。不是自己的活（比如渠道名不对）就别举手，留给别人。

**代码里**：办事一方 `src7/utils/RequestEvent.ts` 的 `onRequestEvent`

```ts
170	    request.handled = true;
```

提问一方：

```ts
132	    void bus.serial(String(requestEventName), fullRequest).then(() => {
133	      if (settled || fullRequest.handled === true) return;
134	
135	      //G 没有任何监听者置 handled = true：立即退回 unhandled。
136	      finish(options.onFallback('unhandled'));
```

`onRequestEvent` 的 `options.filter` 就是“不是我的活就不举手”（`filter` 返回 false 时不标 `handled`）。

**类比**：会议上问“谁负责这件事？”——负责的人马上举手；问完一圈没人举手，主持人当场说“没人管”，而不是干等半小时。

## 概念四：退回——没得到正常回执时拿什么

**一句话**：提问方必须自己写“拿不到回执怎么办”（`onFallback`），它会在 4 种情况下被调：`unhandled`（没人接）、`timeout`（等超时）、`aborted`（外面叫停）、`error`（监听器抛错）。所以 `requestEvent` 总会返回一个值，不会抛、不会永远挂着。

**代码里**：`src7/utils/RequestEvent.ts`

```ts
13	export type FallbackReason = 'unhandled' | 'timeout' | 'aborted' | 'error';
```

```ts
123	    timer = setTimeout(() => {
124	      //M 等待回执超时，调用退回构造器收尾。
125	      finish(options.onFallback('timeout'));
126	    }, options.timeoutMs);
```

退回写成什么，由业务决定。比如 `usage` 查不到价格，就退回空结果、按零计费（`Usage.ts:242-246` 的 `onFallback: () => ({ requestId: '' })`）；`exec` 的命令审批没人回就退回“拒绝”（`src7/plugins/exec/Runs.ts` 的 `getRejected`）。

**类比**：寄出去的信有四种没回音的情况：地址没这个人、等了太久、你自己撤回了、对方拆信时出了事故。每一种你都要提前想好“那我就……”。

## 概念五：两个函数——`requestEvent` 提问，`onRequestEvent` 办事

**一句话**：提问的插件调 `requestEvent`（它包办单号、等回执、超时、中止、退回）；办事的插件调 `onRequestEvent`（它包办“举手 `handled`”、跑你的处理函数、把你返回的内容配上同一个 `requestId` 发成回执，出错时可转成失败回执）。两边各写业务那一小段，其余是公用的。

**代码里**：

```ts
 76	export async function requestEvent<
```

```ts
154	export function onRequestEvent<
```

```ts
176	      //M 调用方要求等待回执（带了 requestId）：原样拼上 requestId 广播结果事件。
177	      bus.emit(String(resultEventName), { ...(body as Record<string, unknown>), requestId: request.requestId });
```

回执是 `emit`（通知），不是返回值：提问方是靠挂监听“听到”它的。如果请求里没带 `requestId`，办事方办完不发回执（相当于“发出去就不管了”的通知式指令）。

另外，`src7/Channels.ts` 的 `requestChannelReply`（第二块那条）是同样的做法，但用手写的一份，没走这个工具（`RequestEvent.ts` 开头注释说过，工具也是为了以后把这类重复代码收编）。

**类比**：`requestEvent` 是“填需求单、盯着回音”的标准表格，`onRequestEvent` 是“接单、办完回单”的标准表格。大家用同一套表，不用每次各自发明。

## 现在的做法 vs 决策图上的 q-ev-serial

这一块讲的是**现在的做法**：两步——发请求事件、等回执事件。

决策图上待定的 **q-ev-serial** 想改成：发一个事件，答案直接从返回值拿，用 Cordis 本来就有的 `ctx.serial`（挨个问到有人返回值为止）。这里只摆两种长什么样，不替用户做决定。

**现在：请求事件 + 回执事件**（提问方，加办事方）

```ts
// 提问方：发 model-catalog/request，等 model-catalog/result；没人接、超时、中止、出错都走 onFallback
const result = await requestEvent(ctx, 'model-catalog/request', 'model-catalog/result',
  { action: 'find', model }, { timeoutMs: 3000, onFallback: () => ({ requestId: '' }) });

// 办事方：只写业务，handled、requestId、回执由 onRequestEvent 包办
onRequestEvent(ctx, 'model-catalog/request', 'model-catalog/result',
  (request) => ({ info: find(request.model) }));
```

**q-ev-serial：一个事件，答案从返回值拿**

```ts
// 提问方：serial 挨个问，第一个返回非 undefined 的就是答案，后面的不再问
const info = await ctx.serial('model-catalog/find', model);

// 办事方：直接 return 答案；不是自己的活就不 return
ctx.on('model-catalog/find', (model) => find(model));
```

两种的差别，按代码事实摆出来：

- **事件个数、代码量**：现在一问一答要声明两个事件（请求、回执），两边各带 `requestId`、`handled` 这些信封字段；serial 方案只一个事件，办事方直接 `return`，提问方直接 `await`。
- **没人接**：现在有明确的 `unhandled` 退回；serial 没人返回时拿到的是 `undefined`，提问方自己判断。
- **等多久、能不能叫停**：现在 `requestEvent` 带超时和中止信号（`timeoutMs`、`signal`）；serial 本身没有超时和中止，要的话得自己再包。
- **要跟现有规矩一致**：README 说过“挨个问”的监听函数不许有返回值，有了返回值 Cordis 就不再问后面的人了。serial 方案正是把这一条反过来利用，所以只能给“答案只需一个人出”的事件用；一个事件的监听者不能同时既当“关口改数据”又当“返回答案”。

## 读完自测

1. 为什么 `requestEvent` 要先挂“听回执”的监听，再发请求？
2. 办事的插件为什么要在第一个 `await` 之前就设 `handled = true`？不是自己的活该怎么办？
3. 提问方能拿到哪四种退回？为什么 `requestEvent` 不会一直挂着不返回？
4. 对 q-ev-serial：“答案从返回值拿”比现在少了什么现成的功能？

<details>
<summary>答案</summary>

1. 办事方可能在被问的当下就同步发回执；如果先发请求再挂监听，回执会漏掉（`RequestEvent.ts:115` 注释，监听在第 116 行，发请求在第 132 行）。
2. `serial` 把请求问完一圈后，提问方立刻检查 `handled`（第 133 行）；如果办事方等 `await` 之后才设，提问方会误判“没人接”。不是自己的活就不设 `handled`（用 `options.filter`，返回 false），留给别人（第 52–57 行、第 168 行）。
3. `unhandled`（没人接）、`timeout`（超时）、`aborted`（外部叫停）、`error`（监听器抛错），第 13 行。每种路径都会走 `finish` 调 `onFallback`；超时有定时器（第 123–126 行），没人接有 `handled` 检查，所以总会返回。
4. 少了超时、中止信号和“没人接”的明确退回原因（拿到的只是 `undefined`）；也不再有 `requestId` 配对，因为答案就是这次调用的返回值。

</details>
